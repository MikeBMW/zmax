# 给节点“加一路新输出”与它的状态真源

适用：要把一个原本在节点外跑的能力（如高保真重建）接进某个节点，让它“看得见、可查、可追溯”。

## 步骤
1. 备份画布：`state_space_obs.json.bak_<标记>_<时间戳>`。
2. 用脚本改，不手写 JSON：源节点 `outputs` 追加 `outN`；新增 link（id 唯一，label 写中文含义+来源文件名）；
   在源节点 `params` 里记四个锚点：真源文件 / 生成脚本 / 常驻服务 / 只读 API。
3. 写后回读，硬断言：JSON 可解、节点 id 唯一、连线 id 唯一、新端口在声明里、link 两端节点存在。
4. 用独立的 verify 脚本定论，口径见下。

## 校验口径：只认“新增”，不做全量否决
这个画布存量本来就有上百条“端口未声明”（GUI 按连线动态生成端口，是容忍的）。
全量校验会把存量问题当自己的错，或者干脆不敢改。正确做法：拿备份与新版逐条 diff，**只报新增问题**；
新增为 0 即 OK（实测基线 110 条存量，改动后新增 0）。

## 新状态量先走旁带，不改 obs 维度
观测向量维度（如 43D）是下游模型/checkpoint 的契约，加维要连带改所有模型头。
先挂成旁带输出（out3 之类）+ 独立 JSON 真源 + 只读 API。要进状态向量，那是一次独立的跨层改造。

## 状态真源服务的形状
- 每 30s 一轮写 `<name>_live.json`（latest）+ `<name>_history.jsonl`（逐轮追加）。
- 字段分层：`stage`（采集中/训练中/已就绪）+ 各子块（capture/train/asset/stream）+ 给状态空间的三元量。
- 阶段判定靠远处日志尾 + mtime 算帧龄；拿不到就写 `unknown`，**不要猜**。
- 跨机取 mtime 用 `date +%s -r <file>`（`stat -c %Y` 在部分平台/远端不通）。
- 取不到时别把 stage 回退成“已就绪”：沿用上一轮的 train 块，否则读数会来回跳。
- 服务要 ssh 到别机时必须 `User=ubuntu` + `Environment=HOME=/home/ubuntu`：root 没有用户密钥，
  `BatchMode=yes` 直接认证失败；症状是服务 active 但每轮都写 unknown，手动跑同一条命令却正常。
