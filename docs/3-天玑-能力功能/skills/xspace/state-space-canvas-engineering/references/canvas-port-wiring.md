# 画布接线: 执行链定序与端口对正

链路「看着接上了」和「真的接通」是两件事。接线错位不会报错, 只会静默丢数据或串语义。

## 一条执行链的标准定序

```
规划引导 → 动作调制 → 安全执行 → 技能 → 运动规划 → 动作执行器 → 机器人执行器
```

顺序是用户定的口径, 改一次就同步到 **三个地方**, 否则下一个人看到的还是旧链:
① 画布连线本身 ② 各节点模块文件头的「执行链位置」注释 ③ 判据脚本的期望。

## 端口对正: 以中间件声明为准, 不要按名字猜

节点的真口名在 `src/lerobot/middleware/nodes/n_<单词>.py` 的 `PORTS_IN` / `PORTS_OUT`。
**先 grep 声明再改连线** —— 按"看起来该是 in1"去改, 会把同一批技能改成一个 in1 一个 in2。

```bash
for i in 1 2 3 4 5 6 7 8; do printf "skill%d: "; \
  grep -oE "PORTS_IN = \[[^]]*\]" src/lerobot/middleware/nodes/n_skill$i.py | head -1; done
```

同类节点(技能 ①~⑧)的端口必须**统一**; 声明不一致时改声明而不是改连线, 让一批节点长一个样。

## 🔴 一口只允许一个上游

总线按口覆盖写 ⇒ 两个上游压同一口 (`sslimit.out1 → ssk*.in1` 且 `ssskill.out1 → ssk*.in1`)
= **后写覆盖先写**, 看不出来、也不报错, 表现为"某一半控制量永远是 0 / 永远不变"。

分工写法(推荐): `in1` = 上游主数据流(动作/指令), `in2` = 编排/元信息(L3 决定这一段跑什么)。
判据: 对每个节点的每个入线口, 上游集合里只能有一个源; 有第二个就换口或删线。

## 串口语义错位的典型形状

- 约束接到了"目标点"口 (`out3 安全约束 → plan.in1`), 而规划只在 `in2` 读 `_limits` ⇒ **限幅整条被丢**。
  改完必须塞值回读: 上游给 50/20, 下游 `plan` 要能打出 `{'step':50,'down':20}`, 不是"连上了就算对"。
- 8 个技能全挤到规划的前两个口 (`in1`/`in2`), 而规划真正读技能的是 `in4..in11` ⇒ 技能输出没人看。
- 技能节点 `in1` 同时收"动作值"和"编排"(见上)。

## 判据脚本(每次改接线必跑)

`tools/verify_exec_chain.py` 的形状(自查可复用):

1. 主链每段 `(from, from_port, to, to_port)` 全部存在
2. 批量节点 → 目标口一一对应 (`skills[i].out1 → plan.in4+i`)
3. 安全输出的限制值 → 规划读约束的那个口
4. 每节点每口只有一个上游
5. 文件头注释与判据期望同一口径
6. 真源符号链接同源(见下)

跑完再 `parse_canvas()` 回读一次节点/连线总数 + 重复边为 0
(`spec.parse_canvas()` 会按 id 过滤, 总数不必等于 JSON 里的全部节点)。

## 真源与 git

- `flows/state_space_obs.json` 是 `data/database/zmax/sources/canvas/state_space_obs.json` 的符号链接 —— 同一份文件,
  别以为是两份、也别指望"改一份另一份会自动跟"。
- 该文件在 `data/` 下虽被 ignore 但**已被 track** ⇒ `git add` 要 `git add -f`, 否则 `git add -A` 静默跳过,
  提交里没有画布改动(症状: 代码进了、链路没进)。
