# 位姿驱动的分布式感知调度

## When to Use (何时用)

- 现场有多台相机（臂上 / 顶置中央 / 工位检测 / USB 调试），要根据机器人当前位置自动决定
  「现在该用哪台、以什么频率、能不能出 3D 引导」
- 用户要求「到了某个位置就启用那台相机」「按路径点位规划感知能力」
- 要回答「融合/下游节点到底接没接到感知结果」（通常答案是没接，见末节）

**先纠正一个常见误解**: 这不是 LBS 式的二值开关（进圈→触发服务）。生物感知系统从不「关掉」周边视觉，
而是**连续调节精度预算**：周边低带宽全程监视 → 眼跳把中央凹对准 → 高带宽采样 → 退出保留余像。
按这个形状做，靠近过程不会被漏掉；按开关做，边界上会丢帧。

## 五步做法（每步都接真源，不手抄数值）

1. **区域表** — 谁管哪片空间。优先复用工程已有分区 bbox（点位台账聚类出来的 `zones`），别自己编坐标。
2. **相机能力表 registry** — 谁能干什么：`id / kind(eye_in_hand|fixed) / intrinsic / extrinsic / depth / role / level / coverage / calibrated`。
3. **3D 闸门** — `extrinsic.mode ∈ {tcp_compose, fixed_matrix}` 才准出 3D，其余降级只出 2D 并返回 `why`（缺什么）。
4. **四态门控** — 见下表，输出**连续增益 gain** 而不是布尔值。
5. **验证** — 拿**真实轨迹点**逐点跑，报区域切换序列 + 覆盖率；断言闸门拒绝未标相机。

## 四态门控（连续增益，不是开关）

| 态 | 条件 | gain | 相机档 |
|---|---|---|---|
| WATCH | 不在任何命名区 | 0.2 | 仅 overview，低帧率(2Hz)全程监视 |
| ALERT | 区外但距区面 < alert_band(100mm) | 0.6 | 即将进入那台相机**预热**(1Hz)，还不采信 |
| FOVEATE | 已在命名区内 | 1.0 | 高精度相机 10Hz，出 3D 引导 |
| RELEASE | 刚从区内退出 | 0.2 | 回落，保留余像，不瞬间断电 |

`gain` 给下游决定「采样帧率 / 本次定位是否采信」—— 这就是预测编码里的精度加权（precision weighting）。
ALERT 阶段要按**即将进入的那个区**取相机（priming），不是按当前区。

## 关键坑（每条都实测过）

### 🔴 区域表覆盖率会极低，必须从真实轨迹派生一层
点位聚类出的区域只能盖住轨迹的一小段 —— 实测 **96 个真实轨迹点只有 11 个**落进命名区（11.5%），
其余全落「其它」，等于大半程「无区可依」。
⇒ 从**真实轨迹**派生命名区（bbox = 实测点集 + 30mm 余量），再与工程区域合并：
派生层用 `setdefault` 合入 ⇒ **工程真源永远优先、派生层不许覆盖**。实测覆盖率 11.5% → 94.8%。
派生区可以自带 `{"cam_id": "role"}` 绑定，优先级高于 registry 的 coverage 列表。

### 🔴 兜底区（「其它」）不许抢具体区
一个点同时落进多个 bbox 时，按「中心最近」选会让兜底区在轨迹两端赢掉具体区。
⇒ 排序前先滤掉兜底区（`其它` / `包络外`），只在具体区之间取最近。

### 🔴 ALERT 判据不能用「离区内边界多远」
薄区（如插入工位 z 只有 11mm 厚）里工件贴在区底，该距离恒 ≈0（实测 0.5mm）
⇒ 永远进不了高精度态。**到达目标区就该全力看**，这才是正确口径：
用「是否已在区内」+「从区外逼近是否 < 带宽」判，不要用内缩深度。

### 🔴 区域边界要带滞回（默认 20mm）
TCP 在边界附近抖动会导致相机反复开关。滞回带内保持上次区域，判据写明原因（便于现场看日志）。

### 🔴 config 目录常是软链到 gitignore 的数据盘
`config → data/database/...` 时，registry / zones 这类 JSON **不进版本库**。
⇒ 进库的是**生成器脚本**（从内参 json + 手眼 json + 相机服务 `/api/cams` 现算），不是数值文件；
换机器/重建环境才可复现，也避免手抄数字。

### 🔴 算法层模块的仓库根层级要数准
`src/lerobot/policies/<pkg>/mod.py` 要 **5 层** `dirname` 才到仓库根；少一层就变成
`FileNotFoundError: .../src/zmax_data/...`（看着像文件缺失，其实是根算错）。

## 验证脚本该断言什么（照抄这 6 类）

1. 区域表非空 且 各工程区齐（数量用 `>=`，因为会叠派生层）
2. 相机数对 且 **能出 3D 的只有已标外参那几台**（列出 id 白名单比对）
3. 每个区的**中心点判定回自己**（防 bbox 重叠/优先级错）
4. 真实轨迹逐点跑 → 每条的**区域切换序列 + guide 是谁**；轨迹取不到时如实打印原因，不编点
5. 3D 闸门：已标的 `can_guide_3d == True`，未标的逐台 `False` 且 `why` 可读
6. 滞回：边界外 10mm 且带上一次区域 → 保持，且 `how` 里出现「滞回」

跑完把**覆盖率**（落进命名区的点数 / 总点数）报出来 —— 这是判断区域表够不够用的唯一硬指标。

## 输出契约

```
{"p_m":[...], "zone":"插入工位/夹具", "zone_how":"...",
 "state":"FOVEATE", "gain":1.0,
 "cams":[{"id":"arm","role":["localize","guide"],"level":"L2","enable":true,
          "why":"外参可用(tcp_compose, 残差 0.06 mm rms)","sampling":"high_rate(10Hz)"}],
 "guide":"arm", "blocked":[{"id":"gold","why":"外参未标 ⇒ 只出 2D"}]}
```
给下游的是**增量**（相对当前末端位置的修正量）+ `sigma_mm` + `frame_age_s`，不是绝对点 —— 下游不会跑飞。

## 末节：下游「有连线 ≠ 有消费」

节点 out 端口连到融合/决策节点，**不代表对方读了**。接之前先查三件事：
1. 上游节点是否 `PURE=False`（走直通）⇒ out 值其实是上游上游的，你的实现根本没执行；
2. 下游实现函数体里 grep 不到那个端口号 ⇒ 连线是装饰，没人读；
3. 下游 `_pick(port, keys)` 找的**字段名**跟你给的对不对得上（实测下游找 `contact_p/p/score`，
   而质量判决给的是 `pass/verdict/defect_n` ⇒ 一个都取不到，还静默退到别的源）。
字段语义也别将就：质量判决不该冒充接触概率，改用注册表里已登记的归一名（如 `quality_score`）。
