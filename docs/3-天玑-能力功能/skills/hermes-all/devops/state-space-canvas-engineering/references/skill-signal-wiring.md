# 把技能信号接进下游节点 (画布接线 recipe)

适用: 用户要求「把技能链做进某场景」「技能节点的信号必须传入 plan」——先把信号路打通, 不要求当下生效。

## 一、三步接线 (改画布 JSON)
真源: `data/database/zmax/sources/canvas/state_space_obs.json`

1. **目标节点声明入口**: `nodes[i].inputs = ['in1','in2',...]`。中间件 `pull()` 只按 `spec.inputs` 逐口拉值,
   没声明的端口永远拿不到数 —— 旧图常见 `inputs` 为空但已有 in1/in2 连线(端口是从 link 反推的), 补线前先写全。
2. **加连线**: `links.append({"id": <唯一>, "f": 源节点, "f_port": 源口, "t": 目标节点, "t_port": 目标口, "label": 显示名})`。
   键名是 `f` / `t` / `f_port` / `t_port`; 用 `from/to` 写进去既不生效也不报错, 自己的核对脚本也会静默漏掉 —— 先打印一条既有 link 校对 schema。
3. **重建派生库**: `python3 tools/mw_db.py sync`, 再 `python3 tools/mw_db.py node <目标id>` 回读,
   断言入口话题数 == `inputs` 数。少于它 = 端口没声明 或 派生库没重建(总线无 topic, 信号到不了节点)。

端口对齐关系先查清: 源节点哪个口是「技能动作结果」(如 `out2` = u/v_req/err/why), 哪个口是「序列/上卷」(如 `out1`);
下游要的是动作结果就接 `out2`, 别顺手接 `out1` 把 MoveIt 指令当技能信号。

## 一-b 「接没接上」只看 links + 实测 n_in, 不看实现里有没有读取代码

下游实现常**早就预留了端口** (`plan_long_impl.run` 里 `in3` 技能序列 + `in4..in11` ①~⑧ 原子技能, 全在代码里读取并透传),
而画布上一根线也没拉 ⇒ 节点输出里 `n_in = 0`。两种状态在源码里长得一模一样, 判据只有两条:

```bash
# ① 该节点真实的入线 (键是 f/t/f_port/t_port)
PYTHONPATH=src gui-venv311/bin/python -c "import sys;sys.path.insert(0,'src')
from lerobot.engineering import flows
d,_=flows.load_canvas()
print([(l['f'],l['f_port'],l['t_port']) for l in d['links'] if l['t']=='<目标id>'])"
# ② 实测有没有值进来 (无 ctx 应返回 0, 喂合成 ctx 应变 8)
```

回答「XX 节点怎么接入的」时, 答案 = **入线清单 + 每个口语义 + 实测 n_in**, 不是文件路径表 ——
用户会当场追问「上游到底是谁」, 拿代码路径当"已接入"的证据会被打回。

## 一-c 接线前先量两端 x: 上游在右下、下游在左上 ⇒ 必然是反向线

画布行带是语义排布, 不是数据流方向: 编排节点可住在最左上 (`x≈240`), 而技能/执行层在最右下 (`x≈8200`)。
技能→编排的线因此是**横跨全图的反向线**, 按「新线必须前向」的规矩不能直接加。
先量再报, 给三选一 (别先动手):
1. **照接反向线**, label 写明「<上游> → <下游>」, 交付时直说它是反向的 (画面上会多几根长回头线);
2. **把下游挪到上游右侧**再接 (线顺了, 但挪节点是交叉变多的主因, 要重新量交叉);
3. **走数据面不拉线**: 上游写文件、下游读文件 (通道/约束/标定参数现在就是这么接的), 画面上没有线但链路真通。

## 一-d 反向线的正解: **改既有线的 t_port**, 不新增长线 (2026-11-01 实做)

场景: 8 个原子技能 (`sssk1~8`) 已经在画布上各有线连到目标节点, 只是接错了口。此时不要删线重拉
(重拉就是横跨全图的反向长线), 直接把 `link["t_port"]` 改到语义正确的口, 连线总数不变、画面不脏:

```python
for l in d["links"]:
    if l["t"] == "n_moveit" and l["f"] in SK:
        l["t_port"] = "in%d" % (4 + SK.index(l["f"]))   # ①~⑧ → in4..in11
```

判据: 连线数不变/只少允许删的装饰线, 其它 219 条逐位一致 (脚本比 before/after 列表, 差异必须只落在预期那几条)。

## 一-e 三个「接了等于没接」的坑 (全部实测踩过)

1. **多上游合流到同一入口 = 后写覆盖**。8 技能全接 `in4` ⇒ 每个 tick 依次 publish 同一话题,
   最后只剩 ⑧ 的帧 (实测抓到 `in4` 里是 `safety_limit`/`l3_nominal`, 技能帧被冲掉)。
   正解: **一个上游一个端口** (`in4..in11`), 下游按 `(active, t)` 选当前生效的那个, 并把
   `n_frames`/`active_ports` 写进输出当取证。
2. **上游实现 `return True` ⇒ 出端口恒空**。壳子只认 dict: 非 dict 就 `直通` (或整个丢), 于是线在值没有。
   技能类实现必须 `return {"out1": 动作帧, "out2": 闸结果}`, 无数据也要给**带类型的空帧**
   (`active=false, reason=no_engine_trace`) —— 让下游能区分「没激活」和「没接线」。
3. **端口语义要按下游代码的头注释对, 不是按名字猜**。`plan_impl` 头写明 `in1=目标点 in2=安全约束`,
   把技能动作接进 in1 等于让规划把 action 当坐标解析。安全约束也不要让下游写死 50/20:
   上游 (安全边界节点) 补一个 `out3 = arm_control.GATE 限值`, 下游真读。

真执行的开关: 目标节点 `params.pure_verified = true` → 跑 `tools/gen_middleware_nodes.py` 重生成 →
壳里 `PURE=True` → 实测 `status=实现执行` (不再是「直通 (PURE=False: 只走数据面)」)。

## 一-f 验证时用独立总线命名空间, 否则读到的是**旧进程的帧**

画布 loop 常驻进程仍跑旧图/旧代码, 却往**同一批 DDS 话题**写。此时在进程里 `load_project().step()` 读到的
可能是 loop 写的值 (表现为「明明改对了, 抓到的还是旧语义」)。验证命令加 `ZMAX_MW_BUS=mem` 走进程内总线,
与在跑的 loop 隔离; 结论要报告「loop 需重启才生效」(按规矩不自行重启)。

## 一-g 探针类调用必须封 TTL, 否则白吃节拍

`plan_impl.run` 里每拍调 `MoveItPlan.plan()` 实测 **50.7ms/次**, 而画布 loop 预算 100ms/拍。
探针 (可用性/健康) 加 TTL 缓存后 `run()` 整拍 **0.08ms**。判据: 改前改后各跑 20~30 次取 ms/次。

## 二、下游节点兑现: 只透传, 不参与控制
- 节点实现按端口读 `ctx`: `ctx["in4"] -> {"value": ...}`(`execute_node_logic` 用 `pull()` 组装)。
- 用户口径「plan 可以不实际使用, 但技能信号必须传入」⇒ 收下后原样写进输出(`out1.skills` / `out3.skills`),
  标 `used_for_control: false`, 并留 env 开关(如 `ZMAX_PLAN_USE_SKILL=1`)供标定完成后切真用 —— 不用重接线。
- 判据: 直接调 impl 喂 1~2 条合成信号 → 输出 `n_in` 与 `u/v_req/err/why` 齐全; 不喂 ctx 不崩。

## 三、场景姿势: 先接骨架, 不追执行
- 用户允许「技能链可以不起作用 / 信号不对, 但功能要有」⇒ 不要为了"能跑"把数据源换成仿真场景。
  `src_state`(AR场景 / 插拔场景)是 ▶运行 的运行分支开关, 换场景 = 换验收对象, 不是修接线。
- 改完发 `ss_canvas` 让 GUI 重载, 并回读 `links` 总数: GUI 内存里另有一份图, 它保存时会把手工加的线覆盖回去,
  所以接线丢失要查「是不是被 GUI 覆盖」, 而不是先怀疑自己写错。
