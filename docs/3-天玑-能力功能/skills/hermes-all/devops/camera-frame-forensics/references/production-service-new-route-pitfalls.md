# 在产线单文件服务里加新接口: 图源会静默错源

适用: 给一台已经在跑的工控机服务 (单文件 Python, 自带取像+裁剪+推理, 端口如 10082/10083)
加一个新路由, 而新路由**需要像素或几何**。

这类服务的内核是“一条用过现场标定的取像链 + 一推全局状态”。新接口的唯一正确姿势是**在这条链上接**,
而不是在同一个模块里另写一段“看上去一样”的取图代码。下面五个坑全是**静默**的：不报错、返回体看着合理，
你只会看到“找不到目标”。

## 坑 1: 全局状态不是谁都会填 —— 分清“取像时填的”与“后台任务才填的”

同一份裁剪信息常被存两处:
- `_LAST_REGION` —— 在取像函数 (`GrabAndSaveImage`) **当场填** ⇒ 任何刚抓完帧的人都能读。
- `_LAST_CROP_INFO` —— 只在**后台检测队列**里 `update()` ⇒ 只有跑过 `POST /capture_detect` 才有值。

⇒ 新接口要条带就读 `_LAST_REGION`。读错那个的指纹: **服务重启后首次必失败**，
而且 bad bbox 落在图像边上一条小得多的块 (实测 365×35 vs 应有 1456×87)。

## 坑 2: `save=False` 时原图**根本不落盘**，但函数照样返回路径

```python
origin_path, _ = GrabAndSaveImage(save=False)   # 只在 save=True 时才 SaveImage
bgr = cv2.imread(origin_path)                   # ← 读到的是上一次的旧文件
```
后果: 条带是**当前帧**的，像素是**旧帧**的 ⇒ 图与几何**不同源**，切出来是废块。
指纹: 自相关 lag 掉到 20~21 (假周期) + `no peak`，而且**不报任何错**。
⇒ 要像素就 `save=True`；只有“只要条带、不读像素”才允许 `save=False`。

## 坑 3: 内存帧是 **JPEG** —— 压缩伪影把窄峰抹平

用内存帧 (`_mem_get("origin")`) 省掉落盘，是个诱人的错。细结构的峰 (
实测金手指每根宽约 50px、峰是尖的) 经 JPEG 一压就摊平 ⇒ 周期能找到、峰数不出来:
指纹 = **`lag` 已经对到 72.8 (周期对) 仍然 `no peak`**。
⇒ 峰/边缘/细结构类算法一律走**无损 PNG** (落盘原图)，不要用内存帧。

## 坑 4: 不要在产线服务里另开取像路径 (哪怕只为省时间)

同一模块里的 `_grab_bgr_only()` 与 `GrabAndSaveImage()` 在**同一时刻抓的帧不一样** ——
前者没有 settle/去坏帧那一层。实测同一刻:

| 路径 | 饱和率 | 条带 | gold_px |
|---|---|---|---|
| `_grab_bgr_only()` | 60% | 365×35 | 0 |
| `/region?grab=1` (走 `GrabAndSaveImage`) | 正常 | 1456×87 | 72344 |

⇒ 省那 1.4s 判据图渲染，换来的是“画面里没有工件”的**假象**，你会去查光/换档/改算法。
**新路由的取像必须与它自己已有的 `/region` / `/picture` 走同一个函数**，并用
`/region?grab=1` 当“参考实现”对账: 同一时刻两个入口给出的 bbox 应该一模一样。

## 坑 5: 部署会把你手调的挡位拨回去

这类服务的部署器常带一步“**复原取像挡位**” (把曝光/增益写回文件里的现场验证值)。
⇒ 你手动调好挡位、验证通过、然后一部署 —— 又回到过曝/过暗，而部署器报“验收全过”。
- 真要在服务里改挡位只能改**文件里的常量**再重启；运行时写参数的接口常返回 `ok:true`
  而画面**逐位不变** (采集过程中写 ExposureTime 静默失败)。
- **挡位是场景相关的，不是常量**: 同一挡在这场能出 19 根，换一次光线就中位灰度 255、饱和 60%。
⇒ 每次接手先打 `/region?grab=1` 读 `gold_px / focus / bright_frac` 再决定要不要降挡，
不要假设“上次验证过的那挡现在还成立”。部署后必须**重新抓图验画面**。

## 「等距 N 根」补根: 用整体线性拟合，不要用相邻间距

峰值检测常给出 N−1 根 (漏一根或被 0.55·lag 合并掉)。补到 N 的判据**不能**是“相邻间距变异系数小”:
实测这一帧 18 个峰间距 **46~95px (标差 ~16, cv 23%)**，而人工标注 19 根的间距 RMS 只有 **1.39px**
⇒ **相邻间距本身带假峰/漏峰，拿它当判据永远不触发**。

正确做法：对已有峰的**下标**做线性拟合 `x ≈ a + b·i`，用 `b` 当 pitch；
比较左右余量，在余量大的一侧补 N−n 根 (实测右边距 138px > 左边距 106px ⇒ 补最右)。
只在 `N−n ≤ 2` 时启用 (防止只找到 10 根也硬补)，并要求拟合残差 < 0.35·b。
验收：补完 19 根中心与人工标注差 **1.85px** (亚毫米级)。

## 3D 位姿引导接口契约 (probe → solve → auto)

“检测请求就直接返回机器人目标位姿”这类接口，`mm/px` 与轴符号通常是**没标定**的，也不该由调用方猜:
- `mode=probe`：返回**单轴走 N mm** (如 2mm) 的试探位姿，并把当前 `center_px` 记进标定文件。
- `mode=solve`：用走完后的新 `center_px` 与记录值反算 `k = N/Δpx` 与 `axis_sign`，写标定，同时给终值位姿。
- **假闭环必须挡**：`Δpx` 小于阈值 (~1px) 直接拒绕并报“机器人没真动, 标定作废”，不写标定。
- `mode=auto`：有标定就直接给终值；单次补偿设上限 (如 8mm) 并在响应里标 `clipped`。
- **只算不下发**：接口返回 `pose_target`，发不发由授权链决定。
- **只给一个自由度**：调用方指定 `axis`，其余轴与姿态原样回填，不自作主张加 Z/姿态补偿。

## 报数纪律

接口“通了”的证据是**返回体里的实测数字**，不是 HTTP 200：至少要有
`n` (找到几个) · `center_px` · `pitch` · `off_px` · `acf_r` · 耗时，
以及拿来对账的参考实现 (`/region?grab=1`) 的同名字段。
`n` 不到期望值时要如实报差几根、中心因此偏多少像素 (换算成 mm)，
**不能拿一个“也够用”的中心值把差根数糊过去**。
