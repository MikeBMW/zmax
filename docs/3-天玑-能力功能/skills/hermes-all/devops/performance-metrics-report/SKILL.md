# 性能指标实测报告 (分类别 · 每项真测 · 带判定)

## When to Use
- 「详细报告, 每个性能指标都要测试, 分好类别」这类要求(用户的指标红线: **不夸大**)
- 上线/交付前体检、交付件里的"测试报告"一章、故障后取证
- 任何"系统现在什么水平"的问题 —— 答案必须是**测出来的数**, 不是印象

## 铁律(先读, 这条决定报告可信不可信)
1. **每个指标真测**: 实跑一次(限幅次数)或读真计数器/时间戳/系统文件。**测不到就写 `err`**,
   绝不用 0 或估计值顶替 —— 一条编的数会毁掉整份报告。
2. **五要素齐全**: 类别 · 值+单位 · 判定(PASS/WARN/FAIL)+阈值 · **来源**(命令或文件) · 样本量。
   没有来源的指标不许进报告。
3. **0/FAIL 先自证再上报**: 出现"一片 0 / 全 err"时先怀疑**工装自己**(取图路径/端口/超时)与**上游**,
   用一条独立命令直接探(`curl -s -o /dev/null -w "%{http_code}" <url>` / `ping <ip>` / `ss -ltnp`),
   分清"现场真挂了"和"我的探针挂了"; 把工装 bug 报成现场结论是最贵的一种错。
4. **代理端点错误码 ≠ 本地服务坏**: 本机服务 200 而它的图片/数据端点 502 ⇒ 背后**上游**不可达。
   顺链路往外探一层再写结论。
5. **降级显式标注**: 输入不可用或退化成兜底实现时, 输出写 `degraded=true` + 原因链, 不静默出货。
6. **交付形态**: md(给人看·分类别表格) + json(机读·带 meta 时间戳)成对落盘; 路径写进回复,
   报告要能重复跑, 且 md 里每个数都能在 json 里查到。

## 标准十类(照这个结构扫, 别漏类)
A 层推理(逐层延迟/整链/成功率) · B 常驻回路(Hz/周期耗时/空转/抖动) · C 视觉链路(每通道 fps/帧龄/
分辨率/亮度/过曝/取像延迟) · D 模型资产(登记数/层分布/推理中计数/权重文件) · E 服务可用(端口/systemd/
API 延迟) · F 系统资源(负载/内存/磁盘/GPU 利用率·显存·温度) · G 训练(在跑进程/最近质检留出指标) ·
H 配置完备性(自检/映射覆盖/漂移) · I 端到端(任务结果/切换台账/回路帧龄) · J 安全(授权闸/来源/veto/真值新鲜度)
每类内部再分: 延迟(中位+最大) · 吞吐/频率 · 质量(精度/PSNR/过曝率) · 可用性(在线率/错误率) · 资源占用。

## 工装(可复制改写)
Z-MAX 现成: `tools/perf_report.py --write [--json] [--cycles N]` —— 十类约 90 指标, 每类独立 try
(采集异常落成一行 FAIL 而不崩), `--write` 同时出 md+json。
新写一个照它的形状: 单一 `Rep.add(cat, metric, value, unit, verdict, threshold, source, samples)`, 输出前
统一过一遍"有没有来源/样本量"。开工前先跑一次**基线**并记住: 同机同日反复跑数要能对上, 对不上先修探针。

逐对象/分层的「指令→反馈」延迟属于另一类工装: 拆腿、阶跃配对、三总体(到达/削过/未响应)、胖尾单列 ——
这套口径与坑见 `references/loop-latency-measurement.md`(浮点噪声造假 107ms、陈旧配对爆 Max 都在里面)。

## 取样与阈值口径
- 延迟取**中位 + 最大**, 不看平均(单次冷启动 13s 会把平均毁掉, 但最大值要如实标出并注明含预热)。
- 流/回路类给**采样窗口**(秒/周期数): 用户可能追问"这 10Hz 是量了多久"。
- 阈值与业务预算挂钩(如 10Hz ⇒ 100ms/周期): 只在有预算处判 PASS/FAIL, 其余标 `—` 不硬判。
- **超预算的组合要给档位结论**: "整链 415ms ⇒ 10Hz 跑不了全链, 只能 1~2Hz" 比单个数有用得多。

## 回复怎么组织(用户要的形态)
1) 定论表: 类别 × 指标数 × PASS/WARN/FAIL; 2) 各类"关键读数"3~7 条(带单位与判定);
3) **FAIL 按根因归并**(同类 FAIL 常是同一个物理原因, 合并成一条并附证据); 4) 本轮顺带修好的 +
待现场/待决策; 5) md 附件 + json 路径 + 重跑命令。详在**证据与判定**, 不在叙述过程。

## 报训练指标前：按**表头名**取列 + 量纲自检（同一件事）

训练产物（ultralytics `results.csv`、各种 `metrics.csv`）的首列之后常夹一个 `time` 列 ⇒ **列号整体右移一格**。
实测口径：`epoch, time, train/box_loss, train/cls_loss, train/dfl_loss, metrics/precision(B), metrics/recall(B), mAP50, mAP50-95, …`
⇒ `awk -F, '{print $5, $6}'` 拿到的是 **`train/dfl_loss` 和 precision**，不是 P 和 R。

两条必做，缺一条就会把错数报给用户：
1. **取数先打一次表头落坐标**：`head -1 <csv> | tr ',' '\n' | nl`；代码侧一律 `csv.DictReader` 按列名取，
   绝不写死 `$5/$6`（列会随版本/任务增删）。
2. **报前过一遍量纲自检**：精度类指标（P/R/mAP/准确率）全在 0~1；**出现 >1 的数 ⇔ 你读错了列**，
   不是"指标坏了"也不是"要上报的异常"。代价实测：把 `dfl_loss=1.386` 当 Precision 报出去，
   还据此断言"P 异常/要查"，下一轮得当面纠正 —— 这比少报一条指标严重得多（违反铁律 1 的反面：不是编数，但同样不可信）。

## 吞吐/节拍指标：先确认「数的是什么」，再算速率

从活的数据流里算 UPH / 件每小时 / 次每秒，错得最多的不是除法，是**数错了字段对象**。
实测：同一条状态流里同时有 `batch`（批次轮次号，1..8 循环）和 `mod`（当前件号，1..14），
拿 `batch` 的切换次数当「件」算 ⇒ 204 UPH；换成 `mod` ⇒ 337 UPH。两个数除法都对，只有一个在数件。

必做两条：
1. **把字段追到发它的那行代码**（`grep -n '"batch"' <src>`），看 `+=1` 落在哪层循环：
   轮次循环里 = 批次，件循环里 = 件。字段名（`batch` / `seq` / `index` / `no`）一律不可信。
2. **实测值要跟独立口径对上**：配方/段表的名义节拍（总时长 ÷ 件数）与实测差 >20% ⇒
   要么选错对象、要么窗口太短（低至几十秒的窗口会被单次预插轮/换批抖动带偏，至少 2~3 个完整轮次）。

🔴 **计划节拍 ≠ 真实产出**，报告里必须分开写：同一条流确实跑到 337 UPH，但 `src=ss_plan_long`、
`vision.src_kind=sim`、且真机位姿真源文件不存在 ⇒ 结论只能是「**计划节拍达标**」，
不是「**产线出了 337 件**」。KPI 上这是两件事，合着报就是夸大。
判真实产出的硬条件：有真实位姿/计数真值、下游质检腿可达、节拍内每一环都在链路里（本例 L5 单次
63.7s 远超 11.4s 节拍 ⇒ 只能旁路，12 题里不含它）。

## 端侧/加速卡报告：一个延迟数必须带**设备名**，TOPS 不是性能判据

同一颗 OpenVINO IR（640×640 YOLO）、同一台 Intel 边缘机，三设备实测：

| 设备 | 均值 | 中位 | P95 |
|---|---|---|---|
| Arc B390 iGPU | 1.62ms | **1.61ms** | 1.67ms |
| NPU (AI Boost) | 3.09ms | **2.85ms** | 4.31ms |
| CPU | 79.77ms | **78.88ms** | 95.25ms |

⇒ **CPU 比 NPU 慢 27.7 倍，比 GPU 慢 49 倍。** 只报一个"推理 78ms"会把这块板子写成不堪用。
跑法见 `scripts/ov_device_bench.py`（wireup：`OPENVINO_MODEL=/path/x.xml ./ov_device_bench.py --iters 20`）。

三条必做：

1. **每行延迟必须并列设备与 precision**（`NPU/FP16` vs `CPU/FP32` 不是同一件事，别混成一行比）。
2. **判"端侧强不强"看利用率，不看 TOPS 标称**。实测这台汇总 **173 TOPS（GPU 122.9 + NPU 50.4）**，
   而两者 `in_use: false` 同时在睡觉，CPU 被 5 个 numpy/torch-CPU 进化任务压到 `load1 22 / 16 线程`、82°C、
   主频从 4800 掉到 3398MHz。**算力富余与算力错配是两回事，报告要点名"谁在空转、谁在烧"**。
3. **超订与降频要各自给证据再下结论**：`load1 ÷ 线程数 > 1` = CPU 超订；`当前主频 ÷ 最高主频` 明显低于 1
   且温度接近节温 ⇒ 降频在参与。两个数都取现场值，别用平均值代替。

顺带一条归因法：同一形态的任务（如 m3 进化单代 683.9s）如果吃了满核却跑在 CPU 上，按上面那张表
的倍差估算改到 GPU/NPU 的空间是**数量级**，值得单列一条改进项 + 一句可验证的落地动作，
而不是写"建议优化性能"这种无法验收的话。

## 曲线类指标：平台期不等于上限（别在 1/3 处下根因结论）

P 挂在 ~0.999、R 连着十几轮**同一个数**纹丝不动 —— 这是训练前中期的**正常形态**，不是"数据学不会"：
模型先把定位做准（只敢高置信输出），之后才放开召回。实测同一 run 在 2/3 进度处 R 从 0.5714 → 0.7227（+26.5%），
同时 P 从 0.9999 退到 0.895（正常的 P/R 权衡）。
- ⇒ 看**全程曲线**再下结论；要判"是不是数据问题"，等训练完成看**逐类 val 的 P/R**（逐类能分出"某一类拖后腿"
  与"整体均匀保守"）。
- 真正该立刻怀疑数据的信号是：**逐类 R 完全相等**（同一个 0.5714 同时出现在两个类上）、或 val 框数/图与标注对不上
  （分辨率或尺度不匹配），而不是"前期 R 低"。
- 报告里写**相对起点的提升幅度**（mAP50 +38.5% / mAP50-95 +67.3%）比只报终值有用；用户会追问"到底改进了多少"。

## 图类交付：字体先验 + 出图后必自视

曲线图/柱状图是报告的一部分，但它**比表格更容易静默报废**：文件生成成功、字节数正常、代码零报错，
而整张图里中文和数字全是方块。根因常是**字体缺字形**，不是代码写错。

1. **字体先验，别拿正式图试**：`fc-list :lang=zh family file` 列出中文字体后，**先渲染一行混排样本**
   （中文 + 英文 + 数字 + 括号 + 正负号）成测试图，**看图选字体**，选定再出正式图。
   实测 `DroidSansFallbackFull.ttf` 在 matplotlib 下**缺拉丁字形** ⇒ 连数字和括号都变方块
   （只报 `Glyph 102 (f) missing` 的 warning，极易被 `2>&1 | tail -3` 滤掉）；`NotoSansCJK-Regular.ttc` /
   `wqy-zenhei.ttc` 正常。
2. **注册 + 逐个显式指定**（`.ttc` 的 `get_name()` 会返回集合里第一个变体，如 `Noto Sans CJK JP`，仍含简体字形）：
   ```python
   for f in (FONT_REG, FONT_BOLD):
       font_manager.fontManager.addfont(f)
   FP = font_manager.FontProperties(fname=FONT_REG)
   plt.rcParams['font.family'] = FP.get_name(); plt.rcParams['axes.unicode_minus'] = False
   ```
   标题/图例/`annotate` 逐个传 `fontproperties=FP`（粗体另用 FONT_BOLD），不靠全局兜底。
3. **出图后自己看一眼再说"已交付"**：`出图 XXX.png 204KB` 只证明写了文件。用视觉工具读四件事：
   ① 中文/数字有无方块 ② 曲线与刻度可读 ③ 标注箭头指向对不对 ④ 图例不压曲线。读不出 = 重出，别发。
   **发一张方块图比不发更伤** —— 用户会据此怀疑整份报告。
4. 环境缺 matplotlib 时**走项目 venv 的 python 跑脚本文件**（`./<venv>/bin/python tools/plot_x.py`），
   别在无该库的解释器里内联绘图代码。

## 报告生成器：结构化取值，不塞原始 JSON 切片

把上游 `summary.json` / A/B 结果**原样 `json.dumps(...)[:1800]` 贴进报告**是最常见的坏形态：
硬截断会把字段切在中间（`"exists": tr` 后直接跳到下一节），读的人分不清"没这个字段"还是"被切了"。

- 一律**解析成表**：按层/阶段各一张表，列 = 指标 · 训练值 · 验证值 · 含义；原始 JSON 只留路径。
- 🔴 **数值从日志解析，别只报退出码和耗时**：`rc=0 / 337.7s` 不构成"训练有结果"。
  多任务模型（INTACT 类）日志末行是 `| k: v | k: v |` 可逐段切；lerobot 类正则取
  `step:(N) … loss:([\d.]+) … updt_s:([\d.]+)` 与 `action_loss:… lew_loss:…`，取**最后一次**匹配。
  顺带核 `skill_ctx_used` 这类"该被用的东西有没有真被用"的字段 —— 它等于在替用户做真实性检查。
- **结论文字按实测值动态生成**，不写死：`%d/%d PASS` 自己从判据算，好处写成
  `cos 0.8010→1.0000 · 泄漏 0.5164→0.0000` 这种从数据拼出来的句子。写死的结论文案一旦数据变了就是在说谎。
- **命令类字段不许截断**：`[:120]` 会把 `reproduce_cmd` 切成 `(HF 上 ~`，重下命令因此不可用。
  长命令宁可独占一行给全；要截就只截"说明"，不截"命令"。
- **口径写进报告正文**：`LoRA 适配 100 步(r=8, 基座冻结) = 验证「能训通、梯度到齐」，不是收敛训练`。
  不写这句，读者（和未来的你）会把 smoke 数字当正式指标。

## 坑
| 坑 | 对策 |
|---|---|
| 报告一片 0/err 就当现场结论 | 先自证工装与上游(`curl`/`ping`/`ss`), 分清"现场挂了"和"探针挂了" |
| 本机服务 200 ⇒ 认定链路全好 | 代理端点(图片/上游数据)可能 502; 往外探一层再写根因 |
| 只有产线网段通时才能取到样本 ⇒ 一断网整类失败 | 工装内置**样本源回退链**(产线 → 本机在线通道 → 本机存图), 每条标出实际来源 |
| 平均延迟被冷启动拉爆 | 中位 + 最大并列, 并注明含首次预热 |
| 把"服务 active"当指标通过 | 回读真产物/计数器(调用数递增、产物时间戳): 进程活着 ≠ 在干活 |
| 指标只有值没有来源 | 五要素必齐, 否则用户会逐条追问 |
| 只有 md 没有机读版 | md + json 成对; 交付时 md 作附件发出, json 路径写清楚 |
| 只有一两个指标却叫"性能报告" | 先按十类扫一遍补齐类别: 报告价值在覆盖面与判定, 不在条数 |
| 出图成功 = 图能用 | 字体缺字形会让中文+数字全变方块而零报错; 出图后必自视一遍再交付 |
| 报告里直接贴 `json.dumps(...)[:N]` | 硬切断在字段中间; 解析成指标表, 原始 JSON 只留路径 |
| 只报 `rc=0 / 耗时` 就说"训练有结果" | 从日志解析 loss/MAE/吞吐等真实指标, 并写明步数与口径 |
