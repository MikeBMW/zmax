# 多模型栈的「拍预算」实测 (in-tick vs async)

面向: 一条实时控制回路里挂了多个模型 (检测 / 世界模型 / 分割 / VLM / 动作头 / 规则计算),
要回答「这个平台跑不跑得动」「哪个模型该上哪块芯片」「换 Thor 能多换什么」。

## 一、先定记账口径, 再测

每个组件必须归到两类之一, 否则算出来的数没法用于决策:

- **入拍 (in-tick)**: 每个控制周期都必须跑完的 (检测、世界模型前向、流形步进、动作头)。
- **异步 (async)**: 按需触发或低频刷新的 (分割掩膜、视觉塔编码、大 VLM)。

拍预算写法: `sum(入拍组件延迟) / 周期 × 100%` = 占空, 余量 = 周期 − 合计。
余量的意义是「留给异常处理/退段重试的预算」, 不是「还没用满可以再塞模型」。

判据示例 (100ms 拍): YOLO 2.90 + INTACT 3.92 + 流形 0.99 + 动作头 0.53 = **8.33 ms ⇒ 8.3%**,
余 91.7ms。把 SAM3 (474ms) 塞进同一个拍 ⇒ 占空 480%, 直接推翻设计。
**分层不是审美, 是预算约束** —— 这句话比任何架构图都能说服人。

## 二、逐设备测, 不要一个数代表一台机器

同一颗 IR/ONNX 在三块芯片上差 1~30 倍, 且**快的那个因模型而异**:

| 模型 | NPU | iGPU | CPU |
|---|---:|---:|---:|
| YOLO 640 | 2.90 ms | 2.19 ms | 98~144 ms |
| INTACT 编码 | 2.73 ms | 1.79 ms | 48~116 ms |
| SAM3 编码 (894MB IR) | 2872 ms | **474 ms** | >170 s |

小模型 NPU 与 iGPU 同量级; 大模型 (近 GB 级 IR) iGPU 快 6 倍 —— 编译/调度开销随图规模放大。
⇒ 结论写成「**按模型分设备**」, 不要「全部上 NPU」。CPU 那一列必须留着: 它是「省掉加速卡」的代价证据。

## 三、显存/内存共存的取证顺序

要证明「某模型装不下」, 必须先在**在役状态**下记占用, 再腾空:

1. 先 `nvidia-smi --query-compute-apps=pid,used_memory --format=csv,noheader` +
   `for p in $(...pid); do tr '\0' ' ' </proc/$p/cmdline; done` 拿到「谁占多少」的明细 (这本身就是报告素材)。
2. 再停服务腾显存 (`systemctl stop` 掉训练/画布/按需分割), 测完**原样起回**并核对产物新鲜度
   (引擎 `cycle` 增长、`engine_latest.json` mtime), 否则「测完了引擎没起来」比没测更糟。
3. 结论写成「总 X / Y MiB, 三件大模型已占 Z, 再加 N GB 的模型 ⇒ 不可能同卡」, 并给实测 OOM 作为证据。
   「配置不够」是判断, 「实测 OOM」才是证据。

## 四、测的坑 (每个都真炸过)

| 坑 | 症状 | 修法 |
|---|---|---|
| 权重按 (out, in) 存 | `mat1 and mat2 shapes cannot be multiplied (1x512 and 39x512)` | 用 `x @ W.T`; 输入维取 `W.shape[1]`, 不是 `shape[0]` |
| 权重键序不可靠 | 逐层前向后维度对不上 | 按 `W<数字>` 排序; 或按「哪一维不出现在其它 W 的输出维」推输入维 |
| 端侧无 torch / 无 hf_hub | `ModuleNotFoundError: huggingface_hub` —— 其实只想 import 一个 numpy 模块 | 按**文件路径** `importlib.util.spec_from_file_location` 加载; 被加载模块里的相对导入要留绝对导入回退 |
| `global ROOT` 放在 argparse 之后 | `SyntaxError: name 'ROOT' is used prior to global declaration` | `global` 必须是函数第一句 (在引用默认值之前) |
| IR/ONNX 不在默认目录 | 组件整行 `N/A`, 看着像模型缺失 | 路径给候选链 (`zmax_data/models/ir` → `ir` → `../edge_models/ir`), 每个候选都试; 命中后把实际路径写进 JSON |
| 用论文/厂商数代替实测 | 报告好看但和现场对不上 | 只写 `mean/p50/p95` + 设备 + precision; Thor 这类未到货平台单列 `est.` 并注明「FP4 稀疏 ≠ int8 TOPS」 |
| 计时不 warmup / 不 sync | 首个样本吃掉编译与加载 | 前 2~3 次丢弃; GPU 每轮 `torch.cuda.synchronize()`; 报告写 N |
| 只测成功路径 | 大模型在 CPU 上「超时未完成」被静默略过 | 失败要落成一行 `不可用 (>170s 未完成)` —— 这本身就是结论 |

## 五、输出结构 (md + json 成对)

```
一、单组件实测表      组件 | 角色(L2/L4/...) | 平台/设备 | 延迟 | 说明
二、拍预算            入拍链合计 / 周期 ⇒ 占空 + 余量 + 一句判定
三、异步清单          哪几件出不了拍, 各自的替代节奏 (1Hz / 按需)
四、共存与显存        在役并发明细 + 装不下的那个 (实测 OOM)
五、目标平台的 projection   标注 est., 给规格与量级, 不给假精度
```

组件表的「角色」列必须写层号 (L2 感知 / L4 世界模型 / L3 前馈 / L4 几何): 只写模型名,
读者无法判断它该不该进拍。
