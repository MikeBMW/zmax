# 主机指标探针的四个假数陷阱

命中口径：给一台生产主机出"各项指标怎么样"的报告。报告的价值全在"每个数字都是真测的"，以下任一条不守，整份报告都可能被一句"实际怎么测的"推翻。

## 1. 先验证字段名，再读数
猜字段名读不到的键会静默得 `None`/`0`，然后被当成 FAIL 写进报告。
- 动手前先 `curl -s <url> | python3 -m json.tool | head -40` 看清真实 schema（例：臂相机桥的计数键叫 `n`/`fps`，不叫 `frames`/`frames_total`）。
- 同一含义在不同服务上名字不同（`frames_total` vs `n`），写探针时为每个字段单独适配，不要一处适配到处复用。

## 2. "端口 200 但 /health 404" 不是服务挂了
是**没有这条路由**。判活顺序：先根路径，再 `/health`，再业务路由；三种结果要分开记（端口没开 / 开了没这路由 / 路由报错），否则会把健康的服务写成 "down"。

## 3. 没有厂商工具就降级到 sysfs，测不到就写 err
- `xpu-smi` 缺失时读 `/sys/class/drm/card*/device/tile*/gt*/freq*/{cur,max}_freq` 拿核显实际频率，`sensors` 拿封装温度。
- 降不下去的项（无传感器/权限）一律写 `err` + 原因。**绝不写 0 或估数**：一个估数会让整份报告的可信度归零。

## 4. 报告里的计数要自洽
- 声明的 `total` 必须等于实际枚举条数；`PASS/WARN/FAIL/err` 四项之和必须等于 `total`（手写报告最常错在这）。
- 每项必须带**阈值 + 判据**，否则那是读数不是指标（例：`load1 / 线程数` > 1 判超订；帧龄 > 1s 判断流）。
- 归一化口径写进报告：min/MAX 值、分母、采样窗口。

## 5. 探针自证两招
- 有一条"已知在动"的对照：上游计数器两次采样必须递增（证明采集链路真在工作，而不是读到了缓存文件）。
- 探针与构建器分层：`tools/<name>_probe.py` 只负责采数出 JSON（跑不通就写 err），`tools/<name>_report_build.py` 只负责定阈值/归并/计数。两层分开，第二次修改不用重跑现场。

## 6. 性能结论要收廖到根因
多项 FAIL 往往是**同一个根因**（例：CPU 被四个重活超订 + 封装 98°C 降频 ⇒ 视觉帧率/训练吞吐一起掉）。报告最后一节写"FAIL 归并"，把 N 条异常收到一条根因 + 两条配置建议，比列 10 条现象有用。
