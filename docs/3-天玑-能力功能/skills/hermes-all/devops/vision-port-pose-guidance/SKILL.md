# 视觉端口 → 位姿引导 (vision-port pose guidance)

## When to Use

- 用户要「检测请求自动返回位姿, 机器人随动」, 但那个检测端口只回 `verdict/count/class`。
- 要把「照片 + OK/NG」升级成「偏差 → 毫米 → 目标位姿」的闭环。
- 任何「视觉量 → 机器人单轴/单自由度微调」的活儿(居中、对中、间隙补偿、边缘对齐)。

## 铁律 1: 位姿必须算在**检测服务内部**, 不在调用方、不在旁路代理

「检测 API 自动返回位姿」几乎从来不是那个端口自己能做到的 —— 判决口不产几何量。
正解是把三样东西缝成一个接口, 对外表现为「检测自带位姿」, 而且**这个接口要长在检测服务自己身上**:
调用方只发一次 `POST <检测口>/guide_pose`, 位姿由它算完随响应返回。

🔴 **先问清"算在哪一侧"再写代码**。旁路代理(本机另起端口, 去调检测口取图再算)看着更干净、更好离线调,
但从调用方视角它就是"第二个服务", 与「10082 会自动返回位姿」这类现场口径直接冲突 ——
实测先按代理做完、起了服务、跑通了数字, 才被一句"这个是请求工控机那个服务的, 服务会反馈位姿"推翻,
代理只能降级成旁路调试。**在检测服务内部加路由才是这个口径的唯一实现**。

```
POST /<svc>/guide   {mode, axis, pose{x,y,z}, target_px, max_step_mm, tol_px}
   → POST <检测口>/capture_detect        (触发真检, 拿判决)
   → GET  <检测口>/picture?grab=1        (取这一帧原图)
   → 定位(条带/ROI + 列剖面周期) → 首尾等距修到 N 个
   → 偏差 px → ×k(mm/px) → pose_target
   ← {measure{center_px,pitch}, off_px, act, d_mm, pose_target}
```

- 返回值里**带着原判决**(verdict/count) → 调用方一次请求拿到「合不合格」+「往哪挪」。
- 接口只一个入口, 不要把它拆成"先检测再查位姿"两次调用: 拍照与定位必须**同一帧**, 中间夹一次新抓帧就错位。

## 铁律 2: px→mm 与「轴正负 = 屏幕左右」都不许猜

按工件尺寸估能差 50%(实测 0.0118~0.0177 mm/px), 而世界轴正负对应画面左右还取决于相机朝向。**猜错的后果是反着走、越走越偏**, 比不动更坏。分三段:

| mode | 行为 | 落什么 |
|---|---|---|
| `probe` | 只走 ±2mm 试探(单轴小步) | 记下试探前后的中心 px 与位姿 |
| `solve` | 用前后画面差反算 `k=d_mm/|Δpx|` + 符号, 写标定文件 | `{k_mm_px, axis_sign}` 持久化 |
| `auto` | 有标定直接给终值; 没标定**自动降级为 probe** | 不编数 |

- 标定一旦落盘, 之后每次调用都直接给终值 —— 试探只需做一次。
- `solve` 的符号判据: `Δpx<0 且 d_mm>0` 或反之 ⇒ `sign=+1`, 否则 `-1`。
- **2mm 的试探量**是刻意的: 在几十毫米级视野里只移百来像素, 即使方向判错也不会跑出视野, 反手就能回来。
- 🔴 **不要把"像素节距变了"当成"k 变了"** —— 这是两个不同的量, 混为一谈会把**准的标定判成过期**。
  `pitch` = 工件自身几何在像素上的投影(N 根之间的间距, 随工件/遮挡/工位变化);
  `k_mm_px` = 相机工作距离与焦距决定的尺度(世界毫米→像素)。两者没有换算关系。
  ❌ 我踩过的错: 标定时 pitch **71 / k=0.011343**, 后来 pitch 变 **56**, 我据此推断 k 应放大 71/56 倍,
  并对外宣称"291px 该走 4.18mm, 服务给的 3.30mm 少算 21%"。**真机实测否掉了这个推断** ——
  走 3.312mm 后 off_px 从 292.0 落到 1.0, 反算 `k=0.011381`, 与标定值只差 **0.34%**。标定一直是准的。
  ⇒ 曲线: 用 pitch 比值去缩放 k 会凭空造出 20% 级的"误差", 然后去"修"一个没坏的东西。
- ✅ **k 是否过期, 只能靠"走一次再回读"实测**: 走一个已知 mm, 读 off_px 变化,
  `k_实测 = |d_mm / Δoff_px|`, 与标定值比 —— 差 <5% 就是准的, 差大才重标。
  这条路不用 probe 试探、不动标定文件, **每次补偿都顺手做一次**, 应作为 `guide_move` 的返回字段
  (`k_mm_px_effective`) 常驻自证, 而不是等用户怀疑数字时才去查。

## 铁律 3: 假闭环守卫 —— "动没动"必须当独立判据

「让机器动一下再反算系数」这类标定, 最容易出的不是算错, 而是**机器压根没动、流程却往下走**。
- 守卫: `solve` 时若试探前后中心差 `<1px` ⇒ **直接拒绝**, 并报实测差
  (「走 2.0mm 后画面几乎没变(Δ0.50px), 检查是否真的动了」)。
- 同理适用于任何"发命令→回读"的链路: 把**回读值与命令值逐位/在容差内相等**当验收, 不要只看命令发成功。
- 自测时要**清掉试探记录**: 机器人没动时留下的 probe 会污染下一次 solve(表现为反复报"没动")。

## 铁律 4: 单轴 + 原样回传

只改一个平移分量(默认 Y), 其余 x/z 与**姿态一律原样回传**。理由: 姿态一动就碰到插入/夹持/工装约束, 而这类居中任务本来只有 1 个自由度。
- 用户说"沿世界 Y 轴横向移动/向屏幕左侧"= 精确的单轴语义, **不要自己加 Z 或姿态补偿**。
- 参数化 `axis`(X/Y/Z), 但每次只允许一个。

## 铁律 5: 服务只算不下发 + 限幅

- 引导服务返回 `pose_target`, **发不发由授权链决定**; 它自己绝不调运动接口。这样"算"和"动"可以分开验收, 也避免算法 bug 直接变成机械动作。
- 单次补偿上限(如 8mm); 超了**截断**并标 `clipped`, 让上层分多次走, 而不是一次跳过去。
- 居中容差(如 20px)内直接回 `act=hold`、`d_mm=0`, 不做无谓微动 —— 否则在容差边缘会持续抖着发指令。
- 🔴 **做界面按钮时要先把"只算不动"这件事说在前面**。用户说"增加位姿调整按钮"时，心里默许的是"点了机器人会自己对齐"；
  而按本铁律服务只返回 `d_mm`，按钮点完臂一动不动，他会直接问"机器人的移动你是怎么搞的"。
  ⇒ 要么按钮文案写明（如「🎯 取位姿（不动臂）」）并在结果里同时给出 `d_mm` 与"需沿 Y 走 X mm"，
  要么在交付时就明确报出"算法+标定已就绪、自动下发这一步未接", 并把接上需要的那条运动通道（笛卡尔单轴微动，非关节步进）写出来。
  别让他自己点完才发現没动。
- 🔴 **这层“未接”要能被一句命令测出来**: `POST <检测口>/guide_pose` 回 `act=move/d_mm=3.3`, 而发完读机器人位姿**一毫米没变**
  ⇒ 证明服务确实没下发。根因通常是运动侧只有"按关节角走帧"那条通道(`step_traj`),
  **没有笛卡尔单轴微动入口** —— 两者不是一套坐标, 不能拿关节步进冒充毫米补偿。
- ✅ **接上它的唯一正解是笛卡尔单轴微动。** 已跑通并真机验证的链(珞石 xCoreSDK):
  ```
  页面按钮 → POST <推流口>/api/aoi/guide_move          ← 新增的独立接口, 不塞进 /api/aoi/guide
    → <检测口> /guide_pose                            抓帧定位, 出 off_px 与 d_mm(不动臂)
    → POST <8797 轨迹台>/api/arm/move_rel {dy:d_mm, speed, max_mm}
    → bash tools/rokae_sdk_run.sh move-rel --dy X --speed 5 --max-mm 5.01
    → 容器内 sdk_ctl.py move-rel → precheck(automatic/power on/无报警) → xCoreSDK 笛卡尔, 姿态锁 p0.rpy
    → 回读再取一次 /guide_pose, 用 off_px_before/after 证明真挪了
  ```
  验收三件, 缺一不算接通: ① 机器人位姿单轴变化量 == `d_mm`(实测 Y 129.75→133.06, +3.31mm, rpy 未变);
  ② `off_px` 明显收敛(实测 292.0→1.0); ③ 反算 k 与标定一致。
  ⚠️ 只看 `rc=0` 会漏掉"发了没动" —— `sdk_ctl.py` 自己的 precheck 不过时也可能回 0, 必须回读位姿。
- ✅ **两个按钮, 不要一个**: 「🎯 位姿调整(只报数)」+「▶ 按位姿移动(真动)」。取数只读、移动不可逆,
  混进同一个按钮出问题时无法判定"是它动的还是只是取了个数", 现场就不敢点。
  🔴 用户说"机器人可以动了"时, 要**当场把移动按钮接上并真跑一次**再回话 —— 他会立刻去点,
  点完不动就是"怎么没动"那一声。
- ℹ️ **这类补偿是迭代收敛的, 不是一次到位**: 实测走到 off_px=1.0 后, 隔几分钟独立再测是 **52.0px(≈0.59mm)** ——
  重复定位/工件微动就是这个量级。所以每次都要报 `off_px_before/after` 供用户决定再点一次, 不要报"已对齐"。

## 铁律 6: 定位算法绑了实时 ROI ⇒ 离线跑历史图必然 0 结果

这类"自动找 N 个"的定位函数, 内部常无条件向检测服务问**当前帧**的条带/ROI:
`_gold_region_band(port, max_age=0.5)` 之类。条带是**当下这一帧**的坐标, 拿去切历史图会整片错位 ⇒ 列剖面无峰 ⇒ 返回 0 个框。

- **指纹**: 同一算法跑**当前帧**给框、跑**历史原图**给 0 框 ⇒ 是绑定问题, 不是数据里没结构。别去调阈值。
- 加个 `live_band=False` 走图自身统计兜底**通常也不够准**(实测 3 个框 / 节距 103 vs 真值 ~71)。
- ⇒ 离线批量预标注必须**先解决"条带从哪来"**: 用一段可靠参考条带、或先做模板配准定位, 再套等距/后处理。

## 铁律 7: 先量"目标是否居中", 别默认它在画面中间

引导之前先把偏差量出来, 它常常是**两个毛病的同一个根**:
- 实测一例: 条带 `x0=824 x1=2280`(图宽 2448) ⇒ 中心 **1552** vs 图中心 **1224** ⇒ **偏 328px = 13.4% 画宽**。
- 后果一层(现在就疼): 条带右界只剩 168px 余量 ⇒ 最右一个易被切半、峰值变弱 ⇒ 算法少报一个。
  实测正是如此: 条带 `[824,975,2280,1056]`(图宽 2448) 只给 **18** 根, 而 `pitch=71.0` 与人手画的 **70.84**
  只差 0.16 ⇒ 节距可信、缺的是**最外那根**。
  判法: `span 差 ≈ 1×pitch` **且** `pitch 与人工值吻合` ⇒ 边缘切根, 不是算法坏, 别去调阈值。
  **修法选"按 pitch 外推补一根", 不要放宽条带** —— 条带一变判据图口径跟着变, 牵动的面比一根手指大得多;
  外推只影响引导口自己的计数, 补在哪一侧由两侧余量决定(余量大的一侧才是被切的那侧)。
  🔴 **补根的判据不能用"相邻间距是否均匀"**。峰本身带假峰/漏峰, 相邻差天然很散
  (实测 18 个峰间距 46~95px、变异 23%), 而人工画的同一排间距 RMS 只有 1.4px ——
  拿 `np.diff(peaks).std()/mean() < 某阈值` 当门槛, 门槛松了就乱补、紧了永远不触发(实测卡在 18 根不动)。
  ⇒ 正规判据是**整体线性**: 对已有峰位置拟合 `x ≈ a + b·i`, `b` 当 pitch, 残差 `< 0.35b` 才认这条线,
  再按拟合相位在余量大的一侧补到 N 根。验收看**中心对账**: 补完中心与人工画值吻合到个位像素
  (实测 1568.9 vs 1570.75, 差 1.85px) 才算补对; 只看"根数到 19 了"会漏掉补错一侧的情况。
  ⚠️ 少一根会让中心偏 **约半个 pitch**(实测 38px ≈ 0.67mm): 闭环能跑, 但收敛点偏, 报数时必须写出来。
- 后果二层(以后疼): 所有样本里目标恒在同一侧 ⇒ 模型学的是**位置先验**("这个位置有东西"), 换机位即失效。
- ⇒ 偏差要同时进两处: ① 当引导的输入(算要挪多少 mm) ② 当采集策略的依据(让目标在画面里换位置采数据)。

## 铁律 8: 往**在役常驻服务**里加路由, 踩的是进程内状态不是算法

在役检测服务(Flask, 后台跑着判据图 + 检测队列)里加引导路由, 三个硬伤:

- 🔴 **新路由读 `_LAST_*` 全局 ⇒ 重启后恒为空**。条带/ROI 这类几何量常由**另一个端点触发的后台检测队列**
  才写进 `_LAST_CROP_INFO` / `_LAST_REGION`; 引导口不走那个队列 ⇒ 首次调用拿到 `{}` ⇒ 静默降级到兜底条带
  ⇒ 列剖面无峰 ⇒ 报「N 根定位失败」。
  **指纹**: `src` 显示兜底来源、`lag` 落在默认值、条带尺寸比正常小一个量级(实测 365×35 vs 1456×79)。
  ⇒ 正解: 引导口**自己调几何生产函数**(如 `crop_goldfinger_regular(bgr)`)拿条带, 不要读别人写的全局。
- 🔴 **共享定位器要按"输入形状"分支，不按"调用方"分支**。`_LAST_REGION` 这类全局除了可能为空，还可能是**已加工过的形状**：
  它存的是 `region_payload()` 的**输出**（带 `region` 键、没有 `strip`），而定位函数内部又调一次 `region_payload(bgr, info)` ⇒ 二次包装
  ⇒ `KeyError: 'region'` ⇒ 位姿口 500/422。按调用方分支（`if caller=="guide"`）早晚漏一个。
  定式：`if isinstance(info, dict) and "region" in info and "strip" not in info: reg = info` 否则现算。
- 🔴 **换成新定位器后，两个端点必须同时换**。实测判据口已用等间距网格法稳出 N=19，而位姿口还在调旧找峰函数
  ⇒ **同一帧一个出 19 根、一个报 `no peak` 422**，按钮点了就失败。更坏的是报错文案写"检查工件是否在观察位"，
  把人往工件/工位方向带，实际是这边算法过时。判据：同一帧同时打两个端口，`n` 必须一致；不一致就是走了不同定位器。
- 🔴 **取图必须与条带同源, 且必须无损 —— 省时间的路会连踩三种坏法。**
  想省掉 `GrabAndSaveImage()` 那 1.4s 的判据图渲染, 有三条"看起来更快"的路, 全都试过且全都坏:
  | 走法 | 症状 | 机制 |
  |---|---|---|
  | 自己另开取像入口(`_grab_bgr_only()` 类) | 条带 `365×35`、`gold_px=0`、0 峰 | 与 `/region` 走的不是同一路取像(settle/去坏帧那一层被跳过了); 同一时刻 `/region` 给的是好帧 |
  | `GrabAndSaveImage(save=False)` + `imread(返回路径)` | 条带对、`lag` 从 71 掉到 21、`no peak` | **`save=False` 时原图根本不落盘**(只有 `save=True` 才写), 返回路径指向**上一次的旧文件** ⇒ 图是旧的、`_LAST_REGION` 是当前帧 ⇒ 图与条带不同源, 切出来是废块 |
  | 内存帧(`_mem_get("origin")`) | `lag` 已对到 72.8 仍 `no peak` | 内存帧是 **JPEG**, 压缩伪影把窄峰抹平 |
  ⇒ **`save=True` 拿无损 PNG 是唯一稳的**。整次调用 2.6s 可以接受: 先保证同源+无损,
  再谈省时; 顺序反过来就是拿三种坏法换 1 秒。判断同源只看一条: 条带坐标切到图上,**能不能切出有结构的行带**。
- 🔴 **patch 插路由会把邻居端点打坏**。在 `@app.route("/picture")` 上方插入新路由时, 锚点若选在函数体首行,
  很容易吃掉邻居的 `try:` 或把 docstring 与首行拆开 ⇒ `py_compile` 照样过、请求却 500。
  ⇒ 锚点取**装饰器行 + def + 函数体首行**整块, 并在替换文本里原样保留; 每次 patch 后 `py_compile`,
  部署后**把新路由和邻居路由都 curl 一遍** —— 只测新的等于没测。

部署流程固定两段: 先 `--dry`(推送 + SHA256 校验, **不重启**)确认字节一致, 再正式跑(备份 + 重启 + 验收)。
⚠️ 不少部署脚本收尾会"复原取像档位"或重放某个预设 —— 复位后画面可能跟算条带时不是一回事,
所以**首次调用前重新看一眼 band/gold_px**, 别拿部署前的画面结论去解读部署后的 0 根。

## 铁律 9: 定位失败先分清"画面坏"还是"算法坏"

报「N 根定位失败」时, 一半的根因不在算法在**取像档位**, 而且它不会以报错的形式出现。

- 过曝时全部特征一起消失: 实测中位灰度 255、饱和 60% ⇒ `gold_px=0`、条带退化成贴边的 `365×35` ⇒ 0 峰。
  判法是看质量字段而不是看返回值: `gold_px`、`bright_frac`、`focus` 三个一起看,
  正常帧(Gold-Px 数万 / 饱和 <40% / focus 两三百)与过曝帧(0 / 1.0 / 几十)差别是量级级的。
- 🔴 **`POST /param?exposure=&gain=` 回 `ok:true` 不等于写进去了**。这类 OPT 相机在采集过程中写
  `ExposureTime` 会静默失败, 抓图**逐位不变**。⇒ 验证方式是**同一接口连抓两帧比字节/比均值**,
  不是看返回值。硬改要走"改档位落盘文件 + 重启服务 + 复验质量字段"。
- 🔴 **连 `applied.ok:true` 也不代表取到你给的值**: 回执里同时带的 `now` 才是真值 —— 实测申请 `gain=1.0`
  回 `ok:true`, 读 `now` 是 **2.0**(设备下限 1.33, 被静默夹到档位边界)。⇒ 每次写档位都回读 `now` 再报生效,
  报数按 `now` 说, 不按你要的值说。
- 档位会随**现场光照**失效: 曾记录的"唯一正确档"(高曝光高增益)在换了光照的当晚就是过曝源。
  ⇒ 换时段/换灯/换批次后**先跑一次质量字段体检**, 不要拿上次的档位结论直接跑视觉。
- 部署脚本常带"复原取像档位"收尾 ⇒ 你手改的曝光会被它拨回去。改档位时**同时改部署脚本复原源**,
  否则每次部署都回到旧档, 表现为"偶尔好、多数坏"这种最难查的间歇性。

## 验证清单(交付前逐条跑)

- [ ] `GET /health` 回服务名 + 检测端地址 + 当前标定
- [ ] 首调用(无标定)回 `act=probe` + `pose_target` **只变一个分量**
- [ ] 未真动就 `solve` ⇒ 必须被拒且报实际 Δpx
- [ ] 真动后 `solve` ⇒ 回 `k_mm_px` 与 `axis_sign`, 且落盘文件可读回
- [ ] 再调 `auto` ⇒ 直接给终值(不再 probe)
- [ ] 已居中 ⇒ `act=hold`、`d_mm=0`
- [ ] `guide_move` 的 `dry=true` ⇒ 只回显 `plan`, 不起容器、位置一毫米不变
- [ ] `guide_move` 真跑 ⇒ 位姿单轴变化 == `d_mm` 且 rpy 未变 + `off_px_after` 明显小于 `before` + `k_mm_px_effective` 与标定值差 <5%
- [ ] 补偿超过上限 ⇒ `clipped=true` 且 `d_mm` 等于上限
- [ ] 部署后在役服务: 新路由 200 **且邻居路由仍 200**(patch 打坏邻居是这类活最常见的事故)
- [ ] 首调用的 `band` 尺寸是正常量级(不是兜底条带), `n` 等于现场真值 —— 差几根就写明差几根、为什么、偏多少 mm
- [ ] 节点入口能打开且显示同一组数字(GUI 改码后需重启宿主进程才生效)

## 已知限制(报数时如实写)

- 服务若用手起进程, 重启机器就没了 —— 要长期在役得做成 systemd。
- 标定文件要跟"相机+工位"绑定: 换镜头/换高度/改曝光后 `k` 会变, 必须重做 probe→solve。
- 定位本身若依赖实时 ROI(铁律 6), 那么"对历史图/离线算"这条路**先别承诺**。
