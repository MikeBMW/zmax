# AOI 工控机 · 时间戳录制

两件事常被一起问到：「AOI 检测程序启动了么」和「把实时数据带时间戳存下来」。
它们的答案都在对端已有服务里，先查再建。

---

## 一、AOI 检测（工控机 192.168.23.23，Windows）

两个独立服务，各管一台相机：

| 端口 | 职责 | 相机 | 图尺寸 |
|---|---|---|---|
| 10082 | 金手指检测 | OPT 整板 | 2448×2048 |
| 10083 | 表面检测 | OPT 表面 | 1280×1280 |

### 真实端点（只有这几个）

```
10082  GET  /picture?kind=origin[&grab=1]   整板原图（grab=1 触发真拍，约 0.7s）
10082  GET  /region                          模板匹配给金手指条带 bbox
10082  GET  /param                           取/设曝光参数
10082  POST /capture_detect                  拍照 + YOLO 检测 + 落盘，约 1.6s
10082  GET  /last_result                     上一次检测的判决
10083  GET  /picture?kind=crop[&grab=1]      判据图（工控机侧切模块 + 调平）
10083  POST /capture_detect                  同上，但 **约 8.8s**
10083  GET  /last_result                     同上
```

**两路端点名完全一样，只换端口** —— 别以为金手指走的是另一个路径。

只读旧图 6~53ms；带 `grab=1` 要 0.6~0.7s（真拍）。

### 取图 ≠ 检测：三个动作代价差一个数量级

```
GET  /picture?kind=xxx           读内存旧图          6~53ms   无副作用
GET  /picture?kind=xxx&grab=1    拍照 + 返回图       ~0.7s    相机被占，设备动一下
POST /capture_detect             拍照 + YOLO + 存图  1.6s(gf) / 8.8s(housing)
                                 还会写 D:\AOI_images\<gf|housing>\incoming\<ts>.png
```

`grab=1` **不等于**检测。用户问「这个检测请求是你发的吗」时，用 `cmd` / 耗时 /
`saved_incoming` 三个字段区分：只有 `POST /capture_detect` 会带 8.8s 级耗时和存图路径。

**10083 的等待别设 5 秒**。`_aoi_detect` 默认 `wait_s=4.0`，遇 10083 自动放宽到 13.0，
因为表面单帧推理实测 ~7.8~8.8s。自己写脚本直连时按 8.8s 留余量，否则会报"还没出结果"
其实是还在跑。

### 8793 上的 `/api/aoi/*` 是 POST-only

`POST /api/aoi/detect?port=10082` · `POST /api/aoi/param?port=10082&profile=pt1`
（参数仍在 query string，body 用 `{}`）。**用 GET 调会返回 `not found` / 404**，
和"路径写错"长得一模一样 —— 别因此去翻代码找路由。

两条路的差别，选之前先想清楚要不要留痕：

```
直连 .23:10082/capture_detect        只有工控机的原始响应
经 8793 /api/aoi/detect?port=10082   额外落盘本地 + 写进 /api/aoi/log（页面终端可见）
                                     + 汇总进 /station/status 的 aoi 统计
```

给用户 PowerShell 命令时写 `curl.exe`，不是 `curl` —— PS 的 `curl` 是
`Invoke-WebRequest` 别名，参数完全不同。

### 探活判据

```bash
# 只读，不触发拍照
curl -s -m 10 -o /tmp/a.jpg -w '%{http_code} %{size_download}\n' \
  'http://192.168.23.23:10082/picture?kind=origin'
file /tmp/a.jpg        # 期望: JPEG ... 2448x2048
curl -s -m 10 'http://192.168.23.23:10082/region'   # 期望: {"ok":true,"mode":"template",...}
```

**别用 `%{size_download}` 判断有无内容** —— MSYS/Git-Bash 的 curl 配 `-o /dev/null`
实测恒为 0，会把正常 body 读成空响应。落临时文件再 `file`。

### `/region` 返回字段怎么读

```json
{"ok":true, "mode":"template", "angle":-3.25, "image_size":[2448,2048],
 "crop_size":[364,18], "bright_frac":1.0, "gold_cover":0.0, "stripe_cols":0}
```

- `angle` = 模板匹配出的整板倾角，供后续去倾角用。
- `bright_frac: 1.0` **且** `gold_cover: 0.0` **且** `stripe_cols: 0` 同时出现 ⇒
  缓存那张图里视野没有金手指（板子不在位 / 遮挡 / 拍的是空台面），
  **不是检测服务坏了**。这只说明"当前缓存帧没内容"，要确认真能检出得带 `grab=1` 真拍。
- 这类"读缓存"接口不反映实时，判活够用，判检出不够。

### 判断「金手指歪没歪」：排列角 ≠ 外壳透视角

用户说"金手指有点不正，能不能调平"时，先把两个角分开量，否则会去转根本不需要转的东西：

- **`diag.pitch` 不是实测倾角**。`/api/aoi/guide` 的 `gold.diag` 里那个
  `{"n":19,"pitch":14.0,"src":"grid","start":0.8}` 是**网格搜索的起始参数**，
  不是测出来的角度。拿它报"歪了 14 度"会直接误导现场。
- **排列角用检出框中心算**：取 19 个 `gold.boxes` 的中心，按 x 排序取首尾，
  `atan2(dY, dX)`。实测首尾 `(1244,1351.5) → (1496,1351.5)` ⇒ **0.00°**，
  且所有框都在同一 y 带（1282–1317）—— 这说明金手指排列本身是平的。
- **外壳会看着斜 ~4°，那是透视**。2448×2048 原图里 USB-C 外壳左右上角高度差
  约 50px（缩放图），即斜 ~4°；那是斜视相机造成的投影，不是工件摆歪。
- 两个角分开报：排列 0.00°、外壳透视 ~4°、位置 `off_px` 还差多少。
  绝大多数"看着不正"其实是**位置没居中**，不是角度。

对照原图别用 `kind=crop`（只有一条竖条纹，看不出姿态），要 `kind=origin`（2448×2048）。

**move_rel 只平移、不改姿态**，所以：要调的若真是排列角，得走 `sdk_ctl` 的 `move-abs`
改 RPY（转轴/方向要先确认，有碰撞风险，不盲目转）；要调的只是位置，直接沿
`off_px` 对应的轴走 `k≈0.0113 mm/px` 的换算量即可。

### 判"实时 vs 缓存"：连采 3~6 次比字段

`/region` 不留时间戳，光看 `ok:true` 分不清是刚算的还是几天前的。连采几次，
**所有字段逐字不变（连 `angle` 的小数位都不动）= 缓存**，不是实时结果。
`/picture` 返回 **0 字节也是常态**：工控机 OPT 只在检测/拍照时留图，闲着时内存里没有，
不是服务挂了。

### 图"有字节但内容无效" ⇒ 查曝光，不要查链路

某格"没图"时先分清三种，处置完全相反：

| 现象 | 含义 | 处置 |
|---|---|---|
| 404 / 0 字节 | 没人叫过，内存无图 | 正常，等触发 |
| 有字节 + JPEG 头正常 | 图在 | 看内容 |
| 有字节但纯白 / 纯黑 | 曝光坏了 | 查 `/param` |

判有无内容必须**看图**，不能靠字节数：960×330 的金手指图 **5.6KB 就是纯白**，
同尺寸 30KB+ 才有内容。纯白 = 过曝，纯黑 = 欠曝。
（“看图”指看图里有没有物体；**颜色和亮度要用像素统计判**，肉眼看会错 —— 见下文“判颜色/内容用像素统计”。）

`GET /param` 同时给出当前值和文件默认值，比对即知有没有被人改过：

```json
{"now": {"exposure_us": 200000.0, "gain_db": 8.0, "model": "OPT-CC1-GG50"},
 "file_defaults": {"exposure_us": 20000.0}}
```

曝光标定值约 **3000us × 1.8 增益**（死白 1.72%、可检出）；48000us 死白 90.74%、检出 0。
10083 没有 `/param`，要改只能在工控机侧改。

**10083 的 `/picture` 端点不保证存在**：同一台机器上实测过 `kind=crop` 回 200（72KB）
也回过 **404**（该 build 只有 `POST /capture_detect`）。判某一路能不能做实时流，先
`curl -o /dev/null -w '%{http_code}'` 打一发 `/picture?kind=crop`；404 就是这条路根本不存在，
不是曝光/相机问题，8793 上那格会永远 `online=false`。

**极重要：不要凭档位名字判断曝光对不对。** `pt1` 的描述写着
“金手指正面 · **产线已验收的档** · 前视 p50≈63”，听着最权威 —— 但那是对
**漫反射**工况标的；金手指是**镀金镜面**，20000us 打上去中心直接冲成
`RGB(253,254,244)`（三通道挤一起 = 白到丢色），`stripe_cols` 归零。
镜面只能看死白占比（`>250` 的像素比例）和实测字节数，不能看档位名。

- **曝光与增益要成对调，不是独立旋钮**。增益抬 6dB 等于信号翻倍，只提增益必然全白：
  实测同一台金手指相机 5000us/4dB 与 2000us/10dB 画面都可检出（bad 同为 3 根），
  2500us/10dB 起过曝、5000us/10dB 直接纯白（输出恒定 ~5.7KB）。用户只给了增益值时，
  **同时给出配套曝光并说明取舍**（增益高 = 暗部亮但中心饱和），别只改一个数就回报「调好了」。
- 每次改完都要**看图**：存 jpg 比字节数（~50KB 有细节 / ~5.7KB 纯白），必要时再跑一次
  `POST /api/aoi/detect?port=10082` 看 19 根是否齐、bad 是几根 —— 曝光偏暗会直接让
  bad 从 3 根涨到 9 根（全是欠曝误判），只看 `code:200` 会把它当成真缺陷报给现场。

**降到 3000us 后空画面会全黑（mean≈4），这是对的，不是曝光太低。**
镜面反射强所以短曝光就够；没有产品进来时镜头前是漫反射背景，光量本来就不够。
此时正确结论是“等产品进画面”，不是“再调回 20000us” —— 一调回去又死白，
会陷入来回摆动。判据：**空画面全黑可以接受，产品进画面后能看见金黄色条带即可。**

**产线在动时不要动相机参数** —— 机器人可能正在用同一套流程，曝光是它设的。
先观察，把"建议改 3000us"报给用户，由他挑停机窗口；**用户明确说改才动**。

#### 相机在采集中会**拒绝**写参数 —— 这是最容易白忙一小时的一条

运行时改参**并不总是被拒，但失败是静默的** —— 唯一的裁决是 `applied.*.ok` 和 `now` 有没有变，
`code:200` 一律不作数。自己先发一次比预判可靠：实测同一台 10082，页面正以 1fps 拉流时直接
`POST /param?exposure=N&gain=N` 依然能写成（`applied.*.ok=true`、`now` 立刻变），所以
**不要凭 `/stats` 的 `online/fps` 就断定「必须改源码重启」**。真正被拒时回执长这样：

```json
{"code": 200,
 "applied": {"exposure_us": {"ok": false, "want": 3000.0},
             "gain_db":     {"ok": false, "want": 1.8}},
 "file_defaults": {"exposure_us": 20000.0, "gain_db": 8.0},
 "hint": "相机在采集中拒绝写 exposure_us,gain_db(实测本机型只能在不采集时写)
          ⇒ 请改本文件里的常数并重启服务; 切勿尝试停采集再写"}
```

三条要记住：

- **HTTP 仍是 `code:200`**，失败只体现在 `applied.*.ok=false`。只看状态码会以为改成了，
  然后对着"还是过曝"的画面去怀疑镜头/标定/链路。
- **`applied.ok=false` 时 `now` 不会变**，`/param` 读回来还是旧值（如 `20000.0`）。
- **不要为了写参数去停采集再写** —— 对端 hint 明确禁止（会打断正在跑的检测流）。
  正解是**改源码里的 `file_defaults` 常数 + 重启那个服务**，这是唯一能落地的路径，
  而且改完永久生效。

所以"能秒级改参"的前提是**没有任何东西在拉这台相机**。判断顺序：
`/stats` 里该路 `online=true` 且 `fps>0` ⇒ 相机在采集 ⇒ 直接走改常数路线，不要在
`/api/aoi/param` 上反复试数值。

#### 落盘文件只管本机那个 8793，管不到工控机

`cam_param_persist.json` 是**本机 8793 进程**写进**本机磁盘**的：
`C:\Users\Admin\zmax\zmax_data\aoi_v4\cam_param_persist.json`
（脚本内写作 `~/zmax/zmax_data/aoi_v4/cam_param_persist.json`）。

它保证的是"本机 8793 重启后不丢"，**不会传到工控机**。工控机自己的 AOI 一重启就回到
它的 `file_defaults`（实测 20000us）。所以在工控机上看到的"我设好了怎么又变回去"，
不是落盘失败，而是**参数从来只存在于本机**。

要真正钉住，只能改工控机那份 AOI 源码里的曝光默认常数（搜 `20000`）并重启。
这条属于"必须到现场/U 盘"一类的动作。

改的手法和验证闭环（**仅在相机空闲时**秒级生效，不用重启）：

```bash
# 预定义档: pt1 = 20000us×8dB (金手指正面, 标称「产线已验收」但对镀金镜面会死白)
#           pt2 = 40000us×8dB (背面)
# 金手指实测可用值: exposure=3000 gain=1.8 (绕过档位，直接给数值)
curl -s -X POST -H 'Content-Type: application/json' -d '{}' \
  'http://127.0.0.1:8793/api/aoi/param?port=10082&profile=pt1'
curl -s -X POST -H 'Content-Type: application/json' -d '{}' \
  'http://127.0.0.1:8793/api/aoi/param?port=10082&exposure=5000&gain=8'
```

回执里 `want` / `applied` / `now` 三块都要看，`applied.exposure_us.ok=true` 才算写进去；
`ok=false` 就是上面那条"采集中拒绝写"，别继续换数值试。

**改完必须验证两件事**：

1. **落盘** —— 让本机 8793 重启后不丢（**但只对写它的那台机器有效**，见上一节）：
   文件里应含 `{"10082": {"exposure_us": 20000.0, "gain_db": 8.0, "profile": "pt1"}}`。
2. **相机真的响应了** —— 改两档拿**原图**比字节数：
   `5000us → 295KB` vs `20000us → 532KB`。差异明显 = 传感器在正常跟随参数；
   两档字节数一样 = 参数没进相机，别再调曝光，去查会话/占用。
   比的是 `/picture?kind=origin`（2448×2048），不是 8793 的 `snapshot`（那已经裁小了）。
   注意 `kind=origin` 有时回 **PNG（约 6.4MB）**、有时回 JPEG（约 530KB），
   体积本身不是亮度指标，要解码后算均值/死白占比再判。

### 页面"延时大" = 相机节拍，不是 8793 拖慢

先量再猜，两个数就把责任分清了：

```
GET /picture?kind=origin       0.004 ~ 0.086 s   读内存旧图
GET /picture?kind=origin&grab=1  0.55 ~ 0.62 s   真拍一帧  ⇒ 上限 ≈1.7 fps
```

0.6 秒里曝光只占 3ms（3000us），其余全在传感器读出 + GigE 传输 + JPEG 编码。
`_aoi_worker` 的逻辑是「有人看这一格就每轮带 grab，顶到 OPT 上限」，所以 8793
**已经榨满**了，转发只占约 0.01s。

结论模板：「这是相机物理极限，不是脚本慢；画面流畅度只能靠降分辨率或改连续采集模式，
而 `/param` 只有曝光/增益/gamma，改不到。」
想换"更跟手"只有一个取舍：把画面改成只读内存帧（毫秒级响应，但看到的可能是几秒前那帧）。
**把它做成用户可切换的开关，不要默认切过去** —— 工控机不主动拍照时，只读模式会显示静止旧图，
看起来像相机死了。

### 守候式观察：用户说"我一会放上去，你看着"

别用 `grab=1` 轮询（会占相机、干扰产线），**只读** `kind=origin` 每 2~3 秒一帧，
每帧记 `(字节数, md5, 平均亮度, 梯度, 中心 RGB)`，与上一帧比，变化超过阈值打 `>>> CHANGED`。

```python
grad = |diff(gray, axis=0)|.mean() + |diff(gray, axis=1)|.mean()   # 4x 降采样后再算
flag = abs(Δsize) > 8000 or Δgrad > 0.4
```

- **梯度**是判"有没有东西"最灵的量：空底色 grad≈4.25 极稳，有物体进来会明显跳。
- 阈值放宽到 `Δsize>20000 / Δgrad>0.8` 会漏掉小的，实测漏过一整个光模块；
  收紧到 8000 / 0.4 才抓得住。宁可多报几条 `CHANGED` 让用户忽略，也别漏掉那一秒。
- 跑成后台进程 + `tee` 到日志，把它当"事件流"读；用户问"到了么"直接贴最近几行。
- 用户说"我拿走了"就停进程、把日志改名归档（`round1/round2`），别让两轮混在一份里。

### 判颜色/内容用像素统计，不要肉眼

肉眼看图的颜色会错。同一张暖光下的底色，我先说"灰褐"、用户看是"金黄色"，
算一遍 `R=163 G=149 B=134 (R-B=29)` 立刻定了：是**低饱和暖调**，不是中性灰。

```python
a = np.asarray(Image.open(f).convert('L'))            # 亮度
a.mean(), np.percentile(a,95), (a>250).mean()        # 均值/高分位/死白占比
r,g,b = np.asarray(Image.open(f).convert('RGB'))[...].mean(axis=(0,1))
```

判据：

- `R-B ≈ 29`、均值 150 上下 ⇒ **暖米色底，正常**。金手指是镀金镜面，饱和度高得多，
  模板匹配靠"条带结构"区分，不靠颜色，所以这个底色是设计好的，不是故障。
- 均值冲向 255 / `>250` 占比明显 ⇒ 才是过曝。
- 中心区域 RGB 三通道挤到一起（253/254/244）是"白到丢色"的特征，比看整图均值更快定位。

### 判决 `OK` 不代表检过 —— 空画面必然 0 缺陷

画面是一片均匀背景、没有任何产品时，检测照样返回：

```json
{"verdict":"OK", "count":0, "defects":[], "ms":595.5, "detect_type":"gf"}
```

因为"没找到缺陷"和"没有检测对象"在判决层长得一样。**判这条结果能不能信，看三处，
缺一条就当"未检出产品"处理**：

- `/region` 的 `gold_cover` / `stripe_cols` 是否非 0（模板匹配到金手指）
- 原图字节数：2448×2048 的整板图 **529KB 全灰 = 空**，同尺寸有板子时画面明显不同
- 必要时抓 `GET /picture?kind=judge` 看判据图本身

同理 `judge_ok:false` 配 `judge_why:"上边缘不直(最直段残差 10.80px > 3px)"` 而 `verdict:OK`，
是"判据图不合格但保守放行"，不是干净的 OK —— 这类要如实报给用户，别只报 verdict。

### 回答"到底有没有请求"：在唯一入口挂环形缓冲

AOI 状态更新通常都汇聚在一个函数（`cam_live_stream.py` 的 `_aoi_note(port, **kw)`）。
**在那一个函数里追加环形缓冲**（`deque(maxlen=120)`，记 `hhmmss/ok/http/kb/kind/err` + 现态快照），
比在十几个调用点各埋一遍可靠且不会漏；`ok` 要用 `"ok" in kw` 判，
别用 `if kw.get("ok")`（否则 `ok=False` 会被记成"未提供"）。再开只读端点
`GET /api/aoi/log?port=10082&n=20` 给页面终端 1.5s 轮询。

页面侧：终端放每个检测格图片正下方，`✓`(绿) / `✗`(红) / `-`(中间态)，
仅在用户已滚到底时才自动跟到底（往上翻历史不会被拽走）；
空态文案写"还没有请求 —— 工控机只在被叫时才出图"，避免下次又被当故障报。

价值一句话：**图没了的时候，一眼分清"工控机根本没被叫"（机器人在别处/没到检测位）
还是"叫了但失败"（相机卡住/超时/曝光坏）—— 这两件事的处置完全相反。**

## 二、时间戳录制（Intel 550C · zmax-ts-recorder）

**对端很可能已经有了。** 建之前先:

```bash
systemctl list-unit-files | grep -iE 'rec|ts-|record|trace'
systemctl cat zmax-ts-recorder.service
cat /dev/shm/zmax_rec/status.json
```

### 契约

```
单位: zmax-ts-recorder.service   (Type=simple, User=intel, Restart=always)
脚本: /home/intel/zmax_550c/tools/ts_recorder.py
频率: REC_HZ=2.0
落盘: REC_ROOT=/home/intel/zmax_map/rec/<YYYYMMDD>/
        ├── index.jsonl          每帧一行
        └── frames/              对应 jpg，文件名自带本地时刻
状态: REC_STATUS=/dev/shm/zmax_rec/status.json
容量: REC_MAX_GB=20             满了自动删最旧的日期目录
位姿源: REC_POSE_URL=http://127.0.0.1:8811/pose   (ROS /robot/tcp_pose)
```

### 一行的结构

```json
{"ts_wall": 1795659584.103,      // 本行落盘墙钟
 "frame": "20261126/frames/101944_109_usb-cam.jpg",
 "src": "usb-cam", "wh": [640,480], "bytes": 46515,
 "ts_grab": 1795659584.109,     // 抓图时刻
 "ts_pose": 1795659732.801,     // 位姿 header 戳 —— 来自机器人控制器时钟
 "ts_pose_recv": 1795659584.120,// 位姿到达本机的墙钟
 "pose": {"x":..., "y":..., "z":..., "qx":..., "qy":..., "qz":..., "qw":...,
          "rx":..., "ry":..., "rz":..., "frame":"base_link"},
 "pose_age_s": 0.018, "pose_stale": false,
 "skew_ms": 11.0,               // 图像↔位姿配准偏差
 "pose_clock_drift_ms": 148681.0}
```

### 铁律：配准只用 `ts_pose_recv`

机器人的控制器时钟**不同步**（实测比本机墙钟快 140~150 秒，且会漂）。

- 图像 ↔ 位姿对齐 ⇒ 一律用 `ts_pose_recv`（本机收到位姿的墙钟）。
- `ts_pose` 只作留证，`pose_clock_drift_ms` 记录漂移量。
- **做跨设备时间对齐分析时绝对不要用 `ts_pose`**，否则会拿 148 秒的系统误差当物理现象解释。

要根治就得给控制器配 NTP，不在软件侧修。

### 健康判据（`status.json`）

```json
{"ok":true, "hz":2.0, "n_ok":1072, "n_err":0,
 "skew_ms_p50":4.3, "pose_stale":false,
 "disk_gb":18.31, "max_gb":20.0, "err":""}
```

- `n_ok` 在涨、`n_err` 不涨、`pose_stale:false` = 正常在录。
- `skew_ms_p50` 单位毫秒，个位数最好，两位数仍可用。
- `disk_gb` 接近 `max_gb` 时靠自动删旧目录腾空间，不必手工清；但**别再往上叠第二个录制器**同写一个 `REC_ROOT`。
