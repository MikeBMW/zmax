## 8802 画面「不动 / 乱动 / 两边不同步」的真因清单 (2026-11-10 实测)
- **显存不足**：`nvidia-smi` 只剩 ~400MB 时 MuJoCo `Renderer.render()` 会在 C 层**不返回**，整个 8802 冻住（n 不涨，`/frame.png` `/video` `/joints.json` 全停，进程 100% CPU 但不出图）。先腾显存，别当链路故障查。
- **两个写者**：8797 页 `mjPushQ` 每 120ms 推 `/armq`，`ar_cmd` 也写同一批 qpos ⇒ 乱动 + 两边对不上。判据用 `/status.json` 的 `ac_driving`（ar_cmd 是否在喂）；为 true 时页面必须停推、只镜像 `/joints.json`。别用 `joints.json.src` 判断——页面一推它就变 `armq`，会自锁。
- **`ar_cmd` 自锁**：只在 `mode=="idle"` 读 ar_cmd，而它一驱动就把 mode 置 `sim` ⇒ 下一拍不再读，姿态冻在第一帧。要每拍都读（新鲜即唯一真源）。
- **IK 与渲染共用 MjData**：IK 每拍在共享 `model/data` 上 `mj_forward`，渲染线程同时 `update_scene/render` ⇒ MuJoCo 内部状态被踩，render 卡死。IK 用私有一份 `MjData`（只同步 qpos）。
- **平滑两道闸**：目标点 12mm/拍 + `ik_solve(rate_deg=6)`；不加闸实测单拍 49°/200ms = 乱动，加硬拒绝又会卡死不动。
- **跨端口读不到**：8802 原来没有 CORS，8797 页 `fetch(:8802/joints.json)` 被浏览器拦掉 ⇒ 静默退回自解 IK。`end_headers()` 统一加 ACAO。
- 兜底：渲染线程打心跳 + 看门狗线程 6s 无心跳 `os._exit(9)`，靠 systemd `Restart=always` 秒级重拉，别让用户对着卡死画面等。
- **第二观察窗要跟主页面同机位同动作，别另开固定机位**：用户提「这些动作要跟 render.html 同步」就是这条。
  8802 支持 `?cam=ar3d&live=1` —— 用 AR 页每拍推来的相机参数（`/cam.json`，`age_s` 秒级）**现场**渲染，
  同一台 MuJoCo、同一步动作 ⇒ 视角与动作天然同步；页面拉帧 1s→**250ms**（1s 看着像幻灯片）。
  判据：连拍三帧 hash 全不同（动作在跑）+ 与不带 `live` 的缓存帧差几十万像素（证明是现算视角，不是旧图）；
  特写仍留一个按钮切回 `cam=close`。
- **"/station 页机器人不动" 与 AR 页无关**：那台页面驱动的是真机，先看 `/ctl/status` 的
  `operation/mode`（`drag`+`manual` ⇒ 前置不满足）+ `motion_armed`；本 skill 描述的仿真臂永远不受它影响。

> 深度参考 (场景同步): `references/ar-vs-mujoco-scene-sync.md` — AR 页 ↔ 8802 MuJoCo 要做到「同机位 + 同关节角」: 机位逐字段照搬并 tz 取反、画幅比先算比例再限幅、推角要自愈不能只试一次、`R_tcp` 锚点删了会静默停臂、夹爪必须画在 tool1 系 (与法兰差 38.7°)、判夹持用跟物特写 + 几何投影对账而不是读图。

> 深度参考: `references/camera-and-rail-layout-stability.md` — 画面上下漂浮（drawVR 每帧自动取景把运动臂算进包围盒）、左栏按钮上下跳（不许有出现/消失的行，信号摘要只上顶部横幅）、播放命令 120s 时效口径与跟版刷新丢播放、浮层在两栏之间居中（§4 多视口几何账 + 离屏 iframe 判交配方）、删「只在某态出现」的横幅时别留半条链（§5）。

### 🏷 「全关」= 连画布文字一起收掉 (2026-10-27)
老倪: 「工程配置点有个全关和全开按钮, 增加按钮的功能, 点击全关的同时, 可以把所有文字显示都关掉,
现在的文字太多了, 影响阅读。全开则是显示文字」。
- 用户嫌的是**信息密度**, 不是某个标签: 点位名/坐标/料盘名/槽名/轨迹标签/TCP 数值一起才叫“文字太多”。
  ⇒ 不要逐个给 `fillText` 加开关(几十处, 必漏), 直接拦画布文字接口一次全灭:
  ```js
  var VR_TEXT=true;
  (function(){ var p=CanvasRenderingContext2D.prototype; if(p.__zmaxTextPatched) return;
    var f=p.fillText, s=p.strokeText;
    p.fillText=function(){ if(window.VR_TEXT===false) return; return f.apply(this,arguments); };
    p.strokeText=function(){ if(window.VR_TEXT===false) return; return s.apply(this,arguments); };
    p.__zmaxTextPatched=true; })();
  ```
  面板/按钮/侧栏是 DOM, 不受影响(照样能点) —— 这是要的效果, 不是缺陷。
- 接在原按钮上(不是新加一对): 「全关」= 点位全隐 + `VR_TEXT=false`; 「全开」= 点位全显 + `VR_TEXT=true`, 两边同改。
- 验收: 全关/全开三次截图的**画布 diff**(实测 29699px, 1.86%, bbox x[309-1207] y[3-608] 正是文字区),
  开回后亮灰像素 16447 完全恢复。⚠ 别用“亮灰像素数下降”当判据: 网格线/坐标轴也亮,g 只降 5% 看着像没生效。

### 实验桌 750 + 箱体落地平齐 + 四轮 (2026-10-26 r22)
老倪: 「在机器人底座箱体前面摆放一个实验桌子, 高度750; 机器人的箱体高也降低到750平齐; 且底座增加4个轮子」。
- 🔴 **只有一种几何能同时满足「750 + 平齐 + 不抬臂」**: 地面(轮底/桌腿落地点) = `z=-0.750`,
  桌面顶 = 箱体顶板 = 两臂安装面 = `z=0`; 箱体**向下长**(本体 680 + 轮露出 70 = 750), 顶板一动不动。
  反过来说, 若把 750 当成"从 z=0 那块 base 网格往上量", 桌面就跑到 +0.75, 比臂安装面高 750, 不可能平齐
  —— 「降低到 750」是箱子向下落地, 不是把臂压低。**先把这个口径写进页面注释再动手**, 否则做出来的图必被退。
- 口径参数: `CHS={L:.6,W:.8,H:.75(落地总高),HB:.68(本体),wr:.075(轮半径),cy:.25}` ·
  `TAB={x0:.35,x1:.95,cy:.25,w:1.6(沿y, 老倪定稿1600),t:.03,h:.75}` · `FLR={z:-.75,x:[-.5,1.25],y:[-.7,1.2]}`。
  桌子摆 +X(前脸 HMI 那侧 = 两臂/顶视相机作业方向), 桌沿离箱体前脸 50mm ⇒ `TAB.x0 > CHS.L/2` 是硬闸。
- 画法: 轮子用**轴沿 y 的圆柱**(`_discY` 22 边圆盘 ×2 端面按屏幕深度排序 + 轮毂 + 亮芯), 比原来的扁盒子像;
  地面层 = 半透明深色 quad + 250mm 暗格 + 标签; 桌子 = 4 腿 + 两条下横撑 + 桌面 + 顶面高光线 + 750 竖标尺。
- 绘顺序: 地面 → 桌子 → 箱体 → 臂。默认视角 `yaw=-0.9` 是从 -X+Y 看过来, 桌子在箱体**远侧**,
  所以必须"先桌后箱", 反过来桌子会盖在箱体上。
- 💥 判据坑(都实测踩过):
  1. **顶视相机视锥(10% 半透青)压在桌面上**, 木色 `#7a5f45` 被染成 `(119,109,84)` ⇒ 只数纯木色只有 66px,
     看着像"桌子没画"。改用"木色域"判(R 90~150 · G 72~135 · B<105 · R>G>B · R−B>28), 实测 15881↔关3437。
  2. 轮毂色 `#39424e` 与暗色抗锯齿杂点撞色(关掉箱体还剩 ~350px) ⇒ 轮子判据改用**轮芯亮钉 `#b9c6d4`**
     (全页独有, 实测 165↔关2)。桌腿色也因此从 `#3d444d` 改 `#4a4f58`(与轮毂同色系会互相污染)。
  3. 工程点位那条判据(亮点 全开→全关 掉 60%)会被**暖色标注/高光**污染: 桌面高光 `#f0d9ac` 与 750 标注
     `#d8b98c` 的 min 通道都 >125 ⇒ `bright()` 必须加 `min(R,G,B)<125` 只数饱和色, 否则 ⑦ 假红。
  4. `baseZ` 别写 `LINKM.base_link`(没有这个键): URDF 基座名是 `XMS5-R800-W4G3B4C_base`,
     按 `/_base$/` 找。它是"臂安装面没被抬动"的唯一硬证。
- 判据已扩到 12 项: ⑩ 箱体 600×800×750(本体680) + 臂安装面 z=0 · ⑪ 桌面在前脸之外/1000×600×750/真画+开关不动相机 ·
  ⑫ 桌高=箱体落地高=750 + 地面 -750 同层 + 四轮真画出来。2026-10-26 实测 12/12 全绿。

## 8793 与 8797 的关系 (老倪问过「通道怎么还变了」)
- 8793 = `tools/cam_live_stream.py`(工位总览 `/station` + 状态空间视频源); 8797 = `tools/tcp_ar_server.py`(AR 真源)。
- `8793/ar` **只做 302** → `8797/ar`, 不代理(`cam_live_stream.py` 的 `/ar` 分支); 所以 8793/ar 秒回 302,
  真正的页面/取帧/判据 API 全在 8797。控制台的页面入口固定 `10.163.146.78:8793/ar`(他记的地址),
  服务探测走 `127.0.0.1:8797`(回环优先) —— 同一台机两个端口, 不是"通道变了"。
- 🔴 **路径全小写, 且 302 的 Location 写死回环** (实测): `/AR3D` 在 8793/8797 都是 **404(9 字节)**;
  可用的是 `/ar3d`。而 `8793/ar3d` 回的 302 是 `http://127.0.0.1:8797/ar3d` —— **手机/别的机器打开会被跳到它自己的
  127.0.0.1 而打不开**。给局域网/手机就用 `http://<本机IP>:8797/ar3d` 直连, 别绕 8793。
  他要"你来打开"时: `DISPLAY=:0 xdg-open 'http://127.0.0.1:8797/ar3d'`, 再用 `wmctrl -l` 找标题
  `Z-MAX · TCP 轨迹 AR/VR 调试台` + `ss -tnp | grep :8797` 有 ESTAB 才算真开了(只看 Popen 成功不算)。
- **打不开的真因**: 8797 是 fork-per-connection(`max_children=24`, backlog 5)。多开几个 AR 页后实测
  24 个子进程 / RSS 合计 12.3GB / LISTEN Recv-Q=6 满 ⇒ 新连接排队, `curl -L 8793/ar` 要 **175.8s** 才通
  (直连当时也 30s 超时), 浏览器窗口一直空白(标题 `Untitled`)。
- 配套坑: `ar_spawn_browser` 只要 Popen 成功就报「页面已送出」, 不看窗口也不看加载 ⇒ 状态栏"送出了"
  但屏幕上没画面。判"开了"要认窗口标题/连接数, 判"页面真出来"要认标题变成 `Z-MAX · TCP 轨迹 AR/VR`。
- **已修(2026-10-26)**: 改成 `ThreadingMixIn` 单进程多线程 —— `request_queue_size=128` · 线程上限 96(信号量,
  满了直接关连接不排队) · `H.timeout=20`(断链线程 20s 必收)。实测 6 个页面同时刷时新开页 4—320ms(中位 122ms)、
  零错误、单进程 103 线程 / RSS 789MB 稳定; 旧 fork 模型是 24 子进程 / 12.3GB / 175s。

任何一环"看着A执行B"都是事故级缺陷, 必须先把链路口径对齐再动手。

### 🧈 右臂「动作不平顺」的量化真因与三件套修法 (2026-11-01 r86)
老倪: 「现在的AR场景右臂 动作不平顺, 怎么回事? 修」——先量再改, 不要先调 PD/增益。

**两个根因(都是实测, 不是推测)**
1. **指令流只有 2.5Hz**: `zmax-ss-canvas-loop` 现在每拍跑**全部 80 个节点**(白名单已于 10-31 按老倪要求删除),
   `canvas_loop.json` 实测 `cost_ms≈278 / budget 100 / over_budget true`, 真实 tick 只有 **2.51Hz**(配置 10Hz)。
   而 `sim_insert.json` 段长中位 **0.3s** ⇒ 一段连一拍都拿不到。判据: 采 `canvas_loop.json` 的 tick 增量算频率,
   不要信 `hz` 字段(那是配置值)。重节点排名: ssintact_dec 78ms · ssintact 77 · ssyolo 36 · ssaoi 34 · ssdec 16。
2. **页面把每个采样硬赋给 `PREV.q`**(`plantAtAR` 里 `PREV.q=ARCMD.q`) ⇒ 每次更新都是一次瞬移。
   基线(239 帧真浏览器 rAF 采样): **218 帧完全静止(91%)** · 21 帧单帧 >20mm · 20 帧 >100mm ·
   **单帧最大 690.7mm · 单关节 48.7°**。这就是「一顿一顿」的全部来源。

**修法三件套(全在页面 `tools/web/tcp-ar.html`, 热读生效, 不用重启服务)**
- `arCmdU(d)`: 同一采样重复读到时按**本地时间**继续推进 `u = u0 + el/t_seg`; 采样身份用
  `kind|seq|u|mt_id|a|b` 拼 key —— 🔴 不能在每帧调用时重锚 `t0`, 否则 `el` 恒 0、u 永不前进(踩过, 静止帧仍 69%)。
- `arPointTarget(d)`: u>1 时按 `/api/sim_insert` 的 **392 段表本地续接**(上限 3s, `ARCMD.age>1.2s` 不续),
  段表匹配用精确 a/b(±0.6mm), 失败再**按 a 点最近 50mm 兜底**(少了这条, 段末仍会停 → 静止帧 52/276)。
- `arPointStep`: 画点按 **600mm/s 限速**逼近目标(段表隐含末速 p90 625mm/s, 所以只吃掉瞬移不吃正常速度);
  IK 后再加**关节限幅 3°/帧**(IK 换解支会让单帧跳 10°+/99.8mm, 等比缩回, 方向不变)。

**验收口径(会动的段内统计, 静止段要单独剔掉)**
| | 改前 | 改后(r86) |
|---|---|---|
| 会动段里静止帧 | 91% | **8%** |
| 单帧位移 p50 / p90 | 0 / — | **9.4 / 14.2 mm** |
| 单帧最大位移 | 690.7mm | **40.7mm**(>100mm 0 次) |
| 单关节单帧最大 | 48.7° | **3.0°**(限幅) |
判「静止」必须用 `seg=dist(a,b)<=5mm` 把**检测停留段**(golden 0.68s 原地)剔掉 —— 否则把正常停顿算成卡顿。

**还剩什么(如实报)**: 约 8% 的帧在段头微停、5 帧 >20mm, 源头就是 2.5Hz 指令流; 要根治得让 loop 里的
`ssplan` 走 10Hz 快车道 —— 那要重启 `zmax-ss-canvas-loop`(AR 会冻一下再续), 属停/起服务, 必须用户点头。

**🚀 快车道(已做, 2026-11-01)**: `ss_canvas_loop.py` 把全量节点**按原顺序切成段**(`ZMAX_LOOP_CHUNK`,
默认每段 12 个) 逐段 `prj.step(only=chunk)`, 段与段之间插一拍 `prj.step(only=['ssplan','ssact'])`
(`ZMAX_LOOP_FAST_HZ` 默认 20)。**语义不变**: 每个节点仍每圈只跑一次、顺序不变(不能用轮转分组,
那会把下游节点的输入推迟一整圈)。实测: `ar_cmd` **2.5Hz → 10.7Hz**, 全量拍仍 2Hz 量级, 80 节点全跑。
改完必须 `sudo systemctl restart zmax-ss-canvas-loop`; 验收读 `canvas_loop.json` 的 `fast_n` 增量
(注意它每 STATE_EVERY 拍才落盘, 直接用 `d['tick']` 增量算频率会偏低一个量级)。
快车道后的画面(会动的段内): 静止帧 5.3% · p50 8.4mm/帧 · 最大 33mm(帧率抖动, 600mm/s×55ms) · 关节 ≤3°。

## 页面显示三条铁律 (违反必然被退回)

1. **导轨/左栏禁止“条件渲染整行”**。要显隐就“在固定行内显隐元素”(按钮并排 + `flex-wrap:nowrap;white-space:nowrap`), 不要 `display:none` 整个 div 行 —— 任何一行的出现/消失都会把下面所有按钮顶上去, 用户看到的是“整列按钮上下跳”。
   验收: 开关关/开/跟随/回关 四态, 取同一个无关按钮的 `getBoundingClientRect().top` 与左栏 `scrollHeight`, 四值必须**完全相等**。
2. **三维视图禁止每帧自动取景**。`drawVR()` 里 `if(VR.auto) vrFitBox();` 每帧重算包围盒, 而包围盒包含正在动的臂点云 ⇒ 臂一上一下, 相机目标点跟着上下移, 整幅图“漂浮”。
   正解: 自动取景 **one-shot** (`if(VR.auto){ VR.auto=false; vrFitBox(); }`), 只有用户点「🎯对准」/双击执行轨迹才重新取景。
   验收: 跟随中隔 3s 读两次 `VR.tgt` / `VR.dist`, 必须逐位相同; 同时 `PREV.ssSeq` 要推进(证明是臂在动、不是画面卡住)。
3. **状态文字放顶部横幅, 不占左栏高度**。seq/帧龄/未接入提示这类“会变长、会来回出现”的串一律进顶部横幅(已在 ssSigShort 汇总); 左栏只放固定高度的控件。想让提示“消失”就整行删掉元素并清掉写它的函数, 不要留一个 `visibility:hidden` 之类还会撑高的壳。

## 🧠 拨杆三态与「画布▶运行」的定稿语义

🔴 **播放命令时效口径 (以本条为准, 覆盖本节其它写法)**: 页面侧 `PLANT._lastPlayTs` 初值 =
`Date.now()/1000 - 120`, 与服务端 `_ar_play_payload()` 的 `play.fresh`(≤120s) **同一口径**。
两端同口径后: ①超过 2 分钟的旧 `ar_play.json` 不能凭空拉起播放(不点不动);
②人刚点过运行、页面因跟版自校(自动刷新)重新加载时, 仍在 120s 内 ⇒ **继续跟随**。
初值锁成“页面加载时刻”会把自动跟版变成“开关开着却不动”, 初值锁 0 会变成“一打开就跑” —— 两个极端都踩过。 (2026-10-28 r56, 老倪三轮纠错后)

老倪原话序列: 「没点运行怎么就开始了」→「开关怎么自动关闭了? 关闭后手臂还动作」→「运行按钮一直是 运行/停止 的跳变」。
定稿语义 (**别再改回去**):
| 动作 | 语义 | 实现 |
|---|---|---|
| 拨杆拨到开 | **只接入** (显示 seq/帧龄/段/元任务), 一帧都不动 | `ssConnect()`: 只 `SSMODE.on=true` |
| 点 `▶ 跟随执行信号` | 才开始按 `ar_cmd` 走帧 | `ssFollowStart()`: on+follow, `PLANT.local=false` |
| 画布「▶ 运行」(AR场景) | **接入并跟随** (开关自己拨到开是故意的, 不是 bug) | 页面 `_pl.action==='start'` → `ssFollowStart()+arViewSet(true)` |
| 画布「⏸ 停止 AR 播放」 | **停住, 开关仍开** (停止 ≠ 断开) | `ssFollowStop()`: follow/plant 清 0, `SSMODE.on` 不动 |
| 拨杆拨回关 | **断并且停** (本地时钟播放也一并停) | `ssDisconnect()` → `ssFollowStop()` (`PLANT.local=false; PLANT.on=false`) |

踩过的坑:
- `plantStart()` 里曾把 `SSMODE.on` 强行拨回关(消"双驱动"假象) ⇒ 他看到的就是"开关自己关了", 而且关掉后 `PLANT.on` 还是 true ⇒ 手臂继续走。**任何按钮都不许改写拨杆状态**, 只许 `ssFollowStop()` 停跟随。
- `ar_play.json` 的 `play` 字段必须同时进 `/api/ar/cmd` 和 `/api/ar/mode` (`_ar_play_payload()`)。只在 mode 里有 ⇒ 画布运行推不动页面。
- 页面 `PLANT._lastPlayTs` = **加载时刻 − 120s**(与服务端 `play.fresh` 同一口径) ⇒ 手写 ar_play 要在**页面开着时**写;
  页面自己跟版重载后 2 分钟内的人点命令仍会被接上, 超 120s 的老命令不许自己拉起播放。
- 信号源 `zmax-ss-canvas-loop.service` 被 stop 后 `ar_cmd.json` 冻住 ⇒ 页面提示 `⚠ 状态空间信号中断 · 帧龄 Ns · 画面停在最后一帧`, 跟随时什么都不会动。查 `systemctl is-active`、`ls -l ar_cmd.json` 再怀疑页面。

## 五个必踩的坑
1. **别自己构造轨迹**。工程配置里没有的元素不要"以某个中点为心造个正方形"——他会立刻指出"不是新的"。
   要么读工程配置里真实元素, 要么读真源产物(planned_traj.json 等), 取不到就报缺什么, 不画。
1b. **"旁边那条粉色矩形"= 页面上的洋红规划航路闭环**, 不是工程配置里的盒子/设备顶面。
   认错元素的后果是轨迹贴着检测设备走(取 z=盒子顶面 ⇒ 净距 0), 他会立刻问"那不碰撞了?"。
   判据: 这条轨迹的首点应当≈当前 TCP(真机刚走过), 且到设备盒子的距离是几十到几百 mm 而不是 0。
2. **自动取景 = 视图跳 / 图像上下漂浮**。`vrFitBox()` 会重算 target/dist 并写回 VR; `drawVR()` 里若有
   `if(VR.auto) vrFitBox()` 就**每帧重取景**, 而 vrFitBox 把**会动的臂点云**算进包围盒 ⇒ 臂一上一上,
   相机目标点跟着上下移, 整幅图"漂浮"(用户原话:「图像不要总是上下漂浮」)。
   ⇒ **`VR.auto` 只能是"一次性"**: `if(VR.auto){ VR.auto=false; vrFitBox(); }` —— 自动取景只在显式入口做一次
   (`🎯对准 tFit/tAFit`、双击『执行轨迹』、`?traj=` 首载), 之后相机锁死, 只有手拖/中键平移才动。
   开关类按钮仍走 `vrKeepCam(fn)`(先存 `{yaw,pitch,dist,tgt}` + `VR.auto=false`, 改完写回)。
   自验(跟随中 3s): `VR.tgt` 与 `VR.dist` **逐位不变**(实测 [0.325,0.25,-0.0647]/2.0175 两次相同),
   同时 `PREV.ssSeq` 与 `ar_cmd.elapsed_s` 在推进(= 相机冻住、臂在动, 不是画面卡死)。
3. **数据变化指纹漏项 = 画不出来**。`drawIfChanged` 的指纹不含 NAMED 时, 点第二个按钮判"没变化"直接 return; 指纹里要放"哪些轨迹亮着 + 总点数"。
4. **同一语义两套 id ⇒ 只测一套会漏**。按钮同时存在顶部工具条 `tA1..tA5` 和三维视图下方 `t1..t5`,
   解析序号若写 `id.replace('tA','')` 对 `t1` 不动手, `Number('t1')` = NaN ⇒ key=undefined ⇒ 那一排**永远不变蓝**。
   必须显式剥前缀(`startsWith('tA') ? slice(2) : slice(1)`), 且自验时**两排各点一遍**——只点自己新加的那排会把 bug 藏起来。
5. **页面被第二个端口转发时, 只转页面不转 `/api/*`**。直接用 `curl <第二端口>/api/...` 验证;
   404 时页面里 fetch 全失败、按钮不亮。改法: 脚本最前面装一次 fetch 兜底, 页面不是从主端口打开就把
   `/api/*` 打到主端口(主端口已带 `Access-Control-Allow-Origin: *`)。
6. **数据是 0 点的按钮也必须点亮**。服务端对没有数据的轨迹回 `ok=false`, 前端若在那分支直接 `return`,
   按钮永远黑着——用户看到的就是"按钮坏了"。**激活是按钮状态, 有没有数据是另一件事**:
   `ok=false` 时同样置 `NAMED_ON[k]=true` 并重绘, 文字写"已激活 · 0 点 · 真机还没走过, 不能执行";
   汇总行不许把这类条目当"关着"过滤掉; 『▶ 执行轨迹』侧加闸, 0 点直接拒(不许走到空下发)。
7. **`confirm()` 会静默失效, 结果必须走页面横幅**。浏览器勾过"阻止此页面创建其他对话框"后,
   `confirm()` 直接返回 false ⇒ 处理函数第一行就 `return`, 什么都不发、无任何提示, 症状与"按钮坏了"一样。
   改法: 执行结果(成功/被哪道闸拒 + 实测数字)同时弹一条 6 秒固定横幅(`position:fixed` + 绿/红),
   不能只写按钮旁一行小字(会被轮询覆盖), 也不要把关键确认只压在 `confirm()` 上。

## 执行链口径
页面『▶ 执行轨迹』→ `POST /api/traj/exec {k,target,speed_mm_s}` → `tools/traj_from_named.py --k`
→ RDP 抽骨架(容差 5mm) → 骨架点间拆段 → `traj_plan.precheck_point` 逐点净空(≥20mm)
→ 写 `planned_traj.json` + `plan_latest.json` → `traj_exec.py` 一次性写 N 行 FIFO → 执行器。

🔴 **`k=real` 的拆段必须是「斜线等分」, 不是轴对齐** (`traj_from_named.build_from_points` 里 `if k=="real"` 分支):
中间点按 `u=i/n` 严格插在起点→终点连线上, 每段 ≤90mm(>100mm 控制器静默当零位移丢弃), 一律
`L2.forward` + `abs_mm`(`build_move` 末尾用 abs_mm 覆盖目标 ⇒ 真斜线 MoveL)。
为什么不能用轴对齐(先 Z 再 X 再 Y): ①画出来是直角阶梯, 直线 260.8mm 被走成 400mm(+54%)
②**实测会丢轴** —— 4 段 277mm 跑完 x/z 到位、y 差 53mm 没走, 而 `plan` 说"4 段都执行了"。
自验: 各段 Δ 的三个轴必须**同时非零且方向一致**(实测两段都是 `Δ=(-61.5,-30.3,+11.2)` ⇒ 共线);
首末点与当前 TCP / 目标点逐位一致; `n_seg = ceil(直线长度/90)`。
- **起点闸**: 当前 TCP 必须离轨迹首点 ≤20mm, 否则拒(与 550C 执行器同口径)。"先去起点"是独立运动, 不许混进轨迹。
- 失败原因必须**原样**回页面(`⛔ 起点闸: ... 差 278.6mm`), 不许只回"失败"。
- 示意坐标 / 已走过的记录(建图、实时)默认拒绝执行, 要试得 `--force`。
- **轨迹5『实时』= 当前位姿 → 安全点1 的待执行路径**, 不是"真机走过的记录"。用户要去安全点时点的是这一条:
  服务端现读当前 TCP + 点位台账的 `安全点1` 生成点列, 规划侧只取两端点按**弧长等分成斜线段**(每段 ≤90mm, 见下文「斜线等分」), 不准拆轴对齐(去安全点要抬 200mm+; 长单段会被控制器静默丢弃)。起点=当前 TCP ⇒ 起点闸天然过。
  旧的 "读 `bridge_real_path.json` 实测记录" 分支要挪走/改名, 别让它继续占着 `real` 这个键。
- **路径形状**: 先去安全点这类动作按「先抬到目标 z → 再平移 → 到位」拆(z 先走), 不要低空横移;
- **激活 ≠ 一直在画**: 把轨迹「保存成围栏点元素」是错的。`savePointsElement` 写进 `fences.json` 的
  `type="points"` 项与按钮状态无关, 每帧都绘 ⇒ 用户没点任何按钮却看见好几条轨迹。轨迹显示**只允许**
  由 `NAMED_ON` 驱动(`drawNamedVR`/`drawNamedOV` 都按它过滤); 已经落进 `fences.json` 的轨迹点要
  清掉(备份后只删 `type=="points"`, 保留 box/line 真围栏), 判据 = 围栏清单里只剩 box/line, 页面未按按钮时零轨迹。
- 🔴 **"以当前 TCP 为基准"的轨迹必须每次按 live 真值重算, 不能读历史计划**。臂走过一趟后位置变了,
  而 `planned_traj.json` 的起点还是上一趟的 ⇒ 550C 起点闸报 `起点已变 100mm`, 页面只闪一行小字,
  用户看到的就是"点了执行没反应"。判据: 这类轨迹(如臂旁那个矩形)取数时 `read_tcp()` 现算
  (抬60 → 后(x-)80 → 降60 → 前(x+)80 这种相对段), 首点恒等于当前 TCP, 点一次就能走。
  绝对位置的轨迹(小红/安全)相反: 保持严格起点闸, 不许为了"能点"而偷偷改成相对。
- 🔴 **覆盖扫描类轨迹(建图)起点必在外, 用 `--lead-in` 而不是让他先手动去起点**: 把「TCP→首点」
  也拆成轴对齐段写进同一份段表, 段表起点=当前 TCP ⇒ 起点闸过。代价是段数会变多
  (三行扫描 ≈ 12 段), 所以 `plan_exec_550c.py` 的收包上限必须从 8 提到 24, 否则发布出去被静默丢弃。
- **拒绝判据要按 `src` 判, 不能按 `k` 一刀切**。同一个键(如建图)可能有两个数据源: 老的
  "2D 栅格平移"示意坐标(该拒)与 `explore_traj_fenced.json`(真 base 坐标、逐点过围栏复核, 可执行)。
  按 k 写死会把它误杀: 页面显示 44 点、执行端却说"不可执行" —— 两处口径必须同源。
- 执行链推 550C 时, 550B 只算段表 + 发 `ss_plan`, 逐段下发与真值对账归 550C; `exec_by.json` 一行切回本机。
  🔴 **`exec_by.json` 指向执行链外的机器 = 点了执行"已下发"但谁都不动**: `{"by":"550c"}` 时 `traj_exec`
  把段表 DDS 发布出去就 `return 0`, 本机一个字都不写 FIFO, 状态还写 `phase=delegated · by=550C`(页面看着"已下发")。
  实测 550C 当时不在执行链 ⇒ 臂不动、无任何报错。判据: `/api/traj/exec/state` 里 `phase==delegated` 而不是
  `running`; 日志只有 `🕹 已把段表发布给 <机器> 执行`, 没有 `受理:` 行。修法 = 把 `zmax_data/runtime/plan/exec_by.json`
  改回 `{"by":"local"}`。**换执行者前先确认那台机器真在执行链上**, 别让"委托成功"冒充"已执行"。
- 🔴 **一票否决的闸必须在页面常驻可见, 不能只靠按钮旁一行小字。** 「点执行怎么不动」的头号原因不是链路, 而是
  授权窗过期 —— 而拒绝理由平时藏在按钮下方的小字里, 用户根本不会看。做法: 标题栏放一个状态牌, 轮询只读端点
  (`POST /api/auth` 返回 `{armed, left_s, left_min, epoch, where}`), **红 = 已失效 + 直接写明去哪授权
  (`8793 工位总览 → 授权真动`), 绿 = 剩 N 分钟**; 状态牌要在首屏, 不靠滚动。
  同一原则适用于起点闸/预检: 拒绝时把「闸名 + 实测数字 + 下一步动作」三样一起回页面, 不说"失败"。
- ⚠️ **只读端点也可能挂在 POST 分支**: 与 `/api/traj/exec` 写在同一段 `elif` 里的 `/api/auth`,
  前端 `fetch('/api/auth')`(GET) 直接 404 ⇒ 状态牌永远显示"查询失败"。新端点先用
  `curl -s -o /dev/null -w '%{http_code}'` 把 GET / POST 各试一遍再写前端。

### 🛑 「点了执行没动 / 你怎么不下降 / 为什么停住了」= 先分到三种情况再查
现场这三句话指向完全不同的故障, 一律先取三样再下结论(详细分诊表见
`references/traj-exec-blocked.md`, 含复现命令与重规划配方):
```bash
curl -s http://127.0.0.1:8797/api/traj/exec/state          # phase / blocked_by / seg_i
python3 -c "import json,time;d=json.load(open('zmax_data/rokae_sdk/tcp_out/latest.json'));print(time.time()-d['ts'],d['x'],d['y'],d['z'])"  # 米
ssh orin 'curl -s http://127.0.0.1:39061/status'          # endInRef/jointVel = 控制器真值
```
- 🔴 **`phase=blocked` + `blocked_by="起点已变 N mm"` 是走完一段之后的误判, 不是碰撞/超时**：段表是一次性预发的,
  臂被段表正常带到目标上方后, 执行器拿「规划起点 vs 当前位姿」复核 ⇒ 差值正好等于它自己走过的距离(实测 336.4mm
  = 起点到当前的三维距离), 于是把这次正常移动当成"有人搬了机器人", **剩余段不再下发** ⇒ 停在目标正上方下不来
  (实测停在 (647,206,300), 还差最后两段下降)。核对: 用 `planned_traj.json` 的起点与当前真值算三维距离,
  **必须等于 `blocked_by` 里的那个数**——对上就是复核口径, 不必去查控制器/网络。
- 止血(不改代码): 按剩余位移**重新规划一条短轨迹, 起点 = 当前真值**(只保留下降/后半段), 起点闸天然过, 再让他点执行。
  `T.LIMIT` 要小于剩余距离, 纯 Z 下降别留 >90mm 单段。治本: 起点复核按**当前段自己的起点**比, 改完回归
  "多段轨迹走到最后一段仍下发"。
- ⚠️ **三维里那条 `type=points` 的轨迹不可执行**: `▶ 执行轨迹` 只读 `zmax_data/runtime/traj/planned_traj.json`
  (有效期 30 分钟, 过期回 "规划已 N 分钟, 位姿早变了 ⇒ 请重新规划")。「我在三维里看着有红线, 点了不动」九成是这条。
- 🔴 **执行前先证位姿链活着**, 否则轨迹/授权/围栏全对也不会动: `l2_daemon` 的新鲜门槛是 `latest.json` 龄 <10s,
  超了就走直读 ROS, 失败即 `拒绝: 位姿读不到(直读失败且常驻缓存过期)`。三级取证 = `latest.json` 龄 ·
  `curl 127.0.0.1:39071/status`(**空响应 = 隧道僵尸**) · `ssh orin 'curl 127.0.0.1:39061/status'`(真源);
  修 = `sudo systemctl restart zmax-pose-relay`, 再看执行器自己打出的龄是否 0.0s。
- 🔴 **端口在听不等于隧道活着**: `ss -ltnp | grep 39071` 有监听而 curl 回空 = 僵尸转发(SSH 通道断了、本地 socket 还在)。
  判活一律用 curl 的**响应体**(`ok:true`), 不要用 `ss`。
- 🔴 `zmax-orin-legs` 的 `ExecStart` 还写着老跳板 `orin-ecs`: 主进程 exit 255、卡在 `start-pre` 等端口,
  重启它会把 39071 和 18792(手臂相机)一起弄掉。换成 WiFi 直连后这条 unit 必须改成可用别名, 否则每次重启都要手工兜底。
- 汇报口径: 先给"走到哪 + 停在哪 + 谁拦的 + 数字自洽校验", 再讲原因和下一步; 别从"我查了什么"讲起。

## 围栏避让规划 (tools/explore_traj_fenced.py)
- 覆盖路径必须按 `fence_store` 真源避让: 逐行扫描, 每行先算该 y/z 上被哪些围栏占掉再减掉(留 30mm 净距)。
- 盒子按三轴重叠判; **直线元素(小兰/小青)也是围栏**, 按线段采样点避——只避盒子会被自己的复核抓住。
- 规划完逐点 `check_point` 复核, 命中就报错不写文件; 汇报每条围栏的最小净距。

### 配置里没有的障碍: 用臂相机深度图现场量成 AABB 再注入围栏
用户问「你看到你面前那个相机了么」时, 光读 `fences.json` 不够 —— 配置里往往只有 侧面检测相机/检测设备/上横梁 三四个盒子,
台面上临时立的相机、支架、料盘都不在里面, 于是轨迹被算成「净距 455mm 很安全」。定式 (`tools/scan_obstacles.py`):

1. 取一帧彩色 + 深度: `http://<orin>:8792/frame.jpg` + `/depth.png`(D405 · uint16 · unit 0.1mm · 65535/0 = 无效)。
2. 位姿用**桥 `/status` 的 `endInRef`(米/弧度)**算 `T_base2cam = T_base2tcp @ T_cam2tool`; 别用 `tcp_out/latest.json`
   兜底时不核对它的 `rx/ry/rz` 是否真值(全 0 = 陈旧), 更别默认 rpy=0 —— 位姿错会把台面推到 700mm 上去,
   整份障碍清单看起来"有 8 个物体"其实全是假的。**先看 z 直方图的峰是否落在台面高度(几十 mm)再采信结果**。
3. 台面高度 = 点云 z 直方图首峰; 台面以上 `>25mm` 的点按 **15mm 体素 8/26 邻域 BFS 聚类**, 保留 ≥800 点的簇,
   每簇出 `p1/p2/size/center/距离当前TCP`, 外扩 20mm 写进 `fences.json`(`type="box"`, note 写实测尺寸与点数)。
4. 加完**必须重跑覆盖规划**并报每条围栏的最小净距 —— 判据是「新盒子出现在净距清单里」而不是脚本没报错。
5. 与既有盒子对账: 实测常在 `上横梁` 范围内(同一条导轨上的顶摄), 先比中心/尺寸再决定是新增还是把旧盒子改紧,
   免得同一物体两个盒子把可通行区扣没了。
- 汇报口径: 「量到的盒 x/y/z 范围 + 尺寸 + 点数 + 距 TCP 多远 + 已注入围栏」, 用户才认这是看过而不是猜的。

### 🧰 「把画面里那块料盘画到三维视图」= 掩膜反投影, 不是拿 AABB 硬凑 (2026-10-26)

用户指着相机画面说「这块料盘画到 AR 三维视图上」时, 两步都要做, 少一步就会画错:

1. **计量: 画面暗块掩膜 → 深度反投影 → base 系 AABB**, 不要用 `scan_obstacles.py` 的「台面以上 >25mm」聚类。
   实测料盘是**扁的**(z 100~140mm, 台面 127mm) ⇒ 整块被当成台面过滤掉, 脚本只报出旁边立着的两个小物体,
   照它画就是画错东西。正确做法: 取暗块最大连通域作掩膜(`g<60` + `connectedComponentsWithStats`),
   掩膜内像素的 `depth.png`×0.0001 + K + `T_base2cam` 反投到 base, 取 **2~98% 分位**做稳健 AABB
   (min/max 会被噪点/边缘拉大)。实测 266×393×40mm · 中心 (519,348,120) · 37078 点。
2. **自检必须先过一条**: 把 AABB 8 角投回原图, 与暗块 bbox 比。判据是**覆盖率**(实测 100%),
   不是 IoU —— 轴对齐盒投出来是矩形, 形状不规则的暗块 IoU 天然只有 0.2~0.3。
   ⚠ 反过来, 覆盖率低(实测一次只有 5%)说明位姿/外参链错了, **此时严禁写进 fences**: 我先按旧位姿画,
   IoU 0.03、框落在画面下部, 与暗块(画面上部)完全对不上 —— 这种盒子进围栏会把可通行区扣错。

🔴 **`scan_obstacles.py` 的位姿优先走 `192.168.23.66:39061`; 本机没产线网卡时它回落 `latest.json`,
而这份 `latest.json` 在采样容器 crash-loop 时会停更十几分钟** ⇒ 投影全错。判定位姿链是否活着, 按这三级看:

🔴 **Orin SDK 桥 `zmax_arm_sdk_bridge.py` 的经典坑: 默认 SDK 路径写死旧构建号**
(`.../tashan_robot_so_20260807_174920_...`) 而盘上只有新构建 ⇒ `import xcoresdk_python` 失败,

  这样以后换构建不用再改; ② unit 里再显式给一次 `Environment=ZMAX_SDK_PATH=<在役构建>`(drop-in)作双保险。

🔴 Orin 上 `tashan` 默认 **sudo 需要密码**(不是免密); 没密码时先用 `setsid nohup` 用户态起桥止血,
但要说明「机器重启后 unit 还会犯」—— 拿到密码后务必写进 drop-in 并让桥回 systemd 托管
(复核 `cat /proc/<pid>/cgroup` = `system.slice/zmax-arm-sdk-bridge.service`)。
桥一通, 本机 `zmax-pose-relay`(读 `ZMAX_BRIDGE_URL=http://127.0.0.1:39071`)会立刻把真值搬进 `latest.json`,
实测从停更 1062s 变成 age 5s —— **先修桥, 不要另写采样器**。

写进三维: `POST /api/fence/add {type:"box", p1:[m], p2:[m], name, color, note}`, note 里必须带
「实测点数/尺寸/中心/台面 z/相机在 base 的位置/时刻」, 用户才会认这是量出来的。
`enabled=true` 会同时进轨迹避让扣减 —— 要区分「只画」和「要避」就明说这一点。
页面验收(不靠肉眼): 左栏「围栏盒」出现该项 + `#vr` 画布统计该盒颜色的像素,

### 🧰🧰 并排第二个料盘: 复用实测 AABB 平移, 别重新量

要在已有料盘旁"再放一个"时 **不要重跑深度反投影** —— 拿实测盘的 AABB 平移即可, 尺寸/高度天然一致:
- 平移量 = 该轴长度 + 间隙(实测取 30mm); 另外两轴**逐位相同**(同高、同进深), 否则看着就是"斜着摆"。
  例: 料盘 x .386~.652 / y .151~.545 / z .100~.140, 沿 **Y+** 并排(间隙 30mm) ⇒
  `p1=[.386,.574,.100]` `p2=[.652,.968,.140]`; 槽位盒跟着同一条 dy 平移(实测 dy=+0.4234m), x/z 一律不动。
- 落库优先用 `fence_store.add(kind, p1, p2, name, color, note)`(`fences.json` 顶层是 `{items, margin_mm, at}`),
  比走 HTTP 稳; note 里必须写清"哪个是实测、这个是从它平移来的、依据哪份实测" —— 推算件要留痕。
- 🔴 **颜色必须与参照盘不同**(实测参照青 `#22d3ee`, 新增用橙 `#f59e0b`), 否则像素判据分不出"多了一个"还是"原来那个"。
- 🔴 **"左/右"的口径 = 顶视相机画面的左侧/右侧, 不是 base 系 y 的正负** —— 现场按顶视画面说方位,
  base 系里 y 的正负与他的"左"经常正相反(实测先按 y 负侧画, 他看到位置才发现反了, 当场纠正:
  「顶视相机的视角的左侧; 世界坐标应该是 Y+, 刚才我搞错了」)。
  ⇒ clarify 的选项必须**方位与坐标同时给**(「顶视画面左侧 = y .574~.967」/「右侧 = y -.272~.121」/
  「靠基座一侧 = x .090~.356」), 光给 `+y/-y` 他答不上; 落库后**回读坐标 + 两色像素 bbox** 复述一遍
  "哪个盘在画面哪一侧", 让他一眼确认而不是等他自己发现反了。
- 验收(两个盘都要数): 分别数两色 px + bbox, 并报各自**最密集的行/列**(确认是框而不是散落的 UI 同色像素)。
  实测 橙 2574px(y 282~286 / x 914~982) · 青 351px(y 464~492 / x 832~886), 两色 y 区间相邻 = 画面上确实并排。
- 两个盘都是 `type=box` ⇒ 都进避让判定; 只想显示就用 `type=points`(但那样左栏没 box 行、也无法单独开关)。
- 🔴 **加盘前先算桌面边界, 汇报必须给「距桌沿余量」**(老倪: 「注意不要超出桌子边缘」): 桌常量在页面里
  `TAB={x0:.35,x1:.95,cy:.25,w:1.6}` ⇒ 桌 x .35~.95 / y **−.55~1.05**; 新件四边都落进这个范围才算过。
  实测: 第三盘(下料盘) y −.2723~+.1211(与左右两盘各留 30mm), 其右侧再放 200×200 废料盘 y −.5023~−.3023
  ⇒ 距桌右沿还剩 **47.7mm**。这类数字必须报, 光说「放得下」不算验收。
- 同一侧连续加物件时**间隙保持一致**(实测每处 30mm), 否则摆出来像随手放的; 「小一点/大一点」用**面积比**说
  (实测 200×200 比 265.8×393.4 小 62%), 不要只说「比它小」。
- 废料盘(不良品)按需求**不给槽位**: 只加一个 `type=box`(仍进避让判定), 颜色独立(实测红 `#ef4444`, 与青/橙/粉三盘都不同)。

### ↩ 用户会用鼠标在三维里拖动物体 ⇒ 围栏编辑必须自带「回退一步」

老倪拖偏一个料盘后, 要的不是"你帮我改回原值", 而是**能力**: 「增加一个回退功能; 回到上一步」。
凡是用户能直接编辑的共享状态(围栏/料盘/槽位/点位), 都要有快照 + undo, 否则一次误拖就得人工算坐标还原。
- 后端 `tools/fence_store.py`: 每个写口(`add`/`update`/`delete`/`clear`/`set_margin`)在 `with _LOCK:` 之后、
  `_load()` 之前调 `_snapshot("<动作>")` —— 把 `fences.json` **原样**存到
  `zmax_data/ar_rs/fences_history/fences_<时间戳>.json`(+ `.meta` 记动作与时刻), 只留最近 60 份。
  `undo(steps)` 用第 N 份覆盖回去, **回退前也存一份** ⇒ 可连续退, 退多了还能撤回(不是单向)。
  快照失败一律 `except: pass` —— 历史写不进去绝不能挡住正常编辑。
- 接口 `POST /api/fence/undo {steps:1}` 回 `{ok, restored_from, n_items, undo_n}`;
  `GET /api/fence` 顺带带回 `undo_n` + 最近一步动作, 页面据此在按钮旁显示「可回退 N 步 / 无历史」。
- 前端: 「↩ 回退」按钮放『👻 预览动作』**同一排右侧**(编辑类操作挨着看), 点完 `await loadFences()` 重画;
  按钮禁用-恢复要包 `finally`, 否则接口一慢按钮就永远"回退中…"。
- 🔴 判据必须**真拖一次再退**: 读坐标 → `POST /api/fence/update` 故意偏 25mm → 点 undo → 读回**逐位相等**。
  实测 `[.3859,.5745]-[.6517,.9679]` → 拖成 `[.4109,.5995]-[.6767,.9929]` → undo → 回原位且 38 个对象一个不少。
  只断言"接口回 ok"不算 —— 覆盖错文件时它照样回 ok。
- ⚠ 只覆盖**经服务端/页面**的写。纯前端拖拽若落手时没发一次 `update`, 就没有快照可退;
  报"退不回去"先查那次拖动到底有没有写进 `fences.json`。
- 删掉「没用了」的围栏/轨迹同样走服务端 `POST /api/fence/delete {id}`(删除前自动快照 ⇒ 后悔了能「↩ 回退」)。
  按名字定位, 不要按颜色/序号猜(实测要删的是备注写着"9段615mm 视觉引导"的 `type=points` 那条)。
  判据用**精确色差 ±10**: 宽容差(±30/40)会把同色系 UI 与别的红色元素一起数进来 —— 实测该轨迹精确像素
  114 → 删后 **0**, 而 tol=18 还剩 379(抗锯齿 + 撞色元素), 会看着像没删干净。

## 自验方法 (不靠肉眼)
浏览器 console 直接量:
- 🔴 **用户只给视觉描述(「上边那行粉色背景的字」「挡住左栏那个窗口」)时, 不要按文字 grep 猜**: 遍历元素读 `getComputedStyle(el).backgroundColor`, 按色相筛(`r>120 && r>g+30 && b>g+10` 抓紫/粉), 打印 `{tag,id,cls,bg,txt,top}` 一眼锁定 id, 再拿 id 回源码 grep。文案 grep 只会命中文案/注释/构建戳, 命不中真正那个浮层 —— 它的文字往往是 JS 拼出来的。
- 🔴 **浮层/布局改动按多个视口宽度量矩形相交, 不是只看自己那个窗口**: 用**离屏 iframe** 复用同一页面(不改窗口大小): `iframe{position:fixed;left:-99999px;width:W;height:H}` → `onload` 后延时约 900ms 等数据到 → 在 `contentWindow` 里调页面自己的定位函数 → `getBoundingClientRect` 两两判交(`a.left<b.right-1 && a.right>b.left+1 && a.top<b.bottom-1 && a.bottom>b.top+1`)。一次 console 求值返回不了异步结果(拿到的是 `'started'`) ⇒ 结果先写 `window.__geo`, 下一次调用再读。⚠ 窄屏下两条栏会叠成一列(左栏跑到底部矩形), 单看 x 区间会误判「挡住左栏」, 必须用**二维相交**判。
- 🔴 **验「播放/动画真的画出来了」用 canvas 取像素, 不用截图**: `document.getElementById('vr').getContext('2d').getImageData(0,0,w,h)`
  在真浏览器里拿到的是**当前帧真实渲染**, 逐帧可读、可数色块。截图那条路有两个坑:
  ① 页面有 4 个 canvas(`vid` 640×480 相机底图 · `ov` 叠加 · `loupe` 176 · `vr` 980×577 三维),
  `document.querySelector('canvas')` 拿到的是 `vid`, 数出来全是相机图像的颜色 —— **一律 `getElementById('vr')`**
  (实测 `#vid`/`#ov` 是 640×480 的相机/叠加画布, 在那儿算 hash 会恒得 0, 会误判“画面没动”);
  ② offscreen QWebEngine 的 rAF 不触发、CDP `Page.captureScreenshot` 对 canvas 也可能拿到旧帧 ⇒
  截图说「没变化」而 getImageData 说「变了」时, **信 getImageData**。
  判据写法: 同一流程取两个时刻(`picked=2` 与 `picked=14`)的蓝/绿/红计数做**差**, 差值 ≈ 个数×每件像素
  (实测蓝 10556→9281, 差 1275px = 12 个模块线框), 比单点绝对值可靠。
  需要真浏览器自动化时用 `<skill>/scripts/cdp_page_probe.py`(headless Chromium + CDP: navigate / eval / captureScreenshot)。
- 🔴 **console 里长表达式会被截断报 `SyntaxError: Unexpected end of input`** —— 几百字的 Promise/闭包一次性贴进 `evaluate` 经常这样失败, 而不是代码错。定式: 先 `window.__t=function(){...}` 存成一个短名字, 再单独调 `window.__t()`; 采样结果写到 `window.__seq` 后用下一次调用读, 不要靠长表达式一次性 return。
- 🔴 **鼠标手势(中键平移/拖拽/旋转)用合成 PointerEvent 验, 不用真鼠标**: `new PointerEvent('pointerdown',{clientX,clientY,button:1,buttons:4,bubbles:true,pointerId:N})` 依次 down → move → up dispatch 到 `#vr`, 就能驱动真实的 handler 链。验平移量时把「手势后 target → 再调一次取景函数 → 再读 target」三步比漂移, 漂移必须 = 0。
- ⚠️ 出现 `getElementById('vr')` 返回 null 时**先读 `location.href`**: 浏览器会话可能已掉到 `about:blank`, 不是页面缺元素。先 navigate 回去再下结论, 否则会去改根本没坏的代码。
- 画点数: `window.__NAMED_DOTS__` 归零后 `drawVR()` 读回, 应等于各亮着轨迹点数之和(如 41+54=95)。
- 高亮是否生效: 点完读 `className` + `NAMED_ON` 的 key 集合, **两套 id 一起读**(见坑 4);
  并且必须读**计算样式** `getComputedStyle(b).backgroundColor` —— className 对但 CSS 被后面的同级规则
  覆盖时, 用户看到的仍然是黑按钮; 只比 className 等于没验。同时确认 `NAMED` 里点数与服务端一致。
- 相机是否被挪: 点按钮前后比对 `{yaw,pitch,dist,tgt}` 四元组, 必须完全一致。
- 是否碰设备: 用 `FENCES` 里的盒子算点到 AABB 距离, 报最小距离 + 落进盒内的点数;
  别只信服务端返回值, 页面侧独立算一遍才算取证。
- 🔴 **本会话看不到图像像素时, 绝不说「我看到了」**。老倪会问「你能看到么」—— 没有视觉输入就直说
  「我看不到像素」, 再给等价证据, 不许拿推测冒充目检。两条证据交叉一致才回话:
  ① **标定反算**(最硬): 拿 `module_calib_ref.json` 的抓取 `quat` 换旋转矩阵, 看第三列(tool1 Z=长度方向)
     落在哪个世界轴上 —— 实测 `[0.998,-0.018,0.061]` ≈ +X, 与「长度平行 x 轴」一致。
  ② **历史帧像素统计**: `zmax_data/vl_safety/<yyyymmdd_hhmmss>.jpg` 是 `vl_safety_monitor` 每隔一两分钟存的
     画面, 取离他说的时间最近那张; Otsu 分割 → 连通域 → 对细长块(宽高比>2.5)做 PCA, 报主方向中位数
     (实测 3.1° = 横着/向前)。够判「长条是横的还是竖的」, 但**分不出模块与亮线**, 只能作旁证。
- 🔴 **`patch` 落盘必须回读**: 在 `execute_code` 里调 `patch()` 曾返回 ok 而文件一个字节没变(grep 才发现),
  于是紧接着那轮截图/判据验的全是旧代码, 结论作废。改 HTML 走带 diff 的顶层 `patch` 工具, 或改完立刻
  `grep -n "<新加的注释原文>"` 确认, 截图前再核一次版本戳 —— 三者缺一就可能拿旧版页面骗自己。

## 让用户一眼确认"你这版到底有没有生效"
- 页面标题旁放**版本戳**（如 `构建 2026-10-26 r8 · 五条按钮都能点亮`），改一次页面就递一次号。
  用户再说"还是没变"时, 让他看这行号——比反复解释省事, 也避免把"他缓存了旧页"当成代码 bug 重查。
- 页面响应带 `Cache-Control: no-store` 也不保证他拿到新版(浏览器后退/标签页复用); 版本戳是唯一可靠判据。
  ⇒ **改 HTML 必须与递号同一个 patch 批**: 本轮改了「轨迹点」行、points 线宽、预览动作三处却没动 `r29`,
  用户看到的还是旧号, 结果还得再花一轮确认"到底改了没" —— 一次改页面 = 一次递号 + 一行"本次变了什么"。
- 重启主服务用 `systemctl restart zmax-traj-ar`; `restart` 可能报 `Connection timed out` 而旧进程仍在服务,
  此后**子进程会继续用旧构建**: 查 `pgrep -af tools/tcp_ar_server.py` 的 master 启动时间是否晚于改动, 不对就
  `systemctl stop` → `start`。同一端口挂十几个 fork 子进程 = 有的连接拿到旧页, 症状就是"时好时坏"。
- 清进程一律走 systemd 或写成脚本再执行; 内联 `pkill -f '<脚本名>'` 会匹配到执行它的那条 shell 自己,
  把自己 SIGKILL 掉(实测两次)。

## 🏭 场景段表 → 550C plan 序列化 (空走补齐 + UPH 口径)

ar3d 里搭好的场景(段表 JSON)要真跑在 550C 上时, 不是把段表原样发过去 —— 中间差两件事: **空走补齐** 和 **按 1~8 段切片**。
工具: `tools/scene_550_planify.py`(场景段表 → plan 序列, 离线跑, 与 `plan_exec_550c.py` 同一套闸门口径)。

- 🔴 **段表的 `a` 不保证等于上一段的 `b`**: 换槽/换盘的 `a` 写的是**中转位**(实测 `[490,499,240]`), 不是上段末端 ⇒
  原样下发就是一条跨 400~570mm 的直线, 从工装/料盘中间穿过去。判据: 逐段比 `a` 与上一段 `b`, 差 >5mm 记一处断点;
  每处断点补一条 `bridge=True` 的空走段(速度单独给 `--bridge-speed`), 并在 index 里记 `n_segs_raw / n_bridge / bridge_mm` 便于审计。
  实测 392 段里 27 处断点(434~564mm) → 补 14,887mm 空走 → 419 段。
- 🔴 **UPH 必须报四组, 不能只报场景自报那一个**: 场景自报 159.43s(316)是**不含空走**的理想值;
  含空走按 100mm/s = 308.31s(163) · 300mm/s = 209.06s(241) · 1000mm/s(运动安全上限) = 174.32s(289)。
  ⇒ 单臂串行**物理上做不到** UPH300, 要 300 只能靠双臂并行(把空走藏进另一条臂的插拔时间里);
  汇报时四组一起给并点明自报值不含空走, 别拿 316 当预期。
- 🔴 **550C 一次只收 1~8 段**(`plan_exec_550c.MAX_SEG=8`) ⇒ 419 段 = 53 个 plan, 每次 200ms ≈ **10.6s 下发开销**,
  几乎吃满 12s/件 的单件预算 ⇒ 双臂方案里**另一条臂的链段数必须压到很少**(否则光切包就超节拍),
  或者先跟老倪确认放宽 MAX_SEG(要改 550C 侧代码 + 重启)。
- 产出: `zmax_data/runtime/traj/plan_550c/index.json` + 每个 plan 一个文件; plan 里保留 `bridge` 标记, 让 550C 侧能区分
  生产动作与空走(速度/审计口径不同)。

## 8802 MuJoCo 场景「少东西/看不见」四类真因 (2026-11-09 实测)

1. **geomgroup 默认是关的**: `mujoco.MjvOption()` 默认 `geomgroup=[1,1,1,0,0,0]`, 只写 `geomgroup[3]=0` 等于永远关。要显示分组几何必须显式置 1: `op.geomgroup[3] = 0 if 顶视 else 1`。症状是“模型里有 geom、渲染里永远不出现”。
2. **两个 builder 打架**: `ar_mujoco_env.py` 里 `fence_geoms()`(画 `eq*` 实心 slab) 和 `build_mjcf()`(画 `pan_*` 薄底+槽) 会同时画料盘 —— 实心 slab z 0.10~0.14 把 z 0.105~0.109 的槽片盖死, 顶视里就是“纯平板没有槽”。料盘只在一处画。
3. **过滤条件筛选过头**: `"槽" not in name` 会把 `下料盘(第三·14槽)` / `废料盘(不良品·无槽位)` 一起筛掉, 只剩 2 个盘体。槽本体是以 `槽` 开头的条目, 只排除这种。
4. **一盏点光只照一个盘**: 被照的盘 250/255 过曝、其余 77~115, 侧盘的槽与盘面同亮度。补光要按料盘逐个放 (三盏 0.45)。

诊断手法(比目测快且不靠猜): 把待查几何的 rgba 临时改成 `1 0.1 0.1` 再渲一帧, 数红色像素及其 u 范围。修前 5335px 集中在一个盘, 修后 16371px 跨三盘, 一眼定案。同类可用 `mj_ray` 从上方打一条射线, 返回第一个命中的 geom 名 —— 直接看出是哪个盒子盖住了目标。

取景验证也要数值化: 把真源坐标(如 place_cells 的 42 个槽)按同一 az/el/dist/fov 投影到像素, 检查 in-frame 数量; 目测“看起来没有”经常只是被截在画外。

**深度手册**: `references/mujoco-8802-render-scene.md` —— geomgroup 默认关/两处 builder 互盖/染色法与射线法/
顶视取景数值化/直播页 img 换图/tool1 夹爪与光模块。改 8802 场景前先读它, 不要在 SKILL.md 里再展一份。

**夹爪位置**: `joint_tool1` 的 Z 轴与腕轴夹角 33.6° (xyz 259mm + 大角度 rpy)。夹爪/法兰盘/指头一律建在**法兰系**,
只有光模块挂在 tool1 旋转系 —— 画错坐标系的表现是“组件悬空脱在腕外, 中间一道黑缝”, 不是穿模。

**8802 机位索引**: `/video?cam=ar3d`(跟随 AR 页相机, 默认) · `top`(正俯视 1.55m/50°, lookat z 0.11) · `topmid`(顶视相机/D435 视角) · `close`(料盘特写)。顶视相机实体与 AR 页 `TCAM` 同源: 两臂中线 x=0,y=0.25 的立柱 r=70mm、高 0.328m(=joint_1), 顶上一台 D435(90×25×25mm, 俯 35° 朝 +X, fov 58)。改场景几何后**必须同时改 `VIEWS` 预设**, 否则按钮/URL 出的还是旧机位。
