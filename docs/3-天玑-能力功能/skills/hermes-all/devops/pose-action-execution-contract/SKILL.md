# 位姿 → action → 真机执行：三层契约与执行红线

## When to Use
- 「引导/检测给了目标位姿，动作规划要出 action」「让规划自己走过去」这类需求。
- 执行阶段出现：手臂乱走/腕部被拧歪、到位判据说到了其实没动、走了半截停住、「全段通过判据」与实际不符。

## 三层契约（先把边界写死，再写代码）

| 层 | 回答的问题 | 产出 | 不许做 |
|---|---|---|---|
| 引导（规划引导/检测） | 抓哪一个、工具该是什么姿态 | **唯一** 6D 目标位姿（一个周期只有一个） | 输出「每周期一个下一步」、自己拆段 |
| 规划（动作规划节点） | 这一拍走到哪、夹爪怎么动 | **逐拍 action**（位姿口径 + 夹爪 + 证据块） | 下发、解 IK、重算别人的轨迹 |
| 执行（机器人节点/执行器） | 照做并回报 | 运动 + 到位偏差 + 夹爪真值 | 重算位姿、改目标、自己发明动作 |

判据：action 必须带 `seg_i/n_seg/u`、`delta_mm`（相对真值）、`truth_fresh`；没有这些，事后分不清「规划给错」还是「执行走歪」。
状态向量与应用层单位不混用（如 `peg_xyz[4:7]` 是米、action 是毫米），坐标原点定义写死一次。

**引导位姿的"原点"口径写死为模块体中心**（也就是 TCP 该去的那个点）；金手指端只作视觉备查字段（`head_mm`）。
换口径就把机器人已走到的老位置一起评：位姿原点从端部改到中心，画面框会自己"向后/向下"到位，不需要调 z、也不要拿端部值去下发。

## 双臂：一个周期 = 一个目标**组**（L,R），不是一个节点再发一个位姿

双臂协同属于引导层，**别为它新建仲裁节点**：目标位姿只允许有一个出处，多一个出处就多一次「半路掉头」。

- 引导层一次算出一对：左臂一块盘、右臂一块盘，带 `pair_id` + 同一 `ts` + 两侧 `valid`。
- **原子性**：一侧取不到几何就整对失效（`atomic=true`），不许一侧单飞——单飞就是一臂按新目标、一臂按旧目标。
- 协调分两层，别混：引导层判「静态可判的」（配对、正/反向相位、节拍错开）；执行侧只留**一道兜底闸**
  （实测间距 < `d_min` 或占位冲突 ⇒ 后到者 hold 一拍），不做全套每拍仲裁。
- 工作区是否重叠决定要不要占用裁决：分区作业（左右半盘互不进入）引导层出双位姿就够；
  交叉共享区才需每拍 owner/hold，且裁决要显式成子步骤并出证据（谁 hold、等几拍、占位率）。
- **硬前提**：同一节点要叫「实时配合」，就必须每拍同时拿到两条臂的真值；状态向量里只有一条臂位姿时，
  只能声称「成对出目标」，不能声称实时协同。
- 两盘的「成对」不等于两份目标文件：一对=一份 `pair` 产物 + 两侧各自的 `pose`，发布器一次写完（同一次调用）。

### 落地的端口形状（引导层一次出四口，下游零改动）

| 端口 | 内容 |
|---|---|
| `out1` | **右臂**目标位姿（下游 `sslimit→n_moveit` 照旧吃它），附带 `pair_id / arm="R" / pair_valid / hold / dual_truth / peer_grasp_mm` |
| `out3` | 左臂目标位姿（同 `pair_id`、同 `ts`、`arm="L"`）—— 没有左臂控制器时只进观测/画面 |
| `out4` | 协同证据：`dual_truth{R,L,r_mm,l_mm,l_src}` · `zone{split,owner,cross_zone}` · `min_gap_mm/gap_warn` · `hold` · `why` |

- 左臂真值来源：`ZMAX_LARM_POSE_JSON` 或 `ss_live/left_arm_pose.json`（旁路）；取不到就 `dual_truth.L=false`，
  `hold=true` 且 `why` 明写「左臂无真值 ⇒ 只做几何引导，不做双臂时序协同」—— 不许拿右臂真值兼左臂。
- 分区 owner：左/右盘按 `ZMAX_ZONE_SPLIT_MM`（默认 600mm）分 y 区；目标落到对面区 ⇒ `cross_zone=true` + `hold=true`。
- 两抓取点间距 < `ZMAX_DUAL_MIN_GAP_MM`（默认 120）⇒ `gap_warn`（只预警，不改几何）。
- 槽号用 `ZMAX_DUAL_LSLOT/RSLOT` 覆盖，两侧同一拍同一对。
- **验收三闸**（逐个真跑，缺一条就是没协同）：① 无左臂真值 ⇒ hold=true；② 补一份左臂位姿 ⇒ hold=false 且
  `why` 变成「两侧分区、目标组原子、各守本区」；③ 把分区边界故意改到离谱值 ⇒ `cross_zone=true` 且 hold 重新变真。
- 端口加进契约 `PORTS_OUT` 不等于上线：画布没连线的口不会发总线（`step()` 返回的 `sent` 里没它），
  左臂没控制器时**宁可不连**也不接假边，并明写「只进观测」。



## 🔴 红线 0：引导位姿的几何必须先对齐「画面上那个件」

同一个物理槽位往往有**两套以上编号/几何源**（配置 JSON、AR 围栏、place_cells 派生库）。它们不是同一套：
实测两套编号**错 7 个槽**（配置的 `槽1..7` 对应围栏的 `槽8..14`），同一位置的 x 差 ~158mm、y 只差 1~4mm。
后果：目标位姿框与画出来的模块整体错开一排，操作者只会说「位置偏上 / 跟件不重合」，而 mm 数值本身是对的。

- **取值顺序**：引导几何先用「画面/真值那一套」（围栏或 place_cells，实测来源），配置 JSON 只作兜底；
  两侧（左盘/右盘）必须同一套源，一边一个源就会一边错一排。
- **判断顺序**：听到「偏上/偏下/不重合/应该移过去」，第 0 步是查**编号映射与几何源**，不是调 z、不是调精度、不是重标定。
  做法：把目标框中心和该编号的件中心各自算出来对齐，看 y 差多少、x 差多少；x 差 ~一个槽距就是编号错位而非标定错。
- **验收**：发布后把框与件投影到同一画面核重合（角点/屏幕坐标），不要只看 mm 数值「对得上」。
- **换源要一次到底**：几何源换了，机器人已走到的老位置要跟着挪；中途两个源并存时，先说清哪个是准的，再动人。

## 🔴 红线 1：下发的姿态不许自己从四元数换算

驱动吃的是它自己那套 `rpy(rad)`，**不是 ZYX 欧拉**。把目标四元数按 ZYX 反解成 rpy 再下发，姿态会与位置在第一拍同时变化，
关节空间插值把臂甩出去（实测：命令只抬 18mm，落点偏 **69mm**，腕部被拧进另一组欧拉分支；现场只会说「乱走」）。

- 首选：**每拍只改位置，姿态保持实测**（把当前 `cartPosture().rpy` 原样带回）。要转向就「先在安全高度用一个**已验证过**的 rpy 一次性摆正」，再走位置。
- action 里的 `a/b/c` 常是**度**，驱动要**弧度**：这类量只能当可读值，喂驱动前确认单位与约定（错一层就够事故）。
- 执行器逐拍记「命令 rpy → 实测 rpy + Δp/Δr」，超差立即停并留证。

## 🔴 红线 2：到位判据必须含姿态

只判 `|Δp|` 的脚本，在「同位置改姿态」时会当场报「到位 Δ=0.0mm」而姿态一度都没转（实测）。
判据固定双门：**Δp ≤ 0.6mm 且 Δr ≤ 0.02rad**，日志把「姿态实际变化」单独打一行。

## 🔴 红线 3：拼接出来的段守同一套单步上限

**同盘换槽也是转移，必须抬过槽盒上沿再横移**：槽面作业高度 ~114mm 落在槽盒(110~125mm)与相邻件的高度带里，
在这个高度上横移 = 从件与侧壁之间穿过去。固定四段：抬到 >160mm（实测用 200）→ 横移 → 到目标 XY 上方 → 分段落。

规划段之外由调用方追加的段（抓后抬升、退让、回位）同样按单段上限切（如 ≤25mm、向下 ≤20mm）。
反例：一条 22 拍轨迹里混进一拍 50mm 抬升，交付件却写「22/22 通过单步判据」；换成 23 拍（25+25）才是真的。
**交付/汇报里的「通过数」必须由脚本从轨迹真源现算**（每步位移、累计角度、段数），再断言文档里写的值等于它，不许手写。

## 执行器设计（照这个搭，别人接手也能验）

1. **默认 dry-run**：`EXEC=0` 只读轨迹并逐拍校验，`EXEC=1` 才动；轨迹文件带 `slot/speed/steps/guard_ok`。
2. **分段开关**：`MINI/MAXI`（走到第几拍为止/从第几拍起）用于「先到抓取点 → 合爪 → 再抬升」这类中间要插动作的场合；
   开关必须走**环境变量白名单**（容器入口脚本通常只透传白名单变量，漏加=静默不生效）。
3. **每拍一步、超差即停**：单拍 MoveJ + 等到位（含姿态）+ 记证据；任一拍超差立即停，不重发不补偿。
4. **只执行不重算**：执行器读的是规划产出的轨迹文件，脚本里不得再出现目标推导逻辑。
5. **规划与执行分离的原因要写清**：宿主 venv 有规划依赖、容器有厂商 SDK，两者互缺 ⇒ 宿主算轨迹、容器逐字执行，中间用 JSON 传递。

## 链路排障顺序（现象都叫「没动」）

1. 这一拍有没有 action？没有 ⇒ 上游目标位姿没下来（看引导输出与字段是否齐）。
2. 守护/限幅节点是否把字段吃掉：**只重建 `{tcp: …}` 的守卫会静默丢弃姿态与预抓点**，下游只能拿「下一小步」当目标。
   守卫必须**原样透传**目标位姿并对它单独再守一次。
3. 执行器闸门：前置三查（power/mode/idle）→ 授权（运动授权只以授权真源为准，`until=0 && mode=debug` 也算已授权，
   别用 `until > now` 自己判）→ 单拍上限 → 台面/工作空间。
4. 只有以上都过，才去怀疑服务/通道。

## 停机与善后纪律

- 听到「乱走/别动」：立刻停（moveReset/停），**再**读 state 确认停在哪，别一边停一边查日志。
- 杀进程按 `/proc/<pid>/cmdline` 精确匹配；`pkill -f <脚本名>` 会匹配到执行该命令的 shell 自己（实测把整条命令 SIGTERM 掉）。
- 事故要如实归类：命令位姿 vs 实测落点、Δ 是多少、有没有报警 —— 「无报警无碰撞」和「撞了」不能混写。

## 常见事故模式速查

细节参考：`references/skill-vs-guide-boundary.md` —— 技能（包络/能力）与引导（目标位姿）的分界，以及「按需技能」新增四处落地（不进主链的原因）。

| 现象 | 根因 | 处理 |
|---|---|---|
| 第一拍就甩/腕部乱转 | 自算 quat→rpy | 姿态保持实测，转向单独在安全高度做 |
| 「到位」但姿态没转 | 只判位置 | 加 Δr 判据 |
| 目标明明给了，规划用不上 | 守卫重建 payload 丢字段 | 透传 + 单独守 |
| 走半截停住 | 某拍超差即停（设计如此）| 看证据里哪拍、Δ 多少，别整条重发 |
| 文档说全通过、实际有一拍超限 | 拼接段没守单步上限 | 从轨迹现算再断言 |
| 框和件错开一排（「偏上/不重合」）| 两套槽位编号混用（差 7 个槽 ~158mm）| 统一到画面/实测那套源，别调 z |
| 下探中途停住、姿态被带歪 | 触到工件/阻挡 | 按接触处理：先抬再探，别加时加压硬压 |
