# 按工程真源渲染设备图并出交付件

## When to Use

- 用户要「渲染后的机器人工作姿态」「来一页 PPT」这类**静态图交付**, 而不是在线交互三维页。
- 用户说「按 AR 场景里画好的尺寸和外形渲染成一模一样」「你看看 web 里的实际数据」——他手里已经有一份画对了的场景, 要你复刻, 不许自己设计。

不适用: 挂在服务上的交互三维页 (`canvas-3d-scene-page`) · 把仿真物体叠加到真机视频 (`sim-real-scene-overlay`)。

## 1. 先找真源, 再动手 (跳过这一步必被退回)

**几何一律从工程里的常量/模型/实测台账取, 一个数都不许自己定。** 自造一套"看起来合理"的台面与基座, 用户一眼看出比例和摆放不对, 直接打回 —— 他会问「这是按什么做的」。

真源优先级:

1. 前端 3D 页源码里的**常量对象** (台面/箱体/相机/配色都在里面, 常带用户当时拍板原话的注释, 是最权威的一份);
2. URDF + 厂家 STL (外形); **STL 单位常是 mm 而 URDF origin 是 m** —— 混用会渲出 272 米高的机器。
   读网格后先打 bbox 看量级, >10 就整份乘 0.001, 再把 bbox 与尺寸表对一遍才进图/进 PPT;
3. 运行服务的只读 API (示教点位、实时位姿);
4. MuJoCo 场景 XML (料盘/槽位这类实测几何);
5. **结构参数表**(关节原点/轴向/行程/力矩/连杆质量) 只能从 URDF 解析 —— `joint/origin@xyz`、`joint/axis@xyz`、`joint/limit@lower|upper|velocity|effort`、`link/inertial/mass`; 力矩单位 N·m、限位是弧度要换算成度。**不许手填、不许抄型号手册** —— 用户会逐项核对, 手册常与真机 URDF 对不上。

🔴 **"机器人的外形"指的是工位上的整台机器, 不是一条臂。** 只画单臂会被当场退回("是有左右臂的, 有顶视相机的, 有底盘箱体的, 这些都没有")。整机几何全在 3D 页常量里, 抄过来拼:

| 部件 | 常量 | 含义 |
|---|---|---|
| 左/右臂 | `LARM.off=[0,0.5,0]` | 左臂相对右臂 y 偏移 ⇒ 双机位中心距 500 mm, 两臂同装于箱体顶板 |
| 移动底盘箱体 | `CHS{L:.6,W:.8,H:.75,HB:.68,wr:.075}` | 本体 680 + 轮 Ø150 露出 70 = 落地总高 750; 600(前后)×800(左右) |
| 顶视相机 | `TCAM{y:.25,r:.07,tilt:35}` | 立柱 Ø140 高 328 立两臂原心中线, 相机体 90×25×25 俯角 35° |
| 台面 | `TAB{x0:.35,x1:.95,cy:.25,w:1.6,t:.03,h:.75}` | 1600×600×30, 顶面 = 两臂安装面 = z 0 |

地面 z = −750; 双臂直立时整机外形 `X600 · Y833.6 · Z1981.1`。先按常量拼整机再谈姿态。

🔴 **不要靠截图取数据。** 截图里可能是空视口、折叠线以下没渲染、UI 压住、帧还没加载完; 用户会明确说「截图不准, 去看 web 文件」。读源码常量, 并顺手确认几份真源**是否同一坐标系**:

- 同一特征数在两处都出现 (如槽中心 z=0.1175) ⇒ 同一系, 可混用;
- 一处台面 z=0.012、另一处 h=0.750 ⇒ 差的是"地面在哪"的定义, 混用就会把机器人放到地板上或架到柱子上。

坐标系与常量清单落进 references (本技能已带 Z-MAX 工位那份), 别每次重新扒。

## 1b. 两套渲染器并存时: 交付前先做「来源审计」

同一份「机器人作业姿态」常有两套产出, 几何口径完全不同, **文件名里必须写清是哪个**:

- **反解版**(工程口径): 台面/基座/作业点取设计常量, 姿态由 URDF 正逆解枚举得出 ⇒ 名写 `…_工位版`;
- **场景版**(实测口径): 几何取场景 XML / 3D 页常量, 目标点取现场示教点位 ⇒ 名写 `…_场景版 / _AR版`。

两份都叫「作业姿态」交给用户, 他会当成同一份然后判「这份错了」。**现场口径: 作业姿态交付以工程反解版为准, 场景版只作对照; 场景版被判错时从交付目录下架** (下架次序见 `deliverable-doc-authoring` 的「变体下架与暂存目录清理」)。

回答「这个姿势是不是场景真实数据」必须逐项验, 不许看脚本注释:

1. `grep -nE "常量名|/tmp|api/points|urlopen" <渲染脚本>` 看目标点到底从哪来 —— 注释常写「取 /api/points 的 N 号位」, 代码实际读 `/tmp/<x>.json`, 没有就落到**硬编码常量**;
2. 把常量与现场 API 现值比一遍 —— **相等也不能证明同源, 只证明值相同**; 烧死的常量在现场改点后不会跟着变;
3. 核交付目录里有没有 `meta.json`: 没有就如实说「不可复核」, 别把注释当证据。

🔴 **每次渲染把 `target / q / tcp / camera / 真源文件路径` 写进 `<图名>.meta.json` 跟图一起归档** —— 交付件脱离参数就是一次性图片; `/tmp` 只允许做一次性覆盖输入, 不能当唯一真源。

## 1c. 拿旧 PPT 复核参数: 指不到真源字段的一律删

被要求「保证所有参数真实, 不确定的删掉」时, 输出一张三列表(真源文件+字段 / 现值 / 结论), 逐项过, 不许通读一遍凭印象点头。真源分工: 关节原点/行程/力矩/质量 ← `config/robot/zmax_robot_spec.json`(URDF 导出); 台面/箱体/相机/臂间距 ← 3D 页常量; 槽位/槽口/孔口 ← 场景 XML。

常见必错项(每条都实测过):

- **四舍五入就是错**: 表里写 `(0,0,0.3)`/`(0.1,0,0.4)` 而真值 0.328/0.05/0.136, 现场一核就对不上; 列头标 `(mm)` 而值是 m 同属错, 单位与数值一起改。
- **「×N」要数出来**: "3 组各 14 槽 + 废料盘" 在场景 XML 里是 2 个料盘 / 13 个槽位 / 无废料盘 ⇒ 整句删, 改成可数的"黑色料盘 ×2 (266×393)"。
- **包络/合计类自算一遍**: 按姿态复算 bbox 与文中数字差 500 mm 且无 meta 留档 ⇒ 删, 别保留"实测"字样。
- **对位结论必须验距**: "法兰对准 1 号槽, 误差 0.00" 用 FK 复算法兰再算到槽心距离(实测 726 mm) ⇒ 删结论, 只留可复算的 q + 法兰坐标。
- **常量 ≠ 标定**: 相机 FOV 取自 3D 页常量(按 RealSense 模板写的) 只能标"模板口径"。
- **有常量不等于有用到**: 3D 页里 `TAB.leg=0.045` 存在但代码从不引用 ⇒ "4 条 45×45 铝型材腿"这种说法无出处, 删。

改完重出 PDF 并 `pdftotext | grep` 把旧数字/旧结论的残留词归零; 原件先备份(`zmax_data/deliveries/_bak/`); 每处改了什么(改/删/留)分行报给用户, 不要只报"已核完"。

## 2. 姿态: 先验可达, 再反解

- **先算可达区间再摆工位。** 台面/作业点放太近, 工具要朝下就必然把肘翘到肩上方 —— 用户会把这种姿态读成「胳膊举高」并要求重做。先枚举「工具轴朝下」时 TCP 的可达 (x,z) 带, 再决定台面中心放哪。
- **工具朝下是解析约束**: 三个俯仰角之和固定 (本臂 q2−q3−q5=π), 代入后自由度降一维, 二维枚举秒级收敛。
- 🔴 **别用随机撒点 + Nelder-Mead 收姿态**: 实测同等目标上收敛到 349 mm 误差、工具轴还朝上; 解析枚举 + 局部精修才稳。
- **选解标准是"像人干活"**: 肘在肩下方、前臂朝下(肘高于腕)、工具轴垂直。先按这些筛, 再在满足项里取离目标最近的。
- **左右臂作业点不同就各自反解**; 照抄一侧关节角再平移, 另一侧会落在空地上(实测差 76.6 mm)。
- 报数: TCP 误差(mm) · 工具轴三元素 · 各连杆 (x,y,z)。误差到 0~1 mm 才算解对。

## 3. 静态渲染 (正交 + numpy z-buffer)

- 🔴 **深度符号与相机基必须自洽。** 缓冲区"保留更大的 camz" ⇒ 相机 z 轴要指向观察者; 且 `y = cross(x, z)`, 写成 `cross(z, x)` 整图上下颠倒(而深度看起来已经修好)。这两个符号错任何一个, 远物会盖住近物 —— 机械臂被台面整片切掉, 只剩基座。
- 🔴 **竖直轴取反同样会把整图翻过来, 而包围盒看不出来。** 相机 y 取 +Z 时箱体跑到天上、臂朝下, 尺寸与宽高比却全正常 ⇒ **尺寸对不代表朝向对**, 每张图渲完都用 §4 的缩略轮廓确认落地件在底部。
- **标注画到画布外会被整条裁掉**: 右侧纵向尺寸文字落在 `x > W` 就消失(该列墨量 0)。画标注前先把画布 pad 出右侧 ~200 px / 底部 ~110 px 白边(`np.pad`), 再用像素列/行墨量峰值确认文字真的在图上。
- **matplotlib 出中文必须显式设字体**: `rcParams['font.sans-serif']=['Noto Sans CJK SC']` + `axes.unicode_minus=False`; 缺字静默变豆腐块, 生成后 grep 日志里的 `missing from current font` 判有无缺字。
- **别把透视相机参数照搬给正交渲染器**: 方向可以照搬, 视距/焦距不行, 会把主体塞满或缩成一个点。
- 🔴 **坐标系与尺寸标注画在图像最上层, 不进深度缓冲。** 坐标系原点在机器人底座, base 轴长 160 mm 小于底座外壳半径 (≈194 mm) ⇒ 整根轴被外壳包住, 塞进 3D 网格等于没画 (实测只露 18 像素)。用 `render()` 返回的 `meta` 自己投影: `px = (v_cam[:2] - lo) * scale + off` (`v_cam = p @ R.T`), 再 PIL 画线 + 轴端方头 + 文字标签。前端 AR 页就是把它当 2D 线画在最上层的, 照这个做法才与场景显示一致。
- 🔴 **尺寸线也自己用 PIL 画, 别拿 matplotlib 版 `draw_dims` 叠坐标系。** 那类函数会把图重画一遍 (自己的坐标轴、边距、dpi), 出来后 `meta` 的投影就对不上, 轴会飘到图外。自己按 meta 画: 全部顶点投影取 min/max 得外形包络 → 顶部横向尺寸线 + 右侧纵向尺寸线 + 刻度短线 + 100 mm 比例尺 (`0.1 * scale` px), 一张图同时有外形尺寸和坐标系。
- **重复几何要显式跳过**: AR 场景 XML 常自带一块 table 灰板, 会盖住你按源码常量画的木色桌面(实测覆盖 92%, 还多伸 178 mm)。
- **悬空件要么补支撑、要么如实说明**: 料盘底 0.100 / 桌面顶 0 之间有 100 mm 空档, 插孔口在 278 mm 也没有柜体 —— 补垫块/底板可以, 但必须**在汇报里说明这是补的几何**, 不能让用户以为来自真源。
- **暗色工位必须提亮**: 源色偏黑时中位亮度可能只有 17/255, 投影一打就没了。用 gamma(≈0.72)+轻微增益, 别改材质基色(改了就不再"同源")。

## 4. 自检 (不靠肉眼也能判对错)

- **朝向**: 单独渲一帧"彩色地面 + 立在地面上的方块", 断言方块像素行均值 < 地面 ⇒ 正立。按颜色匹配猜上下不可靠(暗色件会串色, 会得出相反结论)。
- **主体占比 / 中位亮度 / 内容框**: PIL 直接算; 占比 <10% 说明取景或大地面把主体压小了。
- **ASCII 缩略轮廓(没有视觉模型也能看形)**: 图降采样成 30×72 网格, 按墨量映射 ` .:-=+*#%@` 打印 ⇒ 几秒内看出箱体在不在底部、双臂是不是两根立柱、有没有整片黑块。判朝向比数像素均值直观得多, 交付前每张图都过一遍。
- **标注有没有被裁**: 取逐列/逐行的墨量峰值位置; 纵向尺寸线应在主体右侧形成一个孤立峰, 一条都没有 = 被裁断。
- **部件真的画进去了**: 按部件颜色数像素(立柱 2 万+、顶盖 4~7 万才算在), 别凭"我加了代码"。
- **委派子代理看图**: 给编号问题(姿态/穿模/悬空/黑块/裁切/最适机位), 要求它做像素或源码复算, 不接受"看起来还行"。它会抓到你看不见的东西(整图颠倒、深度符号、漏画的部件)。

## 5. 交付: PPT

**每次重生成都先跑一遍排版自检**: python-pptx 没有文字排版引擎, 中文溢出框是**静默**的。
按全角 1.0em / 半角 ≈0.55em 估行宽、乘行数比框高, 打印「溢出候选」并把它们压到 0 才交付
(本仓 `tools/check_deck_fit.py`); 再用 `soffice --headless --convert-to pdf` 数页数确认没掉页。

### 形态 A · 单页宣传图 (要「渲染后的作业姿态」时)

- 16:9 空白版式, 白底, **图右、字少**(标题 + 一行副标题即可; 首页不上技术参数)。
- 图片等比放到高度约 6.3 in, 右缘留 0.3~0.4 in; 左边留一条竖色带 + 两行字。
- **导出预览自检**: `soffice --headless --convert-to pdf` → `pdftoppm -png -r 110 -singlefile` → 回读页数/尺寸/图数/文字, 并把预览图一并发给用户。
- 同时给**源图全分辨率**和 2~3 个机位让他点选; 换图只改一个参数重出, 不重做。

### 形态 B · 工程图册 (要「正面/侧面/轴向图 + 尺寸 + 坐标系 + 结构参数」时)

四页, 每页一个主题, 不要把所有东西塞一页:

1. **封面** — 立体图 (另一侧机位) + 型号 + 外形包络 `X×Y×Z`;
2. **正面图 + 侧面图** — 各带总宽/总长/总高尺寸线、100 mm 比例尺、base 坐标系; 页脚写每张图的观察方向与对应尺寸;
3. **轴向图 (俯视) + 立体图** — 页脚写轴向投影尺寸 + 反解误差;
4. **主要结构参数表** — python-pptx 表格: 轴/关节原点/轴向/行程/力矩 + 本体各连杆质量 + 安装与行程要点; 表下一行注明「来源: 厂家 URDF, 未手填」。

正交机位按观察方向定, 不要靠调 yaw 试: 正面沿 −X 看 (图内横轴=世界 Y, 竖轴=Z)、侧面沿 −Y 看 (横轴=X)、俯视沿 −Z 看 (横轴=X, 纵轴=Y)。
页脚统一写一条坐标系说明 (原点 = 右臂底座 = 安装面 = 桌面顶 z=0; 地面 z=−750)。
图册用 `tools/robot_deck_build.py` 一次出全套 (渲染 + 标注 + 拼页), 别一页页手工摆。

### 形态 C · 四视图总图 (用户只要「外形」时)

用户说「只要这个机器人的外形, 出渲染图」= **不要 PPT**。做法: 正/侧/俯/透视四张拼一张宽 2400px 的交付图
(matplotlib 白底 + 四个 `add_axes`, 每格标题写观察方向与对应尺寸, 顶部两行写部件构成与坐标口径),
**并把四张单图一起发** —— 他要放大看某一面。中间图不落交付目录, 落 `docs/6-开阳-工程落地/figs_*/`。

被退回「方案里的外形不对」时, **先重出图、后改方案**: 图对了再动页面, 顺序反了要白改两遍; 且告诉用户
那份多页方案现在是旧口径、等他确认再重出, 别默默把两边都改了。

**成品只有一处交付位**: `docs/1-天枢-产品边界/deliverables/<主题>_<版本>_<YYYYMMDD>.pptx`(+ 同版 PDF); 中间图进 `docs/6-开阳-工程落地/figs_*/`; 构建脚本的 `OUT_PPT` 直接指交付位, 被取代的旧路线输出丢 `zmax_data/tmp/legacy_decks/`。**不要往仓库根再建一个 `deliverables/`** —— 堆到 5 份 pptx + 20 张中间图就会被要求"合并精简"。

### 形态 D · 往已有 deck 追加页 (甘特 / 节拍 / 节点清单)

- **幂等重建**: 脚本固定 `BASE_PAGES`(已有页数), 每次先删尾部多余页 `sid=pr.slides._sldIdLst[-1]; pr.part.drop_rel(sid.rId); pr.slides._sldIdLst.remove(sid)`, 再重画 —— 反复迭代不会堆出 12 页。
- **几何自检**: 画完遍历 shapes 断言四边都在页内。**横线别复用 vline**(参数顺序一错就变成 9 in 高的竖线越界), 单独写 hline。
- **渲染验证(无视觉模型也能判)**: `soffice --headless --convert-to pdf` → `pdfinfo` 数页 → `pdftoppm -f N -l N -r 70 -png` → PIL 数每条泳道颜色像素(几万级才算真画上) + 非白占比(>10% 非空页)。
- **数据随图存档**: 窗口/节拍/每根条起止写 `<主题>_数据源.json` 与 deck 同目录; `*.pptx` 在 .gitignore 里 (大件不入库), 但生成脚本 `tools/build_*_slide.py` 必须入库, 换数据只重跑脚本。
- 交付后 `DISPLAY=:0 soffice --norestore <deck>` 打开并用 `wmctrl -l | grep -i impress` 确认窗口真起来(别只信进程在跑)。
- 节点清单类页(如 L2 全部逻辑节点)的抓取法与坑见 `references/deck-append-and-verify.md`。

### 形态 E · 甘特/节拍页: 与消费页面同一份数据、同一个窗口

节拍页被退稿通常不是画得丑, 是口径与现场页面不一致:

1. 先 `grep -nE "fetch\(" tools/web/<page>.html` 找到页面真正吃的接口, `curl` 它并把 `cfg_sha` 抄进图注; 别读磁盘同名文件了事。
2. **节拍抄页面的窗口公式**, 不自创: `loop.ks` 指定的那几轮 `dur=cum[i1]+t[i1]-base`, `节拍=dur/mods`。全轮时长/件数含首轮预插/预热, 偏大, 只能标"首轮", 不能当节拍。
3. **并行必须来自数据**: 段表是一条顺序流就没有"左臂 3 s 摆盘 ∥ 右臂 7 s 插拔"这种分工; 辅路(左臂上料)只能引用页面常量(如 `PLANT.feedS=3.0`)并标注"常量口径"。
4. **流程元素一个不能少**: 模块在孔内停留待测(dwell = `release@hole` → 下一次 `grip@hole`, 与 `cycles_data.dwell_s` 对齐)、上料、补插都要成泳道, 缺一条当场退稿; 再把实测 dwell min/max 与配置 `dwell_min_s/dwell_max_s` 并列 —— 贴边说明轮转已排满, 是提节拍前的硬约束。
5. 每根条 = 段起止相减, 合计与 `loop.dur` 对齐(0.01 内); "合并取图可省 1.5~2 s"这类推算显式标"理论, 未验证"。

## 6. 口径

- 汇报给: 几何来源(哪个文件哪几个常量) · 姿态数值(TCP 误差/工具轴/连杆) · 相机参数 · 文件绝对路径 + 字节数。
- 🔴 **尺寸分三个口径写, 不许混成一个数**: ①**本体**(箱体 600×800×750 + 台面 + 双臂) ②**作业包络**(作业姿态下的最大伸展, 例 1750×1900) ③**外形总高**(全可达姿态的最大高度: 臂直立到台面以上 1231.5 + 地面 −750 ⇒ 1981.5 mm)。把作业姿态高度(1452)当"外形总高"是错的 —— 客户问"机器到底多大"会拿到三个不同答案。三行并列表里逐行注明所属姿态/范围。
- 🔴 **真源对不上时不要用几何去凑**: 如实报分歧并说明你按哪边对齐(例: 示教点 x 与槽位 x 差 158 mm 而 y 逐点吻合 ⇒ 要么料盘标定偏了, 要么号位本身带工具偏置), 让用户定口径, 而不是挪一挪把图凑好看。
- 交付前自己跑通; 没采到就说没采到, 不假 0、不假"已完成"。

Z-MAX 工位那份真源都在 `references/zmax-workcell-constants.md`: 工位/相机/配色常量、**世界坐标系标注规格(LEN/C)**、**URDF 结构参数表(六轴原点/行程/力矩/质量)**、料盘槽位、相机基正负号速查、已建脚本清单。
