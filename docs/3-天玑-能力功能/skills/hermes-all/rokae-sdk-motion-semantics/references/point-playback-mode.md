# 215 点「回放模式」：逐点 MoveAbsJ ＋ 用户勾选停点

用在不要求贴录制时间轴、但要求「每个点都能看、能标、能停」的场合（用户口述：「不用 RT 模式，
回到原来的 215 点回放模式，把 215 个点全都列出来，我每个点都看」）。

## 1. 执行器

`tools/rokae/play_points.py`（docker 内跑，`bash tools/rokae_sdk_run.sh --script play_points.py`）

| env | 默认 | 含义 |
|---|---|---|
| `ZMAX_PP_I0` / `ZMAX_PP_I1` | 0 / 215 | 帧区间，左闭右开 |
| `ZMAX_PP_SPEED` | 100 | 控制器 speed 百分比（100 已是这条路的上限） |
| `ZMAX_PP_DWELL` | 1000 | 勾选的停点停多久（ms） |
| `ZMAX_PP_CHUNK` | 8 | 一个块最多几点（块 = 一次 `moveAppend([cmd…])` + 一次 `moveStart`） |
| `ZMAX_PP_SLOW` | `21-35:15,93-108:15` | 接触段：`a-b:speed`，进入即每点单独成块并降到该 speed |
| `ZMAX_PP_TMO` / `ZMAX_PP_TOL` / `ZMAX_PP_ABORT` | 25 / 0.6 / 25 | 块超时(s，按点数放大) / 到位判据(°) / 跟丢判据(°) |
| `ZMAX_PP_STOPS` | `/sdk/point_stops.json` | 停点表 |

停点表结构（页面写、执行器读，别写回轨迹真源）：`{"<帧号>": {"stop": true, "name": "抓取点·槽6"}}`。

## 2. 实测节拍（别给乐观 ETA）

| 场景 | 结果 |
|---|---|
| 0→11（2 个停点） | 44.6s，每点误差 0.09~0.12°，2 次停留各 1.00s |
| 12→35（CHUNK=24，4 个停点） | 77.5s ⇒ **~3.1 s/点** |
| 全程 215 点（CHUNK=24，30 个停点） | 预估 **~11 分钟**（≈3s/点 + 30s 停留） |
| 全程 239 点新表（CHUNK=24，`SLOW=91-133:15`，15 个停点） | **288.6s**，56 块，每点误差 0.106~0.130°，15 次停留各 1.00s，末帧对表 0.12° |
| 同上但接触段独立计时 | `91-133` 每点单独成块 ⇒ **1.3~2.4 s/点**；快走段 24 点一块 ≈ 0.8~0.9 s/点 |

分块只摊掉 `moveReset/append/start` 的通信开销；剩下的是控制器关节速度物理上限。
要贴录制 42.85s 的时间轴只能上 RT 流式（见 `rt-servo-streaming.md`）。

## 3. 接触段为什么必须挡（真机撞机复现）

**取证方法**（离线、不碰臂）：把该段逐帧位置对「插口口 `mouth` / 插入点 `insert`」算距离，
并分别列出 X（沿插入轴）与 Z：

```
#20  762.6 228.1 190.1  距口 3.3   越过插入 -49.0   ← 口上，正常
#23  811.0 227.6 189.3  距插入 2.9  越过 -0.6     ← 推进到插入点，正常
#33  817.8 229.9 219.3             越过 +6.2     ← 已过插入点仍在动
#34  817.7 230.3 202.2             越过 +6.1     ← X 不动，Z 降 17mm
#35  816.0 230.5 190.2             越过 +4.4     ← 降到孔底高度(187.6)
```

结论一句话给现场：**不是臂乱走，是录制段本身在「越过插入点 6mm 的位置垂直下压 38mm」**，
位置回放没有力反馈，指令继续走 ⇒ 控制器 `13036 … 碰撞力超限` + 柔顺停止。
降速只能减小撞车力度。

## 4. 起跑位姿

`{"step":"start","jump_to_i0_deg":63.79}` 表示这一跑是**关节空间直跳 63.79°** 回到 i0 ——
不走录制路径，途中姿态不可控。启动前必须确认臂已在 `frames[I0]`（逐轴差 <3°），否则先单独跑归位段。

## 5. 现场重新示教时：只读记录器

用户说「我重新走一遍，你看着，记录」时用 `tools/rokae/record_manual.py`：

```
ZMAX_REC_RATE=30 ZMAX_REC_SECS=0 bash tools/rokae_sdk_run.sh --script record_manual.py
#   → zmax_data/rokae_sdk/rec/rec_manual_<ts>.jsonl  (t + 关节(rad) + TCP(mm) + rpy，30Hz 追加)
#   Ctrl-C/SIGTERM 收尾 → 自动转 rec_manual_<ts>.json  (real_traj_joints.json 同构: i/t/j(rad)/p(m)/rpy)
# 事后单独转换: python3 record_manual.py --convert <jsonl>
```

- **只读**：只 `jointPos` + `cartPosture`，不碰 power/op、不发任何运动；示教器在 manual/jog 下也能录。
- 30Hz 对 5Hz 的原始录制是**加密采样**，但逐点回放时点会更密 ⇒ 先按弧长/时间抽稀到 ~5Hz 再当回放表用，
  否则 215 点变几千点、每点 3s 的节拍直接崩掉。
- 收尾后先算「总时长 / 帧数 / 路径长度 / 换向点(§ 判据)」，再和旧表对比差在哪，不要直接覆盖真源。

## 6. 页面侧

`/points` 页（`tools/web/points.html` + 服务端 `/api/pts` GET/POST）：逐点一行、列六轴/XYZ/t、一个「停」
勾选＋可选名称，勾选即时 `POST /api/pts {i, stop}` 落盘。页面是高行数长表 ⇒ 表头 sticky、行高 ~22px、
勾选行加底色，别做虚拟滚动（215 行直接渲染更快更稳）。

## 7. 现场重录 → 生成新点位表（旧表撞机后走这条）

旧表在接触段撞过机时，正解不是调旧表参数，是**让现场按正确动作重走一遍**，用这次的录制出表：

```
# ① 只读录一遍（§5），让现场自己确认「好了」再停
ZMAX_REC_RATE=30 ZMAX_REC_SECS=0 bash tools/rokae_sdk_run.sh --script record_manual.py
# ② 按弧长等间隔重采样（目标 8~10mm/点，约 5Hz 等价），生成 real_traj_joints_v2.json
# ③ 停点 = 录制里「真停住的那几段」的末帧，并给段名 → point_stops_v2.json
# ④ 先用 /points?set=v2 给现场逐点看，再跑
```

**两个坑（都己实际踩到）：**

- 🔴 **停住段检测必须带两道下限**：只判「位移 < 0.5mm」会把手的微抖切成假运动 ⇒ 实测 15 个真段被切成 26 段、
  段名全错位。判据要多两条：`持续帧数 ≥4` **且** `段内累计行程 ≥5mm`，两个都过了才算一段。
- 🔴 **段末帧必须强制进表，不能交给「近点去重」**：重采样时若对相邻点做「<2mm 就去掉」的去重，段末帧被丢掉后，
  按 `段序号 → 名字` 映射会把后面所有名字往前错一格（现场看到的就是「抬升」那行没了、扫码点跳到抬升的帧号）。
  做法：先把所有段末帧无条件加进点表，再补插值点；生成后拿名字所在的 TCP 与「那段末帧的 TCP」对一遍，
  逐行核到 mm 级才算完。
- 重录的节奏比旧表快（实测第 3 段峰值 99.2°/s、旧表同段名义 60 档）⇒ 新表的**时间轴要按新实测反算**，
  不要拿旧表的 `t` 硬套；看板节拍也要按新表的扇区重算。
