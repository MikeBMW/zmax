# xCoreSDK 运动指令契约 —— 命令对象、moveAppend/moveStart、逐点节拍下限

## When to Use
- 要用 SDK 直接下发珞石臂运动（不经 ROS 层），特别是**沿一串关节角逐点走**或想「连续跑不停顿」
- `moveStart` 返回异常码（尤其 `-60611`），或调用后控制器 `PowerState.estop` / `off`
- 逐点回放比录制慢一个数量级，想判断「还能不能优化」
- 脚本在容器里读不到自己的调试开关，量级悄悄放大

配套：连接/读状态/授权链见 `rokae-direct-control`；产线闸门、安全区、事故台账见 `real-arm-motion-control`。

## 命令对象语义（按位置猜参数会 TypeError，读 `.pyi`）

权威来源是 `xCoreSDK_python/Release/linux/xCoreSDK_python/__init__.pyi`（含逐接口中文文档），
**不要用 `dir()` + 关键字筛**——会漏（例：`calibrateForceSensor` 不含 torque/collision 关键字）。

| 对象 | 参数 | 语义 |
|---|---|---|
| `MoveLCommand(cart, speed, zone)` | `CartesianPosition` | 笛卡尔直线 |
| `MoveJCommand(cart, speed, zone)` | `CartesianPosition` | **轴插补到笛卡尔目标**，不是关节目标 |
| `MoveAbsJCommand(jointPos, speed, zone)` | `JointPosition` | 关节空间插值（绕奇异/贴限位的救命通道） |
| `setPowerState(on, ec)` | `on: bool` | 传 `x.PowerState.on` 枚举会 `TypeError` |

- **第三参 `zone` 是转弯区，不是速度**。`-1` 看着像"默认值"，实测**等同逐点精确停**：每点必"静止→加速→减速→静止"，
  这就是"轨迹一顿一顿"的根因（相图上 |v| P50 只有 3 mm/s、静止样本占多数）。要连续传 **>0 的毫米数**（转弯区），
  控制器在到点前就开始切下一点；实测 `zone=3` 让同一段轨迹 |v| P50 从 3.2 → **24.2 mm/s**、静止占比 24%→**13%**、
  `1.40 s/点`（停点档 `2.2 s/点`）。改 zone 只用改这一个参数，不要动 speed 档。
- 🔴 **`speed` 不是「录制速度的百分比」，200% 就是这条路的天花板**：同段 21 点只改 speed ⇒
  `100 → 1.606 s/点` · `200 → 1.071 s/点`（接受）· **`400 → moveStart 后控制器立刻 power=off，臂一动不动（sent=0）`**。
  录制真值是 0.2s/点、末端峰值 862 mm/s、关节 124–141°/s，而连续档实测只到 36 mm/s ⇒ 差 10~24 倍。
  被问"能真按录制速度跑么"直接给这条阶梯 + 一句"要贴时间轴只能上 RT 伺服流（1kHz，见 `references/rt-servo-streaming.md`）"，
  别拿加 speed 去试。
  🔴 **RT 流式不是"调个模式就行"**：接口面、五个必经坑（`connectToRobot(IP, localIP)` / `setControlLoopJoi` /
  `setRtNetworkTolerance` 必须在切 RT **之前** / `startReceiveRobotState` 必须在 `useStateDataInLoop=True` 之前 /
  `stopLoop` 可能永久阻塞）见 `references/rt-servo-streaming.md`。
  修好前提后实测回调 **1009.6Hz（p50 间隔 1.00ms）**，频率不再是瓶颈。
  🔴 **回放的平滑只能做在「速度」上，绝不能动位置**：把位置/速度做时间域低通 = 把录制折线抹圆。实测偏离录制路径
  40ms 窗口 **8.1°** / 150ms **29.9°** / 150ms+限速40°/s **54.2°** ⇒ 指令点已经不在原轨迹上，必然撞机
  （现场原话「位置怎么跟以前不一样」）。正解 = **沿固定折线做速度规划**：保留 1ms 折线 → 对弧长速度做两次箱式低通 →
  按弧长重采样位置（位置恒在折线上，实测偏离 **0.10°**）；拐点自动减速-再加速，"瞬间换向"消失 ⇒ 顿挫消失。
  `tools/rokae/arm_rt_stream2.py` 的 `ZMAX_RT_MODE=path` 即此实现；0.15x 全程实测 286.05s（录制 42.85s）、
  279059 拍、终点误差 **0.00°**、无碰撞无超矩。
  🔴 **不许按墙上时间追帧**：回调被调度延迟时 `idx=int((now-t0)*1000)` 会一跳 1.5°+ ⇒ 控制器 `32006 位置指令大跳变`
  + `13053 关节[6]过速保护` ⇒ 下电锁急停。每拍前进量钳在名义值 1.5 倍（`max_step`），宁可整体慢一点也不跳。
  回调里的 `dt` 上限也必须收到命令周期量级（`dt=min(now-last_t, 0.005)`）：按真实 dt 放行时，一次慢回调就能补几度，
  同样是 32006。
  🔴 **RT 位置模式要求第一拍就贴着实测位姿**：归位容差放到 1.5° 会让臂停在离表首 1~1.5° 处，控制器把**整条流**
  判 `32006 位置指令大跳变` 全拒 —— 回调照样 1000Hz、脚本自己的 `err_deg` 还是 0.00°，臂却一步不动。
  起流前强制精确归位（`ZMAX_RT_ALIGN_TOL=0.02`），判据只认「跑完关节角真的变了」，不认脚本自报的 err。
  细节与排查顺序见 `references/rt-servo-streaming.md` §4g。
  🔴 **量抖动用状态缓冲，别用 `r.jointPos()`**：主线程每 5ms 读一次 `jointPos`（或 2ms 一次 `sleep` 轮询）会抢 RCI 锁/GIL，
  把 1kHz 回调饿到 5~8Hz（现场表现“臂不动”）。实测只能在回调里读 `getStateData(x.RtSupportedFields.jointPos_m, vec, 6)`
  （枚举值其实是 `q_m`，传字符串会回 -1；`PyTypeVectorDouble` 只能 `vec.content()` 取值），每 10 拍记一次 ≈100Hz，
  工具 `tools/rokae/joint_spectrum.py` 出每关节峰值频率与频段能量（§4h）。
  🔴 **RT 会话必须 `setLoad(工具质量, 质心)`**：不设 = 把工具当零负载，腕关节自己扛 ⇒ 实测 `30400 5轴 22.027 > 22.000 Nm`
  （只超 0.03 也停）。工程里 `r.toolsInfo()` 能读（本机 `tool1` = 1.51kg、cog 16/13/31mm）；NRT 不设没事是因为它走工程配置。
  🔴 **快慢只由倍率一个旋钮控**：现场说快就降 `ZMAX_RT_RATE`（1→0.5→0.25→0.15），**不要用 VMAX 限速**
  —— 限速等于改位置，就是上面那条偏航。
  🔴 **指挥表按墙钟 1ms 建，不按录制时间轴**：慢放时录制轴表每墙钟毫秒只前进 RATE 项 ⇒ 同一条位置命令
  被连续下发 6~7 拍（“停住→跳一格”）。实测 250Hz 命令流里 **40% 的拍与上一拍完全相同**（步长 CV 1.05），
  现场原话就是「一直抖」；按墙钟建表 + 表项间亚毫秒插值后 **0% / CV 0.38**。降滤波、降倍率都治不住这个。
  判据与修法（含拐点过渡预算、近 180° 反向点）见 `references/rt-servo-streaming.md` §4e，
  离线量法（不连控制器）见 §4f。
  **动 RT 前先跑零运动探针（`rt_tick3.py`）数回调频率**：<50Hz 才判定做不到，≥500Hz 就继续做流式，
  别拿 `VMAX`/`rate`/`zone` 反复试——那不是参数问题。
  🔴 **先分清两种停止码，别把「力矩不够」当「假碰撞」**：`30401`/`13036 …关节外力超限` = 命令跳变被当外力
  （轨迹质量问题，平滑+阈值可解）；`30400 关节传动力矩超限 Nm > 限定力矩` = 该轴**额定力矩/损伤上限**，
  `setCollisionBehaviour` 改不动它，只能降该段速度/加速度。全程 1x 实测就停在 4 轴 23.04 > 22.00 Nm（§4c）。
  🔴 **RT 会话收尾三件**：`stopLoop()` 会永久阻塞 ⇒ 回调写日志、够时长 `os._exit(0)`，另跑 `rt_back_nrt.py` 退 RT；
  运动中指令流一断控制器就下电并**锁 EStop**（软件清不掉，只能示教器复位）；进场先查 `op`，含 `rt` 就先回 Nrt。
  掉电后只用 `--script arm_power.py on` 上电（实测 0.5s、关节角不变、臂不动），上电后先只读确认再谈下发。
  ⚠️ zone 只在**一次 append 多条**时才有意义（单点 append 时它就是精确到位）；掉不停住点见文末"连续通道"。
- `moveAppend` 第一个参数是 **Sequence** ⇒ 传 `[cmd]`，不要传裸 cmd。
- `cmdID` 必须 `x.PyString(...)` 包装，传 python `str` 直接 `TypeError`。
- 关节目标只能用 `MoveAbsJCommand`：J3 贴近限位时任何笛卡尔下降都被拒，用它把关节拧开即可恢复。

## 🔴🔴 「多次 moveAppend + 只 moveStart 一次」= 控制器 -60611 + 急停 + 真碰撞

想连续跑多点（不停顿）时最直觉的写法 —— `moveReset` → 循环 `moveAppend` 追加 N 条命令 →
只 `moveStart` 一次 —— **被控制器拒绝并直接进急停**：

```
Process joints [...], s:100, z:2, js:-1
Append cmd absj#12
moveStart end (-60611)          ← 一次性追加多条后单次启动被拒
⇒ power=PowerState.estop · 臂已动了一小段(实测 ~8°) · 现场碰撞
```

正常逐点日志是 `Notified absj#214 finish:true (0)`，差别就在**每点一个 `moveStart`**。

- **铁律**: 这条控制器只接受 **每条 append 后单独 `moveStart`**。`-60611` 不是参数问题，
  换 `zone`/`speed` 都救不回来——不要在同一方向上反复试参数。
- 上面那条**只针对"多次独立 moveAppend 调用"**。**单次 `moveAppend([cmd1…cmdN])`（一个列表）+ 一次 `moveStart`**
  是可行通道，而且就是仓库里 `tools/rokae/arm_replay_continuous.py` 的做法：实测 `zone=3` 下 40 点一批
  **55.9s / 1.40 s/点 / 末误差 0.10°**，215 点同样一次追加成功（无 -60611、无急停）。
  区别在"append 调了几次"，不在"一次排了几条命令"。
  🔴 这条通道的**前置条件必须全部满足**，否则一样会把急停交回来：① 先 `--dry` ② 起步用 10~40 点小批量验证
  ③ 任一次 append/start 回 `ec≠0` 立即 `moveStop` 不重发 ④ 全批预检关节跳变（本轨迹 `#19→#20` 31.1° 是最大）。
  已被 -60611 拒过的控制器，**别再在同一方向上加量试**；改用 `MoveL`/`MoveJ` 或 RT/RL 才是另一条路。
- 🔴 **整批下发的超时预算按"录制时长×系数"算会必然误停**：`arm_replay_continuous.py` 的预算是
  `dur_src × ZMAX_REPLAY_BUDGET_X`（默认 3.0 ⇒ 42.85s×3 = **128.6s**），而连续档整条实测要 **321~345s**
  ⇒ 回 `ok=false / why="第 1 批超时未停稳(operationState=moving), 已停"` 且**臂停在半路**。
  起跑就带 `ZMAX_REPLAY_BUDGET_X=8`；判因看一行：`budget_s` 与 `batch.secs` 同量级或更小 = 预算的锅，不是轨迹卡顿。
- 📌 连续回放的完整用法（env `ZMAX_REPLAY_N/SPEED/ZONE/CHUNK`、整批超时预算、收尾到位判据、
  以及"连续档不在夹爪/AOI 点停 ⇒ 只能做相图/节拍研究，不能当生产节拍"）见
  `zmax-real-traj-215-autorun` 的 `references/continuous-replay-zone.md`。
- ⚠️ 急停后 `setPowerState` **救不回来**（回 `-3 The robot is in EStop state, please recover`）
  ⇒ 必须人工按示教器/控制柜急停复位。实测 `clearServoAlarm()` + `moveReset()` 都回 ok 也**解不开**
  （不要以为先清报警再上电就能恢复，白等 20s）。崩了第一件事是**只读确认关节角没乱动**
  （与下发前数值逐轴比），确认臂停在安全位置后再谈下一步。

## moveStart 之后的等待序列（顺序错了会误判「0.15s 就跑完了」）

`moveStart` 返回时控制器**还没起转**，此刻查 `opstate` 仍是 `idle`。写成
`if "idle" in opstate: break` 会当场跳出，日志出现 `secs=0.15` / `sent=0`，
看着像「跑完了」其实一步没走。正确顺序：

1. `moveStart` → **先等它进 `moving`**（上限 2~3s；等不到就判失败，不能判完成）
2. 再等回 `idle`（这一段才是运动时长）
3. 两步都要**先看 `power`**：变 `estop`/`off` 就是被保护拦了 ⇒ 立刻中止并上报，别继续轮询到位。
4. 状态读数**连采几次**再看结论——`on`/`off`、`manual`/`automatic` 在相邻两次调用间会来回跳，
   单次采样不能作判据。
5. 🔴 **`moveStart` 回执里没有 `ec` 键 ≠ 启动成功**：部分固件/负载下回执是空 dict 或只带 `message`，
   旧判据 `ec.get("ec",0) in (0,None)` 把它当成功 ⇒ 脚本空等 300s、控制器始终 `idle`、一步没走。
   判据改成：**start 后 2s 内目标关节角变化 >0.05°，否则判“没启动”立即停**（不要靠 operationState 猜）。

## 🔴 到位判据用“最大轴偏差”，不用三轴平均

`平均(|Δx|+|Δy|+|Δz|)/3 < 2mm` 会让 **z 还差 5mm** 的位姿通过判据（x/y 贴着目标把平均拉下来）——
抓取/插入这种 z 决定成败的动作就停在半空，现场看是“你说到位了其实还高”。
一律 `max(|Δx|,|Δy|,|Δz|) < 1.5mm`，报数时把**逐轴偏差**和最大轴一起打出来；
慢速下降（≤5mm/s）后要用 SDK 直采 `cartPosture` 复核，别只信 30Hz 中继

## 读位姿 / 误差码 / 模式前置（写脚本前先核对这三件，否则白跑一轮）

| 想做的事 | 本 SDK 的写法 | 坑 |
|---|---|---|
| 读 TCP + 姿态 | `cp = r.cartPosture(x.CoordinateType.endInRef, {})` → `cp.trans` / `cp.rpy` | 没有 `getCartesianPosition` / `getCartesianPosture`（AttributeError）；`FrameType.endInRef` 是力控参考系枚举，不是位姿坐标系 |
| 判一条指令是否下发成功 | `ec.get("ec", 0) not in (0, None)` | 成功时返回的是 `{'ec': 0, 'message': 'success'}` —— **非空 dict**，`if ec:` 恒真 ⇒ 把成功当“下发失败”提前 return，臂一步不动 |
| 手动拖动后再下发 | `r.setOperateMode(x.OperateMode.automatic, ec)` | 拖动示教后控制器停在 `manual`，此状态下 `MoveL` 不被接受；切自动要求 `power=on` + `op=idle`，`op` 不 idle 时不要硬切 |
| 状态是 `op=OperationState.drag` | 同上, 但**切不了** | 有人握着使能开关时 `setOperateMode(automatic)` 返回 `{'ec': -19, 'message': 'control mode (position/force) unsupported operation'}`, 且 `operateMode` 仍是 `manual`。这不是参数错误, 重试也不会成 —— 停手, 明确告诉现场「请松开使能开关/回自动」, 再重读三态确认 |

- `r.stop()` 只**保持位置**，不会取消已排队的动作；清队列用 `r.moveReset()`。位置模式下顶住不动时，
  伺服会持续加载（力学后果见 `force-controlled-insertion` §5b/5e）。
- 🔴🔴 **杀掉客户端进程/容器 ≠ 臂会停**：`moveAppend` 下发的指令序列在**控制器内部排队**，
  客户端断开、`docker kill`、`kill -9` 都只是断了喂料的来源，队列里的点照旧一条条走完
  （实测：kill 掉回放进程后臂仍按录制轨迹先到废料点、再往初始点走，肉眼看着像"没人控制"）。
  唯一可靠的停法 = **新开一个会话发 `moveReset()`**（`tools/rokae/arm_stop.py`)；
  `moveStop`/`movePause` 在部分固件上根本没暴露（`no-api`），所以脚本三个都试、能成的那个算数。
  **判停只认真值**：连续 3 次采样 `39071/status` 的 `endInRef` 完全不变才算停住；"进程没了"不是判据。
  现场页面上的 `▶ 执行轨迹 / ▶ 右臂跑真实轨迹` 一类按钮按下去也是这条通道 —— 见 `zmax-ar-traj-8797` 的按钮红线。
- 只读姿态在**下电状态**照样能读到（编码器可读），所以“读到位置”不能当作“可以下发”的判据 ——
  下发前必须另查 `powerState` + `operateMode` + `operationState` 三个。
- `dir(r)` 筛 `ode|Mode` 能快速找到 `setOperateMode` / `setMotionControlMode`；但**方法名不能靠猜**，
  猜不到的接口一律去 `.pyi` 查（见本文开头）。
- 🔴 **控制器日志时钟比主机慢约 4~5 分钟**：拿主机时间去对 `queryControllerLog` 的 timestamp 会把"哪一次事故"认错人
  （实测曾把 37 秒那次全程中止误认成 12 秒那次段测）。先做一次对表——触发一个动作、读日志里新出现的条目、
  算偏移——再换算时间；报事故结论前必须用这个偏移核一遍。

## 🔴 rpy 只能原样回传, 改姿态走关节空间 (真机碰撞换来的)

`cartPosture().rpy` 读回来**原样**再给 `CartesianPosition` 是安全的(实测连续 30+ 段姿态变 ≤0.003°);
但**在它上面加/减一个角度**就不安全: 实测给它 +15° 俯仰后回读的 rpy 与预期差 **180°**,
而按旋转矩阵算的几何夹角只差 15°; 再按"度/弧度"两种假设试探, TCP 被甩到离工装面板 **14.7mm** 处撞上。

- **机制**: 控制器 rpy 在 **±π 附近表示歧义** —— 同一姿态有多种欧拉写法, 端点贴近奇异时逆解分支会跳,
  所以"数值上加 15°"与"姿态上转 15°"不是同一件事。
- **铁律**: 要改姿态就走 URDF FK(当前关节) → 在**目标点**上转 → IK → `MoveAbsJCommand` 下发;
  rpy 只用于读取与逐字回传, 不参与任何运算。
- **枢轴必须是 TCP, 不是法兰**: 固定法兰位姿只改姿态 ⇒ 工具尖画圆弧 `L·sinθ`(L=259.8mm ⇒ 12° 位移 **54.1mm**)。
  正确: `p_flange = p_tcp − R_new·[0,0,L]`, 再 IK 到 (p_flange, R_new)。
- **下发后闸**: 纯姿态动作 `|ΔTCP| > 25mm` ⇒ 枢轴算错, 立即停(实测拦下过一次 54mm 甩动)。
  判读: **关节误差 <0.1° 而 TCP 动了 = 枢轴问题**, 不是 IK 不收敛。
- **到位判据**用关节/位姿**收敛**(连续 N 帧变化 <ε), 不用 `operationState` 字符串 —— 它可能在仍在走时就回 `idle`
  (据此提前读到的还是半路位姿, 会被当成"位姿自己跑了")。
- **JOINT 限位会卡死某些姿态**: 实测 +12° IK 误差 110mm/13.8° 不可达, +8° 可 0.01mm ⇒
  规划器逐姿态输出 **位姿误差 / 间隙 / 相对基准最大关节变化**, 不可达的直接剔除, 不要硬发。
- `operationState = drag`(有人在手扶/示教)时一律不下发; 判据是**连读几次位姿各不相同**, 不是只看一次状态。
- 🔴 **喂 SDK 的 rpy 只能来自「实测回读」或「已验证常量」, 不许自己从四元数反解**: 规划给的 `action.a/b/c` 是**度**,
  而 SDK 的 `rpy` 是**弧度**且欧拉约定不同; 按 ZYX 反解后喂 `CartesianPosition`, 第一拍就是"边升边拧腕" ——
  实测命令 `464.3,344,153.5` 落在 `533.6,327.1,157.4`(偏 **69.25mm**), 回读 rpy `0.114,-1.44,2.925` 与命令无关。
  定式: 执行器**每拍把当前实测 rpy 原样带回、只改位置**(位置轨迹同样能到点); 真要转向就**先在安全高度用已验证姿态
  一次性摆正**(本机抓取姿态 `2.961,-1.49,0.205` 取自真机录制帧), 再走位置。
  判据: 命令 rpy 与下一拍回读 rpy 逐分量差 <0.02rad, 一超就停, 别继续喂。

## 逐点执行的固定开销 = 录制速度的物理天花板

录制轨迹常是 5Hz 采样（`frames[].t` 相邻中位 0.200s ⇒ 0.199 s/点），而逐点 MoveAbsJ 每点有
**~0.33s 固定开销**（`moveAppend` + `moveStart` + 轮询 `opstate` 的通信往返）。开销已超过录制单点间隔
⇒ 逐点执行**物理上不可能**达到录制节拍：实测 215 点，录制 42.85s ↔ 逐点 436s（2.028 s/点）。

- **一次定死的诊断手法**: 找轨迹里 `jump≈0.1°` 的那个点看耗时。实测仍要 0.21~0.33s
  ⇒ 那就是通信底线，与位移无关。此时再调 speed、去 dwell 都无用，不要拿它当「还能优化」继续试。
- **汇报口径**: 录制真值与实跑真值**分开列、写清来源**（录制读轨迹 JSON 的 `dur_s`，
  实跑取全程实测逐点求和），并给「达不到」的机制原因。别把调试档当节拍、也别把录制值当承诺值。
- ⚠️ 逐点日志里的 `secs` 是**单点耗时不是累计值**（依据：全部求和应等于总时长）。
  误当累计会算出偏 2 倍的节拍；报数前先 `sum(secs) == 总时长` 对一次。

## 包装脚本必须显式透传脚本要读的 env（默认一条都不带）

`rokae_sdk_run.sh` 这类 docker 包装只传 `ZMAX_HOST_TS` / `ZMAX_ROBOT_IP`。脚本里
`ZMAX_REPLAY_N` 这类**小批量调试开关不透传 ⇒ 容器里读不到 ⇒ 悄悄变成「整条一次性下发」**，
这正是上面那次急停的诱因。

- 加 `-e ZMAX_REPLAY_N="${ZMAX_REPLAY_N:-}"` 等逐条透传；加完**先 `--dry` 核对 `n_points` 真的是 10**，
  再碰真机——否则「只跑 10 点」的意图会在无声中变成全量。
- ⚠️ 透传成空串后 `os.environ.get("K", default)` **返回 `""` 而不是 default**（变量存在但为空）⇒
  路径变空串报 `FileNotFoundError: No such file ''`。脚本一律写 `os.environ.get("K") or default`。
- 🔴 **容器只挂 `tools/rokae` 到 `/repo`, 且 `:ro` 挂载下不能再挂子目录**: `-v repo:/repo:ro` 加
  `-v repo/src:/repo/src:ro` 会失败 —— 要给容器看源码就另起挂载点(`-v repo/src:/src:ro` + `-e PYTHONPATH=/src`)。
- 🔴 **镜像里没有 lerobot 的依赖**(huggingface_hub 等), 容器内 `import lerobot.*` 直接 ModuleNotFoundError
  ⇒ 规划类代码在**宿主**算、产物落 JSON(如 `action_trail_slotN.json`), 容器只跑"读 JSON + 下发 + 到位校验"
  的执行器。两边各算一半, 不重复算、也不在容器里硬装依赖。
- 🔴 **分片开关也必须进 `-e` 白名单**: 漏一个就静默回默认(实测 `ZMAX_TRAIL_MINI/MAXI` 没透传 ⇒
  "合爪前只走 21 拍"变成 22 拍全跑完, 现场看到的是夹爪还没合就抬走了)。

## 起点跳变：该走归位段，不该整条拒发

真机停在中途、距轨迹第 0 点 60~80° 是常态（上一轮被打断/人工回位）。
**起点跳变单独走归位段**（插中间点，每段 ≤16.5°），帧内跳变另外预检（上限 40°）；
归位点也要有到位超时，超时必须报 **「归位段第 k/N 点未到位，正式点一个没走」**——
只写「失败」会被误读成轨迹本身有问题。

开跑前先把「当前位姿 ↔ 第 0 点」的逐轴差算出来报给现场：实测 1.84° 可直接开跑，
>40° 就请现场归位、别硬发。

## 报警/失败后给用户的第一句话（复盘口径）

真机一报警，用户第一句总是「怎么会报警」——所以**先拿码再说话**，不要凭现象猜：

1. 先跑 `--script dump_controller_log.py 60`（`queryControllerLog`，只读），按**控制器时钟**（比主机慢 4~5 分钟）
   对到本次那一跑，取出错误码 + 原句（如 `30401 关节外力超限`、`30400 传动力矩 23.04 > 限定力矩 22.00`）。
2. 第一句就给三件：① 这条码的人话（“不是撞了东西，是命令跳了一下”）② 真报警还是保护误判 ③ 下一步。
3. **不同码不得混成一个原因**：外力超限（轨迹/命令质量）与传动力矩超限（额定上限）复盘结论完全不同。
4. 必须主动报代价：哪一轴停在哪一位姿、是否锁了急停、需不需要人复位——用户就在现场，骗不了也拖不得。

## 🔴 起跑前的进程/容器卫生（两次真机翻车都是这里）

1. **同时只能有一个 `arm_rt_stream2.py`**。第二个进程进来时 `arm_power.py on` 会回
   「已经是 on, 无需上电」然后 RT 会话拿不到控制权 ⇒ 日志只有一行 `{"ok": false, "why": "上电失败"}`，
   而臂其实在被**上一个进程**驱动 —— 现场看到的行为和脚本打印的计划完全对不上。
   起跑前必须 `pgrep -af arm_rt_stream2` 数到 0 再起。
2. **流正在跑的时候绝不要调 `rt_back_nrt.py`**：它把 `op` 从 `rtControlling` 切回 `NRT`，正在下发的流当场失效。
   实测现场表现就是「该停的抓取点没停」—— 不是 hold 没生效，是这一下把流打断了。
   收尾顺序固定：**跑完 → 确认没进程 → 再 rt_back_nrt**。
3. **清理残留容器只按 `--name`/`--filter name=` 精确删，绝不按镜像前缀批量 `docker rm -f`**：
   RT 回放的容器名是随机生成的（`naughty_hermann` / `sleepy_napier` 之类），**不能靠名字找**；
   按“命令行里带 `arm_rt_stream2.py`”定位再删：
   `CID=$(sudo docker ps --format '{{.Names}} {{.Command}}' | grep arm_rt_stream | awk '{print $1}'); sudo docker rm -f $CID`，
   删完用 `docker ps --format '{{.Names}}'` 确认常驻四件（`rokae_tcp_sampler` / `ss-remote-tap` / `zmax-ft-sampler` / `zmax-moveit`）还在。
   实测用 `--filter ancestor=ros:humble-ros-base` 一次连删 4 个常驻容器（`ss-remote-tap`、`zmax-ft-sampler`、
   `rokae_tcp_sampler`、一个刚起的），其中 systemd 管的能自愈，`--restart unless-stopped` 的**永久消失**，
   只能按原命令手工重建（`rokae_tcp_sampler` 重建命令：
   `docker run -d --restart unless-stopped --name rokae_tcp_sampler --network host -v <repo>/zmax_data/rokae_sdk:/sdk -w /sdk ros:humble-ros-base python3 /sdk/tcp_direct_sampler.py --rate 5 --secs 0`）。

4. **`arm_power.py` 不带参数 = 切换电源, 不是查询** —— 想"读一下状态"而敲 `--script arm_power.py` 会**直接把臂下电**(回执 `power_before: on` / `power_after: off`)。
   读状态只走 `http://127.0.0.1:39071/status` 的 `power`/`op`, 上电/下电一律显式 `on` / `off`。
5. **段区间 `js[i0:i1]` 是左闭右开**: `ZMAX_RT_I1=9` 实际只装到 `#8`, 要停在 `#9` 必须给 `I1=10`。
   同理 `ZMAX_RT_HOLD_AT` 只在**已装载区间内**命中 —— 区间切短了会静默 `holds n=0`(该停不停), 而 `run_done` 照样报 `err_deg=0.0`。
   起跑日志里先看到 `holds.detail` 有你点的帧号才算真加了停留。
   🔴 **停点帧号是绝对帧号，而 `js` 只是 `[I0,I1)` 的切片** ⇒ 查表前必须 `fi_local = fi - I0`；
   少了这步段跑时 `holds n=0`（`js[167]` 直接越界被跳过），臂一点不停、日志全绿。
6. **`pkill -f <脚本名>` 会连自己的命令行一起杀**（模式也匹配当前 shell 的 `bash -c`，实测整条命令被 SIGKILL、
   清理没做完）—— 用括号规避 `pkill -9 -f '[p]lay_points'`，或先 `pgrep -af` 取 pid 再 `kill`。

## 相位口径：`ph` 必须是整条轨迹的绝对相位，不是本段进度

段跑（如 `ZMAX_RT_I0=0 ZMAX_RT_I1=9`）时若把 `ph` 写成 `idx/(len(dense)-1)`，段末即 1.0 ⇒
看板显示 **100%** 而臂只走到全路径 4.7%，现场就是「相位怎么没变/乱跳」。
正确：`ph` 必须与页面/API 用的**同一份数组同口径** —— 取 `traj_phase.json` 的**弧长 `s`**：
`ph = s[round(i0 + SPAN*(idx/(len(dense)-1)))] / s[-1]`（`SPAN=(i1-1)-i0`）。
⚠️ 用「帧号 / N_TOTAL」当归一（`(i0+SPAN*frac)/(N_TOTAL-1)`）**不行**：帧号均匀 ≠ 弧长均匀，
大跳帧处两者差 ~1%（实测 27.1% 对 26.1%），看板方框会落到下一行（臂停在废料点，行却高亮「转移」）。
配套：服务端**不要**对 `meas` 做「跑完就冻结在 100%」——段跑的 ph 是段末，冻结会一直显示 100%；
超时（>6s 无新样本）一律回退到「按位姿现算」，全程跑完时最近点也是 100.0%，数值不变只换来源。
再配套：**防回退高水位只在 playback 真活着时生效**；回退到「按位姿现算」那一支必须用新算的值，
否则上一趟的 27.1% 会被 `max()` 永久钉住（臂已停在废料点，页面仍是 27.1%）。
再配套：**闭环轨迹首末帧几乎重合**（本机 18.8mm），臂停在**初始点**时最近点会判成末帧 ⇒ 显示 100%。
判据：最近点落在末 6 帧内且与首帧 `traj_hopf.frames[0].p_mm` 距离 <30mm ⇒ 归零（站回起点就是新一趟的 0%）。

本机 215 点轨迹的**工艺分段表**（起始点/转移/下降/抓取点/上升/扫码点/对位/力控搜索/插入/设备工作点/离开/拔出点/废料点…，
含帧区间与几何证据）见 `references/traj215-process-stages.md`；按段跑真机、给用户报进度时照它对齐叫法。

## 停点（hold）与「自己的门 / 控制器报警」必须分开

- 🔴 **停点判据用几何换向，不要用「速度≈0」**：录制轨迹是折线，绝大多数停点并没有零速平台（臂只是转向）。
  判法：前后各 `W=5` 帧求方向向量、夹角 ≥45°、两段位移各 >10mm、5 帧内去重 ⇒ 本机 215 帧得 **22 个点**
  （只按「慢 + 近似静止」筛只剩 4 个，现场必然问「这个点怎么没停」）。这 22 个就是 `ZMAX_RT_HOLD_AT`，
  每点 `HOLD_MS=1000`；22 秒停留要算进总时长预期，别按纯运动时长报 ETA。
- 🔴 **不要在已成形的规划上再叠一层加速度限幅**：blend 规划（固定折线 + 弧长速度规划）已经限过加速度，
  回调里再加 `Δv ≤ ACC·dt²` 这类逐拍钳制，实测把命令速度压到 **2.1°/s**、表按墙钟跑到头、臂落后 **64°**，
  看起来像「臂不动」其实是被自己的限幅拖死。要更柔就**调大 `ZMAX_RT_SMOOTH`**（150→300ms），不要加第二层限幅。
  实测 smooth=300 + rate=0.12 全程 215 帧 **334.9s**、11 停点各 1s、无 abort、终点对帧 0.00°。
- 🔴 **跟踪闸门是真的有用，别去掉**：`|cmd − meas| > ZMAX_RT_LAG`（15°）即 abort 并记 `abort_why`；
  没有它就只剩 `err_deg=0.0` 的假成功。
- 🔴 **每个 setter 都要查 `ec`**：`setCollisionThreshold` 之类传超上限的轴值会被**整条拒绝**
  （实测 `{"ec":258,"message":"parameter exceed limit"}`），阈值保持旧值 —— 不查返回码就会把后面那次停
  当成新故障去查轨迹。
- 🔴 **脚本自报 `torque_abort` ≠ 控制器碰撞**：`{"step":"torque_abort","joint":2,"Nm":-80.5,"limit":70.0}`
  是 `ZMAX_RT_TLIM` 自己拦的；控制器真检测只会是 `13036` / `30400`。现场说「没有碰撞」时先看是不是自己的门，
  再决定「调 TLIM 放过该段」还是「改路径」。大角度腕转段（单轴扫 >150°）天然力矩高，先把 TLIM 放到控制器线以下
  （如 J2 70→85，控制器碰撞线 101），让轨迹走完再按实测力矩曲线判断哪段真高。
- 🔴 **`op=jogging/manual` 残留会阻断 RT 起流**：现象是容器起来后**既没有新的 `rt_stream2_*.jsonl` 也没有 `meas_*.jsonl`**，
  stdout 只有一行 `terminate called without an active exception`。判据：起进程后 **30s 内没有新 meas 文件 = 没拿到控制权**，
  别等、别重跑同一份命令；先 `setOperateMode(x.OperateMode.automatic)`（要求 `power=on` + 可切）把 op 拉回 idle/automatic，再起流。
- 🔴 **「全程跑通」的真判据 = 实测关节匹配到录制帧**：跑完取实测关节对整条录制帧做最近帧匹配，
  要同时满足「最近帧 = 末帧」「最大轴差 <0.1°」「TCP 距初始点 <5mm」。实测合格样本 334.87s / 327393 拍 /
  `err_deg=0.0` / 末关节 = `#214` 最大差 **0.00°** / TCP 距初始点 **2.7mm**。`err_deg=0.0` 单独不算通过。

## 回放模式（逐点 MoveAbsJ ＋ 页面勾选停点）—— 只覆盖空走段，接触段禁止回放

用户说「不用 RT，回到原来的 215 点回放模式；每个点给一个『是否停止』的勾选，勾了就停 1 秒」时，
用逐点/分块 `MoveAbsJCommand`（`tools/rokae/play_points.py`），不要偷偷回 RT。四条硬规则：

1. 🔴 **接触类动作不能靠位置回放通过**：`MoveAbsJ` 没有力反馈，指令只会到达表里的点。录制轨迹里常有
   「退出—回落—再压下去」的示教段，回放就会顶在设备/已插入工件上，由控制器碰撞检测兜底停车
   （`13036 RSC检测到关节[N]碰撞力超限` + `关节外力超限，柔顺停止`）。**低速只减损失、不减碰撞** ——
   插入/压入/贴合段必须交棒给力控（`tools/lissa_fc.py`），回放只负责把臂送到对位点。
2. **选段先做几何取证，别凭印象**：把该段逐帧位置对「插口口/插入点」算距离并拆成 X/Z 分项，找
   「X 基本不动、Z 一路下降」的帧组。实测一例：`#33→#35` 在**越过插入点 6mm** 处垂直下降 **38mm**，
   末帧 z=190 正好是孔底 187.6 ⇒ 位置回放必撞。这条取证比任何参数都先做。
3. **停点表由用户勾选，不由算法推断**：页面逐点列出（帧号 / 六轴 / XYZ / t），每行一个「停」勾选，
   勾选即存 JSON（`point_stops.json`），执行器只读这份表；勾选集合就是 `HOLD_AT`，`HOLD_MS=1000`。
   初始值给「几何换向点 ∪ 用户点过名的地标」的并集，别只给几何那 22 个（他会说「这些点我都标过，你忘了么」）。
4. **起跑位姿必须是 `frames[i0]`**：从别处起跑时控制器做一次关节空间直跳（实测 **63.79°**），不走录制路径，
   途中可能穿过不该穿过的姿态。启动前算当前关节与 `frames[i0]` 的逐轴差，>3° 先把臂送回 i0 再跑。

节拍：`speed=100` + 分块（一次 `moveAppend([cmd…])` + 一次 `moveStart`）实测 **~3 s/点**
（24 点含 4 个停点 77.5s；12 点含 2 个停点 44.6s），215 点约 **11 分钟**。分块只摊掉通信开销，
剩下的仍是控制器关节速度上限；要真贴录制时间轴只有 RT 流式一条路。细节（env 表、慢速区、几何取证脚本思路、
只读示教记录器）见 `references/point-playback-mode.md`。

## 验收纪律

- 🔴 **`err_deg` 量的是「最后一个被接受的目标」，臂中途不动它照样报 0.0**：实测一段 105s 的 `#109→#214` 回放
  `run_done ticks=102610 err_deg=0.0`、`ph` 已到 1.000，而臂实际停在 `#166`（关节空间差 2.7°、TCP 差 38mm）。
  机制：该段 J4 从 238° 扫到 61°（单轴 177°），中段之后的下发被控制器连续拒，脚本只按“最后一个被接受的 setpoint”算误差。
