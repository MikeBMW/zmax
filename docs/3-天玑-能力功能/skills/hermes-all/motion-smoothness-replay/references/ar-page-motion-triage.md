# 观看端「动作变形 / 乱动」分层取证 (AR 页 · 8797)

适用: 用户看着 AR/网页里的虚拟臂说「动作变形了」「乱动」「还是老样子」。
症状在画面上, 根因几乎总在**驱动数据**里, 不在 Three.js 渲染。按下面四层从上往下排, 每层都有可执行的判据, 别跳层调渲染。

---

## 第 0 层: 先分清「哪一路在驱动」

同一个观看端可能同时存在多路驱动, 混在一起看就一定判错:

| 驱动 | 来源 | 语义 |
|---|---|---|
| `exec` | 执行器节点逐拍发的实执行段 | 真正在执行的动作 (动作一致性的真源) |
| `plan` | 规划节点每拍重规划的预告 | 只是「打算去哪」, 未必然被执行 |
| 页内回放 | 页面用自己的理想剖面重算整表 | 只验证几何+时序, 不代表链路 |

判据: 拉一次指令 payload, 看它自报的 `drive`/`src` 字段, 以及 `age_s`(帧龄)。
`drive=exec:*` 才算「跟链路一致」; `plan` 在跑就要预期看到「臂追着没执行到的目标」——
这本身就是「差很多」的直接原因。

规则: 驱动分区只取 `exec`, `plan` 另起字段名 (`plan_seg_i`/`plan_label`/`plan_n`) 展示, 两者绝不共用 `a/b/u`。

---

## 第 1 层: 段表本身是否在「每拍归零」

连采 20~40 次指令文件 (0.2~0.5s 一次), 每次只取 `{plan_id, seg_i, n, u, kind, a, b}`:

- `n` 每拍在变 (如 21/22/26/40) → 规划节点每拍全量重规划, 没有段表状态;
- `seg_i` 恒 1 且 `u` 恒 0 → 发布写死了第一段;
- `plan_id` 不存在或每拍 +1 → 没有「一份计划」的概念。

三条中任意两条 + 观看端单帧关节跳变超限速 = 确诊「每拍把臂从段首重拉」。
修法与验收见 SKILL.md「铁律」第 7 条。

坑: 修完必须**重启常驻节点**; 常驻循环不 reload 模块, 只改文件的现象是「改了没变化」, 容易被误判成没修对。

---

## 第 2 层: 段表字段别猜

- 段表里 `k` 通常是**轮次/圈号** (loop key), `kind` 才是动作类型 (lift/move/down/insert/pull/release…)。
  拿 `k` 去比「动作类型」会得到空集 (典型症状: `next(i for i,s in enumerate(P) if s['k']==ks[0])` 直接 `StopIteration`)。
- 取窗口时 `i0 = 第一个轮次==ks[0]`, `i1 = i0 之后**第一个**轮次==ks[1] 的末段`;
  用 `max(...)` 找最后一个匹配会把后面的圈一起吞进来。
- 段时长字段 (`t`) 是「段表口径」, 未必是物理可行时间: 100mm 下沉给 0.30s = 333mm/s, 而慢档常配 300mm/s。
  重算理想剖面时, 这类段会**变慢**, 报节拍要把「变慢的段数和净收益」一起说, 不然用户会以为你在偷时间。

## 第 3 层: 页面内怎么采到真实关节角

页面的运动学函数 (`ikTool1`/`urdfFK`/`arQStep`) 在 `tcp-ar.html` 里是模块作用域, **不在 `window` 上**, console 直接调不到。
做法: 在写 `PREV.q` 的那一行旁边挂只读埋点 (每帧覆盖, 开销可忽略):

```js
window.__ARQ = PREV.q ? PREV.q.slice(0,6) : null;              // 6 关节 (rad)
window.__ARTCP = PREV.M ? [PREV.M[12],PREV.M[13],PREV.M[14]] : null;  // 末端 (mm)
window.__ARD = {kind, label, u, a, b, seq};                     // 当前段身份
```

采样: `setInterval` 100~120ms × 60~80 帧, 算相邻帧逐关节绝对差。
- 正常: 单帧 ≤ 限速 (`180°/s` → 3°/帧 @60fps);
- 异常: 出现 6°+ 且反复回摆 → 数据在第 1 层就被拉扯, 不是插值问题。

看门狗: 若 `__ARQ` 一直是 `null`, 说明页面根本没在走那条驱动分支 (开关没开 / 播放没启动 / 页内回放没点), 别把「没驱动」当成「跳变」。

## 第 4 层: 三份段表对账 (判「动作是否一致」)

要回答「动作和固定轨迹一致吗」, 离线重算, 不靠采样:

1. **全流程段表** (`/api/sim_insert` 的稳态窗口) = 动作几何真源;
2. **固定轨迹** (理想档 JSON) = 几何同源 + 理想剖面重计时;
3. **执行器段表** (执行器自己的生成器 `build()`) = 实发序列。

逐段比 `(kind, a, b)`:
- ① vs ② 应 100% 一致 —— 一致就说明「固定轨迹没换动作, 只换了时间」, 这是最能打消疑虑的一句;
- ② 的点应全部出现在 ③ 里 (② 是 ③ 的稳态切片), 缺几个就列出来, 别用「大致相同」;
- 差异只应出现在 `t` 列, 并把净收益拆开说: 省在横移/抬升, 而不是把下沉/插入时间压掉。

三份都写成每动作一行的 JSON (类型/标签/起点/终点/行程/段表t/理想t/Δt) 落到交付目录, 供人事后复核。

## 常驻服务口径 (8797)

- AR 轨迹页 = `zmax-traj-ar.service`, 页面源 `tools/web/tcp-ar.html`, 接口 `tools/tcp_ar_server.py`;
  改接口代码必须 `sudo systemctl restart zmax-traj-ar` 才生效。
- 状态空间常驻循环 = `zmax-ss-canvas-loop.service`; 改节点实现 (`src/lerobot/engineering/nodes/*`) 必须重启它。
- 播放/场景开关写在 `zmax_data/ss_live/ar_play.json` (`action=start|stop`), 场景开关状态看 `/api/ar/mode` 的 `ar_scene/fresh/play`。
- 非源码层的临时取证优先读文件 mtime (`zmax_data/ss_live/ar_cmd*.json`), 比调接口快且不受服务状态影响。

重启本身是用户的决定: 只改代码 + 报「要重启哪个单元」, 不自行重启常驻服务/GUI。
