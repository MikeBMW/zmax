# 2026-10-08 晚 · 金手指判据图 v22(失败不再端旧口径 + 逐窗救回)

## 现场问题
老倪:「金手指, 还是没改好, 怎么搞? 右侧有方块区域, 不是金手指。工控机改好了么」

版本**其实已经上到 v21**(工控机文件 SHA256 `9316318F90A6A7A7…` 与 v21 交付件逐位一致),
但**约 20.6% 的帧判据渲染失败**, 老代码 `if judge is None: judge = crop` 把 topview
**静默换成旧的 960x960 拉伸图**(右侧灰块没被切掉) —— 这就是现场看到的"右侧方块区域",
它根本不是判据图, 是旧口径那张。

## 根因(实测数字, 非推测)
- 高频守帧实测(150s): **131 帧里 27 帧失败 = 20.6%**;
  失败帧 `judge.sat_before = 0.635~0.668`, 正常帧 `0.221~0.338`(两个**完全分离**的簇)
- 用捞回来的真失败帧离线复现(工控机同款数值栈 py3.10/cv2 4.10.0/np 1.26.4):
  失败帧的**合并键行带 = [680,1249] ≈ 570 行**; 正常帧 = [690,819] = 130 行
  ⇒ 过曝的金属外壳区里多出一个"命中窗"(y≈1200) → `ky1 = max(y1) = 1249`
    把带子从 130 行撑到 570 行
  ⇒ 带内 63~67% 像素 ≥250(外壳过曝成纯白) → 列方向亮度剖面整段通过
  ⇒ 键列塌成 **1 根**(需 ≥3) ⇒ `too few keys after detection (1)` ⇒ 放弃渲染
  ⇒ 回退旧 960x960 口径 ⇒ 现场"右侧方块"
- **复现前提**: 数值栈必须与工控机一致。本机 `gui-venv311` 是 **cv2 5.0.0**,
  同一份代码同一帧会给出不同结果(不能用它下结论);
  另 `templates/gf_strip_template.png` 必须在模块旁, 否则静默走 legacy 几何。

## v22 改了什么(只动判据路径, **模型输入零改动**)
1. **失败绝不端错图**: 保留上一张好判据图 + 红条(帧龄/原因); 一张好图都没有才退回 960 并**如实标注**
2. **失败时逐窗 + 放宽门限重试**: 第 1 遍仍是 v21 原口径(⇒ 正常帧像素逐位不变),
   失败才用候选键行带(单窗优先)×放宽门限重试; 重试结果必须过验收闸
   (`sat ≤ 0.55 / 键 ≥ 5 / 黑底 ≥ 0.45`)才被采纳, 防"救回一张错的"
3. **有界取证**: 失败时把输入帧 + 完整 meta(含命中窗)覆盖式落两个固定文件,
   `debug_judge_fail_last.png` / `.json`, 永不增长(这是本次能把根因钉死的关键工具)
4. **可见性**: `/crop_info.judge` 补 `state/ver/why/err/n_keys/attempt`, 顶层补 `judge_ver`
   —— 原来失败时 11 个别名全是 null, 故障完全隐形
