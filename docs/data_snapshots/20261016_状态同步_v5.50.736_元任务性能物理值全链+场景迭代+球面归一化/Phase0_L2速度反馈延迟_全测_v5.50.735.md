> 老倪 2026-10-15: 「一步一步迭代 phase0 所有L2层的原子技能, 速度反馈延迟, 全测」
> 唯一依据 KPI: **速度反馈延迟 ≤ 10ms** (config/roadmap_phase_texts.json · config/eval/iteration_roadmap.json)
> 测法: `tools/probe_l2_speed_fb_latency.py` — **只读**, 不下发任何真机指令, 不改任何服务

## 一、口径 (先定死, 免得"像但不是同一个量")

速度反馈延迟 = 一条速度指令从**产出**到**该技能速度反馈可见**, 拆三段腿 + 一条物理腿:

| 腿 | 定义 | 唯一依据 |
|---|---|---|
| ① 引擎→块 | 引擎产出动作块的周期 (新速度指令多久算一次) | `/dev/shm/.../engine_default.jsonl` 逐拍 ts |
| ② 块→派发 | 新块到达 → 派发服务认领 (服务自报) | `zmax_data/ss_live/skill_latest.json::块帧龄_s` |
| ③ 派发→反馈 | 该技能速度反馈**跟上新指令值**的时间 | `zmax_data/ss_live/skill_phys.json` 逐技能 `v_mms` + ts |
| 物理腿 | 真机实测速度反馈 (位姿微分) | 位姿唯一依据 `tcp_out/latest.json` / 位姿 tap |

主指标 = ① + ③ (端到端)。**不是** `perf.latency_e2e`(采图→位姿输出), 也不是机械臂实测速度 —— 语义对不上的一律不硬套。

## 四、判定 (对 KPI ≤10ms)

| 口径 | 实测 | 判定 |
|---|---|---|
| 派发腿 ③ (P50) | 9.81 ms | **达标**(压线, P95 16.95ms 已超) |
| 派发腿 ③ (P95) | 16.95 ms | 不达标 (1.7×) |
| **端到端 ①+③ (P50)** | **109.95 ms** | **不达标 (11×)** |
| 端到端 ①+③ (P95) | 197.82 ms | 不达标 (20×) |
| 物理腿 (真机实测速度反馈) | 不可采 | 不可判定 |

⇒ 结论: **Phase 0 的「速度反馈延迟」当前不达标, 主项差在引擎块周期 (10Hz=100ms) 及其胖尾。**
派发服务本身很快 (16.77ms 拍距), 引擎自身计算也只有 0.76ms —— 慢的不是"算", 是"**多久算一次**"。

## 五、胖尾根因 (从引擎自己的埋点取证, 不是猜)

| 观察 | 读数 | 来源 |
|---|---|---|
| 拍期胖尾 | P50 100.07 / P90 232.71 / P95 270.55 / **P99 1015.63** / Max 1155.3 ms; **10.7% 的拍 >105ms, 1.24% >1s** | 引擎 tap 逐拍 ts |
| 多层 pipeline 命中率 | **10.0%** (= `--pipe-every 10`) | tap 里带 pipeline 记录的拍 |
| pipeline 单次耗时 | P50 163.3 / P90 907.7 / **Max 996.9 ms** | tap `pipe.ms` |
| pipeline 逐层 (样例行) | L5 0.01 · MEM 0.09 · L2(yolo) 4.76 · **L4(vote[intact]) 173.99** · L3 0.05 ms | tap `pipe.layers` |
| L4 潜空间编码 | **992~1032 ms/次** (每秒一次, 独立线程) · 成功 5105/失败 41 | tap `z_source` |
| 引擎自算 (投影/梯度/编码) | t_project 0.138 + t_grad 0.063 + t_encode 0.005 ≈ **0.2 ms** | tap 逐拍 |

⇒ 10.7% 的慢拍 ≈ pipeline 每 10 拍同步跑在控制拍上 (163~997ms, 其中 L4 vote 占大头);
1.24% 的 ~1s 拍 ≈ L4 视觉编码线程 (992~1032ms/次) 与 10Hz 控制拍的 CPU/GIL 争用。
即: **认知层 (L4) 的重活压在 L2 反馈拍的关键路径上**, 这直接决定 L2 速度指令的刷新率。

## 六、下一步迭代 (按收益/风险排序, 每步都可独立复测)

1. **把多层 pipeline 移出控制拍** (当前 `self.n % pipe_every == 0` 同步跑):
   改成旁路线程 + "取最近一次结果", 与 L4LiveProvider 同一做法 ⇒ 拍期 P95 应从 181ms 回到 ~100ms。
   判据: 拍期 P95 ≤ 105ms 且 pipeline 命中率不变。
2. **L4 编解码争用**: 编码线程按 1s 周期抢了 ~1s 的 CPU ⇒ 把编码拆到独立进程 (或降频/降分辨率),
   让控制拍不再被 ~1s 级编码拖住。判据: >500ms 的拍占比 <0.1% (现 2.13%)。
3. **L2 拍真正恢复到 10Hz 后**, 再压块周期本身: 若现场允许把回路提到 20~30Hz (块周期 33~50ms),
   端到端才能逼近 50ms 量级 —— 但 10ms KPI 需要把"指令产出"从"每块一次"改成"拍内增量下发"。
4. **物理腿补测** (不可采的原因): 真机位姿 tap 已停更 14.8h (`tcp_out/latest.json` 帧龄 53176s, 最后 08:14),
   产线网段不在位 (Orin 192.168.23.66 与 .23.50 均 ping 不通, USB 网卡未插)。
   接上真机后可直接扩展本探针: 用带 ts 的 50Hz `tcp_pose` 真值做"速度指令→实测速度"闭环延迟,
   这才是机械臂口径的速度反馈延迟 (现在只能测到 L2 收口口径)。
