# 自绘 canvas 三维工艺/示意页 (挂在既有服务上)

## When to Use

- 用户给/贴了一份技术协议、布局图、设备清单，要求在**已经在跑的服务**上开个新 URL，用三维视图把“一根产品周围有哪些设备/工位”讲清楚。
- 要求“和已有页面同一坐标系”（典型：在 8797 `/ar` 的 base 世界系里再做一个 `/autoLight`）。
- 要把“从自动化专机 → 机器人”这类迁移/对比用索画出来，且动画里要看得见谁替代了谁。
- **用户要求「按工艺每一步做一个窗口/工艺卡」「在当前窗口下逐步显示」⇒ 交付形态是一页 N 张卡（§7），不是一个场景塞完再让他挑。** 他从“做一个页面”改口成“每步一个”时，是版式要求变了，加个侧栏说明书交不了差。
- 产线/边缘环境无外网，不能引 CDN，必须单文件自包含。

不适用: 手机端 Three.js 复刻状态空间 (`zmax-mobile-3d-console`)、真机相机画面叠加 (`fixed-camera-ar-overlay`)、纯静态架构图 (`architecture-diagram`)。

## 1. 先定坐标系, 再画东西

- **沿用既有页面的 base 世界系**: 打开那个页面的投影代码, 抄它的约定 (本项目 `/ar`: **X 右 / Y 近 / Z 上, 单位 m, 地面 z=0**)。
  自创一套坐标 = 用户拿两个页面对不上, 等于白做。
- 场景里**画出 base 原点坐标轴** (X 红 / Y 绿 / Z 蓝) 和地面网格, 让人一眼能对标。
- 尺寸统一 mm→m 换算, 布局用「设备真实外廓为中心」的局部坐标 (如 3.0×1.5×1.9 m 以原点为中心), 别把设备丢到离原点几米外。
- 交付里必须写清**示意 vs 施工图**: 协议只给模块关系时, 排版是自己定的 ⇒ 明写「按协议模块关系 1:1 比例示意, 非施工图」, 并说明拿到 LAYOUT 图/实测点位后替换哪一份数据。

## 2. 服务侧接线 (热读 + 只重启一次)

路由加在**已有服务**里, 页面文件**每请求热读** ⇒ 之后改 HTML 一律不用重启:

```python
elif p in ("/autoLight", "/autolight", "/autoLight.html"):
    try:
        with open(os.path.join(REPO, "tools", "web", "autoLight.html"), "rb") as f:
            self._send(200, "text/html; charset=utf-8", f.read())
    except Exception as e:                       # 页面缺失要回可读的 404, 不要 500
        self._send(404, "text/plain; charset=utf-8", ("页面缺失: %s" % e).encode())
```

顺序固定 (与 `live-service-change-discipline` 一致): **写页面 → 加路由 → 用服务自己的解释器 `py_compile` → 只重启一次 → 回读**。
回读三样: 新端点 `http=200` 且 `bytes` == 文件实际大小 · 老页面 (`/ar`) 字节数一字未变 · `/api/*` 仍 200。
改页面文件不需要再重启 (热读), 别为调样式反复重启用户在看的服务。
  ⚠️ **热读只对 HTML 成立: 改了服务端常量(如 `PRODUCT_SPECS`/规格文案)必须重启**, 而"restart 报 started"不等于新进程在服务 ——
  fork 型服务残留子进程占着端口时, 新进程 bind 失败, 启动脚本 `curl` 拿到的 200 是**旧进程**答的。
  判据用**只有新代码才有的内容尾串**(不是 200/ok), 详见 `live-service-change-discipline` §3。

- **整份重做旧页先留旧形态**: `cp -a page.html page_v1_<原形态>.html.bak`，然后**删掉旧文件再 `write_file`**。
  `write_file` 会拒绝覆盖「本任务只 patch 过、没读过全文」的文件（报 `has not seen its full current content`）——
  守卫按“本任务是否读过全文”判，跟备份在不在无关；要么 `read_file` 全量读一遍再写，要么 `rm` 后当新文件写（备份已在，可回滚）。
- **别用 terminal heredoc 拼 python 批量补丁脚本**: payload 里同时出现 `"""`、`'''` 和中文引号时会被 shell/python 的引号打穿（实测直接 SyntaxError，白跑一轮）。批量改页面用 `patch` 工具逐条改，或 `write_file` 落一个 `.py` 再跑。

## 3. 渲染骨架 (不引 CDN, 单文件自包含)

边缘/产线环境常无外网 ⇒ 不要引 three.js CDN。用 2D canvas 自己做投影, 一页 30KB 以内:

- `buildCam()`: 由 `yaw/pitch/dist/tgt` 算 `eye / fwd / R / U`, 焦距 `F = min(W,H)*1.3`, 中心按**安全区**而不是画布中心 (见 §4)。
- `pr(P)`: 视线空间 z, `z<0.06` 返回 null (背后不画), `u=CX+F*x/z`, `v=CY-F*y/z`。
- **画家算法**: 每个面/线 `push(depth, fn)` 收集, 画前按 depth **降序**排序再执行; 文字单独一个队列最后画。
- `box(x0,y0,z0,x1,y1,z1)` 只画 5 个可见面, 按法向给不同明度 (顶 1.0 / −Y 0.78 / +Y 0.68 / −X 0.72 / +X 0.86), 立体感立刻出来。
- 动画: 一个状态机 + 平滑插值 (`q += (qTarget-q)*min(1, dt*k)`), 别用固定帧数假设。
- 机器人用**平面 2 连杆 IK** (够了, 别上完整 DH): `q0=atan2(dy,dx)`; `d=hypot(r,dz)` 夹在 `[|L1-Lt|, L1+Lt]`;
  `q2=acos((d²−L1²−Lt²)/(2 L1 Lt))`; `q1=atan2(dz,r)−atan2(Lt·sin q2, L1+Lt·cos q2)`, 工具与第二连杆共线 (`Lt=L2+L3`)。
  路径点先到目标上方 0.2~0.3 m 再下压, 否则连杆会穿过工装。

## 4. 取景必须自适应 (否则窄窗口裁角、宽屏又太小)

固定 `dist` 一定会出事: 同一份场景在 1280 宽和 3000 宽下, 一个裁掉角点, 一个缩成一点。做法:

- 取设备外廓 **8 个角点**, 对 `dist` 二分 (24 次), 每个候选都**遍历一整圈 yaw** (步长 π/12), 全部角落进框才收窄 ⇒ 任何自转角都完整。
- 「进框」判据用**安全区**而不是画布: 宽屏时左右有信息面板 ⇒ `SAFE={l:330,r:352,t:104,b:62}`, 投影中心和判据都按它算,
  场景就不会被面板压住。
- 只在**视口尺寸变化**或点「复位视角」时重算; 用户滚轮缩放后 `userZoom=true`, 不再抢他的取景。

## 5. 标注: 优先级 + 贪心防重叠

场景标注一多必然叠字, 叠上去比不画更糟。规则:

- 每条标注带 `prio` (主角产品 0 · 工位 1 · 部件 2 · 仪表/说明 3 · 机架 4 · 坐标轴/地面 5~7), 排序 `prio` 升序、同优先级远的先放。
- 依次算像素框 (含 pill 背景), 与已放框相交就**整条跳过** —— 不画半截、不叠字。
- 相邻工位用**交错高度** (如 i%2 ? +0.34m : 0) 让它们能同时显示; 场景里用**短名** (① FC 拔帽·端检), 全名放侧栏, 兼顾可读与不挤。
- 标注总开关 (用户会想截图干净版)。

## 6. 取证: 判据是像素, 不是"我 push 了多少面"

- **面数 ≠ 有画面**: 绘制队列是最后统一执行的, 任何一个 draw 函数抛异常 (例如引用了不存在的字段 `S.station` 而常量叫 `C.station`),
  整帧就什么都不画, 而 `faces` 计数照样是几百 ⇒ 只报面数会把全黑页判成成功。
  判据用 `getImageData` 算**非背景像素占比 + 颜色族数** (实测健康页 46%~50% 非背景、22 个色族)。
- 投影自检 (数值断言, 不靠看): Z 向上 ⇒ 顶面 `v` 小于底面 `v`; 8 角点在全 yaw 下都在 `SAFE` 内 (报最小余量 px)。
- 交互自检: 切模式后颜色族要变 (如机器人臂的琥珀色从 0.00% → 0.06%), 目标点与 IK 解的末端差 < 0.06 m。
- 截图: `chromium --headless=new --disable-gpu --no-sandbox --window-size=2400,1300 --virtual-time-budget=6000 --screenshot=<路径> URL`。
  🔴 **输出路径必须指到 `$HOME`**: snap 版 chromium 的 `/tmp` 是它自己的私有挂载, 报 "bytes written to file /tmp/x.png" 而主机上并**没有这个文件**。
- 页面自己暴露一个 `window.__X={ready,stats(),scene(),setMode()}` 探针, 用 `browser_console` 一次拿全 (面数/标注数/fps/语义字段)。
  浏览器工具偶尔报一条 **空 message 的 exception**, 而 `chromium --headless --enable-logging=stderr` 里 `grep -i uncaught` 是 0 ⇒ 那是工具侧伪影,
  用后者定性, 别为它改代码。
- **一页多卡就逐卡取证**: 每个 `canvas` 单独 `getImageData` 算非背景占比 + 亮色包围盒与质心 (主体该占窗口 40%~85%、质心居中); 只报总面数会漏掉“某一张卡黑了”这种最尴尬的交付事故。
- **中文真的画出来了才算**: `tesseract <全页png> stdout -l chi_sim+eng --psm 4 | grep <某句原文>`。canvas 里中文可能因字形缺失/被裁根本没画, OCR 读回原文才是证据。
- **定位“整帧不画”**: 空 message 的异常没有行号 ⇒ 在 `browser_console` 里把每个 draw 函数单独 `try{fn()}catch(e){e.message+' | '+e.stack.split('\n').slice(0,3)}`, 报错那个就是元凶（常见形态: 引用了不存在的字段, 如 `S.station` 而常量叫 `C.station`, 一个字符整页全黑）。
- 全页截图用高窗口: `--window-size=1600,3800` 一屏拍完 N 张卡, 再按 340 px 条带算非背景占比, 每行都该有内容。

## 7. 逐步工艺卡版式（一页 N 个独立三维窗口）

用户说「每一步做一个窗口/工艺卡」「在当前窗口下」⇒ 交付是**一页 N 张卡**，N **严格等于**协议工艺流程的步骤数（协议 9 步就是 9 张），不是一个场景配一份说明。
**迁移/对比卡不是标配**：只有用户明确要求「和机器人/另一种方案对比」时才追加一张（写法见 references §4）；他没要就多画一张，等于把自拟方案塞进客户文档，会被整份退回。

- **一张卡 = 一个 `View` 实例 + 一个 `<canvas>`**: 各自有 `yaw/pitch/tgt` 预设和**自己的主体包围盒 `FOCUS[n]`**，共享一个 `requestAnimationFrame` 主循环。
- **取景二分的是该卡主体** `[[x0,y0,z0],[x1,y1,z1]]`（工位 + 载具 + 动作范围），不是整机外廓: 同一台 3 m 机器塞进 268 px 高的小窗口会缩成一个点。
- **`IntersectionObserver`（`rootMargin:'200px'`）只跑视口内的卡**: N 个画布无脑全跑在 60 fps 下白烧 CPU; 首帧先全 `visible=true` 画一遍, 再交给观察器。
- **卡内四段固定顺序**: 动作分解（一句 `A → B → C`）· 技术细节 4~5 条（型号/数量/行程/阈值/接法）· 参数表 3~4 行（节拍/容量/信号方向）· 标签 + 来源条（`§2.2 第 n 步 / §2.1 / §2.3`）。
- 卡头放 **N 段进度条**标该步位置, 顶部导航 `1..N` 跳转: 用户要按流程看, 不是要一个零件库。
- 动画按**真实动作阶段**切（取料→拔帽→下压→清洗→回位）, 一个周期末段回位; 别用整体自转冒充工艺动作。
- **动作分解 = 协议工艺流程表的原文句子**, 只加 `<b>` 标机构名; 不改写、不合并、不补中间动作。技术细节每条句尾带条款号（`（2.1）`/`（2.3.2）`/`（6.1.2.2）`），交付时能一条条对回去。
- 协议没给的（供电规格/接口类型/力控阈值）写「设计评审确认」, 给了的原样照抄, 一个数都别自己补。
- 🔴 **自拟的“专业感”细节是最贵的错**: 力控阈值(N)、缺陷类型清单(划痕/污点/凹坑)、IL、节拍解耦、先进先出、缓存满停送、换型只改程序 —— 这些协议里没有, 写进去用户一眼判定「你假设的」。
- **交付前跑溯源审计**: 从页面/docx 回读每张卡的「动作分解」逐字比对协议原文, 再全量 grep 自拟术语表（上面那份）, 命中就删; 术语别手误（`NG` 写成 `NC` 这类自检也在这一步）。
- **卡片网格要限宽**: 宽屏上 `auto-fit` 会摊成 4~5 列, 每列只剩 560 px、行宽窄到没法读 ⇒
  `#wrap{max-width:1900px;margin:0 auto;grid-template-columns:repeat(auto-fit,minmax(560px,1fr))}`（3000 px 屏正好 3 列）。
- 🔗 **每张卡要能直链**: 卡容器 `id="c1"…"cN"` + `scroll-margin-top: <吸顶头高度>`(实测 ~62px)。
  不然用户拿 `URL#c3` 进来, 卡头被吸顶导航盖住, 他会以为跳错了卡。回读判据: `location.hash` 正确 +
  卡片顶边与吸顶头底边对齐(不是被压住)。卡片某一节真进了工程(拖进状态空间/绑上任务)时再加一个
  「已接入 <SCN/TASK 号>」徒标, 让页面自己说清哪些还只是展示。

抽取清单与卡片数据模型: `references/protocol-to-process-cards.md`。

## 8. 汇报口径

给 URL (+ 可选 `?mode=robot&spin=0` 之类的参数) · 坐标系一行 · 场景里每个元素对应协议哪一条 · 迁移/对比映射表 ·
实测数字 (面数/标注/非背景占比/最小余量/两种模式的着色统计) · 截图绝对路径 · 如实说明哪些是示意、哪些等真值替换。
不写过程, 不列选项。

模板: `templates/canvas3d_scene.html` —— 投影 + 画家算法 + 自动取景 + 标注防重叠的最小可跑骨架, 复制后往里加业务对象。

## 9. 工艺卡一键导出 Word（页面为唯一真源）

用户看完页面基本都会要「导出 Word」。规则:

- **文字真源只在页面**: 点导出时前端把 `CARDS` + 当前视角 `canvas.toDataURL('image/png')` POST 给同一个服务, 服务端只排版。
  **服务端不存工艺文字副本** —— 存一份就必然出现「改了页面忘了改导出」。
- **中文字体必须显式设 `w:eastAsia`**（`run._element.rPr.rFonts.set(qn('w:eastAsia'), '微软雅黑')`），否则 Word 里回落成等线/宋体, 交付件第一眼就不专业。
- **每张图单独 `try/except`**: 一个 data URL 坏了不许整份导出失败（退化成文字卡）。
- **ASCII 文件名给 `Content-Disposition`**, 中文名交给前端 `a.download`。
- 交付前必须**回读 docx + 转 PDF 验页数**（页数 = 1 封面 + N 卡 + 1 说明）; 只报「文件生成了」不算。
- **改了排版模块要再重启一次服务**: `from x_docx import build_docx` 首次请求后就进了 `sys.modules`, 之后改 `.py` **不生效**（与 HTML 热读相反）⇒ 别在旧模块上反复排查「内容怎么还是旧的」, 也别说「热读所以不用重启」。
- **视图约定不许冒充协议内容**: 截图图题只写「图 N-1 …（三维窗口截图）」; 坐标系、1:1 示意比例只在导出说明里写, 并注明「视图约定, 协议未规定」。
  逐条命令、文档结构与坑见 `references/page-to-docx-export.md`。
- 汇报时给**导出件绝对路径 + 字节数 + 页数 + 图片张数**, 并说明「截图是所见即所得, 想要标准视角先关掉自转再导」。

## 10. 「这个视角重新开一个新页面」= 抽同一份引擎另起一页, 不重抄

用户口径: 「某个三维视角，需要重新开一个新页面」(本项目: 光纤九步场景)。
交付 = 新 URL + 一个吃满屏的大窗口, **几何必须与原来那页同源** —— 另写一份"看起来一样"的引擎, 两页一定分叉。

- **抽切片, 不重写**: 原页的投影引擎 + 场景函数表 + 卡片数据(`CARDS`/`FOCUS`)按**行区间**切出来
  (`execute_code` 读原文件 → 按行切片 → 拼进新壳), 新文件只写壳层(单窗口 / 步进 chip / 侧栏),
  注释里写明「抽自 <原页> §x」。判据: 场景函数与常量**逐字**来自原文件, 不是"我重新摆了一遍差不多"。
- **壳层最小集**: 步骤 chip `1..N` + `◀ ▶` + 键盘 `1..9` / `←→` + 该步的「动作分解 / 技术细节 / 关键口径 / 来源」侧栏;
  `?step=N` 与 `#N` 两10 都要能直达某一步 —— 用户会贴带参数的链接。
- **取景按该步主体重算**: 每步 dist 不同(实测 1.30~1.88 m), 共用一套会让小工序在大窗口里缩成一个点。
- 服务侧只是**多一条热读路由** ⇒ 路由改动要 `restart` 一次, 之后改页面不用重启(见 §2)。
- 入库入口: 原页顶部给一个「🧊 三维视角」按钮 `window.open('/autoLight3d')`, 别只丢一条 URL 让用户手抄。

**取证两条都要, 缺一条就是"没做"**:
- 页面探针 `window.__X={ready, steps(), setStep(n), card(), geom()}`。
  🔴 控制台里**同步连续调 `setStep` 再读绘制队列 = 读到的全是上一帧**, 会得出"九步面数一模一样"的假结论
  ⇒ 每步 `await new Promise(r=>setTimeout(r,120))`(或 rAF 两跳) 之后再采样; 九步的 `faces/labels/dist` 应**互不相同**
  (实测 faces 108~240、labels 7~11)。
- **桌面真窗口证据**(比 headless 截图更贴近他看到的): `wmctrl -lG | grep <窗口标题>` 取几何 → `scrot -o` 全屏 →
  按几何裁剪 → Canny 数边缘像素(实测 3D 区 1390×837、13871 边缘) ⇒ 证明画面在渲染, 不是空白/黑屏。
  只报 HTTP 200 + 面数, 会把白屏/黑屏判成成功。
- 用户屏上要够大: `wmctrl -i -r <winid> -b add,maximized_vert,maximized_horz`
  —— `--start-maximized` 在已有 profile 下可能不生效(实测只开了 912×1072), 当场拍完再量一遍几何。
- 🔴 **验证页面改动前先强刷**: `browser_navigate` 到**同一个 `#hash`** 属于 same-document 导航, **不会重载**
  ⇒ 会对着旧 DOM 判"改了没生效"。带一个自增 query 强刷: `?v=N#1`。
- 🔴 **别关用户手上那个窗口**: 关窗前先 `wmctrl -l` 看窗口**当前标题/URL** —— 他会把你开的 Chromium 拿去搜别的东西
  (实测同一窗口已经变成某供应商产品页)。要验证就用另一个 profile 另开一窗, 绝不对着他的窗口 `wmctrl -c`。

## 11. 侧栏信息栏: 来料产品 → 设备实照 → 该步工艺 (窄栏的排法)

用户会在大三维页旁要「把产品图/参数、设备实拍也放上去」, 并问「怎么跟工艺卡排列」。
顺序固定: **来料产品(做谁) → 设备实照(谁做的) → 该步动作/细节/口径(怎么做)**; 3D 画布永远占主区, 信息栏不抢宽。

- **产品卡先定形态, 再找图**: `MPO-8FC / MPO-16FC` 这类名字 = **一端 MPO 多芯 + 另一端 N 个 FC 的分支缆**。
  拿"两端都是 MPO 的干缆"图去标 `MPO-16FC` 是型号错, 现场一眼就看出来。先确认形态(几个 MPO / 几个 FC / 是否盘缆)再选图。
- **每张图只证明它能证明的事**: 外观图能数出"8 个 FC"; 16 芯的芯孔被端面挡住 ⇒ **芯数以结构图(两端口位 1~16)为准**。
  卡片下方固定一行「图注：…以结构图为准」, 别让外观图冒充芯数证据(会被当成夸大)。
- **窄栏(≈370 px)里图片必须整宽在上、参数整宽在下**。缩略图 118 px + 参数两列并排, 会让值断成两行、说明文字贴到图上。
- 验收用 DOM 行高, 不靠肉眼: `[...document.querySelectorAll('#prodMeta .row i')].map(i=>i.parentElement.getBoundingClientRect().height)`
  过滤 `> 20` 应为空(= 没有断行)。
- 参数压到一行装得下: `插损 MPO ≤0.35 · FC ≤0.30 dB` · `回损 SM ≥60 · MM ≥25~35 dB` · `线径 3.0 主干 / 0.9~2.0 分支 · R≥7.5`;
  标签列 ~56 px, 其余行收进「＋全部参数」`<details>`。
- **现场口径比参数表更有用**: 写「1 件 MPO-16FC = 16 个 FC 端面 = 1 个载具」这类与设备动作挂钩的一句。
- 图片按**型号前缀 + kind** 命名丢进同一目录(`MPO-8FC_实物.jpg` · `MPO-8FC_外观.png` · `MPO-16FC_结构.png` ·
  `MPO-16FC_细节_16FC端子扇形.jpg` · `MPO-16FC_对照_MPO16转2xMPO12_Y缆.png`), 服务端按前缀分组、按 kind 排序
  (**实物 > 外观 > 细节 > 对照 > 结构**)选缩略图 ⇒ 以后只有换图、不改代码。
- **「对照」是独立的 kind, 不是外观**: 别家别的形态的图(如 1×MPO-16→2×MPO-12 的 Y 缆)只能证明"那家的嘴上长什么样",
  **绝不当缩略图、也绝不替代来料形态**; 图注要写"只看 X 端外形"。
- **一张图里出现两件同款产品就淘汰**: 会让人数成"1 件 = 2 根"(实测一张盘了 2 根缆的图直接剔除)。

找图/落盘/验证的完整配方(含被 CDN 403 时的绕法、**从厂商多格总图里裁单格**): `references/product-photo-sourcing.md`。

## 12. 工艺动作链(N 个动作) 与 工位条(M 个站位) 必须两条并排

用户用「动作序列」描述工艺(`上料—拔帽—端面检测—端面清洁—回损测试—盖帽—扫码—分拣下料`), 而三维场景是按**站位**分步的(9 步工位)。
两者不是一对一: 一个工位干多个动作, 一个动作跨多个工位。光把 9 步 chip 摆上, 用户会说「这些步骤得表达出来」。

- **两条并排**: 动作条在上(①~⑧ 圈号 + `→` 串, 亮色) · 工位条在下(1~9 序号 + 站名, 灰)。一条讲"做什么", 一条讲"在哪做"。
  动作条用圈号、工位条用普通数字, 视觉上分开 —— 两条都用 1..N 时用户会追问"到底几个步骤"。
- 前端放一张映射表 `ACTS=[{n,name,steps:[工位号...],hint}]`; 点动作 → `setStep(steps[0]-1)`, 切工位 → 点亮所有 `steps.includes(站号)` 的动作;
  侧栏补一行「本工位动作：拔帽 · 端面检测 · 端面清洁」, 让"一站位多动作"不用文字解释。
- 映射依据协议工艺流程表的**说明列**(如"缓存 1 满后推料至缓存 2"), 不是按动作数平均分配站位。
- 🔴 `CARDS[i].n` 常是**字符串**(`n:'4'`), `[4].includes('4')` 为 false ⇒ 动作条一个都不亮、侧栏显示「—」, 页面看着能点其实全错。
  统一 `const n=+c.n` 再比。
- 版面代价要量回来: 动作条约 39 px, 加完回读画布 `clientWidth/Height` 与顶部起始 y, 别把 3D 压掉一截还说没动布局。
- 验收取**点亮集合**而非截图: 进含多动作的工位应一次亮多个(②③④), 进单动作工位只亮一个; 点动作后 `stepName` 要跳到对应站。
