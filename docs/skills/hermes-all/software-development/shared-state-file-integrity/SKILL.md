# 共享状态文件: 条目"消失"的取证 + 清理工具的安全设计

## When to Use
- 用户问 **"X 怎么没有了 / 昨天下了怎么看不到"** —— 而 X 的模型/服务/代码都在, 只是画面上/列表里不出现。
- 要写或改**清理、重置、清层、按类别删除**的工具/端点。

## ✍️ 写共享状态文件前: 先看清嵌套层级, 写完用**服务自己的读法**回读 (2026-10-12 自己踩)

症状: 我把恢复后的点位写进 `taught_points.json`, 自己回读一切相符; 但页面/接口仍显示旧值,
一致性检查还报“台账≠L2库”。原因: 该文件真源结构是 `{"points": {点名: {...}}}`,
我写成了**顶层**键 `{"点名": {...}}`。服务只读 `.get("points")` ⇒ 根本看不到。

规矩:
- 写之前先把文件打开看真源结构(一个文件常是 `version/note/frame/points/updated_at` 多层), 别照精脑子里的样子。
- 写完必须用**消费方自己的读法**回读(直接 curl 那个后端接口, 或调服务里那个 `_load_xxx()`),
  不能只看自己的文件 dump —— 自己读自己写的当然对。
- 写错层级会**悄无声息**: 不报错、不丢原值, 只是新值没人看得见(比报错更难查)。
- 覆盖场景先想好回退: 台账/库只存“最后一次”的值 ⇒ 覆盖前确定从哪个同姿态参考点/快照恢复
  (`tools/restore_point_pose.py` 就是为这个写的)。

**值形状也是契约, 不只是嵌套层级**: 往一个已被消费方绑定的 dict 里加参数, 新值必须和它的索引方式同形。
实测形状: `run_cfg` 是一组 `{"label","checked"}` 复选开关, 配置中心逐值取 `v["checked"]`;
往里塞裸 `int/float/str` ⇒ 页面构造抛 `TypeError` ⇒ 整个配置中心页构**建失败**(不是布局变了, 是没建成)。
- **新参数一律开新的同级键**(`task["ar300"] = {...}`), 不拓宽 UI 已绑定的 dict; 下游不读它就不会动布局。
- **不要顺手改 UI 的语义字段**(如 `active_task` = 界面上的“当前活跃任务”)来达成自己的目的 —— 上层链只要拿到
  自己的 `task_id` 就够(GREP 一上实现确认), 改它只会让用户以为界面被动过。
- 判据必须用**消费方自己的验收脚本**(真起页面/真调接口), 不能用“我把 JSON 写对了”代替;
  弄崩后的恢复顺序: 还原旧形状 → 新参数搬同级键 → 跑恢复脚本 → 跑该页判据全绿 → **把修好的真源同步到其它机器**
  (同一份坏数据往往已经推到第二台机了, 别只修本机)。
- 一个多写者共享的 JSON(规格/画布/注册表/缓存)被多个常驻进程与服务同时读写。
- 要判断"这个条目是不是我弄没的" —— 需要证据而不是感觉。

## 铁律一: "没有"有四种, 先分清是哪一种
按顺序查, **不要**一上来重下权重/重装/重启服务:
1. **实物在不在** —— 给路径 + 字节数 + 服务状态, 别用"应该没有"发誓。
   注意"看起来空"的权威来源可能只是**引用桩**: 缓存目录几十 KB 而真权重在数据盘的镜像目录(逐文件复制而不是快照下载) ⇒ 桩是正常的。
2. **条目被抑制** —— 这类文件常带**抑制清单**(`deleted[...]` / 黑名单), 条目被删过就不再出现, 且常被当"负项"传给下一轮生成 ⇒ **只恢复显示而不清抑制项, 它永远不再生成; 只清抑制项而不管错值, 恢复的是错值** ⇒ 两件事一起做。
3. **注册表在但无实体** —— "来源/类别"注册表里有这个名字, 但当前这一轮没有它的实例。注册表存在 ≠ 数据存在。
4. **文件被别的写者整体重写** —— 最常见也最容易被误判成"生成器坏了"。下一个铁律处理它。

## 铁律二: 清点写者 + 用备份链定罪 (不靠"感觉是谁写的")
1. **列写者**: `grep -rIl <文件名> <代码根> | sort`, 然后分两类——
   · **整体重写型**: 命中 `json.dump(..., open(path,'w'))` / 写 tmp 再 `os.replace` ⇒ 它能一次抹掉所有没被它显式保留的东西。
   · **按类别合并型**: 只拿掉自己那一类再加回自己的(`kept = [x for x in old if key(x) != MINE]`) ⇒ 安全。
   速筛: `grep -cE "json\.dump|open\([^)]*<file>[^)]*,\s*[\"']w" <每个文件>`。
2. **常驻者优先怀疑**: `ps -eo pid,etime,cmd | grep <脚本名>`; 进程刚起而文件 mtime 很新 ⇒ 它就是最后写者。cron 也要看一眼(`crontab -l`)。
3. **备份链定罪**: 这类文件通常被工具自己留了 `.bak*`/`bak_<原因>_<时刻>.json`/批次归档 ⇒ 把它们按 mtime 排成时间线,
   逐个统计**同一通道各类别的条目数** ⇒ 一眼看出"什么时候没的"。
   🔴 **先证自己清白**: 在怀疑自己/自己刚做的改动之前, 先把动手前的备份拿出来看 —— 目标本来就为空 ⇒ 不是这一步删的(本类事故里最常见的一次冤枉)。
4. **定罪靠代码 + 备份, 不靠"猜哪个脚本像凶手"**。两个看起来可疑的(名字带 clear/rebuild 的)常常都是安全的;
   真正的凶手往往是**设计上不算错**的那一个(白名单语义), 见下。
5. **同一脚本跑着多个实例 = 最隐形的写者**。重启/重跑常留旧进程: 旧实例用旧 schema 覆盖新实例写的字段,
   现象是"刚加的字段过一会儿就没了"(实测 `skill_phys.json` 的 `a/b/c` 被旧实例整段覆盖回退)。
   核对: `pgrep -af <脚本>` 看**进程数**, 并逐一看 `/proc/<pid>/cmdline` 与启动时刻; 不是"有进程在跑"就算对。
   重启脚本必须: ① 先杀到 0 个 ② 只启 1 个 ③ 启动后回报实例数与 pid ④ 再回读文件确认新 schema 真落盘。
   🩸 别用宽泛的 `pkill -f <脚本名>` 收工: 命令行里含该字样会**匹配到自己/自己的 bash 包装** ⇒ 整条命令被 SIGTERM 打断
   (现象: exit -15, 后面的验证全没跑)。判定条件用 `/proc/<pid>/comm` 必须以 `python` 开头 + cmdline 含脚本名, 两个都满足才杀。

6. **原子写的 tmp 名必须带 pid**: 固定 `<target>.tmp` + 两个进程同时写 ⇒ 后者的 `os.replace` 先把 tmp 搬走,
   前者的 `os.replace` 抛 `FileNotFoundError` (常被上层 catch 成一行日志) ⇒ **那一次写静默丢失**。
   改法: `tmp = "%s.tmp.%d" % (path, os.getpid())`; 同一目标并发写还要在 replace 前重读合并, 否则就是"最后写的赢"。
   证据口径: 日志里出现 `os.replace` 的 FileNotFoundError 就是它 —— 别归因成"文件系统抖了一下"。

## 铁律三: 清理工具必须黑名单语义 (默认保留, 只删点名的)
```python
# ✗ 白名单: 任何没被枚举过的新类别静默消失, 且每次运行再杀一次
kept = [x for x in items if category(x) in KEEP]      # KEEP = ("meas",)

# ✓ 黑名单: 新上线的能力默认免疫
kept = [x for x in items if category(x) not in CLEAR]  # CLEAR = ("vlm","det","plan",...)
```
**为什么**: 白名单把"保留=必须被记得"当成了前提, 而新能力上线时没人会回来改那张名单 ——
于是新类别被删得干干净净, 而且**下一次清理还会再删一次**, 表现为"这东西怎么老是没了"。
- 工具的 docstring 里写明: 保护清单是什么、"新增类别默认免疫"这条语义。
- 删除前**归档 before 快照**(`cp` 到按时刻命名的目录), 并在回复里给出归档路径。
- 同一守则适用于一切"按类别保留"的删除: 配置清理、缓存回收、标注/数据集过滤、注册表裁剪。
- ⚠ 反向的"用户可见动作"也要直接落盘: 用户点"清除"时必须在**服务/工具侧立刻改文件**,
  不能把可见结果托给下游某一轮发布 —— 下游一死, 用户看到的就是"点了没用"。

## 铁律四: 这类工具必须能演练 + 真跑验证
- 给 **`--spec <副本>`**(或等价的路径开关) + **`--dry-run`**, 才能在**不动在役文件**的前提下验证语义。
- **验过 = 在副本上真跑一遍并断言**, 不是读一遍代码、也不是只过语法检查:
  造一个含**三类**条目的合成副本 —— 受保护类 · 点名要清的类 · **未登记的新类** —— 跑完断言:
  受保护类在 · 未登记新类**也**在 · 点名的被清。把断言结果写进回复。
- 改在役文件前 `cp` 备份, 改后**回读计数**。

## 铁律五: "收进统一库"后, 库里的运行时表不许被 build 清空
把散落文件收口进一个**生成物**数据库时, 最容易埋的坑是把"运行时写入的数据"跟"从真源重建的表"一视同仁:
- **做法**: 运行时写入的表在 schema 里用 `CREATE TABLE IF NOT EXISTS`(其它投影表照旧 `DROP`+`CREATE`), 生成脚本**不清空它**;
  若还有历史散文件, 在生成脚本开头按**唯一键去重**一次性并入, 并打印并入了多少条, 之后那个文件才可以退场。
  同时给一对读写口 (`log_x(ev)` / `read_x(limit)` / `count_x()`), 避免各写者自理事务。
- **判据 (缺一不可)**: ① 连跑两次 rebuild, 该表行数**不变**; ② 换写口后, 老文件的 mtime **纹丝不动**(这是"写路径真换了"的旁证);
  ③ 真跑一次会写入的业务动作(改一个参数/跑一次判据脚本), 行数按预期 +N。
- 🔴 **读口要一起换**: 改完写口还会剩 GUI 展示/判据脚本在 open 老文件 —— 它们会渲染成"没有记录"/静默按 0 判。`grep -rn <旧名>` 把读写口都扫一遍。

## 铁律六: 冗余件退场 (用户问"这是啥？没用就删掉")
答与做各三步, 不能只删:
1. **答"是什么"带证据**: 内容/格式/schema + 谁写它 + 谁读它 (`grep -rn <名> <代码根>`, 排除 `_archive/` 与日期快照目录)。
2. **判有没有用看"读口"**: 有进程/GUI/判据在读 ⇒ 活文件, 说清"删了会丢什么", **不删**(实测一个 jsonl 同时被 GUI 与库表两处读);
   只有文档引用、无代码读口 ⇒ 可退场。
3. **退场留退路**: 移到 `backups/` 并**写明重建命令**, 不硬删; 然后把**所有引用点同步改掉**
   (README / 设计文档 / 其它技能里的约定); 最后 `grep -rn <旧名>` 复核零残留。
4. **冻结的发布件不碰**: `release_*/`、`data_snapshots/*/` 里的同名文件是那版发布记录, 改了 = 伪造发布证据 ⇒ 保留原样, 只更新"活"文档。
5. 批量改引用时**先替带目录的全路径、再替裸文件名**(顺序反了会拼出双前缀的新路径); 被 `.gitignore` 的文件 `git mv` 会 `fatal: not under version control` ⇒ 用普通 `mv`。

## 铁律七: 给"记录/清除"口开白名单时, 用**一次性名字**做完整往返验证

把某个页面/API 的"记录当前值 / 清除记录"能力**放开到一批新条目**(原来只允许少数几个)时, 验证必须两段, 缺一不可:
1. **dry/演练跑接受-拒绝矩阵** —— 只需证明白名单: 应放行的都放行, **应当继续拒绝的仍然拒绝**(尤其是被别的
   产物引用的那一类: 技能/配方/外部脚本按名字引用它们 ⇒ 清掉 = 在用的回点失效 ⇒ 结论里要写明**为什么这一类不开**,
   而不是默默排除)。dry 只验"门", 不验"写"。
2. **拿一个本批次里没有任何引用的**新名字**走一次真实往返**(如自动命名的第 N 个同类点): 记录 → 断言①库内条目数 +1
   且它出现在动态列表里 → 清除(按页面口径两下确认) → 断言②条目数回到原值、它已消失、**其它条目的值/时间戳逐字未变**、
   ③台账(jsonl)多一行且带是哪一个库的标记、④备份文件存在。做完把备份/台账路径写进回复。
- 单靠 dry 或单靠"文件没变"都不算验过 —— **写入路径只有真写一次才算通**; 而真写只能用**一次性名字**,
  否则会把在用的点位/条目改成当前值(看起来"成功", 实际是损坏)。
- 清除口的语义照旧: 黑名单(默认保留, 只删点名的) + 删前备份 + 台账 + 原子替换; 演练开关(`dry`)必须真的**不落盘**。

## 铁律八: 发布器只 merge 不删除 ⇒ 规格里删掉的键会永远赖在状态文件里

实测: 状态总线 `tools/ar_aoi_bus.py::publish()` 是 `prev.update(signals)`(纯合并) ⇒ 把两条不再要的通道从 SPEC 删掉、
重启进程、live 文件 `ts` 一直在刷新, 那两条**一条没少**(用户下一轮会说「怎么还有」)。重启与整份重写都清不掉它 ——
它不是缓存, 是被合并保留下来的陈旧数据, 所以最难查。
- **修法(已验证)**: 合并前先按**自己那份规格**过滤陈旧键 ——
  `drop=[k for k in prev if k not in KEYMAP]` → 打一行「清掉陈旧信号 N 个」→ 再 `prev.update(new)`。
  判据: 文件里的条目总数下降(实测 130 → 96)· 被删的键零命中 · 规格里的键**一个没少**。
- **通用规矩**: 任何「把本轮快照写回同一份 JSON」的发布器都要先回答「我的规格缩小时, 旧条目谁删?」
  没有答案就是泄漏。
- ⚠ 过滤条件必须用**自己生成的规格表**(KEYMAP/SPEC), 不能用「我这一轮拿到的键集合」——
  后者等于白名单, 会顺手删掉别的写者新加的键。

## 铁律九: 用户能直接编辑的状态, 必须自带快照 + 回退一步

用户拖错一个物体后要的不是"你帮我改回原值", 而是**以后能自己退** —— 任何用户可编辑的共享状态
(画面里的围栏/图层/点位/规格条目)都要有 undo, 否则每次误操作都得靠人工算回旧值。
- **写口一律先快照**: 每个 `add/update/delete/clear/set_*` 在持锁后、读文件前, 把目标文件**原样**复制到
  `<数据目录>/<名>_history/<名>_<时间戳>.json`(+ `.meta` 记动作与时刻), 只留最近 N 份(实测 60)。
  快照失败 `except: pass` —— 历史写不进去绝不能挡住正常写。
- **回退自身也要留快照**: `undo()` 覆盖前再存一份当前态 ⇒ 可连续退多步, 退错了还能撤回;
  不是单向操作。用完的那份要删掉, 否则同一份会被反复"回退"成空转。
- **接口与 UI 同源**: 写口与 undo 走同一套加载-原子替换; 页面按钮旁常驻显示"可回退 N 步",
  用户才知道退到底了没有, 而不是盲点。
- **判据 = 真改一次再退**: 读值 → 故意改 → 点回退 → 读回**逐位相等** + 对象总数不变。
  只断言接口返回 `ok` 不算 —— 覆盖错文件/错版本时它同样回 ok。
- ⚠ 只覆盖**经服务端**的写。前端直接改内存(拖拽/console 改 `enabled`)不落文件就没有快照;
  报"退不回去"先查那次编辑有没有真写进文件。

| 坑 | 症状 | 修法 |
|---|---|---|
| 同一文件连打多个 patch, 两条锚点落在**同一行** | 第二次把第一次刚写进去的内容换成占位/空, 而语法检查仍然过 ⇒ 功能静默失效(该落盘的不落盘) | 同一行只打一次; 改完**回读该区间逐行确认**, 别用语法检查当验过 |
| 用"最新快照/几分钟前读到的值"推理现状 | 与用户/别的进程当前看到的对不上, 结论全错 | 下结论前重读真值文件; 用户可能正在同时改它 |
| 把"注册表里有名字"当成"数据在" | 断言"功能是通的"而实例数为 0 | 分别断言: 注册表命中数 **且** 实体数 |
| 在共享卡/共享服务忙时跑验证 | 失败被归因到被测对象 | 跑前后报出**整机资源占用**(显存/进程表), 说明是独占还是共用 |
| 重启发布器后字段又没了 | 旧实例仍在跑, 用旧 schema 覆盖 | 先断言实例数 = 0 再启 1 个, 启后回读新字段; 杀进程按 `comm`+cmdline 双条件 |
| 用户说“你把结构/界面改了” | 实际是数据驱动的页面构建失败(某字段值形状不对), UI 代码一行没动 | 先 `git status`/`git diff` 那些 UI 文件证明清白, 再跑该页自己的判据脚本取证; 别先解释设计 |
| 自己写 grab/截图脚本去取证 | 页面带定时器/自动 reload ⇒ 离屏 grab 挂住, 拿不到图还赔时间 | 用仓库里既有的判据脚本(它就是真起页面渲染), 它的逐项断言比截图更能说明问题 |

## 回报口径 (用户问"为什么没有了"时)
三段, 先给物证再给结论:
1. **实物在不在**: 路径 + 大小 + 服务状态(带能自己核对的一行命令)。
2. **"没有"的到底是哪一层**: 模型/服务/注册表/图层, 指名。
