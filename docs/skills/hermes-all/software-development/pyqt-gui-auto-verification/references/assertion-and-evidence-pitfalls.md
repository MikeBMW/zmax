# 断言写法与证据采集的三个坑 (2026-09-13 实测, 都踩过)

## 1. `QLabel.pixmap()` 返回对象会随下一次 setPixmap 变动 → 比较必须立刻取标量
```python
# ❌ 错: 两次比较都读到"最后一帧"的宽度 → 误判"倍率不生效"
win.cmb_zoom.setCurrentText("×1"); app.processEvents(); pm1 = win.lbl_img.pixmap()
win.cmb_zoom.setCurrentText("×4"); app.processEvents(); pm4 = win.lbl_img.pixmap()
assert pm4.width() > pm1.width()
# ✅ 对: 立刻取 int
w1 = int(win.lbl_img.pixmap().width())
```
实测现象: `×1:686px ×4:686px` 被判 FAIL, 而独立探针打印 `×1→224 / ×2→448 / ×4→686` 完全正常。
**凡是断言 Qt 返回对象 (QPixmap/QImage/QByteArray) 的尺寸/内容, 先转成标量再比较。**

## 2. 阴性对照法: 证明"修好了"是因为修复真的覆盖了崩溃路径
- 只做正向断言 ("现在渲染不崩") 是不够的 —— 可能那段代码根本没被执行到。
- 做法: 把 monkeypatch 打回**旧实现** → 断言同一路径**确实报错** → 换回新实现 → 断言通过。
  实测教训: 只 monkeypatch 被调函数无效, 因为**调用点**已经改成传正确类型 (int), 旧函数收不到坏类型;
  真要复现必须回到调用点。更省事的等价组合:
  ① 单元级复现坏类型 (`fm.elidedText(text, Qt.ElideRight, 300.0)` 抛 TypeError / 传 300 正常);
  ② 定点调用**该 item 的 paint()** (而不是整窗 render, 后者可能没走到该分支);
  ③ 全场景 `render()` / 整窗 `grab()` 做最终回归。
- 价值: 一次交互里把"根因→修复→覆盖性"三段证据凑齐, 用户质疑时不用重跑。

## 3. 判据批跑: 超时不是失败, 重型判据要给足时间
- 一个判据一轮跑不完(每臂独立进程 / 多场景逐步真跑 / 加载大权重) ⇒ `timeout 300` 报 **exit=124**,
  在汇总表里长得跟 FAIL 一模一样, 但它是**假红**。实测: 卡空闲状态下 900s 仍不够。
- 做法: 批跑脚本用**可覆盖的默认超时** (`local tmo="${ZMAX_JUDGE_TIMEOUT:-1500}"`), 单点小判据再显式给短值;
  定性时先看日志里有没有 ❌ —— `exit=124 ❌=0` = 只是没跑完, `❌>0` 才是真判失败。
- 判据在 GPU 被训练占满时也会因 OOM/抢卡而假红 ⇒ **训练完要复执行一遍**再下结论。

## 4. 判红先换真实会话复现一次, 再定性为产品缺陷
- 离屏 (offscreen) 渲染类判据红了, 先在**真实桌面会话** (`DISPLAY=:0`) 跑同一个探针:
  - 桌面会话也红 + 偏差数值一致 ⇒ **是真问题** (不是离屏伪失败), 按真问题修;
  - 桌面会话绿 ⇒ 离屏路径的产物, 记“离屏不可判”, 别写成产品缺陷。
- 🔴 **别为了变绿把断言改成自证**: 把搜索范围限制到"期望位置附近"这类改法会让判据永远通过。
  要么做真正的分离 (连通域/尺寸/掩膜约束), 要么如实报未定性 —— 宁可是红的真问题，不要是绿的假证明。
- 判据夹具会过期, 且过期是**静默**的: 端点后来真有了、场景不再过曝、数据里不再含那种坏样本 ⇒
  期望的告警不再触发而判红。修**夹具/期望值**, 不要在断言处放宽。

## 5. offscreen 也能拿真渲染证据 (别把 GL 报错当失败)
- 证据链: `widget.grab()` 或 `scene.render(painter)` → `QImage` → `constBits()` → numpy →
  亮像素计数 `int((a.max(axis=2) > 60).sum())` 断言非全黑; 判"真图非黑帧"用像素 `std > 5`;
  同时把 PNG 存盘当交付证据 (报告/回报里给绝对路径)。
- offscreen 下 `GLViewWidget` 会打印 `pyqtgraph.opengl: Requires >= OpenGL 2.1; Found b'4.6 ...'`
  —— 那是**窗口自身 GL 初始化**失败, QPainter / 子控件 / grab 路径照常工作。
  **不要据此下"窗口是空的/3D 不可用"结论**; 真机 GL 行为要用真实 DISPLAY 另验。
- 取像素的标准写法:
```python
img = pix.toImage().convertToFormat(QtGui.QImage.Format_RGB32)
buf = img.constBits(); buf.setsize(img.byteCount())
a = np.frombuffer(bytes(buf), np.uint8).reshape(img.height(), img.width(), 4)[:, :, :3]
```

## 6. 写"界面文案 ↔ 真值"一致性判据: 先把假阳性类别剔干净

界面数字漂移 (手写字符串 vs 库真值) 是最值钱的一类缺陷, 但审计脚本不剔假阳性就没人看了 ——
一轮 19 条里 18 条是噪声时, 真的一条会被忽略。落到脚本里的剔除规则 (每条都实测过):
- **版本变更历史长行**: 同一个文件里往往有几十 KB 的 changelog 叙述, 里面的旧数字是**历史**, 不是界面文案。
  剔除 `len(line) > 240` 的长行; 多行字符串里的短行还要按"解释性措辞"剔 (为什么/以前/之前/旧值/例如)。
  只扫**短行里的字符串字面量**, 不扫注释行 (注释行同样会引用旧数字作说明)。
- **合法的不同口径**: 同一个词在界面上有多个正确分母 (全局 74 / 子系统 30·4·27 / 画布 89 含背景带 / 库 74 非背景带)。
  判据要按**上下文**(同一行的 layer/sys_id/前一个字符串) 选对应真值, 不能拿单一全局值去比所有出现;
  否则会把正确的卡面判成错, 逼着人去改对的代码。
- **演示/状态行的数字**: '一键搭建 (8节点8连线)'、'节点: 0 | 失败: 0'、'L5 节点' 里的数字是**别的东西**, 不是被审的那个总量。
  用关键词白名单 (一键搭建/全览/审计中/…) + 正则 (`L[0-9]\s*节点`) 剔掉。
- 正面做法: 审计先打印**真值表** (每个口径一个数), 再逐条报 `文件:行 文案 → 值 (真值 X)`;
  修完把脚本挂进批跑判据集, 让它在下次回归里自动拦。
- 更彻底的一步是**消灭手写字符串**: 让界面文案的数字从真值实时算 (按唯一依据 mtime 做进程内缓存,
  数据重建后自动失效), 这样一致性从"每次审计"变成"结构上不会错"。

## 7. "界面上不许出现这几个字" 类判据 (禁词断言)

- 用户说"页面上不要显示 X 这几个字, 太显眼" ⇒ 当场落成**禁词断言**: 把对应控件里的文字拼起来,
  禁词列表必须为空, 并挂进批跑判据集。只改代码不写断言 ⇒ 下次有人顺手把那行字加回来, 没人发现。
- 🔴 **判据自测注入的文本不许含被禁词**: 自测常先往被测控件里写一段样本文本再断言, 样本若写成
  "✏️ 人工改写 · 试改一行", 控件上就真出现了那个词 ⇒ 判据自己把自己判红 (实测踩过, 先怀疑产品缺陷)。
  自测文本用中性串, 并在明细里打印"命中的违规词列表", 一眼分清是产品的字还是自测的字。
- **反向检查**: 之前若已有判据断"必须出现 X 标记/文案", 用户的"别显示 X"与它直接冲突 ⇒ 把旧断言**掉头**
  (改成"必须有图标/标记, 且禁词为空"), 不要两处各留一半 —— 一处要它出现、一处不许它出现, 判据集永远半红。
- 控件文字常分散在多个 QLabel ⇒ 取"这张卡/这一行显示了什么"用 `findChildren(QLabel)` 拼接 text,
  只取父控件 `text()` 会漏掉标记与角标, 禁词断言假绿。

## 8. 写类判据必须幂等 —— 判据自己不许把唯一依据当草稿

- 点「写」按钮的判据: 先断言 **控件当前值 == 它要写的那个唯一依据值**, 再点; 跑完读回比对并复原(含 `_updated_at` 之类时间戳)。
- 🔴 踩过的形态: 判据把微调框设成**另一个来源的值**(画布节点快照 1.0) 再点写 ⇒ 那一下真把唯一依据的现场标定值(3.643)覆盖了。
  判据自己制造脏写, 事后"已复原"也不等于无副作用 —— 中途任何异常/中断就留下被改过的唯一依据。
- 更值钱的是把这条断言当**缺陷探针**: 页面显示值本来就应与唯一依据同源; "页面值 ≠ 唯一依据值"一红就直接证明
  "这个页面按一下写按钮会毁掉唯一依据"(而且要在这条路上验: 唯一依据值 3.643 vs 页面值 1.0 的差异必须由页面自己修正,
  不是放宽断言, 也不是让判据先把页面拨对)。

## 9. 精简/字数类判据: 只量 UI 文案, 表格里的数据单列

- 用户说"字太多/精简"指的是**界面文案**(QLabel/按钮/勾选框/组框), 不是表格单元格里的业务数据。
  把表格单元内容算进"字数预算" ⇒ 页面一旦开始显示实时数据(话题列表/参数表)就假红, 逼人去删真数据。
- 落法: `labels_only(w)` = `findChildren((QLabel, QCheckBox, QPushButton, QGroupBox))` 的 text 长度和;
  `table_rows(w)` = 每张表行数。断言拆两条: 文案总和 ≤ 预算(并打印最长单条) · **数据行数不比原来少**。
- 按页量取时用 **(显示名, 控件对象) 显式配对**, 不要"索引→属性"循环: 下拉项变了以后会把显示的页和对的一错位,
  量到的是隐藏旧控件的数(看着绿, 实际没量到用户看的那页)。

## 10. 判"这次改动引起的红"还是"本来就红": stash 对照法

- 准备提交/交接时发现无关判据红: 既不要急着改判据, 也不要硬着头皮提交 —— 把自己没碰的那个文件暂存回旧版再复跑一次:
  `git stash push -q -- <file>` → 跑判据 → `git stash pop -q`(再 `diff -q <file> <备份>` 确认还原)。
  两次都红 ⇒ 与本次改动无关, 照实写进交付说明; 只有旧版绿/新版红才是自己引入的。
- 期望值(行数/段数/条数)**运行时从唯一依据算**, 不预先固定字面量: 唯一依据会长(标定段 9→10、性能指标 58 条入库)
  ⇒ 固定不变的判据会在某次唯一依据增长后**静默**假红。
- 证据图/报告产物常落在被 `.gitignore` 忽略的目录(本项目 `reports/`) ⇒ `git add` 里带上被忽略的路径会**整条失败**
  (一个都没加)。提交用显式路径并剔除忽略目录, 证据图改用绝对路径写进交付说明。
