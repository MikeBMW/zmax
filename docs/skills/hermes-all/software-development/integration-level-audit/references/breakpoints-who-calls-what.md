# 断点不进 = 找真实调用点（不是断点坏）

规律：调试器里断点不命中，几乎总是**当前被调试的那个程序不经过这条路**。回答这类问题必须同时给三样：**谁调用** · **何时命中** · **一条可执行路径**。

## 实用做法
1. 全文搜真实调用点：`grep -rn "对象\.方法("` 排除 `def` 定义行与 venv 目录；再搜 `类名(` 找谁 new 了它。
2. 区分**进程边界**：目标代码可能在另一个常驻进程/子进程里（服务、总线、bench 脚本）⇒ 在父进程下断点永远不会进。
3. 看 VSCode **CALL STACK 顶部那个文件**，确认“我现在到底在调哪个程序”；多个调试会话同时挂着时这是最快的判别手段。
4. 断点只在**正在被调试的进程**里生效；空心圆（Unbound）= 文件还没进进程。
5. 高频路径（每步/每帧都过）用**条件断点**或 **logpoint**，否则刷爆。

## 实战例（ManifoldEngine）
`step()` 全仓库只有四处调用：画布节点「🌀 流形引擎」（`nodes/library.py`）· 引擎自检 `_selftest()` · hom 演示循环 · `tools/manifold_engine_bench.py`（独立进程）。
真机 10Hz `tools/tdrive_bus.py` **不调 step()**（它 import `metric_field`，直接算 M·(−∇Φ)）⇒ 在那条链路里的进程下断点永不命中。
⇒ 要停就：跑自检 launch 配置、或单跑画布节点、或给 bench 单独配一条 launch。

## 配套结论
- 「代码在进程里」≠「会被执行」；懒加载也要求入口被调用。
- 想让某段代码在调试时**必被走到**，把它挂在**真的启动路径**上（启动期只读预读这类），别指望某个业务节点被顺路执行。
- 只读取证改动（如启动期预读）才能既拿到证据又不污染唯一依据。
