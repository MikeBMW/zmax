# 元任务：登记表全集 vs 「图像+状态」预测子集（含配置完备性判据）

## 两件东西，别混着汇报
- **全集（登记表派生）**：某任务的元任务 = 任务 `enabled_nodes` → 画布节点 → 功能(module_ref) → fn_id，
  每条带参数/依赖/验证方法/归属层。唯一依据 = 功能登记 json + 任务×节点绑定 json + 画布节点/连线（全是配置，不含图像/模型调用）。
- **预测（感知派生）**：**此刻真该跑的子集** = (真实图像 or 渲染图像) × 在役检测器 × VLM × 引擎状态 → 候选功能的子集，
  每条带 `why/src/conf` + 原始证据（检测框、VLM 原始输出、状态字段+帧龄）。
把全集当预测汇报（“元任务就是这么来的”）会被追问穿——两者字段不同、消费方不同。

## 完备性判据（改画布/登记后必跑）
逐任务比：**元任务数 == enabled_nodes 数**；同时功能 → 画布节点映射率必须 100%（N/N）。少一条就是断链。
断链最常见根因：**登记表按“显示名”精确匹配画布节点** ⇒ 节点改名即断（表现 = 多个任务都少同样的那 1 条）。
修法（durable）：归一化匹配（去括号补充 + 去“接入中/todo”之类尾巴）为主、原名精确为备、**唯一前缀**保障，
输出里带 `match: name|norm|prefix` 供复核；**不要**只把数据里的名字对齐（下次改名又断）。

## 感知派生链路必须如实标降级
图像不可用（全黑/纯色，均值≈0 或标准差≈0）/ 检测器 0 检出 / VLM 未跑语言推理——三者任一都要写进
`degraded` + `degrade_reason`，每条预测标明来源（`state:...` / `yolo:...`）。
这类链路最容易被做成“看着在跑”：真绿只需现场一个动作（开灯/摆件/提曝光），而假绿会一直错到交付那天。

## 取证习惯
每个结论带样本量（n<20 不下结论）、带时间戳/帧龄、带“哪个权重/哪个模型”按真路径 `realpath`，
并把模型列全部类名/后端名写进证据（“2 类=在役、80 类=假件”这种对比可以直接穿）。
