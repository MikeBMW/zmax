# 对外交付/产品文档写作

## When to Use
- 用户要求文档「**不要口语化 / 要正式的产品介绍 / 你要专业**」，或说「**这以后是商品，要销售的**」。
- 要写或改 README、产品手册、规格书、部署说明、投标材料 —— 读者是客户 / 集成方 / 二次开发方，不是自己人。
- 内部口径的文档（含内部称呼、需求原话、吐槽式叙述）要转成对外版。

## 铁律一：先定读者与章节骨架，再动笔
对外文档按**产品手册结构**走，不是按「我这次改了什么」走：
`产品概述(定位 + 产品矩阵 + 核心能力指标) → 系统架构 → 数据模型 → 接口 → 部署与运维 → 治理与质量保证 → 目录内容 → 术语表`。
骨架直接复制 `templates/product-manual.md` 逐节填。

## 铁律二：书面语 + 零内部痕迹
- **不写**：内部称呼或人名、需求原话（如「某人说：…」这类引用）、口语与吐槽（踩过的坑 / 别删 / 拷走 / 咱们 / 搞一下）。
- **可写**：文件路径、命令、表名 —— 但按「读者能照着做」的粒度写；内部代号、内网 IP、凭据一律不写。
- 术语首次出现给定义；同一概念统一写法（别一会中文缩写一会英文）。
- 🔴 **内部架构层级编号与内部机型代号，对外页上一律换成职能语言**：分层编号（L2/L3/L4/L5）、内部版本/机型代号（550A/550B/550C）
  客户读不懂，还暴露内部分工。改写口径：`L5 规划` → 「意图理解 / 规划层」，`L2 检测收口` → 「执行判据（视觉·位姿·力）」；
  `550B 单线程版` → 不写，或写「可单步调试的调试版」。技术选型、竞品对比这类**给客户看的判断页最容易被内部编号污染**，
  因为素材直接来自内部讨论稿。
- **出稿前扫禁用词表**：`grep -cE 'L[2-5]\\b|550[ABC]' <生成脚本>` 必须为 0；词表随项目变，写进交付 README，
  下一轮改版照同一张表扫 —— 只在被点名的那两页改，换页又漏回来。

## 铁律三：每个数字都必须是实测值，且能被复核
- 写数字前**从真源现取一遍**（查表行数 / 跑 `stats` / 看 `--help`），**绝不从旧文档抄** ——
  旧文档里的数字会过期，照抄等于编造（实测：旧文档写「17 项判据」，现场只有 15 项）。
- 文末给一条**复核命令**，让读者也能自己核（如 `python3 <工具> stats`）。

## 铁律四：每条命令先自己跑一遍再写进去
- 旧文档里的命令**经常是错的**：子命令根本不存在、位置参数被写成 `--to` 形式、默认端口记错。
- 判据：文档里出现的每条命令都在本机真跑过一次（带真实输出）；参数形式以 `--help` 为准。

## 铁律五：交付文档要进版本库
- 文档所在目录被 `.gitignore` 整体排除时，用 **`git add -f <路径>`** 强制纳入
  （父目录被排除时 `!data/xx` 这类否定写法**无效**）。
- 纯内部留痕（清理清单 / 取证记录）放 `docs/notes/` 之类，不塞进数据目录。

## 铁律六：写完跑自查，不靠「读着挺正式」
两步，都别省：
1. **数字逐项比对**：写个十几行脚本，把文档里每个数字 / 表行数与真源现值逐项比，不一致就报错；
   同时断言关键数字确实出现在**正文**里（防「改了表忘了正文」）。
2. **口径扫描**：用 `search_files`（或 grep）扫一遍人名 + 口语词表确认零残留；顺手扫已废弃的命令形式（旧文档里的错写法很容易被带进来）。

## 同一交付面要统一口径
改一份文档时若发现同目录 / 同交付面的兄弟文档还是旧的内部口径 ⇒ **一并统一**，并在回复里点明「顺手也改了哪一个」。
两份口径不一的文档摆在一起，比一份口语文档更糟。用户会自己判断要不要保留，说一句就够，**不必先问**。

## 汇报口径
交付时只说三件事：**改了什么 / 核过哪些数 / 还剩什么**；再给一行可选的下一步（对外精简版、PDF/Word 导出之类），不要列长选项清单。

## 坑
| 坑 | 症状 | 修法 |
|---|---|---|
| 照抄旧文档里的数字 | 交付物写着过期的判据条数 / 行数，用户一问就穿 | 数字全部现取；文末给复核命令 |
| 把自拟方案/参数写进客户文档 | 用户一句「不要按你假设的写」整份退回重写 | 只写原文 + 条款号；未定项照原样标待确认；交付前逐字溯源 + 术语扫尾（铁律十一） |
| 照抄旧文档里的命令 | 读者照着敲，命令不存在或参数形式错 | 每条先跑一遍，以 `--help` 为准 |
| 只改被点名的那一份 | 同一交付面两份文档口径不一 | 一并统一 + 回复点明 |
| 把「结构对」当成「能交付」 | 章节齐全但通篇口语/内部称呼，还得返工 | 写完跑铁律六的两步自查再交 |
| 生成器模板用 `%` 格式化**中文**交付文本 | 文本里的「99%**」把 `%*` 当格式符 ⇒ `ValueError: unsupported format character '*'`（`%*` 还会报 `TypeError: * wants int`） | 含 `%` 的中文模板一律**占位符 + `.replace('«ROWS»', …)`** 或 f-string，别用 `%` 拼表 |
| 生成器里写死「任务→场景/名称」字典 | 换成新任务一跑就 `KeyError`；该任务缺登记时表里打出 `None / None (色 None)` | 一律 `.get()` + 回落真源字段，缺登记写「**未登记，需补登记**」，绝不输出 `None` |
| 归档/打包脚本的 glob 只列旧文档前缀 | 本轮新交付件（新 SOR、新场景文档）静默不进归档包，MANIFEST 里查不到还以为保存好了 | 归档脚本**显式列出本轮新增文档前缀**；同一任务多批时间戳的配置单**只留最新一批**（按 mtime 取第一条），否则归档一次膨胀一截 |
| 交付件路径落在**软链目录**下(如 `outputs/` 指向数据盘) | `git add` / `check-ignore` 报 `fatal: pathspec ... is beyond a symbolic link`, 或以为提交了其实根本没入仓 | 入库用**真实路径**(数据盘下那个目标路径)或把交付件按**稳定名拷到 `docs/deliverables/`** 再 `git add`; `outputs/` 只当产物区, 不当入库路径 |
| 从 HTML 直接 `--convert-to docx` | `Error: no export filter for <x>.docx found, aborting.` —— 看着像没装 LibreOffice | HTML 被当成 **Writer/Web** 文档, 那种文档类型**没有 docx 导出过滤器** ⇒ 先转 `.odt` 再 `.odt`→docx（铁律十） |
| md→HTML 渲染器没处理 `**粗体**` | 交付件里满屏字面 `**`, 用户一眼看出「这文档没排版」 | 行内标记先 escape 再替换成 `<b>/<i>/<code>`; 出稿后按铁律十抠字复查残留数为 0 |
| 只核「文件生成了」就交付 | 生成成功但内容是豆腐块 / 空表 / 字面标记 | 抠字自检: `pdftotext` 看中文成串 + docx 解 XML 核关键串与标记残留 |
| 中文字体只报「缺字体」就换方案 | reportlab 找不到硬编码的 ttf 路径 | 换 LibreOffice 链路（吃系统字体族），或按系统**实际已装**的 CJK 字体改路径; 别把「某路径没这个文件」当成「没有中文字体」 |
| matplotlib 出中文图（训练曲线/结果图） | 整图全变方块，**连数字和英文也一起变** —— 不只是中文；scipy 也不报错，只是一个 `UserWarning: Glyph … missing` | 被抓到 `Droid Sans Fallback` 时它**缺拉丁字形** ⇒ 别用它。改用 `NotoSansCJK-Regular.ttc`（`/usr/share/fonts/opentype/noto/`），`font_manager.addfont()` 注册后 `FontProperties(fname=…)` **逐元素显式传**（`set_title/set_xlabel/annotate/legend(prop=)` 都要）；先出一张 4 行字体对照小图选字体，再画正式图 |
| 图“生成了”就直接发给用户 | 脚本零异常、文件也有 KB，打开全是豆腐块/标注指向错误 | **发图前自己看一眼像素**（视觉工具）：中文无方块 · 数字可读 · 标注箭头指向对 · 无截断。字体/版式类问题脚本永远不会报错，只会在人眼里错 |
| 交付件目录里多代版本并存(实测同目录同时躺着五套版本号的文档) | 现场/客户分不清哪套才是本轮有效版, 一句话就要清 | 交付件目录只留**一套当前交付版**，旧版归档到 `release_*/docs/` 此类归档目录并在 README 记位置; 版本号必须**单调且格式统一**(别出现 `X.Y.Z` 与 `X.Y.Z1` 这种会被读成数字拼接的写法) |
| 删旧版本交付件前没查引用 | 交付件文件名被生成器/归档脚本**硬编码**(如 `sor_export.py` · `delivery/gen_*.py` · `archive_release_<ver>.sh`) ⇒ 删了文件那些工具有的失效、有的一跑又把它生回来 | 动之前用 `search_files` 扫工具目录里的该版本号; 默认**先归档不删**, 确认无引用再删, 删除提交里写明原因与去向 |

## 铁律七：达标与未达标**分开写**，硬指标不许柔化
- 验收型文档（测试报告 / 原型验证 / 投标应答）必须把命题逐条列出并标结论：**已证明 / 未证明 / 未达标**。
- 硬指标（成功率、节拍、精度上限）未达到就**原样写实测值与差距**（例：目标 <3s、真源验收 ≤3.15s，实测 3.875 s/颗），
  并给出差距归因与下一步；真源里 `value` 为空的指标一律标「待实测 + 实测入口」，**绝不编造实测值**。
- 理由：用户会拿文档去现场复测，柔化过的结论比一份不好看的真话代价大得多。

## 标准交付工程(整包) —— 版本升级时按这套出

**版本双轨口径**(用户明确要求): **开发版 = 纯数字**(如 `5.50.1`) · **正式发布版 = 带字母**(如 `5.50.A`)。
两者同批出, 发布包内文档标注发布版号。
- **落法**: 生成器出文档时 `--ver` 传**交付版字母**（如 `5.50.C`），真源 `CURRENT_VERSION` 保持**开发版数字**（如 `5.50.6`）；
  文档抬头与包 README **同时写明映射**（交付版 5.50.C ↔ 开发版 5.50.6），归档/发布包按交付版命名。
- 迭代顺序（实测跑通的一遍）：保存/归档数据 → `bump_version.py --to <新开发版>` → 回读全部版本位 → 按新交付版号重出文档 → 分档打包投递+回读 → `git add <本次文件>` 提交 → 打 tag 推 origin。

**① 总配置清单必须「扫出来」, 不手写**
- 写一个生成器(如 `tools/delivery/gen_config_inventory.py`), 逐节从**在役系统**读: 版本位/git tag · 在役服务端口(带 pid)+systemd 单元状态+crontab ·
  配置真源文件(逐个 sha256) · 任务与场景(读绑定文件) · 模型权重(大小+sha256) · 相机通道(实时 fps/帧龄) · 数据空间话题 · 画布规模 · 运行环境(CPU/内存/磁盘/GPU/Python)。
- **跑生成器前先把生成物重建一遍**: 打开/保存总工程(刷新 `.proj`) 就会让单一工程库报 `drift ['project']`, 不重建则清单里的
  关联数/绑定数还是旧的 —— 定式 `python3 tools/engineering_db.py build` → 生成器 → 回读; 库被常驻服务读进内存的, 中间补一次 restart。
- 输出 md(给人看)+ json(给脚本核)。**每个数字都带来源**, 抬头写明「来源: 在役系统扫描, 每个数都可回读复核」。
- 抽「最新版本/tag」时**先正则过滤再排序**: 仓库里常躺着历史怪 tag(如 `vv5.16.35`), 直接取
  `git tag --sort=-creatordate | head -1` 会报到它头上; 用 `^v\d+\.\d+\.\d+$` 筛过再取; 版本号读文件时也别把
  首行标题当版本号(实测 VERSION.md 首行被读成版本 ⇒ 清单写错)。
- 好处: 清单永不过期(改完重跑一次), 且用户逐条追问时每一项都能回读复现 —— 手写清单做不到。

**② 一份事物有多份副本时, 取「被引用方」的那一份**
- 实测: 任务绑定工程声明的画布是 `src/lerobot/engineering/flows/state_space_obs.json`(**89 节点/184 连线**, 带 md5),
  而仓库根另有同名 `flows/state_space_obs.json`(**251/242**) ⇒ glob/取最新会报出错的那个数。
- 规矩: **先看绑定/引用文件里写的是什么、带 md5 没有**, 用它的值; 并在交付文档里如实注明「另有副本 X, 非本次交付所用」。
- 同类: 工具内部字段名要与真源对齐(实测任务字段真名是 `task_id`/`recipe_type`/`scene_ref`/`site`/`ss_mode`,
  自己猜 `id`/`mode`/`scene` 会全表输出 None —— 生成器第一次跑完必须回读一遍输出)。
- 🔴 **生成器自身不许用「取最大 / 取最新 / glob 第一个」挑副本** —— 这种聚合写法会让本纪律在生成器里静默失效(实测:
  对 `flows/*.json` 取 `max(节点数)` ⇒ 清单报 251/242, 而绑定声明的是 89/184, 交付件里的画布规模是错的)。
  副本只能**从绑定/引用文件读**; 并如实注明「另有副本 N 个, 非本次交付所用」。
- 🔴 **计数口径要取自真源的运行时事实, 不要正则数文本行**: 话题数/注册项数这类应 import 真源模块或起子进程实读
  (实测正则抠 `NAME = "zmax/` 只数出 1, 真源实际注册 25 条); 文本扫描只能当兜底, 且回读必须对得上。

**③ 发布包结构按既定约定**(例: `zmax_data/release_<版本>_<日期>/`)
- 目录: 交付文档(`docs/deliverables/`)、源码/工具、配置、证据(`evidence/`)、报告、`MANIFEST.md`(逐件 sha256 清单)。
- 文档清单至少含: 功能说明 · 全系统总配置清单 · 供应商 SOR · 项目立项文档 · 任务配置单 · 原型验证测试报告 · 架构设计。
- 功能说明按「分层能力 + 模块清单 + 配置驱动对照表(改什么→改哪里→怎么生效)+ 验收口径 + 本版新增」写, 不是变更日志。
- 归档用 `tools/archive_release_<版本>.sh`（代码 / 真源快照 / 画布 / 证据 / 报告 / 文档 + `MANIFEST.md` + `sha256sums.txt`），
  复制清单**显式列出本轮新增文档前缀**（glob 沿用上一轮 ⇒ 新交付件静默漏归档）；同一任务多批时间戳的配置单只留最新一批。
  归档目录属数据盘（不进 git），脚本本身要进库，改完重跑一遍让新件入包并回读 MANIFEST 计数。

**④ 版本号写入器的坑: `--summary-file` 只能是「短」摘要**
- `tools/bump_version.py --to <ver> --summary-file <md>` 会把该文件**整篇**塞进 `VERSION.md` 的一个表格单元格
  (换行被压平) ⇒ 拿变更说明全文当 summary 会撑爆表格、无法阅读。
- 正确做法: summary 写**一段**要点; 详细变更放 `docs/release/<ver>_changelog.md` 并在摘要里指向它。
- 改完必回读: 机器可读版本位(界面品牌 QLabel · 窗口标题 ×2 · `CURRENT_VERSION` · version_sync 的 `zmax_ver` · docs_sync 两键)
  + 人读的 `VERSION.md` 行(长度正常) + `py_compile` 一遍。

**⑤ 并行会话/多人同改一个仓**: 只 `git add <自己改的文件>`, **绝不 `git add -A`**; 版本号/tag 串行(同一时刻只有一个会话打 tag)。
提交后别人的在改文件(` M 某文件`)保持原样 —— 这既是避免覆盖, 也是可出示的分区证据。

**⑥ 供应商外发 SOR: 先定采购对象, 需求必须可追溯且可迁移**
- **第 2 章第一张表就是「交付分工」**(供应商交什么 / 我方工程集成与收口做什么), 再写被集成系统的作业条件。
  采购对象是「具身模型」时, 整机采购表**不能**当采购范围用 —— 模板里预置的整机条款会与供货边界(SCOPE_IN/SCOPE_OUT)
  直接矛盾, 交付前必须逐条对齐(实测踩过: 买模型却写着买机器人本体/相机/末端)。
- 除常规章节与附录 A–D, 必带三件: **配置表关联性**(每条要求 → 配置项 ID → 关联模块/能力/验收判据 的追溯矩阵)、
  **架构兼容性**(分层职责 + 硬约束: 不自带坐标系 / 不产底层控制量 / 无否决权 / 参数不得硬编码 / 上报契约)、
  **任务迁移**(同画布下各任务的差异配置 + 迁移不变量 + 迁移步骤 + 判据命令)。
  骨架与逐节内容见 `references/supplier-sor-structure.md`。

## 铁律八：功能级交付文档 —— 每个功能都要有「输入 topic / 输出 topic / 可测指标 / 真收发实测报告」

用户要的交付粒度是**功能**，不是「系统整体」。模板固定成六段，数字全部由生成器从真源同源渲染：
`①目标与达成(硬指标写明 99% 成功率 / 3.5s 节拍 + 实测差距) → ②工程配置(场景切换·空间点位·位置/角度·
性能指标目标) → ③任务配置(调用的工艺技能序列+参数覆盖+档位) → ④功能清单(每行: 详细描述+输入topic+输出topic+
可测量性能指标) → ⑤每功能 topic 输入输出实测报告 → ⑥结论与达成路径+复核命令`。

- **功能 = 可独立寻址的执行单元**(实测取「画布节点」: 89 节点，去掉装饰行后 74 个真功能)，
  **输入 topic = 上游节点输出 topic 集合 + 连线总线**，**输出 topic = `ss/<节点id>/out`**(由引用表(总线注册表)给，不自造命名)。
- **性能指标是功能属性，可共用**: 不同功能可指向同一可测指标(节拍/精度/成功率)，每条功能行都要能指到指标，
  指标必须**可测量且有判据与验证方法**(不要形容词)。
- **KPI 真源要顺着关系链取**: 能力(BO_)→产品特征(功能)→模块(节点)，一层层连，别按名字模糊匹配。
- **摆盘/插拔 = 两份独立文档**，同一套模板由配置驱动；单场景文档只列该场景启用节点，另注明「全量 N 个」。

**「输入输出测试报告」必须是真收发，不是登记核对**（实测口径，可照抄）:
- 逐功能 topic 做 **DDS 往返**: 发布/订阅用**两个独立参与者**(同一参与者内 writer→reader 是本地直投，测不出真实通道)；
  载体用一个已有 IDL 结构(如 `zmax::SSTest`)写探针；判据 `收到 ≥ 发出/2`。
- **订阅端必须挂单播配置**(`CYCLONEDDS_URI=file://<repo>/dds/cyclonedds_unicast.xml`)。不挂 ⇒ 走默认多播 ⇒
  与单播发布端互相发现不到 ⇒ 实测「收 0 条」的**假失败**(实测踩过: 修配置前 0/16 话题有流量，修后 6/16)。
- Cyclone API 名是 `get_matched_publications()/get_matched_subscriptions()` —— **没有** `matched_*` 属性;
  用 `getattr(obj,'matched_x',[])` 会静默返回 0 ⇒ 把「通道通」误判成「通道断」(实测 74/74 被误判成 0/74)。
- 注册但**本刻无发布端**的话题如实写「无流量(未起)」，**不许**用「已登记」代替「实测通过」。

**分档打包与投递**(大交付件的常规形态): 按场景各一档 + 平台/协议一档，每档自带 `README_<档>.md`(目标/实测/清单/复核命令)，
逐档 zip → 逐档发(文字摘要 + zip) → **逐档服务端回读核验**(bytes + sha256)。
飞书文件消息返回值里 **`message_id` 顺序是「文字在前、文件在后」**(文件那条紧跟在 `bytes` 之后)，
拿反了回读会报 `KeyError: 'file_key'` —— 核验脚本参数是 `<文字mid> <文件mid> <本地文件>`。

## 铁律九：配置单先行 · 一份文档覆盖多任务 · 未定义项不代填

**顺序固定：先配置单，再 SOR/交付文档。** 用户说「先有配置单」时，文档里每条任务要求都要能回到配置单：
`tools/config_sheet.py --task <任务>` 从在役真源扫出（画布/参数注册表/标定真源/点位台账），文档 §0 **逐份登记**
配置单文件名 + `sha256` + 画布 `md5`，读者可回读核对；配置单一起随包投递。

**一份文档覆盖多任务**（同工程不同任务，如两个插接类任务出一份 SOR）：
- 章节分两层：**任务级章节逐任务展开**（项目与场景 / 性能指标 / 作业要求(工艺技能序列) / 验收要求，每任务一组，用 `【TASK-xx】` 小标题分隔），
  **平台级章节共用**（采购范围与分工 / 功能清单与接口 / 数据平台 / 交付物 / 待商务项）。
- 实现：不要重写第二套文案 —— **复用单任务生成器的 blocks，按 h2 段切片合并**（`_slice(blocks, "3. 性能指标要求")` 取任务级段；平台级段取第一个任务的），
  再补两段本份文档独有的内容：§0 配置单真源登记、§末 **多任务差异对照 + 迁移不变量**（画布/话题/QoS/安全链不变，换任务只改配置）。
  同一口径只写一次，多份文档不会互相矛盾。

**表里要标每行来源，未定义项不代填**：
- 硬指标（成功率/节拍）行标注为**项目级要求**（对每个任务生效）；其余行标注来源 = 任务真源（`tasks.json` + targets/参数覆盖）或**模板继承项**。
  不标来源，模板继承项会被当成该任务的真源要求交付出去。
- 真源为 `null` / 未登记的项（如某任务插入行程未定义、场景卡片未登记）记「**待现场标定 / 采购附件确认**」并在正文点明；
  **绝不代填一个看起来合理的数值**，也不要用模板值冒充该任务的实测/真源值。

## 铁律九·补：立项/投标类材料 = 项目档案真源 + 导出器，缺口让工具自己报

立项材料(项目需求/验收指标/单价/销量/竞品)最容易变成"手写一版漂亮数字"。本平台已有机制是**填配置 → 生成**:
`config/platform/projects/<PID>.json`(项目档案) → `tools/project_profile.py --show <PID>`(合并+缺口) →
`tools/project_doc_export.py --project <PID> --check|--out`(立项文档/协议，成本与 ROI 现算不手写)。

- **先建骨架再问人**: 档案只写身份(客户/机型/站点/场景) + 每项待填值写 `"待确认"`, 然后跑 `--show`。
  工具会打出 `BOM 项 N · 缺口 M` 并逐条列(如 `commercial/price_schedule` / `market/acceptance`)。
  **把这份工具输出原样交给用户当"你需要提供什么"** —— 比你自己列清单可信, 且不会漏, 也不会多问。
- **overlay 语义 = 深合并, list 整体替换**: 档案里把某项写成 `"待确认"` 会**盖掉基线数字**。要的就是这个 ——
  新项目复用平台基线 BOM 时, 商务/市场段必须显式覆盖, 否则基线里泰国/其它项目的单价销量会被当成新项目的值算进 ROI。
- **商务三项绝不代填**: 单台金额、销量预测、竞品报价只能来自商务/客户; 没有就留 `待确认` 并在正文标注。
  代填一个"看起来合理"的价格, 一旦进立项材料就是编造, 比不填代价大得多。
- **预计时间要拆两段给**: ①技术侧(需求映射/验收指标/技术附件/成本测算/竞品公开信息) 给出可交付日期;
  ②完整包 = 商务三项到位后 1 天合并。回复里把"硬前提是哪 3 项"写出来, 别只给一个笼统总天数。
- 新建档案前先 `project_profile.py --list`: 已有同类项目就复用它的 `pid` 与 BOM 引用, 不要另起一个几乎一样的。
- **成本与 ROI 的口径不写在本技能里**: 分层回本 (A/B/C/D)、客户/我方双 ROI、成交区间 (floor vs ceiling)、
  首台与复制台毛利、模式选择, 一律按 `cost-roi-quote-modeling` 的算法出数; 本技能只负责把它的输出写成正式文档。
  立项材料里的回本年**必须带口径标签**, 不能只写一个最漂亮的数。

## 铁律十：Word/PDF 由 Markdown 派生 —— 走 `md → HTML → LibreOffice`

同一份正文**只维护 Markdown**，`.docx` / `.pdf` 是派生件（别手改 docx，改下一轮就被覆盖）。
LibreOffice **不能直接吃 `.md`**，中间必须过一层自带 `<style>` 的 HTML：

```bash
# ① md → html（自写渲染器，见下）
# ② html → odt → docx      ← 必须两步
# ③ odt  → pdf
soffice --headless --norestore -env:UserInstallation=file://<临时profile> \
        --convert-to odt --outdir <out> <doc>.html
soffice --headless --norestore -env:UserInstallation=file://<临时profile> \
        --convert-to "docx:MS Word 2007 XML" --outdir <out> <out>/<doc>.odt
soffice --headless --norestore -env:UserInstallation=file://<临时profile> \
        --convert-to pdf --outdir <out> <out>/<doc>.odt
```

- **`-env:UserInstallation=file://<临时目录>` 必须带**：否则并发的 soffice 抢同一个 profile，第二次调用会静默失败或挂住。
- **中文字体交给「系统字体族」，不要写死 ttf 路径**：CSS 用
  `font-family:"WenQuanYi Zen Hei","Noto Sans CJK SC",sans-serif`，LibreOffice 会用系统已装的 CJK 字体。
  reportlab 那条路（`docs_pdf.py` 一类）要求**指定一个 TrueType 文件路径**，且**不吃 OTF/CFF 的 Noto CJK** ⇒
  纯 md→pdf 用 LibreOffice 更省事；只有需要精细排版控制时才回 reportlab。
- **导出器写成能独立跑的脚本**（`--out` / `--check` 只校验不出文档 / `--json` 给调用方解析），
  GUI 按钮和命令行**调同一个执行体**，不要各写一套。
- **真源是活页面时不要强行走 md**: 交互式页面（三维工艺卡/看板/看板式报告）本身就是内容真源, 正确链路是
  前端 POST 卡片数据 + `canvas` 截图 → 服务端 `python-docx` 直接出 `.docx`（服务端只排版、不复制文字, 否则必然
  「改了页面忘了改导出」）。`python-docx` 的**中文字体必须显式设 `w:eastAsia`**, 不设就是等线/宋体。
  配方（路由 / 文档结构 / 回读与转 PDF 验页数 / 坑）见 `canvas-3d-scene-page` 的 `references/page-to-docx-export.md`。

### 自写 md→HTML 渲染器的最小规则（没装 markdown 库时）
- 行内**先 `html.escape` 再替换标记**：`**x**`→`<b>`、`` `x` ``→`<code>`、`*x*`→`<i>`。**顺序反了标记会被转义掉**。
- 表格：`|` 开头成行，**第二行 `---` 分隔行要丢弃**；遇到非 `|` 行要补 `</table>`。
- 代码围栏内**只转义不解析**；文档结尾补上未闭合的 `</table>` / `</pre>`。
- `@page { size: A4; margin: 18mm 15mm }` 控页边距；中文正文 10.5pt / 行高 1.55 观感稳。

### 现成的转换器 `tools/md2pdf.py`（别每轮重写渲染器）
- 仓库里已有通用脚本：`python3 tools/md2pdf.py --in a.md --out b.pdf --title "…" --subtitle "…"`。
  自带 A4 中文文档版式（h1 20pt 深蓝 + 2.4pt 金色下划线 · h2 14pt 左金竖条 · 表头 `#1F4E79` 白字 · 正文 10.5pt / 行高 1.58 ·
  `@page margin 18mm 15mm`）、表格/引用块/代码围栏/有序无序列表，并内置抠字自检。新文档先复用它，别再手搓一遍。
- 🔴 副标题要插在**主标题之后**：`pos = body.find("</h1>")` 再插入。直接拼在 body 最前面会跑到标题上方，读起来像页眉乱码。
- 自检退出码就是闸门：中文字 <200 或 markdown 残留非 0 返回 1，可直接串在交付脚本里 `&&` 后面。

### 出稿自检（必做，别只看「文件生成了」）
从产物里把字**抠回来核**：`pdftotext <pdf> -` 看中文是否成串（不是豆腐块/空白）+ 页数；
`zipfile` 读 docx 的 `word/document.xml` 去标签后核字数与关键串；**并核 Markdown 标记残留数为 0**。

## 铁律十一：引用型交付件 —— 照客户原文写，不照自己的理解写

交付物是「按客户技术协议/需求文件出的工艺卡、规格对照、应答表」时，内容是**引用**，不是创作：

- 步骤/要求条目用**原文句子**（只加粗机构名），一条对一条；每条细节句尾标**条款号**（`（2.1）`/`（2.3.2）`/`（6.1.2.2）`），读者能翻到出处。
- 🔴 **原文没写的绝不补**：力控阈值、缺陷类型枚举（划痕/污点/凹坑）、性能上限、更“合理”的流程图、自拟的可选方案（换机器人本体/换轴配置/改节拍）都不要。
  这类“看起来更专业”的补充一旦被识破，整份交付件的可信度归零 —— 用户会直接退回重写（原话：“不要按你假设的机器人写，遵守原文”）。
  协议里根本没有机器人、自己却加了一张“迁移到机器人”的卡，就是这件事的典型形态。
- 协议自己标注待定的项（`型号待定` / `功率【待确认】` / `设计评审阶段确认`）**照原样保留并原位标注**，不要替他填一个合理的数。
- 视图/示意图的约定（坐标系、1:1 示意比例、颜色含义）写在图注下或导出说明里，**不要写进图题或正文当作协议结论**。
- 交付前必跑**逐字溯源 + 自拟术语扫描**，比对基准是用户贴的原文，不是自己生成脚本里的字符串；命中的删掉。

## 铁律十二：PPTX 交付件 —— 先保“可编辑”，再过“版面三道闸”，最后挂预览

用户要的是**能自己改的 pptx**，不是导出的图片。同一份内容做幻灯时（分析报告、格局分析、汇报材料）：

- **台账只一份真源**（`roster.json` 这类）+ 生成脚本（`*_figs.py` / `make_pptx.py`）；脚本里不写死任何数字，
  改数只改 json 再重跑 —— 否则同一个数在表、图、正文三处各说一套。
  🔴 **改了「生成 json 的脚本」（`data_*.py`）必须重跑它本身**：只改 .py 不重跑，json 还是旧值，
  而图从记录重算 ⇒ 同一页里正文写「9 家」、图上写 10 家。verify 脚本要从 json **重算**关键计数，
  并在 deck 全文 grep 被取代的旧值（“只有 9 家”这类句子），命中就 fail。
- **每个 page builder 必须自己 `new()` 出这一页，不能接收上一页的 `s` 往里画**：接收 `s` 的 helper 一旦被调用方
  传入上一页的 slide，几页内容叠在同一页上，`len(prs.slides)` 比声明的 TOTAL 少（实测 33 声明 → 29 产出），
  **全程不报错**，每页单看都正常，只有数页数才发现。helper 只收内容参数、内部建页；保存前断言
  `len(prs.slides._sldIdLst) == TOTAL`，并把 TOTAL 同时喂给页脚页码函数。
- **`add_shape` 自带主题 `effectRef` 阴影**：只设 `shape.shadow.inherit = False` 不够，LibreOffice/WPS 仍按
  `<p:style>` 给每张卡片、每个色块渲染脏灰投影。要连 `p:style` 一起摘（`sh._element.remove(st)`，`st` 为
  `qn("p:style")` 节点），之后 fill/line 必须显式给 —— 不再继承任何东西。
- **`vertical_anchor` 收的是 `MSO_ANCHOR` 枚举不是整数**：`tf.vertical_anchor = 2` / `cell.vertical_anchor = 2`
  直接 `ValueError: 2 is not a valid MSO_VERTICAL_ANCHOR`，写 `MSO_ANCHOR.MIDDLE`。
- **表格单元按索引打包，错一位不会报错**：把 `rec[8]` 当 `rec[9]` 用，会把“综合判断”整段塞到“技术架构”
  表头底下，JSON outline 读起来毫无异常。生成后必须**读一页渲染图**，逐列核对该列内容与表头是否同一语义。
- **一页 N 张卡横排会把下半页留空**：5 张卡挤在顶部、下面 60% 空白。改 2 列 × 3 行、左图右文的横卡铺满
  12 × 5.1 in 正文区（`cw=(12.09-gap)/2`、`ch≈1.56`、图位 `1.24×(ch-0.22)`）；末页不足 6 张时把空格做成
  图例位，不拉伸卡片。
- 🔴 **配图位放真实产品照，不许用灰框占位**: 用户看到灰框会直接问「怎么没有实际的图片？是显示问题么」——
  「留个框他自己 Change Picture」这个假设不成立。确实拿不到图的少数卡片，**必须在框内写明缺失原因**
  （如「官网未公开 / 产品整机图」两行小字），绝不静默留空、也绝不拿无关图凑。
  抓图实测顺序（30 家覆盖 14 家）：①官网 `og:image`/`twitter:image` ②从 HTML 正则抠
  `img src|data-src|srcset|_next/image`，过滤 `logo|icon|favicon|sprite|qr|banner|placeholder`，
  按 `宽≥480 · 高≥400 · 字节≥35k` 卡质量 ③官网是纯 JS 站点（HTML<3KB 或 403/526）时改抓**非 SPA 的
  新闻站/经销商页**（这些 curl 能拿到真图）。
  ⚠️ 别指望搜索引擎图片接口：Bing/Google 图片在这条网络上是 JS 渲染 + 反爬（取回 112KB HTML 里
  一条 `murl` 都没有），Wikimedia 上这些厂商的产品实拍也基本没有 —— 试一次不通就换新闻站，别反复试。
  图统一处理成卡片比例（如 900×1125），`ImageOps.contain` 等比缩放后居中放白底，**绝不拉伸**。
- 🔴 **套用客户/公司模板 = 派生，不重写**: 已有能跑的生成器时，写个小脚本读旧 `.py` 做**字符串替换**
  产出新版本（配色常量 · `header()` · `footer()` · 表格表头填充/字色 · 图片位函数），每个替换
  **打印并断言 `s.count(old) >= 1`** —— 没命中就是模板漂移，否则会静默跑出旧样式还以为套上了。
  这样页数、结构、原生图表全保留，只换视觉壳，不会因重排丢页。
- 🔴 **客户直接把 `.pptx` 模板文件给你时，做法是「保封面 + 保内容母版 + 克隆母版页」，不是按它的风格重画**:
  打开模板 → 留第 1 页(封面) 与第 2 页(标题 + 整页大表格的内容母版) → 删掉模板原有其它内容页 →
  `clone(母版)` N 次 → 逐页换标题/填表。背景图、logo、页脚版权、页边距全部原生继承，不用猜配色。
- 🔴 **克隆幻灯片必须连 rels 一起复制并保持相同 rId**，只 `deepcopy(shape._element)` 的话，形状里的
  `r:embed="rId3"` 在新页 rels 里不存在 ⇒ **logo / 背景图静默丢失**（不报错，只是图没了，肉眼一看才发现）:
  ```python
  for rId, rel in list(src.part.rels.items()):
      new.part.rels.add_relationship(rel.reltype,
          rel.target_ref if rel.is_external else rel.target_part, rId, rel.is_external)
  for shp in src.shapes:  new.shapes._spTree.append(copy.deepcopy(shp._element))
  bg = src._element.cSld.bg
  if bg is not None:      new._element.cSld.append(copy.deepcopy(bg))   # 背景图也在 cSld 里
  ```
- **克隆完三件回读判据**：① 每页 PICTURE 数 ≥ 母版（封面 6 / 内容页 1 logo）；② 每页标题命中（模板标题常是
  AUTO_SHAPE 不是占位符，按「top<1.0in 且有文字」找、别按 placeholder 取）；③ 表格底边 ≤ 页脚 y
  （7.5in 页、版权在 7.11 ⇒ 底边 ≤6.9）。行高别用 `min(0.52, …)` 兜底，那会在表格下方留半页白���；
  按 `min(0.78, 5.55/rows)` 撑满正文区。
- **模板里的 logo/页眉优先用原生文字复刻，不裁图**: 模板的 logo 常是 layout 里的位图，抠出来分辨率差
  且不可编辑；用「黄竖条色块 + `ReinBee` 15.5pt 粗体深蓝」+ 右上灰色英文口号 8pt 右对齐复刻，视觉一致且
  用户能直接改字。模板原件在 `~/zmax_data/deliverables/模板.pptx`（ReinBee 汇报模板：白底 · 深蓝 `#1F4E79` ·
  明黄 `#FFC000` · 表头深蓝白字 · 页脚 `© ReinBee All Rights Reserved.` + 页码 · 封面右上黄蓝双圆 + 左下蓝点阵）。
  套完把配色常量也收敛：我方标识别再用紫色，改模板黄系深金 `#B37F00`（白底可读且不撞蓝黄）。⚠️ 深色/装饰圆叠上去会盖住英文 —— 封面单独画品牌行，别直接复用带英文的页眉函数。
- **极坐标/雷达图别用 `bbox_inches="tight"`**：轴刻度标签画在 axes patch 外侧，会被画布边缘裁掉一半。
  这类图存图不带 tight、靠 `subplots_adjust` 留边，2×3 网格 `hspace≈0.58`，否则上排底标签撞下排标题；
  轴名用短词（场景/模型/数据/本体）。
- **像素复检要独立**：`soffice → pdftoppm -r 110` 出页图，交给独立视觉复核，问题清单枚举（溢出/重叠/行高/断词/豆腐块/表头与内容错位/同页数字自相矛盾），
  允许逐页回 `Pn: OK`、并要求像素量化；改完只复检改动页。判**渲染后的页**，不判源图。
  **30 页以上别顺序看**：把 PNG 切成三段并行派三个**只读**子代理，要求回 `页码｜位置｜缺陷｜严重度`；
  全回齐后一次性批量修 —— 同一个缺陷（一个阴影、一列宽度、一处标签偏移）通常在十几页重复出现，
  按单页报告修会重生成三次。
- **可编辑性 = 文字是 textbox、明细是 `add_table`、图是 `add_chart`**：标题正文用 `add_textbox`、明细用
  `add_table`、口径写 `notes_slide`。**数据图必须是原生图表对象，不能是 matplotlib 出的 PNG** ——
  「图里只放图形、能改的字都放文本框」这条不够：用户拿到 deck 第一件事是删行、改数、换配色，
  PNG 让他从零重画，必被退回（原话：「PPT的图表，要可以编辑。我看你的图表是图片，我无法二次编辑」）。
  `add_chart` 为每个图表内嵌一份 XLSX，右键「编辑数据」真能改；判定：
  `unzip -l out.pptx | grep -c 'embeddings/'` 等于图表数（少一个就说明那张图没带工作簿）。
  反过来，**2×2 矩阵、分档清单这类没有数据表可编辑的判断图，用形状+文本框**（能拖、能改色）比 chart 更自由。
  逐图配方（条形/柱状/折线/雷达、对数轴、逐点分色、定性分档堆叠、圆点标签不压点）见
  `references/native-charts.md`。
  中文必须同时设 `a:ea`（`run.font.name` 只管西文），否则字形回落成主题字/方块。
- **插图永远 contain + 夹页内**：给 `w` 和 `h` 会拉伸；只按 `w` 推 `h` 会让高图算出 `y+h > 页高` 被裁。
- **图的比例是版面契约**：`bbox_inches="tight"` 会把坐标轴外的 annotate/注脚扩进画布，横版 figsize 可能存成竖版，
  contain 后被压成窄条并撞上下面的表格。锁 xlim/ylim、文字留轴内、存图不带 tight，并用 `PIL` 断言实际宽高比。
- **碰撞自检要三类**：text↔text / text↔marker（散点压标签）/ text宽↔patch宽（段内标签溢出色块）；只比文字对文字会漏。
- **回读断言再交付**：逐 shape 验 `left/top/left+width/top+height` 不越页（通顶装饰条按 shape 名白名单跳过），
  并打表格底距页脚（> 约 0.2 in 余量）；表格离页脚太空就抬 `row_h`，不塞废话。
- 🔴 **目检只给方向，收敛靠像素量化**：视觉复核会说「文字偏上，上下留白 3:1」，但按它的建议直接改色块高度容易过头 ——
  实测把衬底块收 0.05 in，文字就被顶到块底只剩 3px。定式：用 PIL 扫页图，
  ① 按底色容差匹配衬底块的行范围 `abs(im-bg).sum(2)<10`，② 块内 `>60` 算暗像素并**排除左侧竖条装饰**
  （否则每行都被判成文字行），③ 取文字行范围算上下留白，**比值落在 0.7~1.5 且下留白 >8px 才算过**。
  实测可达 21px/21px（比 1.00）。配方代码：`references/editable-pptx-delivery.md`。
- **衬底块高度由渲染后的文字像素反推，不要按 inch 估算**：改块高或改文字框 `y` 都会让文字重排，
  改完必须重新 `soffice → pdftoppm` 再测一次；同一个块连续调三轮才平很常见，别在第一轮就宣布完成。
- 🔴 **同族表格用同一套列宽比例**：相邻两页表格首列差一寸（1.05 vs 1.38 in）就会让其中一页的长标签
  断成孤字行（「代表（本报告样」+「本）」），客户一眼就看到。首列宽度按**最长标签**定，同族页复用同一组列宽。
- **插页要连页码/章节号/文件名一起改**：`header(..., n)` 的页码、`TOTAL`、文件名里的页数都是硬编码；
  插两页后必须顺延后续页的 `n`、改章节 kick（如原「第 7 章 · 策略」→「第 8 章」）、改 `TOTAL` 与新文件名。
  插入位置按**章节逻辑**排（技术选型在策略章之前），不要图省事追加到末尾 —— 否则会出现
  「第 7 章策略 → 第 7 章技术选型 → 第 8 章策略」这种乱序，而页数断言照样通过。
  改完 `grep '^header(' ` 把所有页的章节号+页码打印一遍，回读顺序。
- **能把 pptx 挂进控制台/网页预览**（用户可能明确要求“在评估分析里直接打开”）：服务端子进程转图、
  缓存键 `(文件名, mtime, size)`、原 pptx 当附件下载、缺转换工具要**报错不出空画廊**。
  完整配方（含 PyQt 薄壳与路由）见 `references/editable-pptx-delivery.md`。

## 铁律十三：对外 PR / 融资稿 —— 借竞品稿的骨架，只填自己的实测数

用户贴一篇竞品融资稿 + 一句「参考这个写一篇我们的」时，要的是**同款叙事节奏**和**我方基本面**，不是改写竞品。

- **骨架照竞品的叙事顺序搬**（画面化痛点开场 → 市场缺口 → 产品三件事 → 技术壁垒 → 为什么是现在 → 团队与愿景 → 收在一句金句），
  但每一个数字、每一句判断换我方的真源，绝不把竞品的数字/客户/团队顺下来。
- **三块能力要各配一句「对客户意味着什么」**，不堆名词。工业具身智能的常见三件套是：本体（能感知能受力）· 全技能智能体（一道工序一个大脑，
  换产品不用重写程序）· 多模态数据采集系统（真实产线的数据飞轮）。每块都用「以前怎么做、现在有什么不一样」讲。
- **精密操作段落用一条真实动作链串参数**：抓取 → 对位 → 插入 N mm → 力上限 N → 检测 N 项 → 良品/NG 分流，
  再落到三个真难点（准：来料会偏所以要拍-算-动-再拍；稳：力超限要退回来重新找角度，示教机器人做不到；可追溯：力曲线与检测结果留档）。
- 🔴 **参数全部标注待研发回签**（如【研发确认修订后定稿】），正文与表格逐处标；研发签完再统一去掉出对外版。
  没标就被当成对外承诺，签不回来要返工整篇。
- 🔴 **融资额 / 投资方 / 创始人姓名 / 客户名 / 专利数一律不编**：用 `【…待披露】` 占位，文末给一张「待确认清单」逐项列出。
  这几项是新闻稿最容易被追问的地方，编了就是埋雷 —— 用户对真实性零容忍。
- 交付时把「待确认清单」原样给出，并点明**哪一两项阻塞二稿**（通常是金额口径与创始人实名），不要列长选项。
- 成稿同时落 `.md` 源 + 派生 PDF，两者放同一交付目录，改完重导即可。
