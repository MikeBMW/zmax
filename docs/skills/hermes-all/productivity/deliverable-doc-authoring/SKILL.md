# 对外交付/产品文档写作

## When to Use
- 用户要求文档「**不要口语化 / 要正式的产品介绍 / 你要专业**」，或说「**这以后是商品，要销售的**」。
- 要写或改 README、产品手册、规格书、部署说明、投标材料 —— 读者是客户 / 集成方 / 二次开发方，不是自己人。
- 内部口径的文档（含内部称呼、需求原话、吐槽式叙述）要转成对外版。

## 铁律一：先定读者与章节骨架，再动笔
对外文档按**产品手册结构**走，不是按「我这次改了什么」走：
`产品概述(定位 + 产品矩阵 + 核心能力指标) → 系统架构 → 数据模型 → 接口 → 部署与运维 → 治理与质量保证 → 目录内容 → 术语表`。
骨架直接复制 `templates/product-manual.md` 逐节填。

## 铁律二：书面语 + 零内部痕迹
- **不写**：内部称呼或人名、需求原话（如「某人说：…」这类引用）、口语与吐槽（踩过的坑 / 别删 / 拷走 / 咱们 / 搞一下）。
- **可写**：文件路径、命令、表名 —— 但按「读者能照着做」的粒度写；内部代号、内网 IP、凭据一律不写。
- 术语首次出现给定义；同一概念统一写法（别一会中文缩写一会英文）。

## 铁律三：每个数字都必须是实测值，且能被复核
- 写数字前**从真源现取一遍**（查表行数 / 跑 `stats` / 看 `--help`），**绝不从旧文档抄** ——
  旧文档里的数字会过期，照抄等于编造（实测：旧文档写「17 项判据」，现场只有 15 项）。
- 文末给一条**复核命令**，让读者也能自己核（如 `python3 <工具> stats`）。

## 铁律四：每条命令先自己跑一遍再写进去
- 旧文档里的命令**经常是错的**：子命令根本不存在、位置参数被写成 `--to` 形式、默认端口记错。
- 判据：文档里出现的每条命令都在本机真跑过一次（带真实输出）；参数形式以 `--help` 为准。

## 铁律五：交付文档要进版本库
- 文档所在目录被 `.gitignore` 整体排除时，用 **`git add -f <路径>`** 强制纳入
  （父目录被排除时 `!data/xx` 这类否定写法**无效**）。
- 纯内部留痕（清理清单 / 取证记录）放 `docs/notes/` 之类，不塞进数据目录。

## 铁律六：写完跑自查，不靠「读着挺正式」
两步，都别省：
1. **数字逐项比对**：写个十几行脚本，把文档里每个数字 / 表行数与真源现值逐项比，不一致就报错；
   同时断言关键数字确实出现在**正文**里（防「改了表忘了正文」）。
2. **口径扫描**：用 `search_files`（或 grep）扫一遍人名 + 口语词表确认零残留；顺手扫已废弃的命令形式（旧文档里的错写法很容易被带进来）。

## 同一交付面要统一口径
改一份文档时若发现同目录 / 同交付面的兄弟文档还是旧的内部口径 ⇒ **一并统一**，并在回复里点明「顺手也改了哪一个」。
两份口径不一的文档摆在一起，比一份口语文档更糟。用户会自己判断要不要保留，说一句就够，**不必先问**。

## 汇报口径
交付时只说三件事：**改了什么 / 核过哪些数 / 还剩什么**；再给一行可选的下一步（对外精简版、PDF/Word 导出之类），不要列长选项清单。

## 坑
| 坑 | 症状 | 修法 |
|---|---|---|
| 照抄旧文档里的数字 | 交付物写着过期的判据条数 / 行数，用户一问就穿 | 数字全部现取；文末给复核命令 |
| 照抄旧文档里的命令 | 读者照着敲，命令不存在或参数形式错 | 每条先跑一遍，以 `--help` 为准 |
| 只改被点名的那一份 | 同一交付面两份文档口径不一 | 一并统一 + 回复点明 |
| 把「结构对」当成「能交付」 | 章节齐全但通篇口语/内部称呼，还得返工 | 写完跑铁律六的两步自查再交 |

## 铁律七：达标与未达标**分开写**，硬指标不许柔化
- 验收型文档（测试报告 / 原型验证 / 投标应答）必须把命题逐条列出并标结论：**已证明 / 未证明 / 未达标**。
- 硬指标（成功率、节拍、精度上限）未达到就**原样写实测值与差距**（例：目标 <3s、真源验收 ≤3.15s，实测 3.875 s/颗），
  并给出差距归因与下一步；真源里 `value` 为空的指标一律标「待实测 + 实测入口」，**绝不编造实测值**。
- 理由：用户会拿文档去现场复测，柔化过的结论比一份不好看的真话代价大得多。

## 标准交付工程(整包) —— 版本升级时按这套出

**版本双轨口径**(用户明确要求): **开发版 = 纯数字**(如 `5.50.1`) · **正式发布版 = 带字母**(如 `5.50.A`)。
两者同批出, 发布包内文档标注发布版号。

**① 总配置清单必须「扫出来」, 不手写**
- 写一个生成器(如 `tools/delivery/gen_config_inventory.py`), 逐节从**在役系统**读: 版本位/git tag · 在役服务端口(带 pid)+systemd 单元状态+crontab ·
  配置真源文件(逐个 sha256) · 任务与场景(读绑定文件) · 模型权重(大小+sha256) · 相机通道(实时 fps/帧龄) · 数据空间话题 · 画布规模 · 运行环境(CPU/内存/磁盘/GPU/Python)。
- 输出 md(给人看)+ json(给脚本核)。**每个数字都带来源**, 抬头写明「来源: 在役系统扫描, 每个数都可回读复核」。
- 好处: 清单永不过期(改完重跑一次), 且用户逐条追问时每一项都能回读复现 —— 手写清单做不到。

**② 一份事物有多份副本时, 取「被引用方」的那一份**
- 实测: 任务绑定工程声明的画布是 `src/lerobot/engineering/flows/state_space_obs.json`(**89 节点/184 连线**, 带 md5),
  而仓库根另有同名 `flows/state_space_obs.json`(**251/242**) ⇒ glob/取最新会报出错的那个数。
- 规矩: **先看绑定/引用文件里写的是什么、带 md5 没有**, 用它的值; 并在交付文档里如实注明「另有副本 X, 非本次交付所用」。
- 同类: 工具内部字段名要与真源对齐(实测任务字段真名是 `task_id`/`recipe_type`/`scene_ref`/`site`/`ss_mode`,
  自己猜 `id`/`mode`/`scene` 会全表输出 None —— 生成器第一次跑完必须回读一遍输出)。

**③ 发布包结构按既定约定**(例: `zmax_data/release_<版本>_<日期>/`)
- 目录: 交付文档(`docs/deliverables/`)、源码/工具、配置、证据(`evidence/`)、报告、`MANIFEST.md`(逐件 sha256 清单)。
- 文档清单至少含: 功能说明 · 全系统总配置清单 · 供应商 SOR · 项目立项文档 · 任务配置单 · 原型验证测试报告 · 架构设计。
- 功能说明按「分层能力 + 模块清单 + 配置驱动对照表(改什么→改哪里→怎么生效)+ 验收口径 + 本版新增」写, 不是变更日志。

**④ 版本号写入器的坑: `--summary-file` 只能是「短」摘要**
- `tools/bump_version.py --to <ver> --summary-file <md>` 会把该文件**整篇**塞进 `VERSION.md` 的一个表格单元格
  (换行被压平) ⇒ 拿变更说明全文当 summary 会撑爆表格、无法阅读。
- 正确做法: summary 写**一段**要点; 详细变更放 `docs/release/<ver>_changelog.md` 并在摘要里指向它。
- 改完必回读: 机器可读版本位(界面品牌 QLabel · 窗口标题 ×2 · `CURRENT_VERSION` · version_sync 的 `zmax_ver` · docs_sync 两键)
  + 人读的 `VERSION.md` 行(长度正常) + `py_compile` 一遍。

**⑤ 并行会话/多人同改一个仓**: 只 `git add <自己改的文件>`, **绝不 `git add -A`**; 版本号/tag 串行(同一时刻只有一个会话打 tag)。
提交后别人的在改文件(` M 某文件`)保持原样 —— 这既是避免覆盖, 也是可出示的分区证据。

## 支持文件
- `templates/product-manual.md` —— 产品手册骨架（八章 + 写作红线自查清单），复制后逐节填。
- `references/feishu-file-delivery.md` —— 成稿怎么送到用户手里（飞书文件通道：`im/v1/files` 上传 + file 消息 + message_id；**发完要服务端回读核验**：翻页/按 id 直查/拉文件逐字节比 sha256；文字结论+zip 的交付口径）。
