# 固定相机 AR/VR 叠加底图 (第二台相机 → 叠加层)

## 🧭 坐标系链 (世界/base · tool0 法兰 · tool1 夹爪—模块头) (2026-10-12 老倪现场定的口径)

老倪原话即口径:「世界坐标系; tool0 = 6 轴末端的法兰盘中心点; tool1 = 夹爪夹住光模块 ——
手臂相机看到的屏幕最下方那个小光模块头部的中心点」。

- **真值源 `tcp_out/latest.json` 报的就是 tool1**(珞石 `endInRef`, 控制器 toolset=tool1;
  旁证: `l2_daemon.py` 的 J6 自转公式把上报值当 TCP ⇒ `p_tcp − R_tool·t_tool = 法兰原点` 同一口径)。
- **tool0 = tool1 ⊖ URDF tool0→tool1 固定位姿**(与当前姿态无关):
  `_J6_RPY=(0.03702518, 0.67516757, 2.37524865)` · `_J6_XYZ=(-0.01588615, 0.01834850, 0.25867757)`
  ⇒ 法兰↔模块头 **259.8mm**。算法: `t_tool = R_off^T·t_off`; `p_tool0 = p_tool1 − R_tool1·t_tool`;
  `R_tool0 = R_tool1·R_off^T`。自检: `tools/verify_ar_layout.py`(独立实现逐位对照, 24 项)。
- 服务端 `tcp_ar_server.read_tcp()` 直接回 `frames{base,tool0,tool1}`, 每系给原点 + 三轴单位向量。

### 📌 相机装在腕上 ⇒ tool1 在画面上是**常量像素**（可一次算好、每帧只重画）

手眼外参不变 ⇒ tool1 原点与三轴在**臂相机**的投影像素固定（640×480 实测**未对齐的原始投影**：
原点 (332.9, 41.8)；60mm 轴端点 X→(340.0,108.4)、Y→(225.8,46.7)、Z→(332.5,127.5)，来自
`models/handeye_state.json` + `real_cam_calib.json` 的 K）。⇒ 页面/脚本算一次存常量，每帧只 drawImage 级的重画，零成本不抖；
现场“把坐标系画出来”最直接的是给一张图（`/toolframe.jpg?len=20`）而不是让人去逐个点开关。
⚠ 上面这组数字是**未做头顶对齐、且按 60mm** 的；页面实际画的是对齐到框顶边中点后的原点（实测 (332.4, 0.1)）
与 20mm 轴——改回 60mm 或去掉对齐都会让画面与用户口径不符。

- 🔴 **夹在夹爪里的工件相对腕相机是刚性常量 —— 别建议"抬一下/动一下让目标入画"**：相机在腕上、工件在爪里，
  两者一起动 ⇒ 臂怎么动，工件在画面里的位置与大小都不变（用户会直接纠正「抬一点也没用」）。
  目标出画/过曝只有两条路：**调光**（曝光/增益/补光）或换**另一台相机**看；靠动臂解决是无效建议。
  反过来这正是好处：**量一次常量就够**，每帧重测既没必要又会引入抖动。

- 🔴 **用户目视微调 tool1 原点 ⇒ 落成配置，不写进代码**: 现场直接给量：「绿框有点高，tool1 的原点应该再向画面的上方移 2 毫米」。
  偏移存**一个文件**(如 `zmax_data/ar_state/tool1_refine.json`: `cam_offset_mm:[0,-2,0]` + note)，
  服务端按 `off_base = R_c2b · cam_offset_mm` 加到工件原点，臂相机框与三维视图读**同一份** ⇒ 一次改、三处一致。
  方向口径：**画面上方 = 相机系 y 负**(图像 v 向下增长)；判据 = 加偏移后 tool1 投影 v **变小**
  (实测 39.7 → 36.1，即 2mm @0.55mm/px = 3.6px)，别靠“看着像上去了一点”。
- 🔴 **「绿框不要总跳动，完全可以固定」= 把逐帧检测换成固定几何**：检测(每帧重算) + 目视偏移两套同时跑，框必然跳。
  定式：尺寸+轴向+偏移都从配置读、框只由 `T_base_tool1 ⊗ 常量` 生成，**路径上不跑任何检测**；
  角标写明 `FIXED(+Nmm up)` 便于目检确认版本。检测路径只在“找目标/量尺寸”阶段用，量完就摘。
- ⚠ **“上移 2mm”这类微调必须在**同一条链**上验**：改完导一张 `/box/arm.jpg` 量框像素包围盒 + 重算 tool1 投影 v，
  两个数字都到位才算生效；只改页面看起来更像没改(页面会热读旧值/旧标签页)。

- 🔴 **`handeye_state.json` 的 `T_cam2tool` 口径（一次定型, 别再试错）**: ① 平移是**米**(0.2147), 旁边 `t_mm` 是毫米;
  ② 它存的是「**相机在 tool 系**」的 `M`(`p_tool = M·p_cam`)。投 tool 点用下面这一套, **不要**把旋转取逆:
  `cam_base = P_tool1 + R_b2t·M[:3,3]` · `R_c2b = R_b2t·M[:3,:3]` · `p_cam = R_c2bᵀ·(p_base − cam_base)`。
  **判据**: tool1 投到 **(333.0, 39.7)**, 与本节文档常量 (332.9, 41.8) 吻合; 一旦把旋转换成 `inv(M)` 的旋转
  (位置仍用 `+R·t`) ⇒ tool1 投到 **(−83.7, 1266.3)** 直接飞出画面。两版都能过“残差 0.06mm / z>0”这类合理性检查,
  只有「投出一个已知的常量像素」能判真伪。旁证: 相机原点应落在**法兰外侧 ~127mm**(装在腕上), 若算到 tool1 再往外
  244mm 的另一侧, 就是符号反了。
- 投出的原点与“标注框”常差几个到十几个像素（实测 11.5px ≈ 5mm@218mm）。两者只能有一个是真值：
  按业主口径（TCP=目标头顶中心）把框/坐标系对齐到同一个点，并把差值**写进接口**（如 `align_shift_px`），
  不要默默各画一套。
  🔴 **对齐目标 = 检测框的「顶边中点」，不是框中心**。框中心是模块中段（框高 59px≈54mm 时偏下约 27mm），
  画出来用户会说“原点怎么在模块中间”——细长件的头顶就是 `((x0+x2)/2, y0)`。
  定式：`frozen_box_tip()` 取顶边中点 → 三轴整体平移到它（姿态不变）→ 返回 `align_to="pegtip"` +
  `align_shift_px`（本次实测 `[-0.53, -41.74]`，即手眼原始投影要往上移 ~42px 才到头顶）+ `tip_clipped`。
  框贴顶（`clipped=["top"]`）时头顶已出画，只能给“可见顶边中点”，必须在返回里标出来，不假装是真头顶。
- **轴长默认 20mm，不是 60mm**（用户口径：「不要显示 60mm，改」）。60mm 的三轴在臂相机画面上会盖住整支模块，
  20mm 刚好当尺度尺（实测 1px ≈ 0.9mm）；`/api/toolframe?len=` 默认值与页面请求**两处都要改**，
  否则只改一处 = 页面仍按 60 画。
- 这套装法下 tool 的 X 轴常指向相机、深度方向被透视压扁（X/Z 投影夹角可小到 ~10°）—— 这是正确投影，
  不是解算退化；要用“三轴张开”当验收得换 45° 侧看的机位。

**三维视图规格**(老倪: 「要跟相机的窗口一样大, 现在太小了, 就放在相机窗口的下面」):
`#leftcol` = 相机窗口 + `#vrcard`(三维视图) 同列; 画布 `width:calc(100% + 24px);margin:0 -12px`
抵消卡内边距 ⇒ 同宽; `syncVr()` 把画布高设成 `#stagewrap.clientHeight` ⇒ 同高, 挂在 `applyRot()`
+ ResizeObserver 上。画 base/tool0/tool1 三色轴(红X/绿Y/蓝Z) + 名称标注 + 读数;
`vrFitBox` 把 tool0/tool1 纳入取景(含 base 原点会拉远) ⇒ 关掉 🧭 再『对准轨迹』才拉回只看轨迹。
重画指纹必须含 `quat` —— 只按 xyz 判, 手腕原地转时三维视图会冻结。
**交互: 滚轮必须能缩放**(用户会直接说「现在无法调整」): `#vr` 上绑 `wheel` → `e.preventDefault()` +
`VR.dist *= exp(±0.12)`, 钳到 0.10~4.0m, 必须带 `{passive:false}` 才拦得动页面滚动; 拖动只改 yaw/pitch、
滚轮只改 dist, 两者都不动 `VR.tgt`(用户手调过的目标点不许被自动逻辑覆盖, 自动取景只在规划签名变化时跑一次)。

## 🔩 tool1 处的工件长方体 + 腕上相机的 AR 框(同一几何, 多处投影)

用户口径(他定的就是真值): **tool1 原点 = 工件头中心**; **X = 上表面法向 → 厚度 T**; **Y = 侧面法向 → 宽度 W**;
**Z = 上表面中轴线 → 长度 L**。本体朝**法兰**方向长 ⇒ `sgn = dot(tool0−tool1, Z) ≥ 0 ? +1 : −1`,
长方体的**中心** = `原点 + Z·(L/2·sgn)` —— 原点在长方体**一端**, 不是几何中心。符号每次按真值算, 别预先固定。

- **尺寸放单一唯一依据文件**(如 `zmax_data/ar_state/module_spec.json`: `L_mm/W_mm/T_mm` + `evidence`), 页面/服务只读它;
  **没直测到的维度必须在 evidence 里写明“未直测”**, 不拿标称冒充实测。同一个数要能在三维视图 + 臂相机框 +
  中央相机框**三处同时生效**才算改完。
- **腕上相机没有固定外参**: 它的 AR 框必须**每帧**用 `T_base_tool1 ⊗ T_cam2tool` 现算(服务端出一条
  `/box/arm.jpg`: 抓帧 → 8 角点 → 投影 → cv2 画 12 棱), 不能套“一次标定把外参存下来”那条路; 固定外参只给不在臂上的相机。
- **框只有一半在画面里, 多半是真几何不是 bug**: 相机离工件头仅 ~244mm, 工件沿光轴朝相机延伸 ⇒ 远端角点 z 变小、
  投影冲向画外(实测 8 角点 4 个在 y≈40、4 个在 y≈−90)。先按 z 与光轴夹角核对几何, 再改代码。
- **验收口径 = 框必须套住实物**: 框的像素包围盒与画面里最亮细长件不重合(实测框 x 7~349 vs 亮条 x 594~639)时,
  先怀疑“检测到的不是工件”或“叠加链口径错”, 不许对外说“已对齐”。

## When to Use
- 用户:「应用 VR/AR 技术把机器人工具中心轨迹可视化出来」「在**笔记本摄像头**这个场景上叠加一条看得见的通道」「场景叠加是为了更好地调试算法」。
- 要给一台**不在机械臂上**的相机(笔记本内置、电视顶摄)画 base 系 3D 内容(管道/框/点)。
- 该相机没有内参/外参, 需要判断「能不能画」或现场标定。

## 本机 RealSense D435 = AR 相机 (2026-10-11 落地口径)

老倪把 D435 接上做 AR 底图(不是 UVC 笔记本相机)。四条硬规矩:
1. **设备独占**: 谁起了 pipeline 谁独占 —— 别的进程 `import realsense_source` 会 `Device or resource busy`。
   ⇒ 取帧/检测/反投影**一律走持有它的服务接口**(本项目 8797 `tcp_ar_server.py`:
   `/rs.mjpg` `/snapshot/rs.jpg` `/api/rs_info` `/api/rs_point` `/api/rs_detect`)。
2. **有出厂内参就不解焦距**: D435 彩色 `fx=603.45 fy=602.22 ppx=320.11 ppy=258.20`(640×480, 1mm 深度)。
   解外参只解 R,t(`laptop_cam_solve.solve(..., f_fixed=, cx=, cy=)`) ⇒ 欠定门槛 6 点降到 **4 点**,
   自检实测 `rms 0.0px / dR 0.0° / dt 0.0mm`。
3. **深度是真值, 别猜**: 像素→相机系 3D 用 `deproject(u,v)`(邻域深度中位), 顺手报 `win_valid/win_px` ——
   中心点常常没深度(实测画面正中无回波) ⇒ 报「该点无有效深度」而不是给个 0。
4. **底图可切, 默认由页面自己定**: `loadCams()` 后要立刻把 `IMG_W/IMG_H` 按**当前选中的那台相机**设好
   (标定点按像素存, 分辨率混用必然投影错); `/cam.mjpg?c=rs` 在服务端要**分流到本机流**, 不能走 8791 代理。
   多相机底图(状态空间工程视频源 4 路 + USB D435)的注册表/端点/切法见 `ar-multicam-scene-tagging`。
   UI 入口: 3D 场景第三个按钮「🥽 AR」(原「🧩 力控」位) + 工位总览页 `station.html` 的「🥽 AR 场景」。
   ⇒ **场景按钮的打开语义 = 原样打开目标页 URL**(用户口径: 「点击 AR 按钮, **直接打开** http://127.0.0.1:8797/ar 这个页面」):
   不拼 `?cam=`、也不做前置门禁(先探服务/探不到就 `return` 不开页面 = **点了没反应**, 是 bug)。
   正解 = 先开页面, 相机在线/帧龄作为打开后的**附带回报**(读不到就照实说读不到); 页面必须**无参可用** —— 默认底图写在页面里。

   🔴 **「AR 服务无法打开」的三个真因 (实测, 别再猜)** —— 现场 4 次投诉，日志逐字:
   `🥽 AR 页面没能自动打开(试过 chromium/firefox/xdg-open/gio/webbrowser/Qt 但窗口没出现) …(服务启动后 12s 仍无响应)`。
   1. **判据错: 只认“顶层窗口标题”**。chromium 在**已开着的窗口里新开标签页**时，顶层窗口标题**不变** ⇒
      六个候选全被判"没出现"。⇒ 候选加 `--new-window`（chromium/firefox/chrome）；
      真判据换成**服务侧硬信号**：页面一加载就会拉 `/api/cams` ⇒ 比较启动前后 **到 8797 的已建立连接数**
      (`ss -tn state established` 里含 `:8797` 的行数)，涨了就是真开了（窗口标题只作辅助）。实测
      1.8s 返回 `chromium(页面已连上服务(8797 连接 +10))`（旧法 6 候选 ×6s 全“失败”）。
   2. **服务探测的 IP 是启动时冻结的**：`_LAN=_lan_ip()` 在模块导入时算一次（控制台 08:58 起时默认路由是产线网
      ⇒ 冻成 192.168.23.50），之后网段一变（拔线/换网）就永远不通 ⇒ 回环一直好却报"服务没响应"。
      ⇒ 探测按**回环优先**逐个真探并记住通的 base（`ar_hosts()` → `127.0.0.1` 再 LAN，实测 0.14s 连上）。
   3. **拉起链路本身是三跳保障 ⇒ 10~13s 且经常失败**: 快路径 1.5s → 独立 profile 5s → 全新 profile 保障,
      日志 `zmax_data/logs/ar_launch.log` 逐次记 `窗口 没出现 · spawn 到出窗 12.89s`。
      判据: 服务侧 `/ar` 200 且 **shell 直拉 chromium 同 profile 1s 就出窗** ⇒ 服务没问题, 病在拉起路径。
      定式 = 所有「打开网页」按钮统一走 `_open_page_window` + **独立 snap profile**
      (`~/snap/chromium/common/zmax_<用途>_profile`), 实测 2.0s 出窗; 不要再叠第三跳保障。
      · snap 版 chromium 的 `--user-data-dir` **只能落在 `~/snap/chromium/common/`**; 放 `~/.cache/` 会因 SingletonLock
        静默退出 —— 没窗口、也没报错, 最容易被当成"服务坏了"。
      · stderr 里 `… is not a snap cgroup for tag snap.chromium.chromium` 是**非致命噪声**(手拉也会打),
        别为它改拉起方式、也别拿它当根因。
   4. 验证要**关掉旧窗口再点一次**（而不是在旧窗口还在时点）—— 旧窗口还在时只会走"已在窗口表里(置顶)"分支。
      判据脚本: `~/.hermes/cache/scratch/ar_open_e2e.py`（关旧→真跑→查返回+连接数+新窗口，输出 ✅/⛔ + exit code）。

### 光模块标定能力(与 YOLO 在役权重同源)
`tools/ar_calib_module.py`: `detect`(AR 帧里跑 `models/yolo_peg_live.pt` 软链 → bbox/conf + 深度 3D) ·
`pair`(追加 uv↔base, base 缺省取 TCP 真值, **帧龄>1s 拒收脏点**) · `solve`(≥5 对, 只解 R,t, 落 `cam_calib.json["rs"]`)
· `selftest`。真点采集需要把模块/夹爪停在**已示教点位**(需 8793 运动授权窗)。

🔴 **建管线前先算“目标在画面上占几像素”，不够就别开标**：56mm 的目标在 2.5~3m 外只有 10~55px，
此时任何外参解的误差都大于目标本身。门槛：**目标短边 ≥60px、末端 ≥100px**；达不到就三选一 ——
相机移到 ≤1m、给末端贴 30~40mm 标记（两机都能 PnP）、改人机在环点 8 个夹爪尖。
量化两招：① 按 `f×实际尺寸/距离` 反推应占像素，再与实测检测框比；② 机构动 80mm 看全图变化像素占比，
与静止噪声比（实测 0.95% vs 0.93% ⇒ 无法区分 ⇒ 目标没进有效视野）。
👉 “链上到底该信不信这个检出”的判据（跟着动 / 帧差响应 / 假阳性）见 `live-camera-detector-adaptation`。

5. **判断机位别只看画面中心**: 中心 ROI 的深度常常落在**桌面以上的背景**(墙/窗) —— 实测本台中心 ROI 2.17m
   而我误判成"相机没对着工作区"; 改用**区域 ROI**(`/api/rs_pose?roi=x1,y1,x2,y2`)量料盘区 ⇒ **1.000m · 有效深度 93.7%**,
   与视觉复核(臂 + 桌面 + 两块料盘)一致。⇒ 结论口径: **区域 ROI 量距 + 视觉描述互证**, 单一数字(尤其中心点)不下结论。

6. **检出 0 先做对照实验再下结论**: 同视角、同在役权重, 只变一个条件(曝光 3 档 + conf 0.10 + imgsz 960)——
   实测四组全 n=0 ⇒ 可排除"曝光不够", 但**不能**据此说"权重不认视角"(权重是在臂相机上训的):
   要分清得先把目标放进视野再跑同一条试验。设 `conf/imgsz` 可调(`/api/rs_detect?conf=&imgsz=`)便于这件事。
7. **绿手把锚点会假阳性**: `place_module_boxes.py` 用高饱和绿找模块; 在 AR 相机上绿色实测全落在**绿色工装/支架**上

## 没外参也能画「世界水平」辅助线 —— 但必须过消失点
用户口径: 在笔记本摄像头画面上「定位桌子上面、横梁内部的空间位置, 给我画几条辅助水平线」,
随即纠正: 「画的线不是以相机坐标系为轴, 要以世界坐标系为轴, 要平行于横梁, 你好好研究一下投影关系」。

- 🔴 **「世界水平」≠「图像水平」**: 像素 y 恒定的横线 = 拿**相机坐标系**当轴, 是错的。
  3D 中平行的直线在图像里**交于同一消失点(VP)** ⇒ 「平行于实体 X(横梁/台面边)」的辅助线必须是
  **过 VP 的斜线**, 且层越低/越远越斜。用户说"要平行于 X"时: **先解 VP, 再画线** —— 直接画横线会被当成没干活。
- **解 VP 只用该实体自身的两条平行棱**求交(如梁的上棱亮线 × 下棱台阶), 不用"画面里随便两族线":
  实测上棱 −7.4° / 下棱 −3.1°, 斜率差 0.075~0.09、相隔 ~310px ⇒ 条件数可用, VP≈(−440, 210)。
- 🔴 **病态解不许拿来画线**: 近正视视角下平行棱**近乎平行** ⇒ 两族线求交条件数极差, 三种拟合给出
  **144 / 248 / 286** 三个互相矛盾的答案。判据: 两棱**斜率差 <0.02 或相隔 <100px** ⇒ 报"本视角解不出"
  (宁缺勿假)。同理"地平线"的**位置**也是病态的(它必过 VP 这一点是确定的) ⇒ 不拿它当交付。
- ⚠ **VP 会随单帧噪声漂 ⇒ 必须多帧取中位**: 逐帧 RANSAC 初值 + JPEG 噪声会让同一静止画面的 VP x 漂
  ±150px, 逐帧拟合的倾角重复性只有 ±1~3°(同一层连跑两次 11.1°→8.3°)。定式 = 采样 **N=8 帧**分别拟合,
  对 **(斜率, 截距) 取中位**(各层特征线同样取中位) ⇒ 重复性压到 **±0.5°**: 三连跑实测 VP x = −383/−372/−413、
  空间顶 −2.83/−2.78/−2.98、作业层 +10.42/+10.65/+9.76、空间底 +15.38/+15.64/+14.63。
  ⇒ **交付前连跑三遍比数**(工具侧留 `--frames` 参数) —— 这是"稳不稳"的唯一证据, 别只执行一遍就发图。
- **精度边界如实说**: 取了中位后 VP 也只定到 ±20px 级 ⇒ 倾角重复性 **±0.5°**, 仍**是目视参考、不是量具**。
  要度量级精确就回到本技能的标定路线: 用 3+ 已知 base↔像素点
  解**平面单应**(固定相机看近似平面桌面时最省事的路径), 别指望像素台阶能把精度提到毫米。
- **落地要 2D 折线元素**(轴对齐薄盒天然画不出斜线), 且线要**在真值带画完之后补画**:
  底部真值带不透明、从底部往上铺 ~120px ⇒ 落在带里的线**一个像素都没有**; 核验时"某条线 0 像素"先查这一点,
  再怀疑画法。
- **锚点取强实测台阶, 不取弱拟合线**: 单点 Δ 大的台阶(实测 −29 @y=264)就固定用该 y;
  只有 11/30 内点的 RANSAC 会把锚点拉偏 33px; 拟合的 **x 范围必须覆盖该特征真正存在的区间**
  (拿只存在于左侧的台阶去右侧区间拟合, 拟出来的是别的东西)。
- **核验逐条算倾角**, 不是只数像素: 只取"落在该线 ±3px 内"的像素做直线拟合 —— 按 x 窗口取会把相邻线
  混进来, 实测造成"目标 −2.97° 实测 −0.07°"的**假失败**。判据: 每条实测倾角与目标差 <1.5°;
  并把 VP 位置与各层倾角写进图例/规格 —— 倾角就是"为什么说它平行于横梁"的唯一证据。

### ▶ 「执行轨迹」的起点闸(相对段规划 + 人手动挪臂 = 必须拒发)

规划出来的段是**相对量**(抬升/后退/…), 只在“规划那一刻的 TCP”下有意义。任何执行入口在发第一段之前都要比对
**规划时 tcp0 vs 当前 TCP**: 位移 >5mm 或姿态变化 ⇒ 直接拒发并写明原因(现场会边看画面边用手推臂)。
配 fail-closed 四复核: 规划 ≤30min · 预检 ok · 授权窗有效 · **起点未漂移**, 任一不过回 `{"ok":false,"msg":<原因>}` ——
不满足就拒绝是设计要求, 不是故障。执行器只往**一个** FIFO 写命令, 每段只读执行状态文件判到位才发下一段,
任一段不达位/被拦就**中止余下所有段**。

🔴 **规划前先校验真值年龄, "接口返回了数"不等于当前位姿**: 链路一断, `/api/tcp` 会退回读 `tcp_out/latest.json`

## 📐 三维视图“上下颠倒 / 地平面上天” = 相机 up 向量算反了

用户口径: 「把窗口旋转 180 度, 现在是反着的, 地平面上天了」。这不是 yaw 要转 180, 是**垂直方向反了**。

- **判据(纯数学, 一眼看出)**: 手写 look-at 里 `U = fwd × R` 在 pitch=0 时算出 **U=(0,0,-1) 朝下**;
  正确的是 **`U = R × fwd`**(右手系) ⇒ pitch=0 时 U≈+Z。写错时整个场景上下翻转, 看起来像“地面跑到天上”。
- **数值验收(不靠看)**: 取台面点 `[x,y,z]` 与其上方 +0.2m 的点分别投影, **高的点 v 必须更小**(v 向下增长)。
  实测修正前后: 台面 v=317 不变, 上方点 v 由 **396 → 237** ⇒ 改正后高的点在画面上面。
- **像素验收**: 网格线颜色像素的 `mean_v` 应在下半(`#1b2430` 实测 303), 橙色轨迹 `mean_v` 在上半(183);
  两者倒过来就是还反着。
- ⚠️ 页面顶层 `const/let` 的全局量(VR/TRAJ 等)可直接在控制台读裸名, **`window.X` 是 undefined**;
  自检脚本里要复制 `drawVR` 的投影公式(含 F/CX/CY)自己算, 别指望调内部函数。

## 🦾 机器人外形 = URDF 点云 + 真关节角正运动学 (不是示意块/骨架线)

用户口径: 「三维视图里, 你要把机器人的 URDF 外形渲染出来」。要看到**这条臂的真实外形**。

三件套(缺一条就只是示意):
1. **服务端一次性出外形**: 读 URDF 的 joint 链(6 revolute + 3 fixed) + 每条 link 的 STL, 每 link 降采样 ~220 点;
   `/api/urdf` 返回 `{links[{name,pts}], joints[{parent,child,xyz,rpy,axis,type}], base, tip}` (~47KB) ⇒
   页面**只拉一次**缓存, 绝不每帧传点云。
2. **关节角随位姿一起发**: `/api/tcp` 里加 `joints`(SDK `jointPos` 前 6 个, rad, 与位姿同 5Hz), 别让页面再开一条轮询。
3. **页面 FK + 凸包填充**: `T = 父 · Trans(xyz)·RPY(rpy) · Rot(axis,q)` → 该 link 点云变换 → 投影 →
   2D **凸包**填充 + 描边 + 关节骨骼线; alpha/线宽 ∝ 1/z 体现远近。实测 1540 点 + 10 个矩阵 **0.8ms/帧**,
   2D canvas 足够, 不需要 three.js/WebGL。

🔴 **STL 单位必须自检**: 这套 STL 顶点是**毫米**(某 link 长轴 517), URDF 场景是**米**。不换算就画出 1000 倍的臂:
投影整体飞出画布、几个 link 的凸包糊成一片(看着像"渲染坏了")。定式: 读入后按 |坐标| 最大值判定, >5 就整体 /1000,
并在返回体里报每条 link 的尺寸(米)便于自检(实测 base 0.240×0.173×0.104m、link2 0.167×0.099×0.517m)。

**验收三条, 少一条都会被当没做**:
- 数值: `FK(tip)` 与 SDK 上报 TCP 的欧氏偏差 —— 实测 **2.8mm**(说明关节链/工具链对得上);
- 屏幕: tip 投影点与 TCP 黄点像素距离 —— 实测 **0.6px**;
- 像素: link 填充色像素数 >0(实测 25,583) 且机器人包围盒**完整在画布内**(占高 ~53%)。

取景与开关: `vrFitBox` 要把外形点云一并纳入包围盒(只按 TCP 一个点定视距时臂顶被裁到画布外, 实测 y=-26px);
按包围盒对角线算的视距会让机器人只占 ~1/3 画面 ⇒ 乘 **0.62** 收紧到 ~55%。外形开关单独一个按钮(默认开),
**别并进「🧭 坐标系」** —— 关坐标系时会把机器人一起关掉。

实现细节(FK 矩阵/Rodrigues/凸包/降采样脚本)见 `references/urdf-shape-rendering.md`。

## 🧱 3D 围栏编辑层 (在视图里画长方体/正方体/直线 = 地图围栏, 不许碰撞)

用户口径: 「三维视图里我需要画 3D 对象, 长方体、正方体(输入对角线点的坐标)、直线(可编辑起点和终点);
坐标在 base 世界系里; 你来设计 UI, 要方便在这个场景里增加东西; 这些东西是你的地图围栏, 不能碰撞」。

**数据模型**(唯一依据一个文件, 例如 `zmax_data/ar_rs/fences.json`, 带 `updated`):
- `box`: 两点 = **对角线** ⇒ 存 AABB(min/max); `cube` = box + 边长 (`p2 = p1 + side`, 三轴同加)
- `line`: 两点 = 端点; 判定用**点到线段距离**
- 🔴 **语义分野(用户当场纠正过)**: `box`/`cube` = **围栏**(障碍, 路径绝不穿越); `line` = **轨迹**(可跟随的路径元素), 不是禁入体。
  碰撞闸只对 `box` 生效; 要沿某条线跑时, 该线**必须从这个闸里摘掉**(整条路径压在线上, 逐点判距离必然 <margin ⇒ 被自己的线拒), 定式 = 只临时禁用它本身、跑完 `finally` 恢复 `enabled=True` 并回读确认, 别的围栏照拦。
  命名也跟着语义走: 按钮「➕ 添加元素」(不是"添加围栏"), 面板标题写「3D 元素 · 盒子=围栏 · 直线=轨迹」, 线那一行给「▶ Follow」; 只改代码不改文案, 用户会一直按"围栏"理解然后问"为什么机器人能穿过它"。
- 每条 `{id,type,name,color,enabled,note,at}`, 余量 margin 全局(默认 10mm) ⇒ 判定一律按 **外扩 margin**

🔴 **单位 + “静默加载 0 条”**：`fences.json` 的坐标是**米**（0.27 / −0.44 …），别当毫米用；元素在 `items`。
把围栏当**运动安全闸**用时，解析完必须断言 `len(boxes) > 0` 再放行 —— 实测一次错误的解析（单位 + 字段名同时错）
让守卫拿到 **0 个盒子**，整轮移动全程“通过”，等于**没有安全闸**，而日志/界面还显示闸门存在（比不加闸更危险）。

**UI 定式**(现场要的是"顺手在这里加东西", 不是让人填表):
- 类型两档按钮(▭ 长方体/正方体 · ╱ 直线) + 两组 mm 输入框 ①②
- **`=TCP` 一键把当前真机 TCP 填进 ①/②** —— 最高频操作, 必须有; 否则人得手抄坐标
- 正方体只填边长, 自动生成 ②
- **🖱 点图取点**: 画布点击 = ①, Shift+点击 = ②; 反投影到"当前输入框 Z 那个水平面"(深度由 Z 给, 不从像素猜)
- 每行: 启用勾选 + `编辑` + `删`; 状态条写「✅ 已加 X · 共 N 个 (机器人路径会避开)」
- **直线行再加「▶ Follow」** = 让真机沿这条线往复运动(默认 3 个来回): 点击先问圈数/速度 → `POST /api/fence/follow {id,loops,speed}`
  → 服务端 `subprocess.Popen` 后台拉起 `tools/run_along_line.py --id <id> --loops N --speed S` → 页面每 1.5s 轮询 `GET /api/fence/follow/status`
  显示 `running / done / error` + 终点坐标 + 离两端误差。跑法(为何要 1 个点一段、zone 混合端点、速度钳位)见 `sim-to-real-trajectory-following`。
  - 子进程只认"前置检查通过"才发动作(未授权/非 automatic/不 idle 一律一行不发), **并把拒绝原因写进状态文件** —— 否则页面只会显示 `running` 到天荒地老或一个红字"失败", 用户问"为什么不动"时无从回答。
  - 状态路由**必须 GET 和 POST 都有**(页面用 GET 轮询); 只加在 `do_POST` 里会得到一句 `not found`。
- 渲染: 盒子 = 6 个半透明面**按深度排序** + 12 条棱 + 名称/尺寸文本; 直线 = 粗线 + A/B 端点

**碰撞闸放在"下发前", 不放腿里**(围栏是地图语义, 腿只有轴对齐包络):
- 每段路径先用**当前 TCP + 逐点累加**换成绝对坐标(路径是相对量!), **逐点**判定 —— 只判终点会漏中段穿越
- 任一点命中 ⇒ 整段不发, 并打印撞的是哪个围栏、第几个点/共几点
- 起点已在围栏内: **只放行"末点在围栏外"的往外走段**(脱困), 往里仍然拒 —— 否则臂进去就再也出不来
- 四类决策离线先执行一遍再上线: 外面往里穿=拒 · 里面还往里=拒 · 里面往外=放行 · 外面远离=放行

🔴 **顶层 `let` 状态声明晚于初始化阶段的绘制调用 ⇒ TDZ 把整个 `<script>` 打死**:
页面所有占位都显示 `—`、按钮全无反应, 但**函数声明因提升仍然存在**(`typeof drawFences` = function)
⇒ 极易误判成"后端没数据/服务挂了"。本项目 `applyRot()` 在初始化时就调 `drawVR()` ⇒
`drawVR` 用到的每个状态(FENCES/VIEW/…)**必须声明在脚本最前面**, 不能写在它们被首次使用的函数旁边。
诊断: 控制台跑 `try{ new Function(document.scripts[0].text)() }catch(e){ e.message }` 直接拿真错;
`node --check` 是**过**的(语法合法, 这是运行期 TDZ), 别拿它当"没问题"。

实现细节(接口表 / 反投影公式 / 渲染与 DOM 驱动验收)见 `references/fence-editor.md`。

### 🖱 画布里的选中/拖动/改尺寸(对象要能被鼠标编辑, 不是只能填表)

用户口径:「这个长方体, 应该能用鼠标选中, 能拖动, 改」。四条铁律:

1. **命中测试与渲染必须用同一帧的相机**: `drawVR()` 每帧把投影函数一并存进 `VIEW.pr`,
   命中测试只用 `VIEW.pr` 反算 —— 各自算一份会在相机转动/自动环绕时错位(点击处与所见差几十像素)。
   2D canvas 上的命中判定 = 6 个投影面做**点在多边形内** + 12 条棱的像素距离(<6px), 多条命中取**最近**
   (平均深度最小)那条; 直线用点到线段距离(<9px)。
2. **先判角点, 再选中**: 选中会点亮角点手柄, 若先选中再判角点, 则每一次点击都命中手柄 ⇒ **永远拖不动盒子、只能改尺寸**。
   顺序预先固定: `const wasSel=(FSEL===id)` → 判角点(仅 wasSel 时) → 才 `fenceSelect()`。
3. **手柄只在"已选中 且 投影足够大(两轴都 >36px)"时生效**: 小盒子(60mm 级)8 个角点在屏幕上挤成一团,
   点中心也会被判成拖角点 ⇒ 一拖就把盒子压成几毫米。
4. **角点该改哪一端, 用"与盒中点比较"判断, 不用序号位运算**: 角点数组的顺序(lo/hi 组合)不是规整二进制,
   `(i>>1)&1` 之类的映射会让 x/y 错轴、把盒子压成 2mm。定式: `hi[i] = c0[i] > (p1[i]+p2[i])/2`。

配套(不做就会被当成"拖坏了"):
- **拖动期间暂停列表轮询**(`if(FDR) return;`) —— 2s 一次的刷新会替换 `FENCES` 里的对象, 拖到一半断掉/跳变。
- **存储层归一化 min/max**(add 与 update 都做): 端点填反/拖过头不会存成负尺寸, 页面也不会显示成反的。
- **拖完立刻落盘并把面板数字同步刷新**, 状态条写明「✅ 已保存 X: [..] → [..] mm」。
- **围栏写操作写审计 jsonl**(`{ts,route,id,client,body}`): 条目"莫名消失"时能查是谁在什么时候删的,
  而不是靠猜(现场确实发生过: 一边测一边有别的客户端在点「清空全部」)。
- **默认值别留 `0/0/300`**: 打开页面就把 ① 填当前 TCP、②=①+80mm; 任一边 <5mm 拒加并提示 ——
  否则用户空着输入框点「添加」, 得到一个 800mm 的大盒子, 还以为画错了。

## 交付形态: 三条一起给(缺一个都会被当成"没做")
1. **VR(不需外参, 立刻可用)**: base 系**软件渲染**三维视图 —— 台面网格 + 轨迹管道 + 实时 TCP 十字, 指针拖动可转。
   不依赖任何 CDN/三方库 ⇒ 标定还没做时用户先有东西看。
2. **AR(需外参)**: 相机画面上叠 3D 管道 —— 逐段按**相机系 z 降序(远的先画)**、线宽 **∝ 1/z**、沿程颜色渐变、
   每 N 点画一个**截面环** ⇒ 才有"走过的通道"的立体感。实测轨迹(绿)与规划航路(蓝)同屏叠, 正好对照
   "算法规划的路"与"实际走出来的路"。
3. **人机在环标定**: 页面四步「进入标定 → 点夹爪尖 → 解算并保存 → 验证对准」, 每步给可核对的回执(点数/RMS/命中率)。

## 标定(人机在环, 最可靠, ~40s)
- 采点: 臂**停稳** → 点画面里**夹爪尖** → 同刻取 TCP 真值(3D)。
  · 采点闸: 点击前先测 **1.2s TCP 漂移**, 还在动就**拒收**(脏点进去会让外参"看着能用")。
  · **≥6 点才开解**(DLT 要 6 点起); 点要**高低/左右都变**; 每次点击把 3D↔2D 对子显示出来便于自查。
- 🔴 **解算器必须 DLT 线性初值 + 内置自检**: 只用"多起点 + LM"会收敛到**退化解** —— 实测 f 真值 520 解成 84.6,
  相机系 z 变 1.4e4 m、RMS 2.4e8 px, **而且它通过了 z>0 的合理性检查、不报错**。
  定式: DLT(Hartley 归一化)求 P → `cv2.RQDecomp3x3` 抽 (f,R,t) 作初值 → `least_squares` 收细,
  并**拒绝任一点 z≤0.02 的解**; 返回体里带自检(见下)。`cv2.RQDecomp3x3` 在本机 OpenCV 返回 **3 个值** `(retval,K,R)`。
- 返回给页面的证据: `rms_px` + 逐点误差 + 点散布 σ/range + `dlt_used` + `solver_selftest`。
- 现成脚本: `scripts/extrinsics_solve_selftest.py`(DLT 初值 + 多起点 + 自检, 自带合成相机自测, 可直接跑)。

## 独立验收(必须, 且和自检分开)
- **自检**只证明**管线**对: 造一个已知相机 → 投已知 3D 点 → 反解, 判 f 复原误差与 RMS(实测 0.36% / 0.46px)。
- **现场验收**才算数: 把 TCP 真值投到"**运动中的机械臂**"掩膜(相邻帧差法出掩膜)里数命中率;
  或者用已知 base 点(如台面/标定板)正投影 vs 图上实检比对。两条都过, 才把管道摊到画面上。
- 跨语言渲染必须同源: 浏览器 `proj()` 与 Python `project()` 用**同一 (f,R,t,主点)**;
  交付前注入一个已知外参、两边投同样 3D 点比对(实测最大差 0.001px), 否则会出现"算得对、画得歪"。
- 渲染器不能只看"没报错": 数**画布像素**(`getImageData` 的 alpha / 非背景计数)+ 段数, 并喂**真实录到的 3D 点**执行一遍。

## 叠加层的开关/清除语义(否则用户会说"数据没了")
- **默认关**(人工开启), 状态存**一个文件**(单一唯一依据), 页面/发布器/服务都读它; 别让每个页面各存一份。
- "清除" = 设**清除线(baseline)**, 只影响画面、不动录制历史 ⇒ 必须同时给 **`显示 / 隐藏 / 清除 / 📜全部历史`**
  四个按钮, 并在状态条写明「**现在画: 实测 N 点 / 航路 M 点 · 已录 K 点**」。
- 发布器是"跑一次就退"的壳每 2s 重拉一次 ⇒ **每轮都要先读开关**再决定"撤掉/发布", 否则关掉后线又被画回来。
- "撤掉"= 从规格**挪到缓存文件**(可原样恢复), 不是删元素。排查"没看到"按链走:
  **开关 → 清除线 → 唯一依据里的点数 → 渲染**, 别先怀疑代码。

## 底图要能「旋转 90°」(老倪 2026-10-12: 「图像增加旋转功能, 左旋/右旋两个按钮, 点一下就转 90°」)

AR 页(`tools/web/tcp-ar.html`, 按 mtime 热读 ⇒ **改页面不用重启服务**)加旋转, 四个定式缺一即出错:

1. **旋转单元必须包住叠加层**: 把 `<img id=vid>` + 叠加 `<canvas id=ov>` + 命中层 `<div id=hit>`
   包进一个 `#inner`, 整体 `transform: rotate(Ndeg)` —— **只转 `<img>` 会让投影/轨迹/L5 框/标定像素全部错位**。
   三者同尺寸、同中心 ⇒ 一起转就永远对齐。
2. **要铺满、不裁边**: 容器(`#stagewrap`)宽高按**旋转后**的纵横比走(90/270 时宽高互换),
   `#inner` 尺寸始终保持「未旋转画幅」比例(`IMG_W:IMG_H`) ⇒ 转完正好铺满。用显式 px 高度,
   别依赖 `aspect-ratio` 的支持面。
3. **指针映射必须逆旋转**: `uvFromEvent` 不能再用 `(clientX-rect.left)/rect.width` —— 先取 AABB 中心,
   用逆旋转矩阵回到「未旋转画幅」坐标(ROT=0 时保持与旧口径逐位等价), 否则**标定点与放大镜采样全偏**。
   放大镜里的内容也要按同角度旋转, 否则点选方向看着不对。
4. **按钮与状态常驻 header**(手机也够得着), 角度存 `localStorage` 并显示「旋转 N°」;
   换相机(`IMG_W/IMG_H` 变)要重算盒子。

**自检(不用肉眼看)**: 在 0/90/180/270 四档下量 `#vid` / `#ov` / `#hit` 的 `getBoundingClientRect()`,
**三者必须完全重合**; 再验逆映射: AABB 中心 → 图像正中心 (`IMG_W/2, IMG_H/2`), 90° 时 AABB 左上 → 图像左下 `(0, IMG_H)`。
⚠️ 页面顶层用 `let` 声明的全局量(`ROT`/`IMG_W`)**不是 `window` 属性** ⇒ 控制台自检要写裸变量名,
写 `window.ROT` 会拿到 undefined 而误判成「没生效」。

## 🔴 「AR 打开后白屏, 好长时间才显示」(2026-10-19 实测收敛)

控制台内嵌 QWebEngineView (tools/gui/ar_web_window.py) 的白屏由**三段**叠出来, 三段都要治:
1. **QWebEngineView 首帧前默认白底** —— 页面 body 再深也轮不到它 ⇒ 窗口先白一片。
   修: `view.page().setBackgroundColor(QColor("#0b0f14"))` (与 AR 页 body 同色)。
2. **prewarm 只建窗不 load** —— 第一次点开才现场跑"起渲染进程 + 拉 90KB 页面 + 解析内联 JS"。
   修: prewarm 里 `w.ensure_loaded()`, 页面在隐藏窗口里先加载完; 点开只剩 show (实测 0.08s)。
3. **8797 `ForkingMixIn` ⇒ 每请求 fork 一个进程**: 泵 60ms ⇒ 16.7 req/s (且默认开光模块 3D 框,
   每拍一次 57KB base64) ⇒ 打开新页面时 HTML 请求排在后面。
   修: 泵周期 100ms (10fps) · 首帧 `pumpTick(true)` 强制走便宜的 `/snap`, 不用等检测线程。

🔴🔴 **别拿流畅度换 CPU** —— 这是本节唯一一次被现场否掉的改法, 记住反例:
为省 8797 的 fork 压力, 一度把泵改成「`document.hidden` 时降到 1s 一帧」。内嵌窗口被 Qt 判成 hidden 时,
画面就是 1fps, 用户的原话是「**没有以前的网页好使**」, 而且**刷新也救不回来**(新页面照样 hidden)。
⇒ 取帧节流一律**不按 visibility 做**; 省压力靠 `period` 本身(100ms)和看门狗, 不靠降帧。
同理不要 `if(document.hidden) return` 停泵: 某些平台上切回可见时**不发 `visibilitychange`** ⇒ 泵永久停 = 冻屏。
`visibilitychange` 只能用来「到可见时立刻补一帧」, 不能用来做减速闸。

**判据 `tools/verify_ar_window_firstpaint.py`** (offscreen 真起 WebEngine, 真走 prewarm→show):
  · 量的是**相机窗口区(左列)白像素**, 不是全屏 —— 右栏浅色文字/表格让全屏白恒 8~14%,
    拿全屏当判据会把正常页判成白屏 (实测踩过)。
  · 现口径: 预载 0.26~0.33s · 点开 0.08s · 点开 250ms 相机区白 0.8% / 彩色 20% ⇒ PASS。
**现场生效**: 改 `ar_web_window.py`/`studio.py` 必须**重启控制台**; `tcp-ar.html` 是 mtime 热读, F5 即可。

### 「AR 不动 / 滚轮没反应？」先分三种，别当成同一个病

1. **画面冻住但面板数字还在变** ⇒ 取帧泵被锁死（重启 8797 时那一拍请求悬挂，`busy` 永不复位）。
   判据：8797 日志里只剩 `/api/*`、**一条 `/snap` 或 `/api/module3d` 都没有**。刷新页面即恢复；
   修法看门狗见 `low-latency-camera-streaming`。
2. **滚轮/点击全不跟手、窗口发涩** ⇒ **GUI 主线程被阻塞**，不是页面。`py-spy dump --pid <studio pid>`
   直接看主线程栈（实测卡在 `_realize_page → 某页 __init__ → subprocess.run(ssh …)`，每次建页卡 2s，
   而后台建页泵每 0.8s 建一个 ⇒ 周期性丢输入）。页构建里的**任何同步子进程都必须挪到后台线程**。
3. **只有滚轮不动、其余正常** ⇒ 先证页面能不能滚（`scrollHeight` vs `innerHeight`），再往
   `view.focusProxy()` 注入一个 `QWheelEvent` 读 `scrollY`（实测 0→60 即滚轮有效）。
   凭“没反应”直接改事件处理会改错地方。

**内嵌窗口加载过就不再取新 HTML**（mtime 热读只对“重新 load”生效）⇒ 必须给 Ctrl+R / F5，
否则现场永远跑旧页面、每个修复都要重启控制台才见得到。

### 🔴 「还是卡」的终局答案常常不是优化，而是**换回浏览器直开**

用户说「回到以前 http://<host>:8793/ar 的状态吧, 以前就不卡」时, 他要的不是把内嵌窗口再调快,
而是**他熟悉的那条入口**。定式:
- 在相机流服务(8793)上加 `/ar` 路由, **只做 302** 到 AR 唯一依据 `http://<同 host>:8797/ar`;
  不要在同端口再挂一层 `/api` `/snap` 反代 —— 8793 是本机最重的常驻流服务, 让 AR 的 10Hz 取帧穿它
  只会把视频流拖慢。302 用请求头 `Host` 拼目标, WiFi/产线两个网段都能用(实测 10.163.x.x 与 127.0.0.1 都对)。
- 改完**必须真验**: `curl -o /dev/null -w '%{http_code} -> %{redirect_url}'` 看 302 目标 + `curl` 直接开一次
  看服务日志出现 `/snap` 或 `/api/module3d`(只出现 `/api/*` = 页面在跑但没取帧)。
- **动手前先确认"以前"到底是怎么打开的**(浏览器直开 / 内嵌窗口 / 别的端口), 再决定改哪一端;
  一路优化内嵌 WebEngine 而用户实际一直用浏览器, 就是白折腾一场。

## Pitfalls
| 坑 | 症状 | 修法 |
|---|---|---|
| 页面在 A 端口调 B 端口的接口 | 按钮点了**毫无回显**; 后端日志里**根本没有这条请求**(跨源被浏览器静默拦掉) | B 端服务回 `Access-Control-Allow-Origin: *`(+`Allow-Headers/Methods`), 并实现 `do_OPTIONS` 回 204 |
| 在浏览器控制台改页面内部变量 | 设 `window.CALIB` 无效(顶层 `let` 不挂 window) ⇒ 误判"渲染函数坏了" | 给**裸标识符**赋值(`CALIB = {...}`), 测完复原 |
| 只用多起点 + LM 解外参 | 解出物理上不可能的参数却"不报错" | DLT 线性初值 + 拒绝 z≤0 的解 + 内置自检 |
| 拿静态共面锚硬解 7 参 | 投影对得上、深度全靠猜, 管道贴歪 | 先判断能否解; 不能就报缺外参, 请人点 6~8 个不同高度的点 |
| 自测/合成外参留在生产路径 | 假标定被当真值加载, 比没标定更坏 | 自测完**立刻删**该文件并明写"已删" |
| 只断言"段数>0 / 没报错" | 死代码或错口径照样"通过" | 数画布像素 + 跨语言投影比对 + 真实 3D 点 |
| `pkill -f "<脚本名>"` 收尾常驻壳 | **杀掉调用它的那条命令自己**(exit -15) | 用 `[c]<脚本名>` 这类括号式, 或按监听端口找 pid |
| 为改页面去重启正在被看的推流服务 | 掐断用户眼前的 MJPEG | 页面按 mtime 热读; 改动攒批 + 先问, 不要反复重启 |
| 重启 AR 服务时用户正开着页面 | 刷新也不动、日志只剩 `/api/*`(取帧泵的 `busy` 永远卡 true) | **先给泵加看门狗再重启**; 重启后叫用户刷新一次即恢复(详见 `low-latency-camera-streaming`) |
| 流式接口只在客户端正常退出时才结束 | 客户端刷新/关窗后子进程停在 CLOSE-WAIT **空转烧 CPU**(实测两个各 38%、白烧 7 分钟, max_children 名额也被占) | 写循环三件套: 单连接硬上限时长 + 每块 `flush()`(让 EPIPE 早早暴露) + `finally: self.close_connection=True` |
| 页面里那个格子的 `data-src` 指的是**原始帧**而不是叠加帧 | 叠加层里画什么用户都看不见, 他会说"没有线/没有轨迹" | 改成 `overlay_<cam>.jpg` 后**回读页面 HTML**确认; mtime 热读 ⇒ 不用重启服务 |
| 在固定相机画面上直按"水平线" | 用户:"不是以相机坐标系为轴" | 先解消失点, 画**过 VP 的斜线**; VP 病态就如实报解不出, 不硬编坐标 |
| 内联 JS 页面里留了一行**孤立残片**(如 `$('x').textContent='…'; });`) | 整段 `<script>` 解析失败 ⇒ **页面上所有按钮同时失效**, 浏览器只留一条空 exception ⇒ 极易误判成"后端崩了" | 抽出 `<script>` 跑 `node --check`; 若 HEAD 与新版报同一处错, 那是历史遗留的真 bug, 顺手修掉 |
| 顶层 `let` 状态声明写在初始化阶段就被调用的绘制函数之后 | 整页 JS 静默全死(所有占位 `—`), 函数还在、`node --check` 也过 | 状态声明一律放脚本最前; 用 `new Function(scriptText)()` 抓运行期真错 |
| 新接口一提交就"连接被重置" | `curl -s -i` 空回包、`exit 52`(Empty reply from server), 服务日志里**连这行请求都没打**; 旁边已知老路由(POST delete)却正常 ⇒ 不是路由写错, 是 handler 一进去就抛异常把连接掐了 | 典型来源: 用了**只在别的函数内部 import 过**的模块(`subprocess`) ⇒ `NameError` 在发响应之前炸掉; 新 handler 用到什么就在**模块级** import 一次。判据: `curl -s -i` 的 exit code —— 52/56 是链路层被掐, 404 才是没这个路由 |
| 围栏/禁入判定只看路径终点 | 中段穿过围栏不报警 | 路径逐点(相对量先累加成绝对坐标)判定 |
| 想造 PyQt 实例来测"点按钮会做什么" | `object.__new__(Cls)` 报 `TypeError: not safe, use Cls.__new__()`; `Cls.__new__(Cls)` 报 `RuntimeError: super-class __init__() of type X was never called`(sip 属性访问要求 C++ 对象已初始化) ⇒ 两条路都不可用 | 轻量: `ast.parse` 找目标方法 + `ast.get_source_segment` 取方法体, 断言关键调用的**实参字面量**(URL)且前半段无提前 `return`; 重量: `QT_QPA_PLATFORM=offscreen` 真起窗口/真插数据; URL·默认参数这类事实再用真浏览器打开复核 |
| 把 GUI 重启与核查串在同一条前台命令 | 重启脚本内部等进程退出/端口就绪, 前台**长时间不返回**(实测卡 >400s) ⇒ 撞超时上限, 跟在后面的核查结论一起丢 | 重启发一条、核查另发一条(进程 pid 变了 + 端口 200 即成功); 长重启用 background+notify; 一批改动攒完只重启**一次** |
| 用户说"某块太拥挤, 恢复上一版布局"就直接改 HTML | 改完自己以为好了, 现场还是"挤"或反而更长 —— 因为**真正的病可能是"面板少了一个闭合标签"**: 被套进别的面板里的那几块会挤在同一个窄列、而且把宿主面板撑到上千 px (实测金手指面板 2844px, 同行相机面板被 grid 拉伸成同样高) ⇒ 用户说的"一长条"就是它 | ① 先**量结构**: 浏览器里数 `.grid > .panel` 与全部 `.panel`（若不相等 = 有面板被嵌套）; 再量每块 `getBoundingClientRect()`（修前 2844 / 修后 941）+ 页高（4152 → 2884）; 实在不行静态跑 `python3 -c` + `HTMLParser` 数标签配平（末尾 depth 应 = 0）; ② 布局需求写清楚（"侧面点在金手指右边 + 号位/空间点在下" = 同级按序排进多列网格，靠 `grid-column:1/-1` 让后两块整行）; ③ 静态判据固化: `tools/verify_station_layout.py`（配平 + 同级 + 顺序 + 整行）。|
| 改区块 markup 时只盯着"新旧样子像不像" | 替换一段 HTML 时**丢一个 `</div>`** 不会报错、不会 lint、页面上大多数东西看着正常 | 改完立刻数结构（父链/同级数）再提交；大块 markup 替换前后都执行一遍 DOM 层级对照 |
| 用户说"某块太拥挤"就直接改 HTML | 改完现场还是"挤"或更长 —— 拥挤往往是 `grid-template-columns:repeat(7,…)` 小格子，而"上一版"是哪一版没定义 | ① 先**量后改**（`gridTemplateColumns` + 按钮宽高 + `scrollWidth>clientWidth` 数截断）; ② 让用户在**具体哪一块**上选一次; ③ 改完同口径重量一遍当证据。 |
| 把点位按钮条 `.slotbar` 放进 flex 的 `.row` | 单列大按钮铺不开 —— flex 把它压成内容宽度(实测 204px) | `.row>.slotbar{flex:1 1 100%;width:100%}`; 另注意媒体查询中同优先级规则**后写者赢** |
| 三维视图/URDF 停在几小时前的位姿, 顶栏写 `TCP 帧龄 153394.3s ⚠` | `/api/tcp` 的 `source` 退回 `file` —— 19061 SDK 桥隧道 unit 挂了, 只能读 `tcp_out/latest.json` 的旧快照 | `sudo systemctl enable --now zmax-orin-sdk-fwd.service`; 判据 `source=orin_bridge` 且 `age<1s`、`stale=false` |
| 拿“最亮细长块”当工件量尺寸 | 抓到的是**垫面亮度斜坡/折痕反光**(框内亮度 130.2 vs 框外 131.2, 零差异), 量出的“厚度 9mm”是假的 | 单阈值必假: 多档阈值(120/140/160/180)一致性 + 尺寸窗口 + 视觉复核端面; 见 `references/workpiece-dimension-measurement.md` |
| 换了 morphology 链之后复用连通域编号 (`lab == best["i"]`) | 编号会变 ⇒ 取到的是**另一个小碎块**, 量出的长宽全错(实测量到 L=6px 而候选是 122px), 而结果照样打印得像成功 | 候选命中时**当场把 `cv2.boxPoints(rect)` 与像素点一起存进候选**, 后续几何全用存下来的那份; 不要再算一遍 mask/lab 去索引 |
| 在“参考基准”附近开窗找目标(hint 窗口) | 基准本身可疑时(控制器 tool1 偏了、或目标压根不在那一侧)窗口把真目标排除在外 ⇒ 得出“画面里没有目标”的假结论 | 先**全图**多档阈值出候选清单(bbox/长宽/角度/离基准距离), 再让视觉复核点名哪一个; 窗口搜索只用于**基准已被证实可靠**之后的加速 |
| 只按“长宽比≈4.2”给候选排序 | 排序第一名常常是背景亮度斜坡/不锈钢支架(实测量到 31×8mm 的“模块”), 与真工件无关 | 长宽比只做**粗筛**, 定案必须靠视觉复核**端面/夹爪/金手指**这类结构特征 |
| 点「绿框定主」返回 `{"ok": true, "locked": false}` | 以为定主接口坏了 / 没生效 | 这表示**当时没有可锁的检测结果**(那一帧压根没检出目标) ⇒ 回到"画面里到底有没有目标", 别去改 lock 逻辑 |
