# 分层安全闸 · 诊断 + 授权 + 下发反馈

## 慢层大模型: 必须非推理型 + 调用方等待上限 > 真实单轮耗时 (实测铁律)

- 推理型模型把 token 花在 reason_content 上 ⇒ content 空 ⇒ 慢层落"降级不安全" ⇒ **fail-closed 拒掉一切动作**,
  现场现象="点了半天不动"。同一端点实测: `deepseek-flash` 140s/空 ✗ · `deepseek-v4-pro` 141s/空 ✗ ·
  **`deepseek-chat` 135s/有真 JSON ✓**(唯一非推理档)。判据: reason_len==0 且 txt 非空且能解出 JSON。
- **延迟与图片大小无关**(64x64 也要 122s) ⇒ 缩图/降灰度都不提速, 别浪费时间。提速只有: 换非推理档 + 裁决复用窗。
- max_tokens 给小 JSON 500~2000 就够; 9000 会让单轮 >600s, 太小又会被 reasoning 吃光 ⇒ content 空。
- 执行器等裁决的上限必须 **> 单轮耗时 x 重试次数**(慢层 135s x 3 次 ⇒ 等待/复用窗配 600s); 否则慢但正常的轮次
  被判"未给裁决 ⇒ 从严不安全"。

## 物理缺席的相机 = 慢层永久判"关键视角缺失 ⇒ 不安全" (最隐蔽的全拒根因)

- 现象: 裁决 1~2 秒返回且理由含"关键视角缺失/丢帧"(远快于模型耗时) ⇒ **根本没调模型**(本地兜底或复用旧结论)。
- 查法: `ls /dev/video*` 对不上映射(如顶视要 /dev/video4 而机器只有 0~3) ⇒ 相机物理不在位;
  快照接口仍返回**冻结旧帧** ⇒ 拼图混进陈旧格, 模型每轮报"丢帧/缺失"。
- 处置: 可缺席视角从"必须"集合移出 + 拼图剔除, 并在**裁决字段 + 拼图标题**如实写"缺席: xxx";
  剔除后行宽不等, 用 np.pad 补黑再 vstack。**是否接受覆盖降级必须用户/现场定** —— 不擅自放宽关键视角判定。

## When to Use (触发)
现场说「技能/按钮又不好使了」「点了没反应」「怎么半天不动」而设备真的没动; 或下发的动作被拒、
被闸门拦住、同一按键时而能时不能; 或要让点击后"立刻动"(需评估现场一次性授权);
或给带安全闸的按钮写回执/进度反馈时。先分清三种: 「**被拦**」(日志有拒发行) / 「**还在等裁决**」(有意图登记、无受理) / 「**受理了却没走到设备**」
(见 3f: 执行器多实例抢队列 · 命令通道静默卡死) —— 处置完全不同, 第三种最容易被误判成"设备坏了/网络断了"。

适用面: 任何"上层给意图、下层在真动作前做安全裁决"的系统(真机运动、触发类设备、产线 AOI 收口)。
别先查网络/注册表/驱动。

## 1. 否决链: 先定位是哪一层拦的

典型顺序(任一不安全即拒发, **fail-closed**):

```
下发 → 命令通道是否活 → 语义层(慢, 模型裁决) → 反射层(快, 本地判据) → 真设备调用
```

- 每层都要有独立裁决文件(JSON) + 日志行, 否则现场无证可查。
- **被拦时受理行必须点名是哪一层 + 为什么**; 写「通道不可用 或 闸门拒发(见日志)」等于没说,
  现场只会得出"没反应"。分档: 语义层/反射层/通道, 各带一句原因。
- 反射层的判据(亮度、纹理、遮挡)容易因为**输入本身错了**而恒定 unsafe: 画面"有帧且在动"但像素质心不对
  (例如采到无照明的 IR/GREY 那一路, mean≈6/median=0)。**先确认喂进闸门的是真现场那路**,
  设备号/取流按**名称+能力**解析, 不要写死索引(重启后会变)。
- 🔴 **快层不只拦臂运动 —— 夹爪同样过它**("免"的只是慢层语义裁决)。执行器日志对夹爪动作明写
  `🎯 夹爪类动作 ⇒ 免意图等待(非臂运动), 仍过快层反射闸门: L2.grip_open` ⇒ 现场报「夹爪点了不开/不合」时
  **先读两行**: ①`🛡 VL 安全闸(快层): 遮挡/糊化([...]): … ⇒ 拒发` ②`🛑 被拦(快层·本地反射(5Hz))`。
  有这两行 ⇒ **别查夹爪服务/夹持力/驱动/授权** —— 是那一路画面判据在拦, 且授权在场也拦得住(授权只越慢层)。
- 🔴 **把"近黑无纹理"量出来 + 做排除法**(判据一次说清, 免得来回两轮):
  ① 读快层判据文件里的逐路指标(`per_cam.<路>` —— 实测坏路 `mean≈5 / uniform_frac=1.00 / lap_var≈5`
     ⇒ 遮挡+近黑+不安全; 健康路对照 `mean≈110 / lap_var≈290`);
  ② **独立抓帧核对, 证明不是推流/解码端**: `GET /snapshot/<路>.jpg` 与**直开设备**(`cv2.VideoCapture(N, CAP_V4L2)`)
     各算一遍同样的指标 —— 数字一致 ⇒ 相机本体就长这样, 别去改推流服务;
  ③ **排除曝光/增益**: `v4l2-ctl -d /dev/videoN --set-ctrl=exposure_auto=3|1` · `exposure_absolute=1000/3000` ·
     `brightness=128` 各抓 8 帧, 均值纹丝不动 ⇒ 定性为**镜头前无光/被挡**, **不是**曝光参数 ——
     此时**不要**去改程序里的曝光常量(那会动模型输入与安全口径), 而快层按设计**关不掉**;
  ④ 出路只有两条: **恢复那一路真实画面**(挪遮挡/换源/换设备), 或由用户明确点头给夹爪类动作单开一条
     带授权+留痕的放行(属动安全闸, 必须先有他的话)。
  ⚠️ 页面上那一格的**标签不一定等于实际设备号**(实测页面「笔记本相机」格显示的是 USB2.0 Camera):
     核设备只看**启动参数/解析函数**(`--local-dev` 之类), 别读格子上的名字。
- ⚠️ **授权在场 ≠ 动作会下发**: 判"此刻有没有授权"看 `until > now`(+"单调 `epoch`", 见 3d);
  **那份文件里没有 `armed` 键**, 它是派生值 —— 直接取 `armed` 会得到 None 并把在场当成没授权。
  过了授权仍可能被快层拦(上两条), 三个层各自成立。
- 🔴 **执行器报链路不通时, 先从宿主独立 ssh 一次对照**: 实测同一时刻执行器日志刷
  `ssh: connect to host <远端> port 22: No route to host` + 看门狗每 15s 重建命令通道都失败, 而宿主
  `ssh <user>@<远端> hostname` 秒通、TCP22 可达 ⇒ **两处结论相反**。此时**不许**据执行器日志对外说
  "网卡不在位/产线断了" —— 那是另一码事, 用 `ip -br addr` / `lsusb` 单独判; 给两条**同刻**证据,
  把范围收在"执行器侧的命令通道态"上, 别让它盖过真正的根因方向。

## 2. 裁决的时效与 seq: 为什么每条动作都要重新等

- 裁决带时间戳 + **意图序号(intent_seq)**; 执行器每次动作前登记意图(seq+1, desc=本次动作),
  **只接受 seq 匹配的裁决**。**不同动作之间绝不复用** —— 拿上一次的结论放行新动作等于取消闸门;
  但**同一动作**在复用窗内(`VL_REUSE_S`, 本机 300s)可直接复用上次裁决 ⇒ 现场体感是:
  **同方向连按秒发; 一换方向(或隔久了)就要重新等一整轮**。现场说"按了十下只动一次"基本都是这个机制,
  不是故障 —— 先解释机制再谈要不要授权, 别含糊成"闸门抽风"。
- 判"这次为什么要等"直接读裁决行原文: 「等针对该动作的裁决, 上限 Ns · **动作不同**(最近裁决=<上一条动作>)」
  = 换了方向, 得重跑一轮; 出现「**复用** Ns 前同一动作的裁决」= 直接放行。
- 因此"点一下"到"真动"= 语义层为该动作跑完一轮。实测 45~190s(远端模型 29~137s/次 + 偶发空返回重试)。
- 缓冲窗口(保鲜期)只用来描述"结论有多旧", 不能用来跳过本轮。
- **调用方超时上限必须 ≥ 单轮耗时**, 而且**要大于现场实测的最大值**: 设 150s 面对 137~168s 的真实轮次,
  每轮都落「未给出裁决」→ 从严判不安全 → 现场看到莫名其妙的拒发。改 env 默认值后**必须重启该守护进程**才生效。
- 只读诊断: 读两个裁决 JSON(看 `safe/why/risk_level/latency_s/intent_seq/age`) + 尾执行器日志;
  日志有「已把本次动作告知评审」但没有「受理: 已下发」, 且裁决 `intent_seq` 落后 ⇒ **正常在跑, 等即可**。
- 🔴 **一次"回点"= N 段 = N 轮审议, 总时长 ≈ 段数 × 单轮时延**: 多段转移(就地抬升 → 高位横移 → 竖直下降 → 落点)
  每段各自过一次闸 ⇒ 4 段 × 25~30s ≈ 2 分钟起, 而**段与段之间臂是静止的**(正等下一段裁决)。
  现场看到的就是「停在半空不动、也没报错」—— 最容易被判成"卡死/设备坏了"。
  判据(只读, 十几秒出结论): ① 连采独立真值 `~/zmax_data/rokae_sdk/tcp_out/latest.json` 10~20s,
  算**到目标点的距离序列** —— 距离在缩短=在走(只是段间停), 恒定=真停; ② 看**尾日志最后一行**:
  「已把本次动作告知评审 · Δ=…」⇒ 在等下一段裁决, **别重发**; 「受理: ✅ 全部 N 阶段完成」⇒ 走完了;
  停在「已下发 阶段 k/N」而真值不动 ⇒ 才按 3f 查通道。③ 汇报按**段**给时刻表(第 k 段/几点下发/几点到位/距目标 mm),
  否则现场不信"它在走"。
- 🔴 **界面授权窗会被「等裁决」吃掉 —— 这是"点了半天最后什么都没动"的一个独立成因**。
  逐条授权是有限窗(本机 10 分钟), 而一轮裁决最长 300s ⇒ 现场常见的白等 =
  「先授权 → 隔几分钟才点 → 等裁决期间授权到期 → 收口回『🛑 被拦(真动授权): … 等慢层期间被撤销, 本条作废(未下发)』」。
  处置三条: ①先读授权剩余秒数, **剩余 < 单轮等待上限就直接叫现场"先重新授权再点", 别让他干等**;
  ②告诉他**复用窗的截止时刻** = 最近一次该动作裁决时刻 + `VL_REUSE_S`(本机 300s);
  在窗内重新授权后立刻点 = 秒过, 过期则重跑一轮;
  ③汇报把"被授权窗拒绝"与"被裁决判不安全"分开 —— 两者都是零下发, 但一个要重新授权、一个要清场, 处置不同。

## 3. 「点一下立刻动」的唯一正路: 现场一次性授权

- 授权只**跳过语义层**, 反射层照旧强制(遮挡/糊化仍拦)。
- 授权文件字段(示例口径): `{enabled, ts, ts_str, ttl_s, max_uses, used, scope:[技能id…], by:<现场人+理由>, note, revoked_ts}`
  + 同目录一份审计 `*.jsonl`(授权/撤销/每次使用各一行)。
- 铁律: `scope` 逐条列 id **不用通配**; `ttl_s` 与 `max_uses` **同时**设上限;
  - 唯一例外, 且要**同时**满足: 现场要的是"一段时间内别拦"而不是"某几条动作"(原话形如「人在活动区 关闭这个功能」)
    + 实现里有"只越慢层"的那份授权文件(快层仍在) ⇒ 给 **空 scope(=全部) + 短 TTL(≤1 小时) + 有限次数(如 40)** 的版本,
    并当场复述 TTL / 次数 / "还剩什么保护"。它比总闸安全(快层遮挡反射照旧)、比逐条 scope 省事; **能用逐条 scope 就逐条**。
  - ⚠️ **写之前先读旧文件**: 里面常留着上一次的 `scope` 与 `note` —— note 往往直接解释"现场为什么老被拒"
    (如某路相机缺失 ⇒ 每轮 fail-closed 全拒), 闭眼覆盖既丢证据又可能把别人正在用的授权改掉。汇报时旧值一并说清。
  撤销 = `enabled:false` + 写 `revoked_ts`(**撤销永远允许, 不需要授权**);
  **只能由现场人在场时给**(他要能看见现场), 事后把 scope/TTL/次数/理由复述一遍再落盘;
  汇报里必须写明「授权期间语义层不参与判定」+ 它的到期/核销状态。
- 🔴 **现场已当场确认安全并明确给了授权时, 立刻落盘 + 只报"窗口/次数/还剩什么保护"**: 不要再复述风险清单,
  也不要把决定权再推回现场。现场原话形如「我在现场, 确认安全, 一次性授权就可以, 你不要再判断了」= **执行指令**,
  不是征询意见; 再问一遍或补一段风险论证, 他拿到的只是"授权了还是没动"。
- 落盘三步(缺一现场就白等): ①**先备份旧文件**(`*.bak_<ts>.json`, 里面常留着上次的 scope/note = 证据)
  ②写新文件(原子 `os.replace` + 0600) ③**用执行器自己的判定函数复验**(别拿"我写了文件"当证据):
  `importlib` 加载执行器模块(**先确认它有 `if __name__ == "__main__"` 保护, 否则 import = 起第二个实例**)
  → `_vl_operator_auth(<一条真实下发调用串>, consume=False)` 必须非空; 顺带读一眼快层文件确认它此刻 safe。
- ⚠️ **一次下发可能被核销 2 次(审计里 2ms 两行) ⇒ 有效条数 ≈ `max_uses`/2**: 报次数时按实际核销口径说
  (例: 设 30 次 ≈ 只够 15 条下发), 别让现场以为"还能点 30 下"。
- ⚠️ **界面的「授权真动」≠ 跳过慢层**: 它只允许真动, 语义层仍逐条裁决; 只有本节这份一次性授权才越慢层。
  现场说"我授权了怎么还不动"时, 先读日志那行是「已把本次动作告知 VL … 等针对该动作的裁决」(在等, 正常)
  还是「现场授权在场 ⇒ **不干等慢层裁决**」(已越过慢层, 该按 3f 查通道/提供方), 别把两种"授权"混成一个说法。
- ❌ 不要用「放宽 seq 匹配 / 复用最近一次裁决 / 放大保鲜期」换速度 —— 那是拆安全边界, 不是优化。

## 3b. 现场要求「关闭安全」时怎么做(唯一正路)

触发: 现场操作者本人就在机器旁并明确说「关闭安全 / 别拦了 / 我要直接调」。那是他的设备、他在场,
不要空谈风险推回去; 但必须按下面这套做, 否则等于留一个"关了忘了开"的隐雷。

1. **开关做成"运行时文件 + 到期时间"**, 不要改代码绕过、不要加永久 env。执行器每次下发都实时读
   `~/zmax_data/<gate>_off.json = {enabled, ts, until, by, note}`; `until` 一到就**自动恢复 fail-closed**,
   不需要任何人再操作。env 开关只用于一次性手工运行 —— 写进 keepalive/cron 就危险: cron 拉起的新进程
   会静默继承它, 现场再也不可能知道闸门是关着的。
2. **一个 `_disabled()` 判定函数, 必须被两条路径同时尊重**: ①闸门函数 ②"等本次动作裁决"的等待路径。
   只改闸门函数 ⇒ 关闸后**每条动作仍要干等一整轮(上限 300s)**才下发, 现场体感还是"点了不动"。
3. **每次下发把开关状态写进审计日志**: 「安全闸: **已关闭** ⇒ 本条直接放行 (到期 HH:MM:SS · by=… · note=…)」。
   关闸这个动作本身也要可追溯(谁、何时、开到几点)。
4. **回复里逐条说清"还剩什么保护"**, 至少四点: ①停机/复位类指令永远放行(不受闸门拦, 本来如此)
   ②物理急停/示教器属机械层, 不受影响 ③上电/idle/无报警这类前置检查仍在读并记录(只是不再因画面判不安全而拒发)
   ④**如实点出这条通道上被关掉的下游保护**(例如控制器碰撞检测按既有口径就是关的) ⇒ 现在实际保护
   = 控制器限位 + 人在现场。缺了④点就是粉饰。
   ⑤**说清这个开关关掉的是哪几层**: 多数实现里它是**总闸** —— 语义层(慢)与反射层(快)一起停;
   而第 3 节的现场授权只越语义层、反射层仍强制(遮挡/糊化照旧拦)。若现场只是嫌慢,
   **优先给逐条 scope 的现场授权**(保住反射层), 再问他是否真要总闸;
   汇报里别把"关掉的是总闸"说成"只关了慢层" —— 那是两种后果完全不同的说法。
   **第三档(现场长期嫌慢时首选): 慢层单独停用开关** —— 见 §3h。它只停语义层、反射层照旧强制,
   比逐条授权省事、比总闸安全; 现场反复抱怨「每次都要等一两分钟」时先上这一档, 别直接关总闸。
5. **默认设到期**(按调试窗口, 例 4 小时)并给出恢复方式: 一句话恢复 = 删掉那个 JSON(或 `enabled:false`),
   不需要重启。**永远不设永久关闭**。
   - 🔴 **到期是静默的 ⇒ 症状复发时第一件事是读这个文件的 `until`**: 现场说"上次明明关过、今天怎么又拦",
     基本都是旧文件已过期、闸门自动恢复 fail-closed ⇒ 先把 `~/zmax_data/<gate>_off.json` 的 `until` 与当前时刻
     比一下, 别去翻执行器代码、也别重新论证该不该关。现场再要求关 = **写一份全新的文件(新 `until`)**,
     并把**到期时刻当场念给他**(他会拿它当"什么时候又会变慢"的答案)。
   - ✅ **关闸后"在途"的那条计划会自己续上 —— 不要重发**: 等待路径每段都实时读开关(见第 2 条),
     所以正在等裁决的那条计划会直接放行、原样走完。现场催「快去X」时的正确动作 =
     关闸/清障 → 盯**同一条**计划逐段走完(日志逐段「安全闸已关闭 ⇒ 本条直接放行」),
     而不是再点一次或重发 —— 重发会并起第二个计划(见 6b 末条"原地反复升降")。
6. **验证(零动作, 照第 5 节)**: ①import 执行器模块 → 读 `_disabled()` 返回值, 再拿**一条真实下发调用串**
   过闸门函数, 期望"不拦"+ 审计行出现; ②走真链路发一条 `dry:true` 规格, 终端要出现「受理: DRY-RUN(未下发)」
   **且没有审议等待**。这两条过了才算关成功 —— 别拿"我改了代码"当证据。
   现成探针: `scripts/verify_gate_off.py`(把①写成可直接跑的命令行工具; 不改状态、不下发动作)。
7. **闸门开关 ≠ 界面授权**: 页面/面板那层「🔓 授权真动」(带 5 分钟自动失效窗)是独立的一层,
   关安全闸不会替它授权。关完必须提醒现场: 仍要重新两步授权, 否则点击只会落在演练档。
8. **现场把决定权交给你时**(「闸的事你决定」): 这是要你**做决定**, 不是要你再问一遍。判据两条 ——
   ①操作者本人在现场 ②这段时间该闸逐条裁决**本来就是通行结论**(日志全是 risk=low/放行) ⇒ 就给
   **带到期的临时授权**(照 3b 第 1~6 条做), 并写清"为什么敢关"(人在场 + 逐条本就放行 + 到期自动恢复 fail-closed)
   与"还剩什么保护"。反例: 出现过"不安全/看不清"的裁决、或现场无人 ⇒ 不授权, 只给
   "**同方向连按**(复用窗内秒发)"这条退路。授权后**必须自己用执行器判定函数复验一次**再回话。

## 3h. 慢层单独停用(长期嫌慢时的正路, 保住反射层)

触发: 操作者反复说「慢层太耽误事 / 每次都要等一二百秒」—— 他要的不是"这一次放行", 而是**长期不等**。
做法: **默认关 + 一行可复原, 别删代码、别去动总闸**。
- 加一个**独立开关**(env, 例 `ZMAX_VL_SLOW`, 默认 0=停用), 与"关整个安全闸"的开关(`ZMAX_VL_GUARD`)在命名、注释、
  日志里明确分开: 前者只停语义层, 后者连反射层一起停。混用一次, 现场就再也说不清"还剩什么保护"。
- 🔴 **两条路径都要跳过, 少一条等于没关**: ①"告知意图 + 等裁决"的等待路径 ②闸门函数里读裁决文件那段。
  只改① ⇒ 闸门仍因缺裁决/旧裁决 fail-closed 拒发; 只改② ⇒ 每条动作仍干等一整轮(现场体感"还是慢")。
  停用时**连"告知意图"也一起跳过**(不再往外发意图、不再登记 seq), 否则白留一个往返。
  闸门函数里用不到的运行量(裁决时刻等)要补占位, 否则末尾那行汇总日志会 NameError 崩在下发前。
- 停用状态下**只提醒一次**(前 3 条 + 之后每 N 条一次), 别刷屏; **启动横幅把状态打出来**, 例:
  「🛡 安全层: 慢层=停用(<谁>现场指令) · 快层(本地 5Hz 遮挡/糊化反射)=**强制**(任何开关都不越过它)」。
- **零动作验证**(照 §5): import 闸门模块 → 调 `_gate_blocks(<一条真实调用串>)` 期望"不拦", 且日志里**两行同时出现**:
  ①慢层停用提醒 ②反射层那行(`快层: 放行 (裁决 0.0s 前 · 纹理正常无遮挡)`)。只看到"安全闸已关闭"那种一行 =
  你关的是总闸, 反射层一起没了。验收还要看记录里**没有**新增的审议等待。
- 恢复 = 起服务时带 `ZMAX_VL_SLOW=1`(或删掉默认值), 不改代码; 汇报时把这句一并给出。
- 副作用**必须在汇报里点名**(别只说"快了一点"): 语义层那类判断(路径上有散落物 / 关键视角缺失 / 画面异常)
  不再参与 ⇒ 剩下的保护 = 本地反射层 + 包络/位移/限速 + 控制器自身(碰撞检测按既有口径)+ 人在现场。
- 它同时消掉一个伴生故障: 界面按十几秒的 fetch 超时先报 `Failed to fetch`, 而计划正卡在慢层等待里(见 §4)。

## 3i. 「点了不动」另两种与闸门无关的成因: 控制器在 `drag` / 自愈换了运动学

### ① 控制器在 `drag`(人手施教/拖动) ⇒ 前置自检直接拒发
日志原文: `❌ SDK 腿失败: … | rc=3 · ABORT 前置条件不满足: 机器人不空闲 (OperationState.drag)`。
- 场景: 操作员刚**手拖臂去示教/录点**, 臂正被人扶着 ⇒ 拒发是对的(防与人争抢)。
- 判据: `rc=3` + `OperationState.drag` ⇒ **别查链路/技能/授权**, 都不是原因。处置 = 等人松手,
  控制器自己回 `idle/automatic`(实测十几秒) ⇒ **重点一次就能走**; 点前只读三查确认 `idle`。
- 区分 `rc=3 … (OperateMode.manual)` = 示教器还在手动模式, 要现场切自动。
- 🔴 **第三个状态字: `(OperationState.moving)` —— 控制器卡在"运动未收尾", 这时连操作者自己也发不出命令。**
  成因通常是**上一条动作回执超时**(日志 `❌ SDK 腿失败: … rc=-2 · 等 SDK 代理回执超时 136s`) ⇒ 控制器状态没复位,
  之后每条(包括现场自己点的)都回 `rc=3 · ABORT 前置条件不满足: 机器人不空闲 (OperationState.moving)`。
  现场把它说成"我得命令发不出来", 而这不是闸门、不是授权、不是网络 —— 别往那三个方向查。
  处置: **重启执行腿(只重启它, 别碰其他服务)** → 读 `/ctl/status` 的
  `robot:{power,operation,mode,has_error,estop,collision}` 确认回到 `operation=idle, has_error=False` → 再让现场点。
  ⚠️ **回执超时 ≠ 动作没做**: 实测那条"超时"的上升其实已经升了 ~19mm ⇒ 判完成只认真值;
  也因此别据"超时"重发(重发 = 叠上第二个动作)。
  ⚠️ `被拒(距上一条 1.2s < 1.5s)` 是**防连点**, 恰好证明腿活着、在响应 ⇒ 看到它不许去重启任何东西。

### ② «MoveL 被 50102 拒 ⇒ 自动改 MoveJ 重试» 的自愈常开 = 把直线换成了关节插值
- 为什么危险: MoveL 走直线 ⇒ 操作者预期 = 目标 Δ; **MoveJ 是关节插值, 末端路径在可达空间内任意,
  中途高度不受目标 Δz 约束**。实测(目标 Δz 只 +86mm): 臂途中明显升高/摆动 ⇒ 现场只能按急停;
  代理回执 `MoveJ · rc=6 · 残差 [0.86,-7.66,-6.51]mm`, 执行器再等满预算判"未到位"中止 —— 没人能预测路径。
- **铁律**: ①**默认关**(执行腿里的 `MOVEJ_RETRY` 默认 False, 只显式 env 才开) ②只许**下降/纯平移**
  (目标 z ≤ 当前 z + 30mm 且姿态差 ≤5°)被拒后重试; **升高类一律不许自愈**, 被拒就停 + 问人
  ③**自主跑点流程(建图/扫描/回点循环)必须带自愈关** —— 自动流程里出现关节乱摆只能靠人按停
  ④ 开自愈要同时带扫掠包络盒, 但**盒子只管"出界", 管不住"路径离谱"**, 有盒子不是放开它的理由
  ⑤ 判"该不该开"只看一个数: **这条动作的中途高度会不会超过目标 z**。
- 只读核法: `grep -n 'allow_movej_retry' <腿模块>` 看是硬编码 True 还是读模块开关; 判生效看代理回执里
  `MoveJ · rc=…` 行有没有出现。改完必须**重启执行器**(腿模块是一次性 import)。

### ③ 急停/「升太高了」之后回安全区: 纯 -Z 分步下降定式
现场喊「赶紧下降，回到安全区域」时 **不是**发一条大位移下降 —— 那正是会被 50102 拒、或直接压到台面的写法。
1. **先停一切自主动作**: 按显式 pid `kill` 掉建图/采集进程, **执行器留着**; `pgrep` 无残留 +
   真值连采 4~5s 位移 0 ⇒ 确认静止再谈动作。
2. 只读三查 + 帧龄, 记下起点 `(x,y,z)` 与姿态(姿态是不是"正常那组"会决定能不能走直线)。
3. **纯 -Z 分步**: 每步 ≤20mm · 慢速 · **`allow_movej_retry: false`** · 带包络盒; `dx/dy/dz` 单位是 **mm**
   (与日志 `残差 [0,0,100.0]mm` 同量纲)。直发代理可绕开腿里写死的自愈。
4. **每步核真值**: 实测 Δ 与指令差 >3mm、`rc≠0`、或报警时间戳变化 ⇒ **立刻停手**, 不再往下压。
5. 设**硬地板线**(不低于"按规矩转移高度"+50mm 这类已知安全高度), 到线即停并报数等现场口令 ——
   别自己判"够低了"。
6. 报数口径: 起点 z → 终点 z · 共降多少 · 每步实测 Δz · 水平是否一字未动 · 距转移高度剩多少 · 报警有无变化。

### ④ 点位库姿态分成两组 ⇒ 跨组移动必被 50102 拒(看起来像"又不动了")
手拖臂施教时**工具姿态会跟着变**, 同一批示教点会分成两组(实测两组差 164°):
- **零运动判定**: 逐点算 `angle(该点 quat, 当前臂 quat)` 打表 —— 出现"两簇"(如 3 个 ~30° / 4 个 ~165°)就是分了组。
- **后果**: 跨组移动的直线 MoveL 必被 50102 拒 ⇒ 触发自愈 MoveJ ⇒ 关节乱摆 / 升太高被守卫挟停 / 人按急停。
  **不是速度问题, 不是授权问题, 不是链路问题。**
- **修法(首选)**: 把少数那组对齐到**"臂此刻正握着的那组姿态"** —— 臂就在这组上, 对齐后第一次移动零摆动。
  只改四元数, **位置一个都不动**; 改前备份点库, 改后回读核验全库一致并把各点位置打出来存档。
- **反例**: 改多数那组去迁就少数 ⇒ 臂从当前姿态出发还要先甩一整圈 = 自己造事故。
- **施教纪律(防复发)**: 录点时工具姿态与已录点保持一致(尽量不翻腕); 拖动施教后**先核姿态再录**。
- 修完再跑多点自动流程(建图/扇扇/连续回点)前, 先取一个点空跑/真跑验证"零摆动到位", 再放全量。

### ⑤ 回点/转移的路径 = **三条单轴段**, 姿态对齐了也别走斜线 (2026-10-08 实测)
把两组姿态对齐(④)只解决了"姿态差大"那一半 —— **斜线直线本身照样会被 50102 拒**
(`rc=6 · [SDK MoveL] 轨迹前瞻遇奇异点`, 见最大偏差 100.002mm)。实测**纯竖直**(分步 −20.0mm 逐位准)
与**纯水平**都稳 ⇒ 回点技能固定拆三条单轴段:
①**竖直段**(纯 ±Z, 姿态不变) ②**保高横移**(纯 X/Y) ③**竖直落**到目标点 z(到位即停, 禁下压)。

🔴 **①③ 的竖直量默认就是 0 —— 执行器里的"自动抬升"已按现场要求整段删除, 别再以任何形式加回来**:
过去 `adapt_point` 会把目标 z 自动抬到"该点高度 + 余量", 这是所有"没让它升它却升了"的唯一来源(连续五次碰撞)。
⏭ **别把这条与"要不要允许上升"混成一条**: 曾有一道**临时的**否决闸「目标点 z > 当前 z + 5mm ⇒ 整单拒发」
(日志 `🚫 拒发(上升逻辑已删除): 去 spaceX 需要上升 Nmm …请人工把臂抬到该点高度以上, 再点`) ——
它**已被现场明确取消**(操作者本人就在现场、逐字确认安全)。现口径 = **手动抬升保留可用**, 由既有的
**第二道爬升闸**(相对计划起点 ≤`climb_limit_mm` 默认 100mm)兜底, 补偿条件是 **慢速 + 警报在先**;
且这道"警报在先"要做成**硬闸**而不是口头约定(警报进程不在线 ⇒ 抬升直接拒发)。
⇒ 收到"取消某条闸"的现场指令时的定式: ①**只删那一条**, 逐条列出**其余保留的闸**(包络/天花板/下压/
爬升/防连点/30s 超时/碰撞检测)并复查生效; ②**不要再用昨天或更早的口令当拒绝理由** —— 现场本人的当前授权
覆盖任何历史限制, 反复拿旧令拦住只会换来一句「你别总用以前的命令限制我」(现场要的是执行, 不是再论证一遍);
③拆闸后**不要顺手放宽别的闸**, 尤其别再引入"横移净空/余量/必升豁免"换可达性 —— 让现场把点录在**同一平面**
才是可达性的根本解(实测 7 点全部 z 相同 ⇒ 段①③ Δz=0、点间只剩纯横移)。

🔴 **"去某个点一步不动"里最会被误认成"闸"的一类: 控制器奇异点**。报警码 **50102 / 50113**, 原文
「[奇异规避]路径中改变的姿态最大值超过设定的阈值」; 腿日志 `❌ SDK 腿失败: … MoveL · rc=6 · CHECK · 最大偏差 NNNmm`,
而**受理行写着「已下发」** ⇒ 只看回执会误判成"被闸拦住了"。实测一次斜线 MoveL 要同时走 Δ=(+245.9,-10.5,+68.5)mm
并转 **146.7°** 姿态 ⇒ CHECK, 最大偏差 245.938mm、保护停**未执行**。正解 = **拆单轴段**(见本条 ①③),
不要去改闸门/阈值/速度(现场把速度提到 200 档也没用)。零运动判据一次到位: 读 `/ctl/status` 的 `last_alarm`
+ 尾腿日志那一行。
- **横移高度** = `max(当前 z, 该点参考 z)`, **最多微抬 5mm** —— 只为抵消编码器/重力沉降的**亚毫米噪声**
  (实测当前 z=0.1726 比参考点 0.1727 低 0.1mm, 旧口径判成"下压" ⇒ 整段拒发, 现场现象正是"点了不动")。
- 🔴 **下压守卫的容差必须留亚毫米余量**(`z_floor` 容差 1e-6 → 5e-4, 即 0.5mm): 它的本意是"不许攻进夹具"(毫米级以上),
  卡到 0.001mm 只会把正常横移误杀。判据 = 拒发行写着「低了 0.0mm」这类**差值为零还被拒**的行 ⇒ 是容差太紧, 不是几何真有问题。
- ⚠️ **末段的 `guard.dz_down_limit_mm` 要给大(实测 260 ≈ 天花板 0.3885 − 最低点 0.1550)**:
  横移高度在目标点上方 40mm, 但**臂可能比"目标点+40mm"还高** ⇒ 末段落差可上百 mm, 沿用小值(20/40)
  会**整条计划拒发**(日志 `🛡 阶段 3/3 拒绝 …`, 受理行里**没有**「已下发」, 页面只显示"超时")。
  真正防下压的是 `z_floor_point`(= 该点自身 z)+ 到位即停, 不是这个限值。
- 抬升 40mm 仍在"≤100mm"铁律内, 但**最高点位 z + 40mm 必须 ≤ 安全区天花板**, 否则该点不可达 —— 报出来, 别硬发。
- 配方写在**幂等注册器**里(`register_*_skills.py` 式), 不手改 `data/`(runtime state)。
- 现场提醒: 三段在速度 1000 档约 20 秒、默认 8 档要两分多钟 —— 别把"慢"当"卡住"。
- 🔴 **改写注册器的脚本: 锚点 assert 失败必须硬中断, 且"改写"与"重新注册"不许串跑**。实测一次: 断言
  (精确空白不符的字符串替换)没拦住、后面的注册步骤照跑 ⇒ 配方被**静默打回旧版**(段数与 `speed_max` 一起变),
  日志还写着"已写盘"。定式: 用**行号 + 括号配平**定位块 · 断言处显式退出 · 改写与注册分两次调用(或 `&&`)看退出码 ·
  改完**回读** steps 块 + dry 出逐段 Δ。
- 验收(**零运动**, 看受理行的逐段 Δ, 每段**只有一个轴**非零):
  `阶段1 Δ=(+0.0,+0.0,+106.5)mm↑上升 | 阶段2 Δ=(-0.9,+7.7,+0.0)mm→平动 | 阶段3 Δ=(+0.0,+0.0,-40.0)mm↓下降`
  ⇒ 某段两轴都非零 = 又变回斜线; 只看到一两段 = 解析或配方不完整。

### ⑥ 当前姿态本身已出包络 ⇒ **一切**下发被保护停(连零位移的原地旋转也被拒)
现象: 现场点任何按钮都不动; 日志是 `rc=6 · CHECK`, **没有任何"闸门/授权/通道"字样**。
- 🔴 **一条动作定性: 发一条"位置不动、只转几度"的轴旋转**(本机 `L2.rot_b_neg`, 服务端限 1~30°)。
  回执残差 `[0.0, 0.0, 0.0] mm` 却仍被拒 ⇒ **不是目标不可达/点位问题, 是当前位姿本身过不了扫掠包络**。
  **只发一条就够** —— 再试第二、三条是同一个结论, 那些下发都是白发的。
  🔴 **但这条探针不是"零副作用": 位置不动 ≠ **工件不动**。** 姿态旋转是**连工件一起转**的 —— 爪里夹着、或正被相机看着的工件
  会被转出视野(实测一次 5° 试探就把连接器转出取景, 判据链随后全错、要好几步才恢复)。
  ⇒ 工件在爪里 / 有相机正对着它时, **改用纯只读判据**(读保护停字段 + 比"当前 z vs 天花板" + 读包络界 vs 当前真值),
  别把这条旋转当"安全的探针"。
- 定量核: 读失败行尾部的**保护停字段**(`保护停=🛑 扫掠越界急停: ['z'] 轴出包络(实测 [x,y,z])`);
  再比当前 z 与 `taught_z_ceiling()`(本机 = 最高空间点 z + 50mm = 0.5666) —— 臂 z 高于它就任何扫掠都出界。
- 🔴 **为什么臂会在闸门之上: 手动拖动/示教器不受软件闸管** ⇒ 操作者能把它放到"命令永远跟不过去"的高度
  (常见是为了靠近某个高处示教点而升上去)。此时**别再一条条下发试探**, 先把这条几何事实报出来。
- **点位自身在闸门之上 = 该点用命令永远不可达**: 如实报出 + 给"降位姿 or 就地重记该点"两条路;
  **天花板/包络阈值是现场定的闸门, 助手不自己调**(台账已立: 助手不得提拔现场定的安全闸)。
- 🔴 **操作者已经下令"你自己开过去"、而唯一拦路的就是他自己定的闸 ⇒ 不要再把同一份选项列第二遍。**
  那时他要的是执行, 不是菜单: 一句话给"哪条闸 + 唯一那个要他定的事(授权提阈值 / 他在示教器里走 / 他拖到位后你零运动重记点)",
  并把"我不自己动你定的闸"说在前面。重复列选项只会让他再催一遍, 问题一毫米没推进。
  ⚠️ 同时别跳另一头: 也不能为了"执行"去分段绕 rc=6 / 提阈值 / 开 MoveJ 自愈 —— 那正是台账里每次事故的做法。
- 顺序: 先 `/ctl/status`(有 `power/operation/mode/estop/collision/has_error/error_code/last_alarm/last_estop`)
  排除设备侧(**实测 `power:on · estop:false · collision:false · has_error:false` 时命令仍被拒 ⇒ 就是闸门, 不是控制器**),
  再往闸门方向查。别把 `rc=6` 一律说成"控制器拒绝" —— 那会把自己的闸门报成别人的问题, 现场白跑一趟。

### ⑦ 当前姿态越过【学出来的包络盒】⇒ 某个方向键点了**静默不动**, 现场毫无提示
现象: 单方向点动无反应、其它方向正常; 授权窗 `armed=true`; 日志里还有"✅ 包络内"的历史行(那是别的目标)。
- **一条命令定性**: 读包络产物(`~/zmax_data/env_model.json`)各轴界, 与**当前真值**比 —— 实测 `x=0.3348` 而
  `x_min=0.3368` ⇒ 凡往 −X 的每一条都被包络校验拒掉。拒发行在**执行器**侧, 页面只显示"无结果/超时",
  于是现场拿到的是"没反应"(与"在等裁决""通道卡死"现象完全不同, 别混)。
- 🔴 **根因是"包络由示教点学出"**: 边界取示教点的 floor/ceil ⇒ 示教点**自己贴着界**, 正常的毫米级点动几步就出界。
  ⇒ 别先去改点位数据, 先想"这台机器本来就该能在示教点附近自由走动"。
- 🔴 **运行期它会自己长大(安全隐患)**: 执行器在守卫**之前**就把本帧目标写进学习流水 ⇒ **每一条被拒/从未到达的目标
  都把包络推宽一格**(实测 x 下界因此额外降了 6.9mm, 而现场真实活动区没有变)。⇒ 包络学习只认**到达过的位姿**(真值流),
  不认命令目标; 发现"界比预期宽"先查近期的拒发记录, 别当成"设备本来就这么大".
- **修法(正路)**: 在包络**真源**(生成 `env_model.json` 的那个脚本)里加一个**可配置的外扩余量**再重建
  (只放宽"能退/进多少"; z/升降方向单独给更小的余量, **绝不放宽到危险区**) —— **不要手改 JSON**,
  那是产物, 下次重建就被覆盖。重建前备份 + 贴出前后各轴区间对照, 并证明"当前姿态已在新界内"。
- **现场即时退路**: 让他**反向点一下**回到界内(通常几毫米), 别让他对着同一边反复点。
- 🔴 **被闸拦住必须让页面说人话**(用户口径: 按钮点了必出结果): 被包络/守卫拒时页面要有**红字原因 + 数字**
  (例"出界: x=0.3348 < 下界 0.3368"), 并且每次下发无论成败都留一行**可复制**结果(技能+参数+结果+原因+时刻)。
  只在执行器日志里有拒发行 = 现场看到的就是"卡死", 他会把机器当成坏了。
  ⚠️ **页面渲染的真坑: 回执先返回「受理: 已下发」(ok=true), 真正的否决在**后面几行**
  ⇒ 只看 `ok` 会把"被拒"画成「✅ 已下发」, 现场体验就是"点了没反应"。修法 = 扫 `msg`+`lines` 里的否决标记
  (`目标出已验证包络`/`扫掠越界急停`/`拒发`/`拒绝`/`未授权`) 命中即按被拒渲染;
  反馈区/横幅要放在 `poll()` 会清空的容器**之外**(否则每轮刷新把它抹掉)。

## 3j. 方向级否决(「只有某个方向点不动」) + 「慢」的三层分解

### 方向级: 别把"自动逻辑已删"当成"该方向被封"
一个方向(如抬升)被挡, 可能挡在**三层**里, 只动其中一层 = 看起来还是能/还是不能动:
① **自动路径**: 执行器在转移计划里的判定(本机已按现场要求删掉"自动抬升" ⇒ 目标点高于当前 ⇒ 整单拒发);
② **手动路径白名单**: 服务端那份 `_CTL_SKILLS` 里的条目(本机 `"L2.lift": ("d_mm",1,300)`) ——
   **不受①影响**, 授权后照样能发; ③ **页面按钮 + 键盘映射**(热读那份 HTML)。
⇒ 核一个方向能不能动, 三层都要读; 只读一层必然得错结论(现场会对"到底禁没禁抬升"反复追问)。
- 🔴 **判"到底哪个方向被挡"最快的一条: 读 `/ctl/status` 的 `last_cmd`** —— 实测 `L2.lower` 回
  `ok:true · 已下发(真动)` 而抬升被拒 ⇒ **链路是好的、只有这一档被挡**, 不必去查通道/控制器/授权窗。
- 白名单是**模块级常量** ⇒ 改它要重启承载服务; 页面文案是**热读** ⇒ 刷新即生效。

### 抬升 = 授权动作, 警报是它的**前置条件**(不是"把按钮禁掉")
现场口径: 手动抬升**保留可用**; 要收紧的是"**没有警报就不许抬**" —— 不是把按钮禁掉、也不是把
抬升从白名单删掉。
- 实现放在**服务端下发前**: 查警报服务是否在线, 不在线**拒发**并给人话原因 + 恢复方式。
  **选"拒发"而不是"请求里自动拉起音频进程"**: HTTP 处理路径 fork 常驻音频不稳(重复起/静默失败),
  失败要朝**安全侧**倒 —— 挡住"无声抬升", 而不是赌它能起来。
- 🔴 **抬升限速不得低于警报判据的阈值**: 警报判的是真值 z 分量 `dz/dt > 0.30mm/s`;
  把抬升压到 <0.3mm/s ⇒ **警报永远不响** = 自己把刚设的前置条件废掉。要"慢一些"必须留在阈值之上,
  且改完速度要**实发一次确认警报真响**。
- 🔊 **「警报没听到」先问它响在哪台机器上**: 发声是监控侧那个小进程用**本机声卡**放 WAV ⇒ 它响在
  **跑监控的那台机**, 站在设备旁的人**听不到**。要让现场听到, 必须把"发声"这一点挪到现场那一侧,
  并让"发声链路不通 ⇒ 同样拒发该动作"(不给"没声也敢动"留口子)。

### 现场说「怎么反应这么慢？局域网应该快啊」—— 三层分开答, 别去查网络
先读拒绝文案原文(`… 上一条动作还在执行(…, 9s) ⇒ 拒(不排队)`), 然后按三层报:
① **网络(基本无关)**: 指令是毫秒级到的, LAN 快慢进不了这个瓶颈 —— 这句话要**说在前面**;
② **速度换算(真正的量级)**: 面板那个"速度"不是 mm/s, 实测 **1000 档 ≈ 3.0~5.8mm/s**(≈0.0999mm/s 每单位),
  腿内 `min()` 上限 ~60mm/s ⇒ 一个 20~30mm 的动作天然要 7~10s; **默认 speed 取很小值是主因之一**;
③ **忙就拒(把现象放大)**: 腿在上一条未走完时**不排队、直接拒**(设计如此, 防连点把臂当摇杆刷),
  另有防连点闸(距上一条 <1.5s 拒"太快了") ⇒ 那段窗口里点任何键都被判"忙"。
- 处置: 把面板速度档拉到顶(该路能给的**最快** = 腿的 `speed_max` / 控制器限速), 并**等动作真停下
  (3~5s)再点下一条**; 结构性改进只能做"短队列(≤1) 或 拒绝时明说还要等几秒 + 自动重试一次",
  **超时/未完成绝不自动重发**(这条是铁律, 不许为了手感破掉)。
- 汇报纪律: 三层都要点名 —— 不把"网络不是瓶颈"说出来, 现场会一直往网络/机器坏了的方向追。

## 3c. 「点了没反应」的第三种原因: 执行器**位姿读不到**(与闸门无关)

现场说「回到某个示教点/点1 还是不好使」时, 日志若反复出现
`拒绝: 位姿读不到(直读失败且常驻缓存过期)或点位不存在` + `受理: 位姿缓存未就绪` ⇒ **不是闸门, 是执行器拿不到当前 TCP 位姿**,
任何运动技能(含点动)都会被拒。判据链(全只读):
1. `_pose_direct()` 有两条路(见 `tools/l2_daemon.py`): ① ROKAE SDK 直采文件 `~/zmax_data/rokae_sdk/tcp_out/latest.json`
   (要求文件龄 <10s **且位置非全 0**) ② 退回容器里 `ros2 topic echo --once /robot/tcp_pose`。
2. 零副作用判法: `importlib` 加载执行器模块 → 直接调 `_pose_direct()` / `_pose_best()`(返回 src=direct/cache/none),
   这样量到的是**执行器眼里的**位姿, 而不是你自己另开一个订阅者。
3. 🔴 两条路都可能**静默失效**, 都踩过:
   - SDK 会话陈旧时 `robot.posture()` **返回全 0 而不抛异常** ⇒ 采样器把它当成功写进 latest.json,
     执行器判"位置全 0"无效 ⇒ 拒发一切动作; 而采样器因为"没异常"永不重连(实测容器日志里 读失败 0 条)。
     修法(已落在 `~/zmax_data/rokae_sdk/tcp_direct_sampler.py`): 把全 0 当读失败 raise ⇒ 触发既有的".每 5 次失败重连"路径。
   - DDS 话题的发布者**端点已过期**: 老订阅者(长连的录制器)还在收 5Hz 真值, 但**任何新订阅者 0 帧**
     ⇒ `ros2 topic echo --once` 拿不到 → 执行器的第二路兜底形同虚设。别用"录制器还在收"证明"话题是好的"。
4. 先看网络: `ip -br addr` —— **产线网卡(USB 网口)一不在位, .66/.23/.23.160 全不可达**, SDK 直连报
   `RuntimeError: network: network connection`, DDS 也只剩本机缓存值(实测位置值恒定 + 容器时标是 UTC, 别把它当新鲜)。
   这条判据一次就能把"按钮坏了"与"现场网络断了"分开。
5. 页面侧要**如实分级回执**: 执行器已收到·在等裁决 ≠ 已下发。定式: `/ctl/move` 回执加 `pending` 字段 +
   只读 `GET /ctl/log?n=` 给页面追日志尾, 页面每 5s 追到 `受理:`/`🛑 被拦`/`⇒ 拒发` 那一行原文为止(上限 = 闸门 300s + 余量)。
6. **绕对点位技能的按钮**: 点位锁在技能定义里(`point_locked` + 示教点 JSON), 页面只送 `{"skill": id}`;
   手动控制白名单要按"无数字参数"的技能单独收(本机 `_CTL_ABS_SKILLS`) —— 只把它塞进 d_mm 白名单会直接报"不在白名单里"。
   **加一个新技能按钮 = 三步, 少一步就是"点了没反应"**:
   ① 页面 HTML 加按钮 + JS 函数(抄已有那套: 写 `/ctl/move` → 未授权只演练 → 追 `/ctl/log` 到受理/拒发行);
   ② 服务端白名单加技能 id(带数字参数的表 / 无参数的表, 选错 = 拒);
   ③ **重启承载该接口的服务**(白名单在代码里, 不是热读)。
   ⚠️ 先确认**哪个文件是页面真源**: 服务端常按 mtime **热读**一个 HTML 文件, 而代码里另有一份**内嵌死码**页面 ——
   改错文件的现象就是"改了但页面上没有"。判据: `curl -s :<port>/<page> | grep -c '<新按钮文字>'`(改完必须 >0),
   再数 `<div`/`</div>` 平衡 + 抽内联 `<script>` 喂 `node --check`(页面 JS 语法错 = 整页白屏; 长连接画面又让
   浏览器打不开页面, 所以只能静态验)。
   **零动作验技能 id/参数对不对**: 走 `dry` 空跑, 执行器会把**将要真发的字节**原样打出来
   (`DRY-RUN <skill> → ros2 service call <服务> <接口> "{...}"`) ⇒ 用它核对技能 id、服务名、量纲与
   **语义方向**(例: 夹爪 `target_pos: 0`=合 / `1000`=张 —— 按钮文案与它写反了现场会夹坏件)。
   🔴 **同一个 dry 空跑还要用来查"字段有没有被中间层吞掉"**: 把调用方发的 payload 与 dry 打印的字节
   **逐字段 diff** —— 服务端代理常只转发一份**白名单字段**, 放行/豁免类字段(如"允许抬升 Nmm")会被**静默丢弃**,
   现场现象 = 「我说了动、臂一步不动」而且日志里只有拒发行。判据: payload 里有 `X`、dry 打印里没有 `X` ⇒ 是代理吞的,
   **别去改执行器判定**。绕法优先改**几何**而不是加字段(见下条)。
   - **多段计划的"抬升量"闸门是相对"计划起点"判的**: 目标点本身比起点高时, 相对抬升必然超限 ⇒ 别急着开豁免字段;
     先**降横移净空重注册**该技能(`--traverse-dz 30` 之类; **注册表热读**, 不用重启执行器) ⇒ 最高点 = 点位+30mm,
     抬升 = (点位z − 起点z) + 30, 常常自动过闸。改完**必须重新 dry 空跑**确认新的段数与目标 z。
     同一闸门对**单段**下发只警告不拦、对**多段**才拒发 ⇒ 单段能过不代表多段能过。
   - 🔴 **去"录在高处的点"是两道闸各拦一次, 只治一道等于没治**: ①**目标 z 低于该点下限** —— 第 1 段"就地抬升"
     若写死一个固定量, 臂比该点低得多时抬完仍低于该点 ⇒ 第 2 段的 keep_z 横移被\"低于下限\"拒发;
     ②**相对计划起点抬升超限**(上面那条)。两道各拦一次 ⇒ 计划**一个字节都不发**(受理行里**没有**「已下发」),
     而现场/上层只看到"超时未到位"。只降横移净空只治 ②; 开豁免字段又常被中间层代理吞掉。
   - ✅ **根治定式(现行口径, 已取代下面那套"自适应抬升")**: **不做任何自动抬升** —— 目标 z 比当前 z 高 >5mm
     ⇒ 整单拒发并提示人工先抬(见 §3i⑤)。点位一律**录在同一平面**(现场重录后 7 点 z 全相同)⇒ 点间纯横移,
     两道闸自然都满足。
     ⚠️ 曾用"阶段级 `adapt_point` 自适应抬升 + 计划级爬升豁免"绕开闸门换可达性 —— 代价是**五次碰撞**
     (臂在无人预期时自己升高, 现场只能按急停)。**别走回头路**, 也不要为了"够到更高的点"再引入任何抬升。
     ⚠️ 点位/技能定义常落在 `data/`(runtime state, 不入库) ⇒ 必须能用**幂等注册器**重建, 别只手改。
     ⚠️ 改完**两档都 dry 对照**: 一档"臂高于该点"(应走常规抬升、行为不变), 一档"臂低于该点"
     (应触发自适应)—— 后者现场很难恰好在低位姿, 正解是**打桩执行器的位姿源**再跑完整 `dry`, 否则复现不了"必被拒"。
     ⚠️ 改执行器代码必须**重启执行器**; 只改注册表是热读。重启后**确认现役进程真的加载了新代码**(见 §4 那条
     "别用下发接口的 lines 判代码版本")。
   📎 按钮工程的完整定式(三处同口径 · 服务端判据驱动绿/灰 · 一行均分布局与几何取证 ·
   「点了没反应」读日志梯队 · 可用性上限 vs 防撞红线 · 四元数分量数体检验收)见
   `references/console-button-engineering.md`。
   📎 **去任意绝对位姿 / 「按人拖动的轨迹复现」**(内联目标 `to_pos` 不占点库 · 航点间距 25~30mm 避开奇异 ·
   这种技能的守卫怎么配 · 现场一次性放行的爬升量取他自己的轨迹 · 逐段验收与 ETA · 边走边采)见
   `references/arbitrary-target-and-trajectory-replay.md`。

## 3d. 授权必须做成「单一真源 + 单调 epoch」, 并在**下发收口**强制

现场问「我都取消授权了, 设备怎么还在动」时, 把授权只做在界面上/某个服务进程的内存里就是**假闸门**。
三条并存的漏洞(实测):
1. **会动的路不止一条**: 除了那个页面, 还有一堆脚本/GUI/自动流程直接写执行器队列
   (`grep -rl <队列文件> tools/` 常是十几个文件) —— 授权只活在一个进程的内存里, 这些路径完全绕开它。
2. **执行器下发前不校验授权** ⇒ 点授权 → 命令排队等语义层(上限 300s) → 期间人点撚销 → 照样下发。
3. 已经交给设备的慢速动作(几十秒才到位)**不会因为点撚销就停** —— 用户看到的"还在动"就是它。

改法(照搬):
- 授权状态**落文件做单一真源**(本机 `tools/ctl_auth.py` → `~/zmax_data/ctl_auth.json`): `armed = until>now`
  (到期自动失效, 无人操作也安全) + **单调 epoch**(每次授权/撚销都 +1)。界面与执行器读同一份。
- 界面写队列的命令**带上签发时的 epoch**; 执行器在**所有下发收口**校验: ①此刻必须有授权(不是"签发时有")
  ②命令 epoch 不旧于当前(撚销即作废) ③**等裁决期间每一步复核**, 一撚立即作废本条。
  收口往往不止一处: 运动 / 服务步(力控) / 夹爪 三条路都要堵, 只堵一条等于没堵。
- **带外叫停已在途动作**: 撚销只拦新命令; 已下发的要靠主动停止服务(本机 `/robot_stop` = `std_srvs/srv/Trigger`,
  实测 `success=True … 'ec': 0` —— 它内部的 `rt_stopMove` 子步会回"非实时模式"异常, 不影响 stop 生效)。
  写一个**独立常驻小进程**轮询授权文件: 一旦"epoch+1 且未授权" = 有人**显式撚销** ⇒ 若最近 N 分钟有
  真下发留痕(执行器每次过闸后写一份 `<skill, ts, epoch>` JSON) ⇒ 立即调停止服务, 全程审计。
  (**自然到期不 bump epoch ⇒ 不叫停**, 只记录 —— 否则会每 5 分钟无意停一次。)
- 真源缺失时执行器 **fail-closed 一律拒发**; 停/复位类白名单永远放行(闸门不许挡急停)。
- 界面要**如实分三种情况回话**: 撤销后"已对在途动作下达停止" / "近 N 分钟无已下发动作, 无需叫停" /
  "已交给设备的动作收不回来, 只能等它走完或按急停"。只说一句"未授权了", 现场仍会判"闸门没用"。

**三条取证缺一不可**(缺一条现场就当没修):
① 未授权 + 界面带真动标志点按钮 → HTTP 403 **且执行器日志零新增行**;
② **绕过界面**直接往队列写一条真动命令 → 执行器回「🛑 被拦(<授权层名>): … 拒发」(臂零位移);
③ 授权 → 写一条真动命令 → 让它进入"等裁决" → 点撚销 → 1s 内日志出现"本条立即作废(未下发)"
   且 `grep -c 已下发` = 0, 同时叫停服务日志出现 `success`。

## 3e. 代发边界: 什么时候我可以替现场下发

🧭 **动臂去“改善画面/修指标”之前, 先证明这是姿态问题** (通用前置, 费几分钟省一次白动):
在**固定姿态**下连拍 N 帧, 看目标指标跳不跳 —— **跳 ⇒ 不是姿态问题, 动臂无效, 先修算法/上游参数**
(实测: 同一姿态下画面上报的计量值在 16/18/19 跳, 姿态量全程不变) ; 稳定但不好 ⇒ 才值得动臂;
且先看姿态量本身是否已经规整(偏移/倾角/残差都在容差内 ⇒ 期望收益≈ 0)。
“糊”要分两类: **离焦**(与距离相关, 动臂有效) vs **镜面/过曝/光照**(与角度和光源相关, 先查相机与灯),
且相机是固定安装时, 动臂能改的只有“工件相对相机的姿态角”这一条通道 —— 别把它当成万能旋钮。

判据三条**同时**成立才代发: ① 该点位**不是**现场判危险的新点位(是已现场确认过的安全位, 如已录的准备点)
② **已授权**(授权窗内; 先读一次剩余秒数) ③ **用户明确要动**(原话形如「已经授权, 动啊」)。
三条齐 ⇒ 发**页面同一个技能 / 同一个 `/ctl/move` 口径**(不另开通道、不自己拼坐标), 发完只读盯,
逐段报 `已下发 阶段 N/M` → `✅ 到位 · 真值偏差 N.Nmm`(日志原文) + 方向/行程/偏差。
**缺任一条就不发**: 危险点/新点位永远是他先做我先看(连演练也别抢发); **他正在手动点动/微调时一律不发**
(哪怕刚说过"动"); 他只抱怨"慢/不动"而没让你发时, 先解释机制或给授权入口, 不要自己动手。
  🔴 **「你走的不对 / 停掉, 我自己走」= 交还控制权, 不是换个方式继续发**: ① `delegate_task(action='stop')` 停掉**所有**
  可能下发动作的子任务(并行子代理会各发各的) ② 自己此后**一条都不发** —— 在途的让它走完, 不追加、不"补偿",
  也不换新的分段/新技能再试 ③ 立刻报**当前真值位姿** + 现场可用的操作建议(速度档位 · 防连点要隔 >1.5s · 该点是否需拆段)
  ④ **别把自己验证用的位移留在原地**(哪怕 5mm): 明说移了多少、问是否复原, 别默默留着。
  🔴 **你发、他点 —— 两个来源互相污染, 结论不可信**: ①你的命令被防连点限流拒
  (`太快了(距上一条 1.3s < 1.5s), 防连点把臂当摇杆刷`); ②你"动作前后"的读值里混进他手点动那一段
  ⇒ 你会把"没修到位"报成失败, 其实是两笔动作叠在一起(实测姿态残差里 2° 是你的、2° 是他的)。
  要么请他停手几十秒由你**一条命令**做完并回读, 要么把配方交给他自己点 —— 不要边点边发。
- **现场要求"一个点一个点来"时**(原话形如「每次移动一个点, 你先把点告诉我, 我批准后, 你移动」): 一次授权只走
  **一个点**; 报点必须带 **坐标 + 计划(几段/每段多长/是否过包络)+ 建议速度**, 等他明确批;
  到位后**先报真值偏差, 立刻收回授权**, 再递下一个点等他批。别在一个授权窗里连走几个点, 即使都批过 ——
  现场要的是每一步都由他点头。

- 🔴 **健康判据不能用"进程活着"**: 保活脚本/看门狗查的都是**命令通道的 ssh 子进程在不在**, 不查它的 ROS 客户端还能不能用
  ⇒ 通道进程活着但 `rcl` context 已坏(日志里 `failed to check service availability: rcl node's context is invalid` /
  `[RTPS_TRANSPORT_SHM Error] Failed init_port ... open_and_lock_file failed`)时, 看门狗判"健康"、保活判`RUNNING`、
  永不重启, 而每条命令都落地成"已下发 + 永远等"。**此时唯一出路是人工重启执行器**(不要只依赖保活)。
  同理: 用一次性 ssh + `ros2 service list` 探服务可见性时, 本地 participant 起不来也会返回空清单 ⇒
  单次探针**不能**当"服务不存在"的证据, 必须与"提供方进程在不在""连探 3 次"\"`service type` 返回"合起来判。
- 🔴 **「已下发」但设备一步不动: 执行器**多实例抢队列** + 命令通道**静默卡死**

第四类「点了没反应」, 与闸门/授权/位姿都无关。前提认知: **受理成功 ≠ 调用发生**。

- 🔴 「受理: 已下发」只证明命令被那个进程收下了, **不证明它走到了设备**。真下发的硬证据是日志里那条
  **服务调用输出**(`ROS: requester: making request: …TargetPose…` / `DRY-RUN <skill> → ros2 service call …`)。
  判法: 取日志里**最后一条该行的时刻**, 与现在比 —— 若差了几分钟以上、而期间日志明明排着一堆「已下发」,
  ⇒ 命令全卡在受理之后, 设备从未收到(现场体感正是"点了一小时什么都没动")。
- **一条 `waiting for service to become available...` 就能把常驻命令通道永久卡死**: 服务端没就绪时
  `ros2` 客户端会**无限等**, 而通道是"一条长连 stdin 循环" ⇒ 这条命令占住循环, 后面的技能全在通道里排队,
  却仍会被逐条记成「已下发」。这是通道架构的固有失效模式, 不是网络抖动、不用去查网线。
- 🔴 **一趟腿失败之后, 命令通道可能被那个失败计划占住 ⇒ 后面的点击「一个字都不回」**(与「在等裁决/被拦」都不同):
  判据三件一起看 —— ①**回执内容为空**(不是“超时”, 是零行) ②代理侧**最新命令回执的时间戳不再前进**
  ③执行器**日志停在失败那一行**且 CPU 增量 0(实测 4s 内 0.00s、`wchan` 停在定时睡眠)。
  ⇒ 处置: **重启执行器**(前提: 臂已静止 + 失败那段确实没真起来 —— 失败判词里 `took_s≈0.01` 即代表腿没启动),
  再用一条 `dry` 确认回执**真有输出**, 才让现场重点; 不确认就让他点 = 他只会继续拿到空响应。
  持久修法: 段失败即**干净收尾并释放通道**, 别把计划挂在等待里 —— 否则每踩一次都要重启一次。
- **先数实例**: `pgrep -af "<执行器脚本>"` 必须只有 **1** 个。多实例(实测同时 3 个)在抢**同一个队列文件**,
  命令被某个已卡死的实例吃掉、另一个只负责打日志 ⇒ 症状与单实例卡死一样, 而重启一次只解决一半
  (保活脚本/cron 很快又拉起一个, 除非加了锁)。
- **排除法(证明"不是设备拒绝")**: 同一条 SDK 会话上读控制器报警日志 —— 无新报警、**也无新警告**
  ⇒ 请求根本没到控制器。对比: 真被控制器拒会留下编号 + 物理量 + 阈值的记录。
- 🔴 **第五种(重启后最常见): 提供服务的那个栈根本没在跑**。判据不能只看 `ros2 service list` —— 先看
  **提供方主机上的进程**: 没有驱动/launch 进程(实测重启后只剩一个相机节点) ⇒ 服务不存在, 与网线/DDS 无关。
  再查那条栈有没有自启: `systemctl list-units | grep <栈名>` 为空 + 起法只有 bundle 自带的 `scripts/start.sh`(手工)
  ⇒ **主机重启后没人拉 = 运动服务全无**, 而执行器会把每条命令排进通道**永远等**, 界面照旧显示「已下发」。
  查证顺序(全只读, 1 分钟): ①`ros2 service list | grep -c '<运动服务>'` 连查 3 次都 0 且 `service type` 输出空
  ②进程清单确认提供方没跑 ③主机 `uptime -p` / 引导时刻 —— 引导时刻晚于最后一次成功下发基本即定性。
  ⚠️ 启动那条栈会连带拉起仲裁/状态机(**红线**), 必须先给现场命令原文 + 说清会拉起什么, 由现场决定谁敲;
  现场也可能选择"改走本机 SDK 直连" —— 给判据, 不替他决定。

## 3g. 换执行腿(transport): 只在「闸门之后、下发之前」换, 并**连停止路径一起换**

现场选「改走本机 SDK 直连」(或任何"后端调用路径换一条")时的定式。产线提供方栈没在跑,
但**闸门/授权/裁决一条都不能动** —— 换的是运输, 不是安全边界。

- **换腿位置 = 所有运动下发的唯一收口里, 过完所有闸之后、真正下发之前**。上面每层(真动授权 / 意图 /
  语义层 / 反射层 / 包络 / 下向守卫 / 限速)照旧生效, 只把最后一段 `ssh → 远端服务调用` 换掉。
  换在别处(闸门之前 / 各技能各自换 / 页面层换) = 要么绕过闸门, 要么漏掉某些下发路径(服务步/夹爪/多段计划)。
- **开关必须热切 + 默认等于改前行为**: 优先级 `env > 运行时文件 > 默认(原腿)`(带 mtime 缓存的执行器不用重启);
  默认值下行为要与改前**逐字节一致** —— 这是"**加一条腿**", 不是"改一条腿"。切换文件本身就是审计
  (谁、何时、为什么切), 汇报要念出来。
- 🔴 **停止/复位/急停类调用必须跟着改道 —— 否则臂停不下来**。带外叫停(3d)走的是
  `ssh <提供方主机> → ros2 service call <停止服务>`, 而那条路正是被换掉的那条栈 ⇒
  换腿后它**叫不停**(接口回 success=False 而没人看它)。定式: 撤销/急停时**先直达新腿的停止命令**(ms 级)
  + 置"在途中止"位(分片循环逐片检查, 已发的那条不再续走), **再**照旧尝试旧路(失败只记日志, 不阻塞撤销)。
  只有运动改道、停止不改道 = 表面全绿, 真出事时按了撤销臂不停。
- **不许静默回落旧腿**: 旧腿是死的, 回落 = 静默不动。新腿不可用 / 认不出这条调用 ⇒ **如实拒发并写清原因**
  (宁可不动); 一条动作在飞时后续一律拒(不排队、不并发), 避免两套计划叠上来。
- 🔴 **SDK 直连腿的队列语义与 ssh 腿不同: 它是"排队"不是"拒发"** —— 代理在执行一个动作(盯真值循环)时
  **不读下一条 FIFO**, 后写的 `stop` / 新指令会**排队到那个动作的预算到点**才被读(实测 stop 回执要等数分钟)。后果:
  ①"发了 stop"≠"停了": 判据是**真值静止 + 回执到手**; ②要**立刻**腾出通道 = **重启代理容器**打断在途动作
  (低速爬行阶段重启零风险), 别干等预算; ③现场再点一次也只会排队, 看起来仍是"点了没反应" ——
  用"执行器有没有新的 `已下发` / 腿有没有新动作"区分**排队**与**被拒**;
  ④ 代理在盯真值循环里时**心跳会停更** —— 别据"心跳旧"判它死了(判死看容器进程 + 动作回执)。
- 🔴 **但「在飞即拒」会把同一条计划的相邻段也一起打死 —— 发下一段之前必须先等腿空闲**:
  异步腿的 `in_flight` 位是**到 worker 线程结束才清**, 而执行器用**真值**判到位 ⇒ 判到位常比腿清忙早几秒,
  下一段一进腿就撞「上一条动作还在执行 ⇒ 拒(不排队)」⇒ 执行器按自己的口径**中止剩余阶段**,
  臂停在目标点正上方不落地; 上层脚本只判"到没到位" ⇒ 白等超时(实测建图类脚本 240s), 现场看起来像"走点坏了"。
  位移越小越容易踩(10mm 微调段的 worker 常要 10s 以上), 长段反而蒙得过去。
  定式 = 每段在**下发之前**有界等腿空闲(上限做成 env, 例 150s), 超时就**照原口径发**、由腿自己决定收不收
  (不在这一层默默放宽判据); 同计划的相邻段本来就该串行, 跨计划并发仍由"不排队"挡着。
  ⚠️ 查忙闲的 helper 要**自己把腿模块目录插进 `sys.path`** —— 下发处才插, 而查忙在它之前 ⇒ 否则拿不到状态;
  取不到状态时**记一行日志后照发**, 别把"查不到"当成"忙"来拦动作(fail-open 在这里安全, 腿自己还会拦)。
  ⚠️ 与守卫拒发分清: 守卫写 `🛡 阶段 N 拒绝/拒发`, 这条写 `🚚 …腿: 上一条动作还在执行 … ⇒ 拒(不排队)`;
  看到后者别去改守卫/阈值。
- 📎 腿自己的机械细节(解析下发串 · 位移/速度上限与分片 · 速度量纲 · 姿态口径 · 换腿前的只读预检)见
  `references/execution-leg-swap.md`; 底层 SDK API 链见用户自有的 `rokae-direct-control`。

### 任务启动时的闸门口径(「点了开始, 什么都没发生」的另一半)
- 🔴 **后台任务只在 t=0 读一次授权, 且 fail-closed 一次就退出、不重试** ⇒ 点"开始"比点"授权"早几秒
  = 任务在启动那一瞬静默死亡(页面毫无反应, 现场以为按钮坏了)。改法: 在**按钮那一层**当场判授权并把原因
  **返给页面**(「未授权真动 ⇒ 先点授权再点开始」), **不要偷偷起一个必死的后台任务**; 重复启动也在按钮层挡
  (已有实例在跑就回"已在跑+它跑到哪一步"), 避免两个任务抢同一个真机。
- 🔴 **授权窗长度必须 ≥ 任务时长**: 逐条授权窗通常 10 分钟, 而采集/建图/长流水线动辄 30~40 分钟 ⇒
  跑到一半窗到期, 后面每一步都被"真动授权未开"拦下(现场体感: 走到一半不动了)。
  口径: **不自动授权**; 只在"启动那一刻**已经在有效窗内**"时把窗**延长**到覆盖整轮(写审计 + 页面显示新的到期时刻),
  并把"窗口多长、谁延长的"一并汇报。窗口不够长又不想延长 ⇒ 就按任务分段, 别让它半途自己熄火。
- **长任务的等待上限跟着距离/速度算, 不要写死**: 执行器/腿盯到位的预算若写死十几秒, 在长转移上会提前退出,
  报"未到位"而设备其实还在走(现场据此重发 = 并起第二个计划)。等待上限 = `距离/速度 x 余量 + 常量`。
- ⚠️ **卡在通道里的那条命令会一直等, 也可能在服务恢复后突然补发**: 所以"重建通道/重启执行器"不只是让新命令能走,
  它同时是**清掉在途那条**的手段; 清完要向现场明说"那条不会事后补发"。反之若只恢复了服务、通道里的命令还在,
  现场会看到"没人点它自己动了"。
- **修复顺序**:
  ① 清掉**全部**实例 —— 用现成的一键全停脚本, 不要手敲 `pkill -f <模式串>`(会匹配到执行它的 shell, 自杀;
   本机实测**一晚踩三次**, 命令里连 echo 都没执行到)。**安全形态**: 按 pid 杀(先 `ss -tlnp` / `pgrep -af` 取号,
   再 `kill <pid>`), 或**锚定整条命令行** `pgrep -f '^/abs/path/python tools/<脚本>\.py$'`(`^ $` 锚住 => 长命令行不会误匹配)。
   手敲模式串时永远假设"它一定会匹配到我自己"。
   ⚠️ **容易漏的一半: 参与匹配的不只是脚本名 —— 你同一条命令行里写的日志路径/文件名/参数也算**。
   实测一条命令里既写进程名又写 `<服务名>.log`(没写脚本名), 照样把自己 SIGTERM 了、且**后面步骤一步都没跑到**
   (exit -15, 看起来像"命令超时被杀")。⇒ 最稳的顺序: **先用 `ss -tlnp` / `pgrep -af` 取到 pid, 再 `kill <pid>`**;
   必须按模式匹配时, 把匹配串**拆开写**(`"名字前""半段"`)且命令行里**不要再出现完整串**(含日志路径)。
   同一个坑一晚能踩两次 —— 看到自己那条命令返回 `-15` / 输出只有一行就停下改写法, 别原样重试。
  ② 用**保活脚本**拉起(它带启动前 ssh 探针, 避免"通道建完即死"变僵尸);
   ⚠️ **别用 Hermes 会话的 background 任务起长跑服务** —— 会话回收会给它 SIGTERM(实测几分钟内被杀, 现场看到
   "刚才还在、突然断了")。走 cron 守护(本机 `~/.hermes/scripts/cam_stream_guard.sh`, 每 5 分钟自愈)、
   `nohup ... &`(口径见 `tools/boot_restore.sh`)或 systemd。被杀后**先确认守护有没有已经拉回来**
   (`ss -tlnp | grep :<port>` 有监听就是回来了), 再决定要不要手工起 —— 别起成第二个实例。
  ③ **根因加锁**: 执行器入口做**单实例锁** —— `flock(锁文件, LOCK_EX|LOCK_NB)`; 拿不到锁就读出持有者 pid、
     `SIGTERM` 请退(最多等 3s 再 `SIGKILL`)、然后接管; 规则是**"新实例赢"**; 锁 fd **故意不关**(关了锁就释放);
     取不到锁只告警、不阻塞启动。锁防得住多实例, 防不住通道卡死 ⇒ **两条都要**。
- **验证: 先最小代价探针, 再上真目标量**。发一条最小步进的运动(本机 `L2.lower d_mm=1`, 参数下界 1mm),
  三件一起看 —— ①日志出现**新的**服务调用行 ②真值位姿**真的动了那么一点**(1mm 也读得出)
  ③控制器无新报警。三条齐 ⇒ 通道真通, 再发真正的目标量。别拿"再试一次大动作"当探针。
- ⚠️ **排障期间每条下发都要核验效果**: 回读"服务调用行有没有新增" + "真值有没有朝目标走";
  只把「已下发」转达给现场 = 下一条仍然白下, 而他会以为在推进。
- 关掉闸门(3b)之后这条判据更干净: 日志里不再有审议等待, 只有「安全闸已关闭 ⇒ 直接放行」+ 服务调用行
  ⇒ **没有服务调用行就一定不是裁决问题**, 别再往闸门方向查。

## 4. 下发反馈: 让点击"有感觉"(现场最常抱怨的一条)

- 🔴 **界面报「请求没发出去/超时: TypeError: Failed to fetch」≠ 没下发**: 这是**客户端**的 fetch 超时(常见十几秒)
  先炸, 而服务端那条计划**仍停在慢层等待里**(甚至已排到下一段)。⇒ ①**绝不重复点**(会并起第二个计划, 现场看到
  "没人点它自己又动了") ②先去执行器日志 + 真值判它到底下发没有, 把结论如实回给现场 ③根治是压掉慢层时延
  (§3b/§3h), **不要去调浏览器超时**。反过来说: 慢层停用后这类报错应当消失, 若仍出现就按 §3f 查通道,
  别当成"慢层还在等"。
- 🔴 **慢层已停用、报错却还在(或"点了没反应"): 先数同源连接名额** —— 浏览器对**同一个 origin** 只有约 6 条并发连接,
  而运营页常把 **6 路视频/快照**开在**它自己的端口**上(本机站台页 8793 正是如此) ⇒ 媒体把名额占满, 控制/状态请求
  排在后面 ⇒ 现象 = 「点了没反应」+ `Failed to fetch` + **迟到的旧动作才执行**(现场会说"我没点它自己动了"/"怎么后退了")。
  判据(一条命令定性): `ss -tn "sport = :<站台端口>" | grep -c ESTAB` 已到 6, 而同进程的**另一个**端口为 0。
  修法(已验证): **媒体改走另一个端口** —— 媒体地址基址用 `//<host>:8791`, 控制/状态留在站台端口; 页面里
  由**唯一入口**统一加基址(媒体加载器那处改一行), 别逐个 `<img>` 改。改完**必须让现场刷新页面**(老页面地址还是旧的),
  并确认改的是**页面真源**: 本机 8793 的真源是 `tools/web/station.html`(**热读**), `tools/cam_live_stream.py` 里
  另有一份内嵌副本 —— 判据 `curl -s :<port>/station | grep -c '<改动标识>'` 必须 > 0(改错文件的现象就是"改了但页面上没有")。
- **立即回执 + 后台补回**: 点击后马上回「✓ 已下发」,**不要死等回读**(一个回执动辄十几~上百秒,
  等待上限设几秒 ⇒ 界面永远显示「未回读」= 用户判定"点了没用")。回执/原因由后台轮询日志补打到
  **用户看得见的那块终端**, 并同步一份到主控制台底部日志栏。
- **等的时候要说话**: 每 **15s** 一行「⏳ 已等 Ns · 原因」, 原因要能区分:
  ① 评审正在为本次动作重跑(带 本动作 seq / 最近裁决 seq / 上轮多久前 / 单轮耗时范围)
  ② 本次裁决已到, 正在下发/等设备回执。等待上限 = 闸门等待上限 + 余量(例: 300s → 320s)。
- 点击那一刻先打一行**闸门现状**(两层 safe + 帧龄 + 原因) —— 被拦时它能当解释用。
- 被拦时补一行:「↑ 这一条就是「没动」的原因」+ 现状。
- ⚠️ 读日志增量时**偏移量口径要统一**: 若函数吃的是**字节偏移**(`os.path.getsize(log)`),
  传行数会把历史结果行(如 `受理:`)当新行读回来 → 自测里**假成功**; 判"真完成"只认结果行。
    两条同族坑: ① 执行器日志里混有二进制字节 ⇒ `grep` 只回一句 `binary file matches`、什么都看不到, 一律加 `-a`;
    ② **别用时间戳串(`HH:MM:SS`)过滤"只看新的"** —— 日志是跨天累积的, 昨天同一格式的行比较起来同样"满足 ≥ since",
    会把**上一轮的结局**当成这一轮的终态(实测据此误报过"被拦", 而当时计划正在跑); 判新行只认"下发前记下的字节偏移或行数"。
      更硬的一条: 执行器日志**只写 `HH:MM:SS`、跨天累积** ⇒ **任何"今天/刚才发生了 X"的结论都不许只靠时间戳匹配**。
      实测踩过: `grep '19:13'` / `awk '/19:15/,0'` 把**别的日子**的同一时刻行读成"今天的事件", 据此对外报过
      "臂刚才往返跑了五段/刚上升 20mm"(纯属旧纪录, 当天其实一次没动) —— 被现场追问才推翻。
      定性至少满足其一再下"发生了"的结论: ①该行行号 > **本次启动行**(`常驻执行器启动`)的行号 ②日志文件 mtime
      ③带日期的审计 jsonl(`*_log.jsonl`) 里有对应条目。三者都不支持 ⇒ 只准说"日志里有这一行, 但无法确认是今天"。
- 🔴 **别用下发接口响应里的 `lines` 字段判"现役进程是不是新代码"**: 那个窗口只带**最后几行**
  (下发/受理那几条), 规划期的早期行(如"自适应抬升"这类标记)根本不在里面 ⇒ **假阴性**, 会误判"新代码没生效";
  规划段与下发段还可能交错。正解 = 先记下日志的**字节偏移或行号**, 触发一次 `dry` 空跑, 再只读**新增字节**找标记行。
  行号一律从**最后一次启动横幅之后**数(同一条日志跳天累积, 而且可能不止一个写手往里追加 ——
  会让你看到"技能 N 个"与旧路径这种**历史行**) ⇒ 按 `HH:MM:SS` 匹配必然读错。
- 反馈文案别用自报式「已发送」, 要带**设备侧原始行**(可复制)。
- 🔊 **让操作者“听得见”机器在动**(现场要求过的形态, 自己选音色): 移动就发声、停就不发声;
  音色柔和(阻尼正弦 ~90ms · 幅度 ~78% · 不刺耳); **间隔随速度** `= 1.8 ÷ 速度(mm/s)`(高频对应快速),
  ≥5mm/s 切高音/慢速低音; 迟滞 ~2.5s 判停(**段与段之间的小停顿不掐音**, 否则听起来一直在启停);
  **位姿读不到就静音**(宁可不响, 也不谎报在动)。
  实现 = 独立的 5~8Hz 读真值常驻小进程(`tools/motion_beep.py`), 每一声记日志(间隔 + 当时速度)便于对账;
  播放用 `paplay`/`pw-play` + 预生成 WAV(工控机常只有 HDMI/内置声卡 ⇒ 先实测一次真出声, 再向现场承诺)。
  - 🔴 **阈值的定法: 用「滑动窗净位移」, 不要用瞬时速度** —— 实测真值只更新 **~1.86Hz** 而监控脚本按 **8Hz** 轮询,
    同一帧被重复读 ⇒ 刷新瞬间 `dt` 被人为压小 ⇒ **静止时也冒出瞬时假峰**(实测平移单帧峰 6.28mm/s、姿态 2.90°/s,
    p95 6.06 / 2.23) ⇒ 0.5mm/s / 1.5°/s 这类阈值全被顶穿, 静止也响, 现场直接反问「你也没动, 怎么警报了」。
    定式: 滑 **1.2s** 窗取"窗首→当前"的**净**位移(零均值抖动不累积)。实测 22s 静止净姿态峰仅 **0.166°**、
    净平移峰 2.25mm(还含真值源自身慢漂移 ~1.25mm/s 后归零) ⇒ 阈值 **姿态 1.0° / 平移 4.0mm** 有 ~6 倍余量,
    真点动必命中。**验收条件写成「静止 ≥60 秒零响声」**, 不是"阈值看着够高"。
    数值表 / 复现探针 / 静止+点动两条验收: `references/motion-alarm-tuning.md`。
  - ⚠️ **改完阈值先确认它真被引用**: 实测 `DEBOUNCE_START_N=3` 这类常量**声明了但逻辑里 0 次引用**(真判据行仍是旧的
    单帧比较) ⇒ "3 帧去抖"是假的、改了等于没改。改判定件一律 `grep -n <常量名>` 数引用次数。
  - ⚠️ **多实例 = 双响**(现场听成"一直在响"): 按 pidfile / `/proc` argv 精确收成 1 个。
    日志里**每行出现两次**大多不是双实例, 而是启动脚本把 stdout 重定向进日志、日志函数自己又写一遍。
  - ⚠️ **先问清它响在哪台机器上**: 监控进程用**本机声卡**放音, 不一定在现场人员旁边 ⇒
    "警报没听到"经常是**声源不在他站的那边**, 先确认"谁会听到"再谈调参。
  - 🚨 **抬升要有专用警报**(现场口径形如「也可以抬升, 但要慢一些, 而且要发出警报声音。**先确认警报声音**」):
    抬升放开的代价必须用“**慢 + 可听见的警报**”补回来, 且**先把警报确认到真能出声**, 再谈动臂。
    实现同样放在监控侧、**不动执行器**(判据 = 真值 **z 分量**在涨, 如 `dz/dt > 0.3mm/s`): 抬升中**只响专用警报音**
    (更扎耳的多脉冲+颤音), 不与常规提示音混; 停升即回常规音。任何路径的抬升(页面/伺服/GUI 技能)都经过真值 ⇒ 全覆盖。
    警报 WAV **丢了要现场自愈重建** —— 安全件不许因缺文件而静默失效。
  - ✅ **声音的硬证据 = 录回环量电平, 不是“命令执行成功”也无需人耳**:
    `pactl info` 取 Default Sink · `pactl list short sources | grep monitor` 取回环源 →
    `ffmpeg -hide_banner -f pulse -i <monitor> -t <秒> -ac 2 -ar 48000 -f s16le /tmp/loop.pcm` →
    numpy 读 int16 算峰值/RMS(实测三音峰值 **82.4% FS** ⇒ 音频确实从声卡出去了)。
    回环只能证明“音频流发出去了”; “现场真听得到”仍要人在场确认(硬件音量/功放)。
  - **触发时机要零运动验证**: 把 `sys.modules["<真值模块>"]` 换成桩模块喂 静止→上升→静止, 并用桩
    `subprocess.Popen` 记录被播的文件; 判据 = 警报**只落在上升段**、数量/间隔对得上。
    ⚠️ 桩必须实现**完整 Popen 协议**(`args/stdout/stderr/pid` 属性 + `returncode` + `__enter__/__exit__` +
    `communicate/kill/terminate/wait`) —— 模块里的 `subprocess.run(["which",…])` 会逐个调到, 缺一个就抛异常。
- ⚡ **「速度慢」/「调了没用」: 面板值 → 真进链路的 `speed` → 四道收口 → 名义 vs 实测, 逐层核**。
  ① 先比对**日志里实际下发的 `speed NNN`** 与面板值(例: 面板填 200 实际发 150 就是技能字段截的) ——
  两者不等说明面板值没进链路(读输入框的时机/字段被中间层白名单吃掉), 别去调控制器/驱动。
  ② 再往上找**四道收口(自下而上)**: 代理 `MAX_SPEED_MM_S`(常在容器内、只读挂载 ⇒ 改它要重启容器) ·
  腿 `MAX_SPEED_MM_S` · 技能 `speed_max` · 服务端上限。只改面板数字、不动这几道 ⇒ 现场看到的就是"填了没用"。
  ③ 🔴 **名义 ≠ 实测: 轴的实际速度 ≈ 名义 ÷ 10**(三次独立位移轨迹测得一致) ⇒ 报"能到多快"必须用实测口径,
  并给出**当前天花板**(打满最小那一道后实际是多少 mm/s)。要"填多少就是多少"得改**换算系数**, 不是加倍数。
  ④ 🔴 **有"下发了但看不见"档**: 低设定值经换算后可能只有 **0.1mm/s(10 秒走 1mm)** ⇒ 现场就是"点了没反应",
  而日志有 `已下发`、真值也在动(极慢)。**判据: 连采真值 10~20s 看位移方向与速率** —— 在动 = 速度问题(见 ③),
  一丝不动 = 才按 §3f 查通道/闸门。**别把"太慢"报成"坏了"**。
  ⑤ 上层脚本/流水线常**自带写死的速度**(与面板无关) ⇒ 面板调它不动时先查那个脚本自己的常量。
  技能定义(注册表)是**热读**的: 改完下一条真实下发即生效, 不必重启执行器 —— 复核口诀 = 盯下一条的 `speed NNN`;
  改宿主/容器里的常量则要**重启对应进程**才生效。

## 5. 零副作用验证(不动真设备)

1. **过闸自检**: import 执行器模块, 直接调它的闸门函数(`_gate_blocks(<真实调用串>)`) → False/True + 原因串。
   要证明"这条规矩真的会拦"(而不是"代码里应该会拦"): **在进程内临时改小阈值, 再走真代码路径 dry 下发** ——
   `importlib` 加载执行器 → 猴补阈值函数(例 `taught_z_ceiling` → 0.20) → 调真 `dispatch(..., dry=True)`
   ⇒ 必须出现拒发行 · **无**「已下发」· 设备一动没动。零风险、可复制, 是最有说服力的一类证据。
   🔁 用户把**同一条安全规矩说了两遍** = 他第一遍没看到可验的东西: 不要再解释一遍规矩, 直接把它落成
   **硬闸门**(动态读现场数据源, 别写死坐标 —— 他改点位闸门自动跟着变), 并给出上面这条拒发日志的原始行。
2. **空跑规格**: 走真链路(FIFO→受理→回读→界面)但只算目标不下发(如 `{"skill": ..., "dry": true}`),
   终端要依次出现「已下发 / 目标与增量 / DRY-RUN / 受理」才算整链通。
   🔴 **但 `dry` 只对单步技能生效**(旋转/自转那两条路径才读 `spec["dry"]`): **多阶段技能(带 `steps`)不吃它** ——
   它是**整单预检**: 先把每段的守卫全算一遍, 任一段不过 ⇒ **整条计划零下发**(日志打到那段拒绝就停,
   受理行里**没有**「已下发」), 全过才逐段真下发。
   ⇒ ①别把"带了 dry 却没动"直接当成"dry 拦住了" —— 先读代码确认那一路有没有读它(本次就是靠读代码 +
   连采真值不变才排除"真动了 48 段"的误判) ②多阶段想零运动验证: 让某段**必然被拒**(或进程内临时改小守卫阈值) 停在预检;
   ③这条"预检不过即零下发"是天然的**安全垫**: 一次 97 段的复现计划, 第 49 段被爬升闸拒, 臂一步没动 —— 就是它兜的底。
3. **界面侧离屏起真类**: `QT_QPA_PLATFORM=offscreen` 下 import 真模块、实例化真对话框/面板类,
   调真方法(读闸门状态、模拟"已等 17s"调一次轮询), 不需要桌面/不弹窗。
4. 改完代码**重启对应进程**(GUI/守护)再验 —— 已 import 的旧模块不会自己更新。

## 6b. 现场反例与读法 (每条都被判过"没动")

1. **授权状态的历史包袱: 曾经只存在服务进程内存里 ⇒ 重启承载它的服务 = 授权失效**(现场现象: 刚授权完,
   点方向键「不动」, 复核 `auth.armed=false, ip=""`)。⇒ 改完流服务/任何承载授权的进程后**要复核授权状态**;
   把它落成**文件单一真源 + epoch**(见 3d)之后, 重启不再清授权(文件在、未到期就仍 armed),
   所以**不要**再无脑让现场重新授权 —— 先读一次授权状态再决定怎么回话。
   恢复(等价于页面两步授权, 源 IP 必须与被授权页面一致 —— 连本机 LAN IP 才会用该源地址):
   `curl -X POST -d '{"on":true,...}' http://<本机LAN_IP>:8793/ctl/arm`; 撚销同理 `{"on":false}`。
2. **判"动了没"只看真值采样 —— 但采样窗口必须盖住动作结束**。
   - 只看真值(TCP/关节逐点采样), 不看 `success`、不看日志「已下发」、不看「到位 0.0mm」这类自报。✅ 这条一直成立。
   - ❌ 但**采样太早会得出反向错判**: 驱动的 `success=True` 只代表服务端受理完成, 慢速单次动作(`speed=8`)实测
     十几~几十秒才停; 在回执后 60~80s 采样仍见位姿一位未变, 据此报过"控制器回成功却没动" ——
     之后同一目标位置(= 起点 + 10mm)出现在读数里, 说明动作其实执行了, 那条结论是错的、必须显式作废。
   - 纪律: 采样要**持续到出现目标值或跨过整轮超时**(单次慢动作至少看 60~90s 再回读一次), 过了窗口才允许说"没动";
     之前基于早采样发出去的结论, 要在回复里明说"作废", 别让现场拿着错结论往下追。
   - ⚠️ **`rc=6 · CHECK` 本身不是"被拒"的铁证**: 这条腿的代理在超时/拿不到回读时也会回 `rc=6/CHECK`
     (代码注释就记着"其实控制器还在走, 臂后来真的到位了")。判"没动"只认**真值采样跨过整轮预算**(上一条);
     判"被拒"要能指出是**哪条闸**(保护停字段 / 拒发行点名的层)还是**控制器**(无保护停字段 + 控制器报警日志有新增)。
   - ⚠️ 这类机器上时钟会被 NTP 回拨(实测小时级回跳; 驱动侧 ROS `stamp` 可差 ~2 天) ⇒
     **判事件顺序用文件追加顺序, 不用时间戳; 判新鲜度用帧龄(now − ts), 不用绝对时刻**。
     日志里出现"未来时间戳"的行 = 写入时时钟曾前跳, 不代表它在文件里排得更后。
3. **三查(上电/急停/碰撞)必须读"当下还活着的那条路"; 缓存 JSON 一律不作数 —— 但"驱动 topic"本身也可能是死的**。
   实测两代死法, 都要能认出来: ①缓存 `robot_status.json` 帧龄 87381s(>24h) —— 它只说明"上次谁写过";
   ②该 topic 的**发布者也不再通告端点** ⇒ 任何新订阅者 0 帧(`ros2 topic echo --once` 拿不到),
   而**位姿那条直连控制器会话一直新鲜** ⇒ 三查改走与位姿**同源**的那条路读 SDK 原生状态
   (`powerState / operationState / operateMode`), 由采样器顺带写一份 `state.json`(2s 一刷),
   页面按 `ts` 算帧龄; 直连也不可用时才退回缓存, **并如实标成旧值**(不许把小时级旧值当"当前无报警")。
   判据: `state.json` 的 mtime 与 `date` 差 <5s = 活; 别用"某个长连老订阅者还在收"证明一条话题是活的。
   报警类真值见第 7 条。

7. **事故/报警的真值 = 控制器自己的报警日志, 不是任何推测**。日志给到 编号+时刻+物理量+阈值, 一次说清
   "谁在什么时刻撞了什么、撞的是哪个关节"(例: 「检测到碰撞，关节传动力矩超限！触发柔顺停止。
   2轴 101.024243 Nm > 限定 101.000000 Nm」+「RSC检测到关节[2]碰撞力超限，触发安全停止」)。
   读法(只读·零下发): 与位姿同一条 SDK 会话上 `queryControllerLog(N, {LogInfoLevel.error/warning}, {})`;
   现成探针 `tools/rokae/dump_controller_log.py`。页面/汇报里"急停/碰撞"按**报警时刻的年龄**分级:
   3 分钟内的当"当前"(拦得住动作), 更早的只当历史(「上次碰撞 07:55 关节2(安全停止)」) ——
   既不能把历史当现在, 也不能因为"当前无报警"就把历史抹掉(现场要的是"每一次"都留痕)。
   📎 死源/活源怎么分辨、怎么把显示接到活路(含页面字段映射与"一行状态"契约)见
   `references/status-source-forensics.md`。
   🗂 **"每一次都留痕"要落成自动台账, 不靠人记**: 从控制器报警日志自动识别碰撞条目(力矩超限码 + RSC 超限码),
   ±N 秒配对同一次事件只留一行; **事件当时的位姿只在"事件后 N 秒内首次看到"才采**(设备触发保护后会停住 ⇒
   那时读数 ≈ 事件点), 采不到就如实写"未采到", 倒序落一份原子写的 JSON; 展示挂在页面同栏的列表卡上
   (形态约定见 `user-facing-dashboard-delivery`)。上游日志缓存只有最近十几条 ⇒ 老事件靠落盘文档留档。
   📎 **撞后处置顺序**(停执行器 → 主动停设备 → 撤授权 → 取证 → 落档)与台账口径见
   `references/incident-and-alarm-ledger.md`。
4. **授权与通道都正常时, 下一步是去找慢层的"拒发"行**(最容易被漏掉的一步)。
   - 判据链: `auth.armed=true` + 点击记录 `dry=false` + 真值位姿不变 ⇒ **先按 3f 排除"受理了却没走到设备"**
     (最后一条服务调用行的时间 vs 现在 · 实例数必须 = 1 · 控制器无新报警) —— 确认通道真发出去了, 才轮到这个分支 ⇒ 去执行器日志找
     ⚠️ 别用"位姿没变"排除通道问题: 通道死掉时位姿同样一丝不变, 两者现象完全一样。
     「🛑 被拦(慢层·VL 判断): **不安全**(risk=… · <裁决时刻> 裁决) … ⇒ 拒发」这一行, 它带风险等级 + 危害列表原文。
   - **逐条**把危害读出来, 并把每条翻译成现场能做的一个动作(「人臂伸进围栏内工作台上方」→ 人退到围栏外;
     「全局相机被近距人脸/身体遮挡」→ 人别站在该视角正前方)。只回一句"不安全"= 等于没答复。
   - 同时给反证: 真值位姿全程不变 = "被拒没发", 不是"发了不动" —— 两者的处理完全不同。
5. **裁决输入里有一路死源 ⇒ 每轮都带坏图, 永久抬高拒发率**。
   - 语义层的输入是多路拼图(工具相机/全局/顶视/深度…), 任一路停更(实测深度路死在 26.6h 前那一帧)
     都会持续出现在裁决画面里, 每轮被判「画面异常/伪彩混乱/时间戳与其他画面不同步」⇒ 拉高拒发率。
   - 体检: 读每路状态里的 `age_s` / `stalled` / `dead` / `frames_served`; `dead=true`、`frames_served` 不增长、
     `age_s` 到小时级 ⇒ 那一路要修, 别用"其它几路正常"放过。
   - 修那一路往往要重启承载它的服务 ⇒ 会触发第 1 条(授权失效), 修完让现场重新两步授权。
   - ⚠️ **“设备整路缺失”比“帧停更”更硬, 症状是“全部动作都被拒”**: 相机根本没枚举到
     (`lsusb` 里就没有那台设备 · 设备解析脚本输出 `-1` · 页面那格恒 `无帧`) ⇒ 拼图里是**空白格**,
     语义层每轮都写「关键<某视角>画面缺失, 无法确认动作路径无侵入」⇒ fail-closed ⇒ 不只
     某一类动作, 是**所有**运动全被拒(现场会当成“闸门/机器坏了”)。判据一次定性: 列 USB 设备 +
     跑一次相机解析; 处理只有两条路 —— **把设备插回**(换口/供电/换线) 或 按 3b 关闸,
     **不要去调闸门阈值/保鲜期**。
6. **防抖规则会让现场觉得"时好时坏"**: 有的实现里"同一动作相邻两轮结论不一致(上轮原始=安全) ⇒ 从严当不安全"。
   ⇒ 现场看到"刚才还能动、现在不动了"不是随机故障; 解释时要带上这条规则, 并给出稳定通过的判据
   (清场后连续两轮都 safe, 或对这一段用现场一次性授权)。

**「机器在原地反复升降」= 同一"回点"技能被重复下发, 不是循环/自走。** 多段回点技能的结构是
①就地抬 50mm(相对) ②高位平移到目标正上方(绝对) ③垂直下落(绝对); 臂**已经在目标正上方**时,
第②段的目标就是当前位置 ⇒ Δ=0 空段不下发 ⇒ 现场看到的运动只有"抬 50 → 落 50"= 原地上下, 连点 N 次 = N 遍。
判据(只读): 执行器日志里**数计划** —— 一个完整计划是一对 `已下发 阶段 1/N` … `受理: ✅ 全部 N 阶段完成`,
数出几对就是下发了几次(`grep -a -c '已下发 阶段 1/'` 对 `grep -a -c '全部 3 阶段完成'`);
再用 `GET /ctl/status` 的 `last_cmd` 看是不是同一点位技能、来源是不是同一个按钮。
⇒ 汇报要把"第几次点击 = 第几个计划"对齐给现场, 别只说"动过了"; 也**别把现场自己的重复点击当成执行器自走/死循环**去查
(慢层复用窗内秒过时, 连点会连着起好几个计划)。

## 7. 「断点打不中」/ 想看下发链: 先定执行发生在哪个进程, 别为看日志改执行器

现场问「我在跑 L5 / 点了 MoveIt 节点, 为什么断点进不去」时, 按这个顺序答, 不要先怀疑调试器:

- **上层节点逻辑 ≠ 执行器**。画布/编排节点里的实现常常只做「构造 + 探针」(三查 / plan / 读状态),
  **一行下发调用都没有**; 真下发在**常驻执行器进程**里: 队列(FIFO) → 执行器 → `ros2 service call …`。
  先证伪路径: `grep -rn "\.move_pose(\|move_pose(" src/ tools/` 看这条链到底调没调那个函数, 再谈断点。
- **断点只在被调试的那个进程里生效**。IDE 的调试会话是它自己新起的进程, 与常驻执行器不是同一个 pid。
  判法: `pgrep -af <执行器脚本>` 取真实 pid + 启动时刻; 想断就 attach-by-PID 到它。
- 🔴 **别把断点留在'可能正在动'的真实执行器里** —— 断在那 = 暂停下发。只在设备静止时挂/停, 或干脆不用断点。
- 🔴 **不要为了看日志去改执行器源码**: 执行器常带热加载(`maybe_reload`), 存盘可能触发重载 ⇒ 现场在跑的时候
  等于动生产进程。零侵入定式 = **只读追日志镜像**: tail 执行器日志 → 解析 `ros2 service call <服务> <接口>` 行
  → 追加落 JSONL(时刻 / 服务 / 接口 / 技能名 / 是否 DRY-RUN), **不写队列、不碰进程、不改判据**(实测工具:
  `tools/l2_dispatch_watch.py`)。这比断点更适合现场: 不暂停执行。
- 镜像必须**同时解析新旧措辞**, 并把每行归类成 `pending(目标) / verdict(放行·否决·已关闭) / dispatch(已下发) / accept(受理)`:
  执行器日志文案换过之后, 只匹配旧关键词(如 `ros2 service call`)的镜像会**一条都抓不到** —— 现场明明在动, 镜像却恒 0 条。
  判据: 镜像条数为 0 时**先怀疑解析词**, 从现网日志里搜出真实动词再改(用 `search_files`), 别急着说"没下发";
  改完**要让镜像进程重启**(已 import 的旧模块不会自己更新), 再复验它抓得到新动作。
- **"这段时间到底有没有下发"的零侵入判据(三件一起看)**: ①队列文件(FIFO)的 mtime ②执行器日志最后一行时刻
  ③日志里的 `受理: DRY-RUN(未下发)` / `已下发` 行。三者都停在同一个旧时刻 ⇒ 那段时间**根本没有下发到执行器**,
  现场说"我点了"也就不是执行链的问题 —— 结论要这么给, 别含糊成"可能是网络"。
- **同源调用点要分清**: 同一个执行器类可能只被**脚本**直接 import(跑那些脚本时断点会命中), 而生产路径走
  「队列 + 服务」。汇报里必须写明"哪条路径命中断点、哪条不会", 否则现场会拿调试脚本跑通当成生产链也通。
- **三类证据凑齐再回话**: 真实执行器 pid+启动时刻 · 队列文件 mtime · 执行器日志尾。缺一条就别下结论。

## 6. 汇报口径(给现场工程师)

按**时刻表**给证据, 一行一步: 点击时刻 → 裁决时刻(耗时/结论) → 下发时刻 → 设备回执时刻,
再给出「点击到真动 = N 秒」这个总数, 并说明这段等待是设计还是故障。
把"被拦"与"在等"分开说。没跑通就说没跑通, 不要拿"应该有动作"当结论。
