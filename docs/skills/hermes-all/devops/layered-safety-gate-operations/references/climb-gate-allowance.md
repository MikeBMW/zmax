# 抬升闸的放行量 (`allow_climb_mm`) —— 回「高位点」的按钮为什么点了不动

## 规则（不许放宽）

多段计划里相对**计划起点**的抬升 > `climb_limit_mm`(默认 **100mm**) ⇒ 执行器**拒发**。
现场规矩原文：升高不要超过 10cm（来自一次真撞：横移高度写成"目标点z+180mm"，与起点无关）。

⇒ 任何**本身记在高位**的点（安全点/退让点/准备退让位）从低处回点，所需抬升**必然**超限，
现场看到的就是"点了这个按钮没反应" —— 那是闸，不是按钮坏、不是链路断。

## 判据行（先读日志尾，不要猜）

```
🛡🛡 阶段 1/3 拒发: 相对计划起点抬升 219mm > 上限 100mm
```

受理行里没有「已下发」= **零下发**（与"慢/在途"是两回事，汇报要分开）。
注意可能同时出现一行"计划级抬升豁免(adapt_point)…不计入自主多抬"——豁免曾被有意取消，
**看拒绝行才算定案**（豁免行不是放行）。

## 放行通道（两条必须同时成立）

1. **请求带 `allow_climb_mm=<毫米>`**（执行器从 `spec` 读；夹到 [0,1000] 防填错）。
2. **端点必须显式透传该字段**。8793 `POST /ctl/move` 只转发白名单字段，其余**静默丢弃** ——
   症状恰恰是"现场说动、臂不动，执行器还在报拒发"。加透传后，请求 → FIFO 命令 → daemon `spec` 才成立。

现场口径：**规矩不放宽，把"人确认"做进链路** —— 拒发回执里带放行量，页面在已记点位的按钮上
弹一次「现场已目视确认上方净空、无人?」，**确定**才带同一个数重发，取消就不发。
绝不：改闸门阈值、给某个技能写死放行量、默认带上放行量。

## 零动作验收（成对跑，缺一条就是没透传）

同一个技能，只改放行量：

```
POST /ctl/move {"skill":"<回点技能>","speed":8,"arm":0}                  # 不带放行量
POST /ctl/move {"skill":"<回点技能>","speed":8,"arm":0,"allow_climb_mm":<同一个数>}
```

期望：前者必见拒发行；后者必出**完整 N 段计划**，含真实 `ros2 service call /move_line …` 目标与逐段
`Δ=(±x,±y,±z)mm ↑上升|↓下降|→平动` 拆解（`arm=0` ⇒ 只出计划，不下发）。
报给现场时把"相对当前的高度变化"和"绝对高度"一起给，别只给绝对 z。

## 别踩

- **别用 `arm=1` 去测"应该被拒"的动作**：授权窗内（默认 5~10 分钟）它会被合法接受并**真的下发**。
  要看闸是否生效一律 `arm=0`。
- 目标点本身就高 ≠ 可以自动放行；只有人确认才能给放行量。
- 拒发回执要指路（哪一层闸 + 为什么 + 需要的字段），只写"被拒绝"现场等于"没反应"。
