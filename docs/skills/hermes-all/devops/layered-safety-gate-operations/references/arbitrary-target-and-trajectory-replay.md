# 只走位置 / 按人拖动的轨迹复现 —— 任意绝对目标怎么过闸

适用: 现场说「你得按照我拖动的轨迹走」, 或要把臂送到一个**没有示教过**的坐标(回某个中途位、
沿一条已探明的路径扫场)。核心矛盾: **执行器的绝对目标只认命名点位**, 而人的轨迹有几十上百个点。

## 1. 不要把航点塞进点库

`plan_stage` 的非 rel 分支只从点库解析目标(`pts[name]`, 无则 `点位 X 不在点位库`)。
往 `space_points.json` 里写几十个航点 = 把现场 UI 的点库刷威垃圾(他那排按钮就是靠它画的)。

**正确做法 = 在执行器里加一个内联目标分支**(与命名点位同一收口、同一闸门、同一审计):

```python
# plan_stage 的非 rel 分支开头
_tp = st.get("to_pos")                     # 3 元内联绝对目标
if isinstance(_tp, (list, tuple)) and len(_tp) == 3:
    name = str(st.get("to_label") or "path")
    t = [float(v) for v in _tp]
    _tq = st.get("quat")
    if isinstance(_tq, (list, tuple)) and len(_tq) == 4:
        q = [float(v) for v in _tq]
    else:
        q, _qsrc, _qage = _fresh_quat()    # 只走位置: 姿态现读(不吃陈旧缓存), 不转姿态
else:
    ... 原命名点位分支不动 ...
```

步骤 JSON 形如 `{"stage": i, "to_pos": [x,y,z], "to_label": "traj_007", "tol_mm": 2, "timeout_s": 40}`。
- 只走位置 = **不引入旋转**, 风险最小; 要跟随人的姿态就把 `quat` 显式给 4 元(逐段小角度变化才可接受)。
- 改完 **必须重启执行器** 才生效(代码不是热读, 注册表才是)。

## 2. 轨迹从哪来 — TCP 直读流水

`~/zmax_data/rokae_sdk/tcp_out/tcp_direct_<采样器启动日>.jsonl` · 5Hz · 平铺
`{ts,t,x,y,z,rx,ry,rz,qx,qy,qz,qw,frame,src,joint}` (与页面同源, 只读)。

- ⚠️ **用 `ts`(epoch)定时段, 不要用 `t`** —— `t` 带 8h 时钟偏移(NTP 回拨), 会让你把不同时段当成同一段。
- ⚠️ 文件名是**采样器启动那一刻**写死的(可跨天), 一律取**最新存在**的那个, 别用今天日期拼。
- 抽段定义: 相邻采样间隔 <2s 且位移 >0.3mm ⇒ 连续运动; 间隔 >2s = 断开(人手停顿/换段)。
- 采样: **每 25~30mm 一个航点**。这个间距不只是为精度 —— **单段位移小, 天然避开 >260mm 触发的
  50113/50102 奇异规避**(人拖的路径天然无长直线)。
- 现成工具: `python3 tools/traj_from_tcp_log.py --path <jsonl> --from HH:MM:SS --to HH:MM:SS
  --spacing 25 [--reverse] --skill-id L2.replay_traj --out /tmp/traj.json [--register]`。
- 🔴 **先问清"起点"是哪个起点**: 整段轨迹的起点(他开拖前臂的停放位) 与 "第一个运动段的起点"
  可能相隔几百 mm。报目标时把坐标并写出来让现场确认, 别拿自己的理解往下跑。

## 3. 这种技能的守卫怎么配(否则第一次就整单拒发)

- `guard.max_lin_mm` ≥ **单段最大位移**(实测 25mm 间距时约 57mm)。小于它 ⇒
  `本阶段目标点 traj_xxx 离当前位姿 Nmm, 超过守卫 N ⇒ 先点动靠近`. 本来就是小段, 给 120 就够。
- 阶段级 `guard.dz_down_limit_mm` ≥ **单步最大下降**(实测 ~46mm), 给 100。
- `z_floor_point` + `z_floor_offset_mm`: 把地板放在**轨迹自身最低点略低处**
  (例: 参考点 z=0.2166 + offset −70mm = 0.1466, 而轨迹最低 0.1604)。
  偏移量取**他自己的轨迹**算出来的数, 不要自己拍一个"看起来安全"的。
- **爬升闸是按"相对计划起点"算的**: 人拖的轨迹往往跨几十上百 mm 高差 ⇒ 中段必然超 100mm 上限:
  `🛡🛡 阶段 49/97 拒发: 相对计划起点抬升 111mm > 上限 100mm 「现场规矩: 升高不要超过 10cm」`。
  两个选择, **优先前者**: ①让现场重新拖一条低高差的路径 ②现场明确授权后, 下发时带
  `allow_climb_mm=<他轨迹实测的最大爬升>`(取他的数, 不自己定), 并在汇报里写明"值来自现场轨迹 + 现场授权"。
- 多阶段是**整单预检**: 上面任一条不过 = 全部阶段零下发(受理行里没有「已下发」)。
  所以"加了 allow_climb_mm 再发"是安全的: 过不了就不会动。

## 4. 下发与验收

```
printf '{"skill": "L2.replay_traj", "speed": 150, "allow_climb_mm": 300}\n' > ~/zmax_data/l2_cmd.fifo
```
- 逐段验收: `grep -aE '✅ 阶段 [0-9]+/97 到位' <执行器 stdout>` 数到位段数; 完成判据永远是
  **TCP 真值 vs 目标**(到位偏差 mm), 不是回执 success。
- **速率与 ETA 用到位行的时间戳算**(例实测 2.07 段/分钟)。现场臂速约 1~3mm/s ⇒ 3.6 米路径 ≈ 40~45 分钟;
  短航点还会叠加"每段固定开销", 所以"段数多 + 速度低"两者共同主导时长 —— 报 ETA 用实测, 不算理论。

## 5. 改成"边走边采"(一趟干两件事)

如果这一趟的目的本来就是扫场/建图: **在轨迹走的同时就开采集**(`gs_capture.py --out <会话目录> --hz 8 --secs 0`),
采集器本来就是"边动边采 + 逐帧配对位姿"的设计, 到终点再停。比"先走一趟到位、再重走一遍采"省一整趟。

## 6. 开工前的静默坑

- **动之前先算整组点位的 Δz 并报给现场**: 新录的一组点若跨高差, 固定顺序里必然有多段"需要上升" ⇒
  与"绝不抬升"直接冲突 ⇒ 执行器**整单拒发**。先报"哪几段要升、升多少", 由人决定手动上位/换顺序/只跑无上升的点。
- **重启执行器加载新代码**: 走**脚本文件**按显式 pid 杀(命令行里出现脚本名会匹配到自己那条命令 ⇒ 自杀),
  再跑保活脚本; 重启前连读两次真值确认臂静止(位移 ≤0.05mm)。
- **动作在飞时绝不重启执行器 / 绝不重发** —— 在途指令不会撤销, 重发 = 并起第二个计划。
- 说话口径: 报"沿他的轨迹反走 N 段 / 每段多长 / 预计多久 / 到位偏差", 不要只报"已下发"。
