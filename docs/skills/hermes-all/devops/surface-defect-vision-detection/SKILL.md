# 表面缺陷视觉判据 (本机算法 / 借产线算力)

## When to Use
- 用户说工件表面**有缺陷**(划痕 / 凸凹不平 / 磨花 / 污点 / 麻面), 要你检出来。
- 要判一片**面积很大或强度很弱**的缺陷, 小斑块判据抓不到。
- 本机没有缺陷检测权重, 又不该拿 VLM 的"是/否"冒充判决。

前置: 图要已经是**摆正后**的模块 ROI(`judge-image-rigid-body-rectify` 的口径)。在斜的整幅图上判缺陷, 后面全白做。

---

## 🔴 铁律 0: 先定缺陷形态, 再选算法 —— 形态错则全盘错

| 形态 | 像素表现 | 判据 |
|---|---|---|
| **线状**(划痕/裂纹) | 细长、方向一致、跨很长 | Hough 共线接续 + 长宽比 + 排除贴边 |
| **斑块**(坑/凸起/麻点) | 局部起伏大、圆度高、面积小 | 局部 std + 圆度 + 明暗跨度 |
| **大片**(凹凸不平/磨花) | 整片持续偏高、**峰值不极端**、形状不规则 | **片内平均** + 大核平滑 + 不看圆度 |

开工前先量/先问: 是**线**、是**点**、还是**一片**? 别默认是划痕。

> 实测踩过: 用户说"表面是有划痕的", 我按线状追了两轮(78px → 830px 还做了定量), 用户才纠正
> 「那个长线是**正常的安装接线**, 缺陷是**凸凹不平**的」—— 两轮全废。

---

## 🔴 长直线多半是正常结构, 不是缺陷

安装接线、模块棱线、夹具边都是**横贯整宽**的直线, 比真缺陷还长。
- 排除距上下沿 **<8px** 的直线: 实测 `y=186 长1094` / `y=0 长985` 都排在真缺陷 `y=93 长830` **之前**
- 追到一条特别长的直线时, **先问用户"这条是不是结构件"**, 再决定要不要做定量

---

## 🔴 遮罩正常结构必须设硬上限 —— 遮掉的往往正是缺陷

为排除"安装接线"用 `HoughLinesP` 找长直线做遮罩, 2 通道 × 3 核尺寸重复检出同一条线,
加上凹凸区本身的方向性纹理也被当成直线 ⇒ **遮掉 46.8%**, 而网格一打就看见:

| 区域 | 局部 std | 被遮罩 |
|---|---|---|
| 右侧 | 25~41 | **55~99%** |
| 左下 | 30~35 | **80~93%** |
| 中间(平坦/正常) | 8~11 | 13~76% |

⇒ 缺陷区被整片遮死, 报 0 个候选。

**修法**: 只取**最长几条** + **总遮罩硬上限 12%** + 只看近水平线(`|dy| ≤ 3`)。修后同一帧报出 4 大片。

🔴 **每次做完遮罩, 必须打印"每格被遮 X%" 并与该格的不平整度并排看**; 遮罩率 >20% 就停下来重想,
而不是继续调下游阈值。遮罩是唯一一种"越努力越错"的预处理。

---

## 🔴 大片缺陷不能用峰值判据

实测同一帧: 一片缺陷 **峰值 z=3.77 而片内均值只有 1.45**; 一个 32×29 的小坑峰值 z=6.60。
用「z峰值≥6 + 圆度≥0.2 + 面积≥300」筛 ⇒ **大片全被筛掉, 只剩小坑**。

大片的正解:
- 用片内**平均** z(持续性), 不用峰值
- **大核(31×31)平滑**先把图像平滑一遍: 单点亮斑被摊平, 只有成片的区域还能过阈值
- **不看圆度** —— 大片本来就是不规则的, 要求圆度高等于把它排除
- 面积门槛按**占模块百分比**(1.5~2%), 不按绝对像素

---

## 检验「算法到底看到了什么」: 网格诊断

没有视觉也要能判断。把 ROI 切 **4×12 格**, 打印每格的 局部std均值 / 被遮罩%, 缺陷区会自己跳出来:

```
         c1      c2      c3   ...   c9     c10    c11
中带   15.8     28.1    17.6       27.9   40.9   33.2
下带   30.2     30.9    30.2       22.8   30.5   30.6
```

中间 8~11(平坦) vs 两端 30~41(缺陷) —— **数据早就在眼前, 是判据把它筛掉了**。
先打网格再调判据, 比反复改阈值快一个量级。

---

## 线状缺陷: Hough 共线接续才量得出全长

连通域是按"对比度连续"切的 ⇒ 一条长划痕中间有一处亮度过渡就断成 8 段, 于是只报最亮那段(78px)。

```python
cv2.HoughLinesP(bw, 1, np.pi/180, threshold=25,
                minLineLength=60, maxLineGap=60)   # maxLineGap 足够大才能跨断点接续
```

- 实测 **78px 段 → 696~830px**(占模块 64~76%): 一条长划痕的量级差 10 倍
- **端点不稳是常态**(实测右端 878 vs 1009): 多组核大小/间隙各跑一遍取稳健上界, 别拿单组参数报死数
- ⚠️ OpenCV 5.0 的 `HoughLinesP` 返回 `(N,4)`, 不是 cv4 的 `(N,1,4)` ⇒ 用
  `np.asarray(L).reshape(-1)[:4]` 解析, 直接 `L[0]` 会 `TypeError: numpy.int32 is not iterable`

---

## 🔴 不要用 VLM 的是/否当缺陷判据

实测本地 SmolVLM(500M): 同一张图问「有划痕吗」答 **yes**, 问「是不是完全干净、无划痕」也答 **yes** ——
**顺着问题说(yea-saying bias)**。它的 yes 是"你希望我说 yes", 不是"图里有缺陷"。

- VLM 只配出**描述**(如 "metallic connector with a small hole in the center"), **不能出判决**
- 验一个 VLM 能不能当判据, 两条一起做:
  1. **空图基线**: 纯黑/纯灰/纯噪声 各问同一问题 —— 全答 no 才算不是无脑 yes
  2. **反向提问**: 同一图问相反的两个问题 —— 两个都答 yes ⇒ 有 yea-saying bias, 不可用
- 500M 级模型给 JSON schema 模板会被**照抄**, 改二选一提问也救不回判据能力

---

## ⚠️ 单帧局部统计会抖: 报结论前先量重复性

实测同一工件、同一曝光、同一姿态, 两帧的 top-1 候选从 `[447,138,32,29]` 变成 `[50,155,61,17]`
(前者直接掉出候选榜)。局部方差对微小曝光波动和镜面反光极敏感 —— 低曝光下模块只有 112 灰度, 信噪比本来就紧。

- 报结论前**连拍 3~5 帧**, 只有**持续命中**的才报
- 或多帧取中值再算 std
- 两帧结果对不上时, 先承认"这一条不稳", 不要挑好看的那帧当结论

## 借产线算力: 直接调工控机的加密 YOLO

本机没有缺陷权重(或类别不对)、又不该拿 VLM 冒充判决时, **别自己训** —— 反向通道能在工控机上跑任意 Python,
权重和签名都不用碰(加密 `.pt.enc` + 解密器 `yolo_detector` 全留在工控机)。

```python
# 工控机端调用形态(实测通过)
import sys, json
sys.path.insert(0, r'D:\xspace\ultralytics_AOI')
from yolo_detector import YoloDetector
d = YoloDetector()                       # 无参; 一次加载 housing + gf, 预热 5.6s + 2.1s
d.detect(path, detect_type='housing')    # 也吃 'gf'
```

链路四步:
1. **送图**: 本机写进 8794 静态目录(`agent_hub.py --dir` 指的那个)
2. **入队**: `gui-venv311/bin/python tools/agent_hub.py --enqueue "<PowerShell>"` —— PS 里
   `Invoke-WebRequest` 把图下到 `C:\Windows\TEMP\`, 再调产线解释器跑检测
3. **解释器**: `D:\xspace\ultralytics_AOI\venv\Scripts\python.exe`。🔴 **`python` 不在 PATH**,
   裸写会报「无法将项识别为 cmdlet」⇒ 必须写全路径; 路径从在役进程的 `CommandLine` 里捞, 别猜
4. **回执**: `zmax_data/agent_hub/out/<epoch>.txt`, 含
   `{"result":0,"detections":[],"detect_count":0,"saved_incoming":...}`;
   命中时 `detections[*]` 带 `xyxy / class_id / class_name / confidence`

三条硬坑:
- **引号地狱**: Python 源码 base64 → `[Convert]::FromBase64String` → `WriteAllText`(UTF8 无 BOM) 落成 `.py` 再跑
- 🔴 **回执必须按文件 mtime 判"这是本次的"**: 通道是 **pull 模式**, 工控机还没来取命令时最新 out 文件里躺的是
  **上一轮的 RESULT_JSON** —— 实测直接读 `outs[-1]` 拿到几分钟前那次的结果, 差一点当成新结果。
  **入队前记下最大 mtime, 之后只看 `mtime > t_mark` 的文件**
- 额外起一个 detector 进程是安全的(实测 GPU free 3359/4096 MB, 产线服务无感)

### 送入前必须「摆正 + 不过曝」—— 过曝会把缺陷冲掉

同一工件、同一摆正, **只改曝光**:

| 送入图 | 模块 ROI 死白 | 工控机 YOLO |
|---|---|---|
| 摆正 + 48000us | **90.74%** | `detect_count = 0` |
| 摆正 + 3000us | **1.72%** | `detect_count = 1` · conf **0.473** |

⇒ **「没检出缺陷」先怀疑过曝把细节冲掉, 不要先怀疑模型或类别表**。

按**模块 ROI**(不是整帧)扫真实曝光, 死白率随曝光**单调恶化** —— 和"降曝光压死白"的直觉相反:

| us×gain | ROI mean | 死白% | 清晰度 |
|---|---|---|---|
| 48000×1.8 | 244 | 90.74 | 12.0 |
| 12000×1.8 | 223 | 76.11 | 135.6 |
| 5000×1.8 | 171 | 19.30 | 85.1 |
| **3000×1.8** | **110** | **1.72** | **44.6** |
| 2000×1.8 | 73 | 0.21 | 24.4 |

- **3000us×1.8 是平衡点**: 死白进 5% 口径而 mean 仍有 110; 再降到 2000us 死白更低但 mean 73、清晰度 24.4, 细节开始丢
- 降 **gain**(1.8→1.33)也能压死白(5000us 时 19.3%→5.94%)但清晰度一起掉(85→58)
- 3000us 下**也能直接搜到刚体**, 不必来回切档(省两趟 ~2.6s settle)
- 送**整幅旋正图**, 不要只送裁出来的模块条 —— 裁剪改了画面构图, 模型见过的比例/留白全变
- 工控机的类别表可能**没有你要的那一类**(housing 只有 pit 等) ⇒ 它检不出 ≠ 你没做对, 换本机算法或提类别

## 交付口径

- 每个缺陷必须报: **位置 xywh / 尺寸(px + 占模块%) / 量化特征**(明暗跨度 · 起伏幅度 · 局部 std)
- 放大图 + **剖面曲线**(穿过缺陷中心的水平/垂直灰度曲线), 2~5px 宽的缺陷在 1400 宽压缩图上会糊掉
- 输出用 **JPG q≥93 保原始像素**(PNG 太大发不出去, 缩到 1400 宽又会丢细节)
- 图上标**编号**, 判不准时**让用户指认**("哪个是真缺陷?") —— 用户指认的才是真值,
  算法候选永远只是候选, 别自己挑一条当结论

## 自检清单 (缺一条就不算做到)

- [ ] 形态判定过(线/点/片), 且与用户描述一致
- [ ] 遮罩率 ≤12%, 且打印了每格被遮%
- [ ] 大片用均值判据、小斑块用峰值判据 —— 没混用
- [ ] 边缘(距上下沿 <8px)的直线已排除
- [ ] 同一工件连拍 ≥3 帧, 结论稳定
- [ ] 缺陷报的是尺寸+量化特征, 不只是框
- [ ] 未用 VLM 的是/否当判决(或已跑过空图基线+反向提问)
