# 成品图「被切/糊/跳」的裁切范围取证 (配方)

适用: 用户对着**加工出来的图**(AOI 判据图、裁剪条带、任意定尺渲染图)说
「上边和下面少了一小块」「为什么反而更模糊」「还在跳」。
这些常常是**同一个裁切框**的三个侧面, 先量后改; 量的对象是**原图坐标里的那个矩形**。

## 0. 先确认"两边的图是同一帧/同一比例"
- 跑加工链的那张帧(如工控机 `GET /preview.jpg`, 2448x2048) 与页面上给用户看的「整板原图」
  (如本机快照 `1400x1171`) 若**长宽比相同** ⇒ 它是等比缩放 ⇒ **在任一张上量出的相对位置 1:1 通用**, 就在用户看的那张上画框。
- 必须明确输出哪张 URL 给用户 —— 画在哪张, 数字就报哪张的坐标。

## 1. 截取框 = 加工函数的返回值, 不是猜的
```python
clean, meta = clean_judge_frame(rgb, out=900, return_natural=True)   # 加工链本体
x0, x1 = (meta.get("x_trim") or {}).get("x_span") or (0, meta["src_w"])   # 列裁
Y0, Y1 = meta["kept_rows"]                                                 # 行带 + pad
best = meta.get("candidate") or {}          # 检测带本身: {y0,y1,h,sat,edge}
nat = meta["natural"]                        # 原比例条带(未加工)
```
- `kept_rows` = 检测带(`best`) 上下各 `DEF["pad"]`(实测 8) 行;
- `x_span` 在**没有饱和列**时返回**全宽** ⇒ 常常把大片背景一起裁进来(实测目标只占宽 63%)。
- 直接拿这个框画在原图上, 不要用"目测"。

## 2. 真实范围用独立口径量 (不信程序自己的带)
逐行数「亮块段」(行内亮于 `bg + 0.45*(p97-bg)` 且宽度 6~40px 的连续段)个数:
```python
cnt[y] = 亮块个数            # 目标行的特征: 个数 ≥ 6 且宽度量级一致
real_band = 最长的 cnt>=6 连续段
```
- 该口径与"边缘密度 P92"独立 ⇒ 可用来量化"检测带切掉了多少行":
  `上少 = max(0, Y0-real_band[0])`, `下少 = max(0, real_band[1]-Y1)`。
- 左右跨度同理: 只在 real_band 行内累加亮块列 ⇒ 取 1%~99% 分位 ⇒ 建议框的 x 边界。
- ⚠️ 累加列剖面时**必须先限定在 real_band 行内**, 否则会把画面别处的亮结构算进来(实测宽 1155 vs 真实 879)。

## 3. "糊"量化: 输出像素当量
```python
sx = 内容宽 / 条带宽 ; sy = 内容高 / 条带高       # 内容区 = 画布去掉上下/左右留白
1 输出像素 ≈ (1/sx) 源像素  # 横 ;  (1/sy) 源像素  # 纵
```
实测(定尺 900x332, 内容 864x225): 源条带 1400x81 ⇒ `sx=0.62`(1 输出 px = 1.62 源 px)、
`sy=2.79`(**1 输出 px = 0.36 源 px**)。
- `s>1` = 输出比源像素还多 = **插出来的细节** ⇒ 一定看着糊;
- 两个方向都不该 >1; 有背景白占像素时, 紧裁能把 `sx` 拉回 ≈1。
- 对照历史口径能看到为什么"以前更清": "先纵拉 3× 再缩到定尺" = 净缩小; "缩完再拉" = 更糊。

## 4. "跳"量化: 源抖 × 放大倍数
- 先量**源**行带逐帧极差(实测 ±1px), 再乘上 `sy` 就是**输出**上看到的抖(2.79×1 ≈ 3px)。
- 输出侧量法: 逐帧取成品图, 算 ①内容行范围(行均值 > 背景中位+12 的头尾行) ②质心行 ③与上帧整图平均绝对差,
  报**极差**(实测 12 帧: 质心极差 **3.0px** / 上沿极差 **5px** = 用户嘴里的"跳")。
- ⚠️ **取帧源选错会得出"不跳"的假结论**: `/snapshot/<slot>.jpg` 在**没人在看那条 MJPEG 槽**时是**冻帧**
  (实测连取 8 帧逐位相同 / 帧差 0.00) —— 槽是给 MJPEG 客户端用的, 没人拉就不重抓。要量跳变就**解析 MJPEG 流**
  (`逐帧找 ffd8…ffd9`)而不是快照。
- 顺手判"多口径逐帧切换": 新口径常会画一个外框(纯绿系) ⇒ 逐帧数绿像素, 若**有的帧有大片绿(新口径)、有的帧几乎没有(回落旧口径)**
  ⇒ 那就是"逐帧在两种渲染之间切"= 用户看到的闪, 这是**路径切换**不是抖动。

## 5. 修法配方(与用户对齐范围后再改)
1. **紧裁**: 行 = 真实范围 ± ~8 行; 列 = 目标列跨度 1%~99% 分位 ± ~8 列 ⇒ 不切、也不把背景压进输出。
2. **不拉伸**: 输出画布尺寸不变(页面布局/显示口径不动), 内容 **1:1** 居中贴在深色画布上(留白而不是拉伸);
   要更宽就**加宽画布**而不是压缩内容。
3. 抖动的根是放大, 去掉放大后残留的 ±1px 就看不见了; 若还要稳, 在**时间维**锁带(静物用中位/保持上帧带),
   不要在空间维继续调阈值。
4. 同套口径的另一路(如另一台相机/另一个检测项)记账: **同时改还是先只改一路**, 在汇报里写明。

## 6. 证据图的交付(用户要"我看看范围"时的标准做法)
- 画布: 左 = 原图(框外 `*0.4` 压暗, 绿框 4px, 真实范围青线, 建议框黄) 右 = 现在那张成品图(放大到 ~720 宽) + 文字块。
- 🔴 **`cv2.putText` 画不了中文** ⇒ 转 PIL: `ImageFont.truetype("/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc", size)`;
  line/text 颜色是 **BGR**(要青色写 `(250,210,60)`; 写 `(60,190,250)` 会得到橙色 —— 实测踩过)。
- 存 **PNG**, 放静态目录, URL `http://<host>:8799/dl/<file>.png`。无头屏时也可直接给绝对路径。

## 7. 为什么 URL 要给 .png (静态服的 CT 表)
本机 `tools/dashboard_server.py`(8799) 的 `/dl/<file>` 只服务 `tools/web/dl/`, 响应类型走写死的表:
`.html/.json/.apk/.png/.js/.css` —— **没有 `.jpg`** ⇒ JPEG 回 `application/octet-stream`,
浏览器**下载而不是内嵌显示**。要用户"点开就能看"就存 PNG; 要改的话把 `.jpg/.jpeg` 加进 CT 表(需重启该服务)。
判据: `curl -s -o /dev/null -w '%{http_code} %{content_type}\n' <url>` 应为 `200 image/png`。

## 8. 本类问题的校准数字(2026-10-12 实测, 用来做量级参照)
| 量 | 值 |
|---|---|
| 原图/页面图 | 2448x2048(加工链) · 1400x1171(页面) · 同长宽比 |
| 截取框(页面坐标) | y400~481(81 行, 整图 6.9%), x 全宽 |
| 检测带 + pad | 边缘密带 408~472 + 上下各 8 行 |
| 真实目标范围(独立量) | y389~513(125 行), x232~1111(63% 宽) |
| 被切 | 上 11 行 / 下 32 行(整图 0.9% / 2.7%) |
| 输出像素当量 | 横 0.62×(1 out px = 1.62 src px) · 级 2.79×(**1 out px = 0.36 src px**) |
| 跳(12 帧, MJPEG) | 源带 ±1px → 输出质心极差 3.0px / 上沿极差 5px |
| 建议框 | x232~1111 · y381~521 |
