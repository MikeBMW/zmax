# 相机画面异常取证 (全黑 / 偏暗 / "图是不是真传过来了")

## When to Use
- 面板/窗口里图片框**全黑**, 或用户问「图片是不是真传过来了」「相机是否真在采集」。
- 检测节点(如 AOI 金手指/表面)喂进去的图没内容, 但接口返回 200 / 日志说"取到照片 N KB"。
- 相同时段**一会儿黑一会儿正常** —— 需要分清是"设备坏/参数跑偏"还是"现场光照/遮挡"。
- 用户对着**成品图/判据图**提意见(「歪斜」「太亮/过曝」「右侧那块不是产品」「只保留 X, 其余全黑」「多带了背景」)
  —— 要改的是"人看的那张图"的渲染口径, 且必须先把形容词**量化成像素统计**再动手(见
  `references/judge-image-rendering-and-region-forensics.md`)。

## 铁律 0: 文件大小不是证据 (最容易骗人的一条)
纯噪声**不可压缩**, 所以一张"全黑"图也能有 2 MB+ 的体积。
实测: PNG 2448×2048 = 15,040,512 像素, 全图 `mean=3.35/255`, `max=5`, `std=0.52`
(只有读出噪声底, 全部落在最低灰阶桶) —— 文件 2,324,280 B。**只看大小会得出"图没问题"的错误结论。**

## 三步取证 (每步都要有数字, 不许用形容词下结论)

### ① 传输/显示层: 本机字节 vs 源头字节
```bash
curl -s -o /tmp/now.png "http://<dev>/picture"                    # 面板走的那条取图通道
smbclient //<dev-ip>/<share> -U 'user%pass' -c 'cd <dir>; get <同名文件> /tmp/src.png'
md5sum /tmp/now.png /tmp/src.png                                  # 相同 ⇒ 传输层无关, 问题在成像
```
顺带核一次**文件大小 ↔ 日志里的 KB** 是否精确对应(`2291901 B ÷ 1024 = 2238.2 KB`),
这是"面板收到的就是那只文件"的最短证据。再取 `?meta=1`(若有)要文件名/拍摄时间。

### ② 成像层: 像素统计(判定唯一依据)
```
mean / std / min / max / 低灰阶桶占比 / 中心与四角 200×200 均值
判据:  max ≤ 12 且 mean < 8   → ⚠️ 全黑(只在拍但进光≈0)
       mean < 25              → ⚠️ 偏暗(进光不足)
       否则                   → ✅ 正常
```
可直接跑 `scripts/image_health_probe.py <文件或URL>` (输出上述全部指标 + 判定)。

### ③ 采集真伪: 源头文件时间戳 + 序号连续性
- **触发时刻对秒**: 我按下技能/接口的同一秒, 设备侧出现新文件 ⇒ 每次请求都真拍真落盘。
- **文件序号连续性** ⇒ 采集服务**没有重启** ⇒ 曝光/增益参数没被重置(常驻相机参数只在首次
  open 时设一次) ⇒ 变量只可能是**光/遮挡**, 不是参数或代码。实测: 同进程内 23:14 全黑、
  23:15 正常(mean 75.2 / max 164)、次日早上全黑 —— 同一进程、参数相同, 黑/亮来回变。
- **两帧差分非零**(如 38.7% 像素有差异) ⇒ 传感器在实时重新曝光, 不是静态占位图。

## 🔒 用 webcam 做"量测"前先锁死曝光 (2026-09-27 实测: 差分/跟踪的共同前提)
笔记本/USB 相机默认 **自动曝光 + 自动白平衡**, 画面平均亮度会自己漂。
实测同一静止场景连拍: 帧均亮度极差 **5~20** ⇒ 任何**帧间差分/模板匹配**都会把静止背景当"动的东西",
连续 4 种自动找目标的方法全被这一个变量毁掉。
```bash
sudo apt-get install -y v4l-utils
v4l2-ctl -d /dev/video2 --list-ctrls | grep -iE 'exposure|gain|white_balance'   # 先看当前值
v4l2-ctl -d /dev/video2 -c auto_exposure=1 -c exposure_time_absolute=140 \
         -c white_balance_automatic=0 -c exposure_dynamic_framerate=0
```
锁死后同场景连拍 4 帧亮度极差 **20 → 0.20** ⇒ 差分才可用。
- `auto_exposure` 的值: **1 = Manual**(要的就是它) · 3 = Aperture Priority(自动, 出厂默认)。
  手动之外的其他控件会显示 **`(inactive)`** —— 看到 inactive 就是还没切手动成功。
- 判据不能靠"深色/面积大"找目标: 那样必然被**更大更黑但静止**的东西抢走(托盘/键盘/阴影)。
  唯一可靠的判别条件是**帧间位移**; 最稳的用法是**先让 VLM 在一帧上点准目标, 再用差分/光流跟到其余帧**。
- 反例记录(都实测踩过): 帧间差分→曝光漂移污染 · 深色团块→静止托盘 · 深色+运动→静止键盘 ·
  模板匹配→NCC 0.28~0.60 落在静止背景。⇒ 先锁曝光, 再谈算法。

### ★★ 锁曝光是**临时动作**, 用完必须恢复 (2026-09-27 自己踩的坑)
锁死只在"做差分/量测的那一会"需要。**用完不恢复 ⇒ 这台相机从此永久偏暗**, 而且现场会
把它当成"相机坏了/被挡了" 排错半天 ✗✗。实测(笔记本内置 `/dev/video2` = Integrated RGB Camera):
```
auto_exposure=1(Manual) + exposure_time_absolute=40   →  画面 mean=8.01, 84.7% 像素近全黑 ✗
auto_exposure=3(自动)                                 →  画面 mean=100.55, 低灰阶仅 1.8% ✓ (亮 12.5 倍)
```
**判据(画面长期暗, 30 秒定位)**:
```bash
v4l2-ctl -d /dev/videoN --list-ctrls | grep -iE 'auto_exposure|exposure_time_absolute|white_balance_automatic'
# value=1 (Manual) 且 exposure_time_absolute 远低于 default(实测 40 vs 默认 156) ⇒ 就是这个原因
v4l2-ctl -d /dev/videoN -c auto_exposure=3 -c white_balance_automatic=1     # 恢复
```
- **手动值会一直存着**: 切回自动后 `exposure_time_absolute` 显示 `flags=inactive` 但仍记着 40 ✗,
  此时写它报 `Permission denied`(inactive 控件不可写) ⇒ **将来任何一次误切 manual 会立刻再次变黑** ✗。
  要么彻底别锁, 要么锁完在同一处恢复。
- 判定"暗"必须用**像素统计**(mean/std/低灰阶占比), 不许用文件大小(铁律 0)。
- 一行防复发: 恢复后 `stats` 里该路 fps 应**不变**(实测曝光 40→自动, local 仍 15.09fps)
  —— 若帧率被长曝光拖低, 说明选到的是"靠拉长曝光补光", 需改增益/补光而不是继续加曝光时间。

## 显示链路自证 (别把"窗口显示不了"当显示 bug)
用**同一解码/缩放路径**解一张已知正常的亮图, 看统计是否正常:
```python
pm = QPixmap(path); img = pm.toImage()          # Qt 路径
# 亮图 mean=75.21 ⇒ 显示链路没问题 ⇒ 黑框只是"如实显示了一张黑图"
```
另外: **无论窗口能不能显示, 都把原图落到本机稳定路径并给出绝对路径**
(用户偏好原话: 「如果在状态空间的窗口显示不了，那就保存让我用别的看图工具打开」)。
命名带来源与时间戳, 例: `~/zmax_data/aoi_frames/gui_received_074402.png`、
`ref_bright_0919_2315.png`(对照组), 并保留一张固定名的"最新一帧"便于反复查看。

### 网页那一格「没图像」: 在**真浏览器**里量画布像素, 别只信 200/字节数
接口全绿(`/snap/<key>.jpg` 200 + 50KB + magic `ffd8` + 两帧 md5 不同)与「用户屏幕上真有画面」是两件事。
判据落在**页面画布**上(`browser_navigate` 到那页 → `browser_console` 里取样):
- 对主画布 `getImageData` 抽样算 `mean` 与暗像素占比, **隔 ~1.5s 再算一次**: `mean>30` 且两次数值不同才算“真有画面”。
  对照: 底图 canvas `mean≈112` 而叠加层 canvas 全 0(透明黑)是很正常的一对, 只看均值会把透明层误判成故障。
- 同时读页面自己的无图横幅(`getComputedStyle(document.getElementById('nofeed')).display`)—— 它显示 = 前端已连续多次
  取帧失败, 比任何后端指标都直接。
- 这类页面常是“单帧 JPEG 轮询 + 解码成功才换上”的泵 ⇒ 服务短暂停 1~2s 会自愈, 但用户屏幕上可能停在横幅/旧帧上。
  **接口全绿时正确处置是让他刷新一下, 不是重启服务** —— 重启只会把页面再打断一次, 还会被当成“你越改越坏”。
- 先确认是哪一条链在供图(页面轮的 `/snap/<key>.jpg` vs `/cam.mjpg` MJPEG), 再去查对应的上游; 两条链可以一死一活。

## 🧊 用画面下结论之前, 先证「源是活的 + 这一帧是新的」
画面能取回来 ≠ 它是现在拍的。发布端冻结(节点进程僵死/崩溃)时会**一直吐同一张缓存帧**, 而且回得极快
(实测连取 8 次 md5 全同、0.001s 秒回 —— 比正常还"快"), 最容易骗过"接口 200 + 图非黑"这一层粗判。
拿这种图去判读场景 = 把几小时前的现场当现在, 结论必错, 而用户会把画面当结果。
- **解释像素之前先过新鲜度闸**(顺序固定, 不许省):
  ① 连取两帧比 md5, **相同 ⇒ 已冻结**, 转采集/发布链取证(`references/ros-image-chain-forensics.md`);
  ② 读发布端自己的状态口(如桥的 `{"n","age_s"}`), `age_s` 大于一轮间隔就是停了;
  ③ 判读/标注/汇报一律挂**拍摄时刻 + 帧龄**, 帧龄大就明说"这帧是旧的, 不能当现场”。
- **确认源曾冻结后, 要回头作废用它得出的结论**: 冻结窗口内发布过的画面判读(物体在不在、槽里有没有料、
  姿态、朝向)**全部不成立** ⇒ 源恢复后重取一帧重判, 并在回复里明确指出"前面那条基于冻结帧, 作废”。
  省了这一步, 用户会拿着一个错结论继续往下追。
- **"源已恢复"仍要复测帧率**: 恢复只证明有新帧, 实测恢复后发布侧仍可能只有 0.2~2fps ——
  这时"画面不连续"的瓶颈在发布端, 别去优化显示/播放端。
- **多路拼图/多路状态要逐路看存活, 不要只看聚合 fps**: 状态口通常每路带
  `{fps, age_s, src_age_s, stalled, dead, dead_s, frames_served, age_basis}`。判死源就三条:
  `dead=true` / `frames_served` 不增长 / `age_s` 到小时级(实测某路 26.6h、`frames_served=1`)。
  一路死源不只是那一格难看——它会**被拼进下游判据/模型裁决的画面**, 每轮都被判成「画面异常/伪彩混乱/
  时间戳与其他画面不同步」, 抬高下游的拒发/误判率。⇒ 逐路修, 别用"其它几路正常"放过。
  ⚠️ 修那一路往往要重启承载它的服务 ⇒ 会清掉其进程内状态(如页面授权), 修完提醒现场重新确认。

## 🛰 主机不在产线网段 ⇒ 服务命令行里写死的**内网 IP** 会静默全死 (2026-10-22 实测)

现场原话:「机器人的相机，怎么看不到」, 给了两个页面 (8797/ar · 8793/station)。两页同源 (8791 cam_live_stream),
而那几格的做法只是如实显示 8791 的 `/stats`: `arm online=false frames_served=0 age_s=-1`。相机本身**没坏**。

- **判据顺序**: ① 页面 → ② 它读的 `/stats`/`/api/cams` 逐路行 → ③ 服务**自己的命令行** (`tr '\0' ' ' </proc/<pid>/cmdline`) → ④ 源端口直连一次。
  实测卡点在第 ③ 步: `--arm-http http://192.168.23.66:8792/frame.jpg` 写死产线网段, 而本机只有 WiFi `10.163.146.78/23`,
  **没有 192.168.23.0/24 路由** ⇒ 每帧 `No route to host`, 重试日志 20 次才打一条, 于是"服务在、端口在、页面在, 就是没图"。
- **同一条链的两个数就够了**: 直连目标 `curl --max-time 4` = 000/No route; 本机 ssh 转发口 `/health` 回 `{"n":133万,"age_s":0.1}`
  ⇒ 相机活、链路死。**别去查曝光/驱动/USB**, 那些在这类故障里全是无关变量。
- **修法 = 候选源自动切换, 不是改死一个地址**(网络会来回变: 现场 WiFi / 产线网段 / 转发口):
  服务里 `--<key>-http` 支持逗号多值 + 环境变量兜底 (`ZMAX_ARM_HTTP_FALLBACK=http://127.0.0.1:18792/frame.jpg`),
  失败 N 次就换下一条, 换到能出的那条停住, 只打一条切换日志; `/stats` 里带 `src_url`/`src_switch`/`src_err`,
  页面和我都能一眼看出这帧是从哪条路来的(**别让"能看图"掩盖"图从哪来"**)。
- **同一个坑通常不止一路**: AOI 两路 (金手指/表面) 默认源 `192.168.23.23:10082/10083` 同样是内网 IP, 一起 offline;
  实测本机已有 `ssh -L 127.0.0.1:10082:192.168.23.23:10082` 转发 (可直接 `/region` 200 · `/picture` 110KB 真图)
  ⇒ 重启时一并给 `ZMAX_AOI_HOST=127.0.0.1`。**修一路顺手扫其它路的源地址, 别等用户下一次说"另一台也不行"**。
- **转发口必须有保活**: 手工 `ssh -NT -L` 一掉, 相机就"又看不到了", 而代码里看不出任何错。
  保活判据三层 (缺一即重起): 端口在听 + `/health` 的 `n` **在增长**(在跑不出帧也要重起) + 进程 cmdline 含该端口;
  用 `setsid nohup ssh -NT ...` 拉起, cron `@reboot` + `*/3`, 正常时**输出 0 字节**。
- **验收要落在像素与页面上, 不是 200**: `/snapshot/arm.jpg` 两帧 **md5 不同** + `mean≈183 / 暗像素 0%`;
  再到真浏览器里取样画布 (`canvas 0 mean 194.9 / dark 0%`) —— 底图 canvas 亮、叠加层 canvas 全 0 是正常的一对。
- **顺手核的另外几路**(同一次只读取齐, 一条回复): `depth` 帧龄 54 万秒 = 容器 `ros_depth_stream` 源停写;
  `local2` 无帧 = 启动参数 `--local2-dev -1` 显式关闭; `rs`(D435) 8789 未起, 且 `lsusb` 里没有该设备 (物理没插);
  TCP 位姿 8032s 陈旧 = 同一条网络问题 (SDK 代理直连 192.168.23.160), 与相机无关但页面会一起报警。

## 结论口径 (四选一, 每条都要挂数字)
1. **没传过来** — md5 不一致 / 字节数对不上
2. **没采集** — 设备侧无新文件 / 序号不前进
3. **采到了但没进光(黑)** — 像素统计如上 + 序号连续 + 差分非零 ⇒ 查光源/镜头盖/工件在位/曝光
4. **显示/解码问题** — 同路径解亮图异常 / QPixmap 加载失败

## 自动化: 图像类 HTTP 取回应自带"健康度 + 帧龄"
在取图的客户端(常驻执行器/助手脚本)里落盘 + 量化输出, 而不是把二进制灌进日志:
```python
if raw[:8] == b"\x89PNG\r\n\x1a\n" or "image" in ctype.lower():
    open("~/zmax_data/aoi_last_frame.png","wb").write(raw)
    log("图像 %.0fKB · 2448x2048 mean=3.48 max=5 → ⚠️全黑(相机在拍但进光≈0) · 拍摄 07:56:38 · 帧龄 59s"
        % (len(raw)/1024,))
```
- **禁止** `body = r.read().decode("utf-8","ignore")` 打日志 —— 满屏 PNG 乱码且丢失一切有用信息。
- 支持 `?grab=1`(现场重拍一帧) 与 `?meta=1`(文件名/拍摄时间) 这类 query; **帧龄**要和画面一起给,
  否则用户看的是几十秒前的旧帧却以为实时(与"负帧龄拒用/画面要标状态"的红线同源)。
- 语义分离: 「读当前照片」与「重新拍一张」做成两个入口 —— 检测判决是异步跑在**上一张**上的,
  若把读图改成重拍, 画面与判决就不同源了。
- 🔴 **取图接口对不认识的参数会静默忽略, 照样回 200 真图** ⇒ 探接口时 `200 + 合理字节数`
  **不能当成「这个参数被采纳了」**。实测 `?picture` 上加 `name=<历史文件名>` 回 200 / 49KB 真 JPEG,
  但内容就是**当前帧** —— 库里 54 张历史原图一张也没取到。
  判据: **参数变了内容必须跟着变** —— 用两个期待不同结果的参数各取一次, 比 md5/像素统计;
  相同就是参数没生效。要取历史图只能靠**服务端真支持的文件名/目录端点**(去源码里数路由),
  或者走反向命令通道让那边把图打包送过来; 两者都不存在时**如实报「取不到」**, 别把当前帧当历史图用。

## 🎯 「画面在跳 / 图没了」先量两个数: 整幅均值(排除曝光) + 锐度基线(定位镜头)

诊断顺序固定, **别一上来就怀疑曝光或算法** —— 这两次测量就能砍掉一整类假设:

- **整幅亮度均值逐帧恒定 ⇒ 曝光/AE/光源一次性排除**。实测连续帧整图 `mean 45.16→45.51`(极差 0.35 · std 0.13),
  而**上下半区亮度反相关**(一边升一边降) ⇒ 跳的不是成像参数, 是**工件在视场里平移**(模板追踪 y 逐帧
  +7 / +26 / +138 / +162px)。这组签名(整幅均值恒定 + 区域反相关)一句话就能把结论从"相机/曝光在跳"
  改成"**工件在动**" —— 后者是机械/工装侧, 改代码没用。⇒ 此时再去扫曝光/增益/光源是纯浪费
  (实测把 曝光×增益 全网格扫一遍, 关键指标一次都没出现过中间值)。
  同理: 程序自报 `ExposureAuto/GainAuto` 已 Off(代码里在设曝光/增益之前先调 `set_auto_off()`)时,
  更不要把它当变量 —— 先看均值是否恒定。
- **锐度要用同机基线对比, 判到"镜头/进光"而不是"算法"**: `cv2.Laplacian(im, cv2.CV_64F).var()`
  对同一台相机同一镜头有稳定量级 —— 实测同一条带: 好帧 **17.4** vs 坏帧 **1.6**(低 11 倍),
  再配上 p95 亮度(好帧上百 · 坏帧 25)与**唯一亮块的位置**(实测只剩右下角一块)
  ⇒ 结论 = **严重失焦 + 进光极低**; 处置是**现场拧对焦环/补光**(工件在、灯亮但相机没对上焦),
  软件只能"报数 + 盯对焦": 让现场一边拧、一边定期回读【锐度 + p95】, 拧到锐度回基线量级为止。
- 用户说「图没了 / 整版原图怎么没了」时: **先确认接口给的是不是真 JPEG**(magic `ffd8` + 合理字节数)。
  是真图就**别追管道**, 直接落到像素内容上(本案 `mean=19 / p95=25` —— 一张"合法但几乎全空"的图),
  把"图没了"翻译成数字再回答; 否则会去查网络/服务/端口, 白跑一圈。
- **改相机的接口常只认 query 参数, 而且写方法必须与路由声明一致**: `POST /param?exposure=24000&gain=6` ✅;
  发 **JSON body 会静默 no-op**(回 `applied: {}`, 一个键都没进) · **用 GET 带同一串 query 也照样静默无效**
  (路由声明 `GET=只读 / POST=写` 时) ⇒ 现场体验都是「你说调了, 可没变化」。
  🔴 **回执会骗人**: 只读 GET 的响应里夹着上一次写入留下的 `last: {us_ok: true, ...}` ⇒ 看着像"写成功"。
  ⇒ 规矩三条: ①先 `curl -X OPTIONS -D - http://<ip>:<port><path>` 或读源码路由声明确认**写方法**;
  ②写完必须**回读一次**确认值真变了 **而且画面真变了**(值变了画面不变 = 假可控);
  ③"画面变没变"要**超过同档重拍的噪声底**再判, 否则把帧噪声当成灵敏度(见下「爆炸/增益判据要按 ROI」)。

### 🌑 画面近全黑时, 扫一遍曝光就能把「相机坏」和「视野里没东西」分开

**两分钟的测试, 能省掉几小时的瞎猜。** 按 4 档把曝光拉上去, 每档同时记 **`mean` 和锐度(`Laplacian.var`)**:

| 曝光 us | mean | 锐度 |
|---|---|---|
| 5000 | 9.5 | 0.4 |
| 15000 | 30.5 | 1.1 |
| 40000 | 83.8 | 2.2 |
| 80000 | 162.4 | 2.5 |
| *同机正常基线* | ~110 | **44.6** |

- **`mean` 随曝光线性上升 ⇒ 相机在响应**: 快门/增益/传感器/到传感器的光路**全部正常** ⇒ **不是相机故障**,
  别再查 USB/带宽/驱动/设备号。注意: 一面白墙也会随曝光线性变亮 —— 单看 mean 只能证明"相机没坏",
  证明不了"画面里有东西"。
- 🔴 **判「视野里有没有东西」看锐度, 不看亮度**: 上表 mean 从 9.5 涨到 162.4(17 倍)而锐度只从 0.4 到 2.5,
  离同机正常基线 44.6 差 **20 倍** ⇒ **相机在拍、亮度也能拉、但视野里没有工件/没对上焦**。
  这类只需一个锐度基线对比就定案, 且结论是**远程改不了**(要现场摆件或拧对焦环)。
- 正确处置: 把相机结论写成「相机健康 · 无工件在视野」而不是「相机坏/曝光不对」, 并把**四档数字一起给现场**
  —— 这是他能直接行动的证据; 同时**停止改代码**, 不要再在算法/标定上打转。
- 🔴 **扫完必须恢复原值并回读确认**(值层面零变更), 别把诊断档留在产线上; 回读后顺手看一眼画面回到原亮度。
- ⚠️ 写曝光的**传参形态要先读源码路由声明**: 实测同一类服务有的只吃 **query string**(`POST /exposure?us=5000&gain=1.8`)
  而发 **JSON body 直接回 400 BAD REQUEST**; 另一种实现是**静默 no-op**(回 `applied: {}`)。
  两种表象相反但治法一样 —— **不要靠试错猜, 去看源码里 `@app.route` 的写方法声明与参数解析**。

## 🔍 模糊/复焦判据 (2026-09-24 真实测, 三条"想当然"被否)

场景: AOI 图模糊 → 要不要移机械臂去"复焦"。相机在臂上 (eye-in-hand) ⇒ 臂动=相机动 ⇒ 沿光轴移动即对焦移动。

**① 有效帧闸放最前面 (真机实测缺口)**: 现役 AOI 帧 `~/zmax_data/aoi_last_frame.png` (2448×2048) 实测
**mean=8.4/255 · std=2.38 · 全图 Tenengrad≈4 · 9 宫格全平** = **黑帧/无结构帧** → 对 0 结构的图判"清晰度"毫无意义。
判据 `ten<50 或 std<5 或 mean<3%` → `no_target`: **不判不修**, 先查取图链路。

**② 模糊量用 σ_est(px) 表达, 且必须选对反演指标**: 高频能量比在 σ≥2px **下溢乱跳** (σ_est 4.7→18.3 非单调);
**拉普拉斯比** `σ = c·sqrt(1/√(lap/lap*)−1)` 在 **0.5~6px 全程单调** (0.41/0.77/1.02/1.47/1.85/2.44/2.96) →
只有它能当扫焦信号。`q = exp(−(σ/2)²)`, **q_ok=0.78 ⟺ σ≤1.0px**; 相对标定帧归一, **禁用绝对阈值**
(同一 σ 在细节丰富 ROI 上 lap 可差 10×; 旧 AOI 的 `focus_min=60` 就是这个坑)。

**③ 归因: 图像判"糊不糊", 系统状态判"为什么糊"**
- 运动模糊**不能**用图像方向性判: 实测 ① 方向依赖 (0°/90° 拖影 aniso 反降到 0.52×/0.62×基线, 漏检)
  ② **深离焦把方向性比抬得比真运动更高** (2.70× vs 2.17×) → 用它会误杀离焦。正解 = **臂速 (编码器真值) >0.15**。
- 曝光判据**相对参考帧** (`mean < 0.5×ref`): 暗场工件 mean 8.4/255 属正常, 绝对阈值 0.15 会全体误报欠曝。
- "能否修" = **扫焦后 q 峰值能否到放行线** (`q_best ≥ q_ok`), 不是"q 随 Z 变不变" (相机在臂上, 任意模糊都随 Z 变)。

**④ 扫焦律用对比检测式 AF, 不要梯度爬山**: 深离焦 (σ>4px) 时 q 落地板 ≈0.11 **无梯度** → 爬山实测
12mm 偏差走不回来。正解 = 微探 ±1mm 定方向 → **3mm 粗扫 ±travel/2 (不依赖梯度)** → 1mm/0.3mm 细化。
实测 (真机 D405 真图 + 合成离焦): σ 估计误差 0.056px · 单帧量测 2.75ms · 两方向起步 (-9/+12mm) 均复焦成功
· 扫焦峰值落点 ±0.00mm。

**⑤ 修不了的别修**: 扫焦后仍 `q_best < q_ok` (或曲线平坦 <5%) = 端面散射/破损/污染/遮挡 → 报 NG 转人工,
**绝不"移臂硬修"**; 也不在接触/插入段动 Z (阶段白名单 + L2 收口闸)。

实现/证据: `src/lerobot/policies/left_right/state_space/focus_quality.py` · `tools/blur_refocus_demo.py` (10/10 判据)
· `tools/probe_focus_metrics.py` (指标探针) · `tools/diag_aoi_frame.py` (真机帧诊断)
· 方案: `docs/design/fusion_localization_blur_refocus_20260924.md`

## 📈 “数出来的数”帧间跳变 (同一姿态下计数忽多忽少) —— 先量三列, 别先改算法

症状: 程序自报的**个数/分片数**在跳(实测 16/18/19), 而**几何姿态全程不变**(框中心/倾角/残差都稳)。

- **取证(先量再改, 三轮共 20 帧, 全程只读)**: 每帧同时记三列 ——
  ①待查指标(程序自报的计数) ②它依赖的**预处理窗**(裁剪/ROI 起止, 如 `x_trim.dropped_cols`/`x_span`)
  ③**上游亮度量**(如 `sat_before`/条内饱和占比/整幅均值)。
  实测: 计数 16 与 19 **一一对应**裁剪窗 `[0,493]` 与 `[0,442]`, 而亮度只在 3 个离散档间漂(0.235/0.279/0.294)。
- **真因范式**: 预处理里用的是**绝对阈值**(如边缘强度 `|dI/dy| >= 2.5`) ⇒ 亮度一动、窗端点就动 ⇒
  端上的目标“这帧够格、下帧不够格” ⇒ 计数变。
  ⇒ **参数回执会骗人, 别拿它当判据**: 工业相机在 `ExposureAuto/GainAuto` 开着时**每帧覆盖写入**,
  而 `/param` 的 `now` 照样回你设定值(实测回 20000/40000 恒定, 画面却自己在漂)。
  **最快的判据 = 写两个差异大的值看亮度跟不跟**: 写大值反而更暗、写小值反而更亮 ⇒ 写值根本没生效,
  相机还在自动档(反着走是因为它以目标亮度自动互抵)。想区分"参数没生效"与"光真变了", 只认这一条。
  **修法: 重启采集服务** —— 让"尚未开始采集"那段初始化时序去跑 `set_auto_off()`(实测重启后原始帧亮度 10 帧恒定)。
  ⚠️ 采集过程中写参数是**静默失败**; 而**为了写参数先停采集**会把相机卡死, 别试这条路。
  这也只治"取像在漂"; 若回执可信、写值也确实生效、亮度仍在漂, 才是光源侧。
  ⇒ **定位"跳"在哪一环: 同一次抓取同时取"上游原图"与"派生图"**, 比两者均值/帧间差**是否同比例同相跳**。
  实测原图与判据图**同步同比例(1.28×)跳** ⇒ 跳在读像之前 ⇒ 渲染/算法层的一切改动都是白改
  (先去查错层是这类调试里最常见的浪费)。
  ⇒ 还差一层: **应用层的"按视角/工况档位"会被服务重启打回默认**(部署/异常/人工重启都会, 即使相机侧
  自动项已关)。实测同一视角在默认档下判据图每 4~5 帧整幅换区域(均值 13.7→50.7 · 帧间差 55.6% · 行带在
  1039/1469/1199 间跳), 换回该视角该用的档立刻恒稳(帧间差 0.9~5.4%, 行带恒定) —— **同一现象、两个量级不同的亮度环境**。
  ⇒ 规矩: 凡"改设备参数"的功能都要问一句**"重启后它还在吗"**; 不在就落盘 + 把复原挂在重启路径上
  (部署/启动钩子里自动补), 否则现场看到的是"改过没用/自己变回去了", 而代码里看不出任何错。
- **修法**: 把该绝对阈值改成**按本帧对比度归一化**的相对阈值; 只动“人看的图/判据”那条渲染路径,
  **模型吃的那张图的裁剪函数一行不碰**。验收 = **同一帧做多档亮度缩放离线复放, 每一档都给对值**。
- **选档要按“跨帧恒定性”, 不按单帧最好值**: 扫描 N 组(曝光×增益)×M 帧, 取**读数逐帧完全相同**的那一档
  (实测赢家是唯一 4/4 帧同为 18 的一组; 其余组单帧值好看但帧间在跳)。单帧最优值在这里没有意义。
- ⚠️ **诊断期别在用户盯着的时候现场扫参数**: 每改一次档画面就整幅跳, 用户看到的是"你越改越跳"。
  要扫就先声明"接下来这一段的跳是扫描造成的", 或在录好的帧序列上离线扫; 事后汇报必须把自己的干预
  从故障现象里**摘干净**(哪些帧的跳是我造成的、哪些是真故障), 否则用户无法判断到底修好没有。
- ⚠️ **改了没效果 = 假设被证伪, 不要上线**: 怀疑渲染层某段(如 p99 自动增益)时, 先拿同一批帧做 A/B
  (改前 vs 改后各打一遍图); **逐像素完全相同 ⇒ 该段根本不是原因** ⇒ 撕回补丁、如实上报。
  没有 A/B 就上线, 等于把一个无效改动留给下一个排查的人当"已修"。
- ⚠️ 别去调下游的**资格窗口/认领阈值**去凑数 —— 端上的目标已被裁掉, 下游怎么调都会抖(治到症状上)。
- ⚠️ 别把这类跳变成“动机械臂去调姿态”: 固定姿态下数值都在跳 ⇒ 病在上游预处理/算法。
  粗判法: 同姿态连拍 N 帧, 指标**跳** ⇒ 不是姿态问题(动臂无效); 稳定但不好 ⇒ 才值得考虑动臂。

### 🔬 计数**恒为 N±1**(不跳) 时: 别去扫曝光/增益, 用「带内计数不变量」一刀证伪

先分清两种病: 忽多忽少(16/18/19…) ⇒ 亮度/上游; **恒定多 1 个(N vs N+1) ⇒ 算法侧**。
- 现场第一反应常是"过曝把某个结构多认了一个"。**一次扫描就能证伪, 不要改相机参数**:
  在**算法已选中的那条正确带**内把像度拉开(实测 5 曝光 × 5 增益), 过曝量掉 **10 倍**而**计数恒为 N+1**
  ⇒ 多出的那一个**不是过曝造成的**。
- 🔴 **判据: 全网格里若从未出现过"目标值−1", 就没有临界点可言** —— 实测出现过的一切计数值只有
  `{1..17, 20}`(目标 19, **18 与 19 一次没出现**)。继续调暗不是"20→19", 而是**带选择崩塌**:
  算法抢到另一个假周期结构(带位置与 pitch 双双跳变 —— 实测 band 跳 200px、pitch 报 278~438), 计数掉到个位数。
- 🔍 **判"算法是不是选错了带"用客观量, 别用肉眼/最亮行**: 沿**全图高度**逐行算**列向自相关**, 在已知节距的 lag 上取峰 ——
  真键排会给出明显峰值(实测现役带 0.4~0.79), 而旁边看着更亮/更周期的候选带只有 0.24~0.28
  ⇒ 现役带是对的, **别去改选带规则**(目检很容易反过来: 把"更亮的那条"当成真排)。再沿真节距把带切成 N 格、
  逐格量**衬度**, 用一个一个格确认"这一格是一个真件", 比看整条带的统计量开题得多。
- 🔪 **改算法前先做一次消融**: 只把那个疑心的阈值放宽(实测"重切分电平"从 190 放到底), 若读数**一点不变**
  ⇒ 那一级不是瓶颈, 别在它上面继续磨; 预算留给未被证伪的环。
- 真因落在两处, 都只能改算法: ① **端点认领**(实测一端一块 ~3× 目标宽度的金属边块被并认/拆分);
  ② **选带规则**(取"最上簇"时会被真目标**上方**的过曝亮面假周期抢走 ⇒ 所以暗档反而更差)。
  修法用"只减不增"的端点有效性门(只对两端生效) + 「与上帧带一致 / 跨度≈n×pitch / 对比度归一化后周期最强」三联合约束。
- 扫描完必须**把参数恢复原值并留证**(值层面零变更), 别把诊断性的调参留在产线上。
- 顺带: 这类相机**请求 `gain=0` 常被静默钳到硬件下限**(实测钳到 2.0) —— 别把它当"无增益"用。

## 🧱 "面板某格没图像" 的第四类根因: 服务端状态端点挂了 / 载荷把页面拖死 (2026-09-28 实测)
源端、取图、解码都正常 (HTTP 200、图非黑), 面板/网页那格就是不出图 —— 先不要往相机上查, 查**状态端点**。
- **序列化崩**: 端点里 `json.dumps` 撞上 numpy 标量/数组 → `TypeError: Object of type ... is not JSON serializable`
  → 每次轮询都 500 → 前端拿不到状态、MJPEG 格不刷新 = 用户看到的"没有图像"。
  修法: 序列化统一走 `_json_safe()`/`_jbytes()`(带 `default=` 兜底), 不要注释改数据类型。
- **载荷带整图像素**: 产线 `/last_result` 的 `caliber_meta.natural` 是 2448×2048×3 的整图列表 = **5164.6KB**,
  原样进状态响应 ⇒ 单次 `/station/status` **10.4MB**, 而页面 **1.5s 轮询一次** ⇒ 页面假死/白屏。
  修法(对前端透明): 进状态前一律瘦身 —— 超长数组换成摘要, 字段名不动:
  `d.update({k: _slim(v) for k, v in kw.items()})`, `_slim` 把 `len>64` 的 list/`size>64` 的 ndarray
  换成 `{_omitted, _len/_shape, _dtype, _why, _head[:8]}`。修后实测: 10.4MB→7500B(1.8ms) · 5.04MB→1462B · 5.29MB→3232B。
- **判"真出图"的硬指标**(不看日志措辞): ①格元素 `naturalWidth>0 && complete` ②`/stats` 的 `frames_served`
  **在递增**(实测 aoi_gold 18 帧/1.11fps、aoi_surface 15 帧/0.78fps) ③每路 `ok=true` 带 `kb/shape`。
- **MJPEG 格要自带断线/停帧自愈**: 快照格会自己再请求所以自恢复, 长连接的 MJPEG 格不会 ⇒ 推流进程一重启,
  那格就**永远停在死连接**上。JS: `onerror` 1.5s 后换 `?t=Date.now()` 重连 + 每 6s 比对 `/stats` 帧序号,
  连续 2 轮不推进就换 src 强制重连 (页面把最新 stats 存 `window.__stats`)。
- **设备号一律按"卡名+能力"解析, 不写死索引**: 实测控制台按钮写死 `--local-dev 2` 打到 `/dev/video2`
  = 笔记本相机的 **GREY(IR) 路** (逐帧 mean≈6) ⇒ 那格全黑; 同时另两路串线。修后抓 DOM 自证:
  `i_local` 源 "Integrated RGB Camera" 640×480/15.1fps、`i_local2` 源 "WT15: MAXHUB-Camera" 1280×720/26.5fps。

## 🔌 "某格图冻结不动" 第五类根因: 生产者在**容器里常驻**, 重启后没人拉 (2026-09-28 实测)
表现: 某格图有内容但永远不变(用户叫"没有反映/看着是旧图"), `/stats` 是 `dead=true` + `age_s` 到小时级 + `frames_served=1`。
- **定性两步(不用猜)**: ①看**源文件 mtime** —— 若它与同目录其它产物在同一时刻冻结, 就是**生产者死了**(不是相机/带宽/曝光);
  ②看**容器内进程** `sudo docker exec <c> ps -eo cmd | grep -c '[r]<producer>.py'` —— 宿主只读落盘的 npy, 真源在容器里。
- **修法**: 按脚本自己的官方用法在容器内**分离**拉起, 不要另写一套:
  `sudo docker exec -d <c> bash -lc 'source /opt/ros/humble/setup.bash && export ROS_DOMAIN_ID=0 && python3 /repo/tools/<producer>.py --hz 5 >> /tmp/<producer>.log 2>&1'`;
  复核看**源文件齡降到秒级** + `/stats` 的 `stalled=false/dead=false/frames_served` 递增 + 快照非空(实测 640×526 · mean=121.3 · 非零像素 94.3%)。
- **必须同时做两件事, 否则下次重启再死**: ①把"拉起"写进开机脚本(check 段加“源文件齡 + 容器进程数”体检);
  ②把该路纳入已有守护(判据 = 容器进程不在 **或** 源文件齡 > 阈值 ⇒ 拉起; 正常静默)。
- **自愈验证必做**: 杀掉容器进程 → 守护应自己拉起并复核源文件齡 → 再跑一次应恢复静默(输出 0 字节)。
- ⚠️ `grep -c` 命中 0 条时**退出码是 1**(不是错误) —— 只解析 stdout 的数字, 依赖 returncode 会把"死了"误读成"查不了"。

## 🚫 "某格没图像" 第六类根因: 渲染/门控把图**整张吞了** (抑制显示 ≠ 不显示)

现象: 用户说「怎么还是没有图片」, 而取图接口 **HTTP 200 + 真图头(ffd8) + 29KB 级字节数**; 解码后却是
**83% 纯黑底 + 一条红字横幅**, 一点内容都没有。服务在、相机好、网络好**全部排除** ⇒ 病在**渲染层**。

- 真因: 新加的"抑制门"抑制分支写 `out = banner()`, 而 `banner()` = **全新黑画布** ⇒ 把已渲好的原图
  **整张丢掉** —— 与设计意图"不画错框 + **保留画面** + 横幅说明"**完全相反**。
- 🔴 铁律: **"抑制显示"永远指"不画判定框/标注", 绝不等于"整张不显示"** —— 任何 gate/门的抑制分支
  都要**以原图为底**(在原图上叠横幅/灰框), 只有**真的没有图**时才退回纯色画布。
  下游凡是"不达标就不显示"的需求, 动手前先问清"不显示的是**框**还是**整张图**", 实现与验收都按"框"写。
- 🔴 **字节数 / HTTP 码抓不出这种坏法**: 黑画布也有几十 KB(实测 29635B)。⇒ **改渲染类代码后必须
  自己解码取回的图, 量黑底占比与可见内容**(判据: 抑制态黑底占比 <0.5 且能看到目标; 实测坏版 0.83 全黑,
  修好后 0.31 = 图 + 横幅)。部署器那种"出图字节 >0"的探针在这类改动上等于没验。
- 判"是渲染门而不是相机/服务"的最快三步: ①读程序自报的 `gate/state/banner` 类字段 ②同刻取**另一路/另一档**
  图(如整板原图)是否正常 ③解码判据图量黑底占比。三步全过 ⇒ 别去查相机。

## 🚦 别的 App 打不开摄像头(微信/视频通话): 先查**我们自己的常驻预览**是否独占 `/dev/videoN`

现象: 用户说「笔记本摄像头怎么微信不好使了 / 摄像头打不开了」, 而相机自检完全正常。
本机常驻的预览/推流服务(本项目 8791 `tools/cam_live_stream.py`)从开机起一直握着 `/dev/video0`。

- **一句命令行定位**: 用**独立的短进程**去 open 同一节点 —— 实测 8/8 次 `opened=False`、帧数 0、全部失败。
  同时 `扫 /proc/*/fd 找 /dev/videoN` 显示持有者就是自己那条服务。
- 🔴 **机制(最容易搞错的一条)**: 独占冲突在 **`open()` 阶段就失败**, 不是"能开但取不到帧"。
  所以靠「巡检 `/proc/*/fd`, 发现别人持有就让位」的自动让位机制**永远触发不了** —— 对方根本拿不到 fd,
  日志里连一条冲突都不会出现。⇒ 这类问题的唯一可靠修法是**自己先不占设备**。
- **修法**: 给预览服务加一个显式「关闭/让位」源档(`kind=off`): 不 open 设备、worker 空转;
  该路快照端点回 **503 + 原因文案**(不要回冻住的旧帧, 旧帧会让用户以为相机坏了); 档位**落盘持久化**,
  开机/重启后必须保持关闭。让位巡检保留, 但只作为"对方能成功 open"时的补充, 不能当主修法。
- **验收三件**: ①切 off 后扫 `/proc/*/fd`, 该节点持有者为**空**; ②独立进程取帧 N/N 成功且有画面(`mean>20`);
  ③切回后快照仍 200 且非黑(**可逆**), 持有者重新是自己。
- **汇报口径**: 说清「谁占着 · 在哪一步失败 · 现在谁能用 · 自己想看画面时怎么切回」, 别只说"重启试试"。
  代价要主动交底(自己那格会显示"已关闭"及原因), 否则用户会以为是你弄坏了一路。

## 🪞 画面"总变"的两种非算法根因 (尺寸相同 + 状态字段 ok 都能骗人)

**先量化再归因**: 连拍 N 帧, 每帧记 ① 图尺寸 ② 均值/中位 ③ **与上一帧的像素差占比**(差值超阈的像素比例)
④ 与图相关的元数据(行带/裁剪窗/计数)。"总变"必须落成这四列数字, 不许用形容词。
实测一例: 尺寸**恒 900×332**、状态字段**全 ok**, 而每 4~5 帧**整幅换一次**(均值 13.7→50.7、帧间差 55.6%、
行带在 1039/1469/1199 间跳) ⇒ **尺寸相同、状态码正常都不等于内容一致**, 这层粗判会直接漏掉它。

两类根因(按排查顺序):
1. **上游取像档位不对 / 被打回默认**(见「数出来的数帧间跳变」节末条) —— 先查它: 它同时污染行带与下游所有量。
2. **失败回退端了别的视角的图** —— 渲染失败时用"上一张好图"顶上, 而那张缓存**不分视角**时, 切视角后失败帧
   端出来的就是**另一视角的图** ⇒ 画面在两张不同视角的图之间来回切。旁证: 失败帧的图**尺寸常与成功帧不同**
   (退回裁剪图 960×960 vs 判据图 900×332), 或均值/中位落在另一个档。
   修法: 缓存**按键(视角)隔离**, 键要能从**失败路径也算得出**的量来算(失败时手里往往只有裁剪块 ⇒ 用裁剪块
   形状粗桶); **宁可退回一张如实标注的退图, 也绝不端别的视角的图**。

**归因顺序(别一上来就怀疑算法)**: ① 取像档位(该视角该用的曝光/增益) → ② 行带/裁剪稳不稳 → ③ 计数 →
④ 才是判据算法。前三项被带偏时, 算法侧任何改动都会得出"改了没用"的错误结论。
多帧状态隔离与回归台的做法: `references/multiframe-state-regression-harness.md`。

## 📐 「成品图被切掉一块 / 反而更糊 / 还在跳」= 先把裁切范围画在原图上给用户看, 再改代码

用户对**加工出来的图**(判据图/裁剪图)投诉「上下少了一小块」「为什么反而更模糊」「还在跳」时, 这些往往是**同一个裁切框的**
三个侧面(切少了/拉伸了/框在抖) —— **第一步不是改代码, 是把框画在原图上给他看**: 在原图(页面上那张)上叠三层标注
①现在截取框(绿) ②独立量出的目标真实范围(青线) ③建议范围(黄), 框外压暗, 右边贴一张现在的成品图对照, 底部写量化数字,
出 **PNG** 给他。**范围这种事必须先对齐再动手** —— 用户往往有具体的边界意见("保留外边缘小区域"这类)。

要量的四件事(缺一个都不算有证据):
1. **截取框从哪来**: 加工函数返回的 `kept_rows`(检测带 + 上下 pad) × 列裁剪 `x_span`。
   **别假设它贴着目标**: 没饱和列时 x 是**全宽** —— 实测目标只占宽 63%, 剩下 ~37% 背景被一起压进输出、白占像素。
2. **真实范围要独立量, 不许信程序自己的带**: 逐行数「亮块段」(宽约 6~40px)个数, ≥6 个的行 = 在目标上, 取最长连续段。
   实测: 框 y400~481(81 行, 占原图 6.9%) vs 真实 y389~513(125 行) ⇒ **上少 11 行 / 下少 32 行**(用户说的"少一小部分"就是它)。
3. **"糊"量化成缩放比**: 输出内容 `864×225` ÷ 源条带 `W×H` ⇒ 横向 `0.62×`、纵向 `2.79×`
   ⇒ **1 个输出像素只对应 0.36 个源像素 = 纵向像素是插出来的**。
   铁律: **拉伸(上采样)一定显糊; "先压缩再拉伸"比"先拉伸再缩小"糊得多** —— 实测旧口径属后者所以看着更清,
   新口径"缩完再拉"反而被投诉更模糊。
4. **"跳" = 源抖 × 放大倍数**: 源带每帧只抖 ±1px, 经 2.79× 放大后输出质心极差 **3.0px** / 上沿 **5px**(12 帧实测)。
   稳定化只有两条路: 时间维(静物锁带/多帧中位) 或 **把放大倍数降到 1**。
5. ⚠️ **量跳变不能用 `/snapshot/<slot>.jpg`**: 没人在看那条 MJPEG 槽时槽是**冻帧**(实测连取 8 帧逐位相同 ⇒ 会误判"不跳")。
   要量就取 MJPEG 流; 顺带逐帧数"标注/外框像素"可判"多口径是否逐帧切换"(那也表现为闪)。
6. 修法方向: **按目标+宽度跨度紧裁(四周各留 ~8px) + 输出 1:1 贴深色画布(不再纵向拉伸)**, 画布尺寸不变 ⇒ 页面布局/显示口径不动。

交付这类证据图(照抄): 中文标注**必须用 PIL**(`/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc`; `cv2.putText` 画不了中文),
画线/文字颜色是 **BGR**(要青色就给 BGR 的 (250,210,60); 给 (60,190,250) 会画成橙色),
存 **PNG** 放静态目录, URL 给 `http://<host>:8799/dl/<file>.png` —— 8799 的 CT 表只有 `.png/.json/.html/.apk/.js/.css`,
**没有 `.jpg`**(JPEG 会回 `application/octet-stream` ⇒ 浏览器变成下载而不是直接显示)。
现成脚本 `scripts/crop_range_evidence.py`; 配方/代码片段/实测数字见 `references/crop-range-blur-jitter-forensics.md`。

## 🔌 相机是「后插」的: 真帧口空转、参数写不进去, 而 HTTP 层照样答 200
服务先起、相机后插 ⇒ 服务的 pipeline **从没打开过设备**。表象极像"相机坏了/带宽不够/曝光跑偏":
真帧口返回 **200 但 0 字节**、快照空、参数接口报错, 而端口在听、页面照常渲染。三条只读命令定位(先别动相机参数):
```bash
ls -l /dev/v4l/by-id/                 # 符号链接 mtime ≈ 设备插入时刻
tr '\0' ' ' < /proc/<服务pid>/cmdline; ps -o lstart= -p <服务pid>   # 服务启动时刻早于插入时刻 ⇒ 从没握过设备
# 谁持有节点: 扫 /proc/*/fd 找 /dev/videoN —— 一个都没有 ⇒ 没人打开(比"服务在线"有用得多)
```
- **修法 = 重启承载它的服务**(有 systemd 单元就用 `systemctl restart <unit>`, 别手起不脱离),
  重启后必须复核两件事: **某进程确实持有该 `/dev/videoN`** + 真帧口字节 >0。只看"服务就绪 200"会再次被骗。
- dmesg 里 `uvcvideo <bus>: Non-zero status (-71) in video completion handler` 反复出现 =
  **USB 带宽/供电/多进程抢同一 UVC 设备**的签名 ⇒ 直插机箱 USB3 口、别走 hub/延长线, 并确认只有一个进程开它。
- 该类 SDK 的参数常**只在管线 start()~stop() 之间可改**: 直接取 profile 会抛
  `get_active_profile() can only be called between a start() and a following stop()` ⇒ 控制函数"假失败"。
  做法: 控制函数**先记档**(模块级 pending), 由取帧循环在活跃管线上调用 `apply_pending()` 应用 ——
  这样"先调参数、后插相机"也成立; 且回执要如实给 `pending` 而不是假装写成功。

## 🌈 depth 正常而 color 恒 `Frame didn't arrive` ⇒ 彩色接口被内核 uvcvideo 独占 (D405 实测)

**判据(先分路单测, 不要整体判"相机坏了")**: 分别开 depth / color 各取 20 帧。
实测 D405: depth **10 帧 / 0.7s ≈ 14fps 正常**, color 恒 `Frame didn't arrive within 1500`
且 `sequence size exceeds remaining buffer` 刷屏, 同时 `fuser /dev/video*` **全空**
⇒ 不是进程抢设备, 是内核 uvcvideo 自己绑着 UVC 彩色接口, libusb 侧拿不到帧
(depth 走 vendor 接口, 所以不受影响)。

🔴 **不要 `modprobe -r uvcvideo`**: 实测卸掉后整个设备从 USB 掉线(`No device connected`、
`/dev/video*` 全消失), 要 `modprobe uvcvideo` 才回来 —— 这一下就把"能连上"变成"连不上"。

**正确解法 = 分路取像**: color 走 **UVC(`/dev/videoN` + OpenCV)**, depth 仍归 librealsense,
两条路互不抢。节点号**自动探测**(以"能 open 且读到一帧"为准), 别写死索引 ——
重插/USB reset 后节点号会变。

**UVC 路上两个必设项**:
- **不设 `CAP_PROP_FPS`**: D405 UVC 显式请求 15fps 实测只出 **4.7fps**, 不设反而 **30fps**。
- **gain 必须显式给**: 默认 `gain=16` → 画面 `mean 29`(目检只能说"有东西, 看不清");
  `CAP_PROP_GAIN=240` → `mean 47.9`, 能看清台面/夹具/标定板轮廓(噪声可接受)。
  D405 UVC 上 `auto_exposure`/`exposure_time_absolute` **读回 -1 = 不支持**, 只能靠 gain。
- 提亮要留证据: 同一场景改 gain 前后各取一帧比 `mean` 与字节数(实测 7438B → 23960B),
  并把图真的看一眼 —— mean 是数字, "能不能目检"只有看图能定。

**帧率掉一大截(cv2 单测 30fps, 服务里 4.7fps)先算发布开销**: 640×480 bgr8 = **921KB/帧**,
rclpy 发 30fps ≈ 27MB/s ⇒ 序列化+拷贝把循环拖到 4-5fps。要满帧就**另外**发
`sensor_msgs/CompressedImage` 给只做 HTTP 伺服的 relay(JPEG ~30KB/帧), 别去改那个已有
多处订阅的 `Image` 话题 —— 改类型会静默打断所有老订阅者。

**服务形态**: 发布节点与 JPEG relay 是两个 unit, 都要 `enabled` + `Restart=always`。
`curl :8792` 回 **000** 而不是 503 时, 先 `systemctl is-active` —— 实测 relay 在
"反复 stop/start 直到 restarts 上限"后会 `inactive` 并放弃, 这时重启 unit 即可,
与相机/曝光/网络全部无关。

### 曝光/增益判据要按 ROI, 不按整帧 (高反差场景)
实测一场: 整帧 `mean 49 / 中位 26`, 而 3×3 九宫格里**只有一格 161**(其余 6~20) —— 一个亮工件压在暗背景上。
此时"整帧过曝 3.3%"与"整帧偏暗"**同时成立**: 一路降曝光能把过曝压到 1%, 却把工件那格 161→94、暗部占比 43%→78%
⇒ **整帧指标既判不了"该不该降", 也判不了"降到哪一档"**。做法固定三步:
1. 先用 **3×3 网格均值 + 过曝像素的包围盒**定位亮区(通常就是被检对象), 它才是 ROI;
2. 目标档按**该 ROI 的过曝率与中位亮度**定(实测 166us/增益64 → 3.4% 过曝; 100us/40 → 1.7% 且工件仍亮; 60us/32 → 工件开始发暗);
3. **现场人说"下面有工件/就是它"时, 那句话就是 ROI 的定义** —— 别拿整帧均值去反驳, 也别只按整帧去调;
   扫档后把每档的 ROI 数字与图一起留证, 别把诊断性的档位留在产线上(用完回读原值)。
- 数值判据会漏**局部**过曝: 数值说"曝光正常", 而视觉复核(把图交给视觉子代理)指出四角/边缘**过曝白块**
  并读出图上横幅「识别 20 根 ≠ 19」 —— 白块把最外侧结构切掉了。**逐块量, 不能只报整帧**。
- 同一台相机的**原始取像口与"给人看的图"是两条路径**: 实测 `?kind=origin&grab=1` 回到 near-black(`mean 4.0 / max 18`),
  而同名判据图/送模型图 `中位 130+`(经压缩曝光等派生加工) ⇒ 用哪张图量曝光, 先确认它是哪条路径的产物;
  报"过曝/偏暗"必须挂上图片名与路径, 否则两人量的是两张图。
- 🔴 **曝光档与判据是一对, 必须一起定**: 有些判据的几何基础就是"过曝亮条"(找亮条 → 量上下边缘/台阶) ⇒
  降曝光会把判据直接废掉; 反过来, `Otsu + 矩形刚体` 那类在过曝档下前景连成一片、根本搜不到候选。
  实测同一台表面相机: **5000us** 下原图 `mean=16.5 / p50=9 / p99=232 / 饱和 0.79%`, 本机矩形判据出图 **1285×188**;
  **48000us** 下 `fg_frac=0.402 / p99=255`, 同一算法直接 `ok=False`; 而设备内置的"亮条"判据在 5000us 下又报
  "找不到亮条"。⇒ 先读清"这套判据靠哪个物理特征", 再定曝光; **不要单方面改曝光, 也不要改阈值去迎合另一套判据**。
- 🔴 **`fg_frac`(前景占比) 是区分"工件位姿变了"与"曝光/算法变了"的最快一个数**: 同一视角好帧 **0.034**、
  坏帧 **0.402**(12 倍), p99 从 142 跳到 255 ⇒ 画面从"黑底上一条工件"变成"一大片都亮" —— 这是**工件朝向/位置变了**,
  不是调阈值能救的。判据图出 `None` 时先比这两个数, 再去改代码。
- 🔴 **判据图"看着没了"的归因顺序(照走, 别跳)**: ① 上一轮 commit/文档里已定的曝光与算法结论 →
  ② 回读当前曝光值与程序默认值 → ③ 本机判据能否算出结果 → ④ `fg_frac`/p99 对比好帧(判工件位姿) → ⑤ 才是阈值/算法。
  实测诱因优先级 **改曝光 > 改算法 > 连续取图**, 三者症状一模一样; 而**连抓同一台相机三次会打坏句柄**
  (之后全部超时, 只能等保活拉起), 重试必须两次之间 ≥10s、最多 3 次。

## 🧬 HTTP 200 但 **0 字节** / `frames=0` 却有内参 = 取帧线程不在这个进程里 (fork 型服务, 2026-10-20 实测)

现场原话:「你的 USB realsense 相机怎么不好使了」。表象一组, 分开看会走弯路:
`/snap/rs.jpg` → **200 但 0 字节**; `/api/rs_info` → 内参/分辨率齐全但 `frames=0`、`err=""`; dmesg 刷
`uvcvideo ... Non-zero status (-71)`; 间或 `xioctl(VIDIOC_S_FMT) failed, errno=16 Device or resource busy`。

**判据一(先看父进程模型)**: `grep -nE "ForkingMixIn|ThreadingMixIn" <服务>.py`。若是 forking(每连接 fork):
pyrealsense 的取帧线程**不会**被 fork 继承 ⇒ 子进程里的 pipeline 是空壳, `snap()` 恒 None。
而且 `_ST` 这类模块级状态是 copy-on-write 的旧快照 ⇒ **子进程看得到内参却一帧都收不到**,
这就是「200 但 0 字节」的全部来源。2~9 个子进程轮流开设备还会互抢 UVC ⇒ EBUSY / -71。

**判据二(谁真占着节点, 按 fd 反查不信名字)**:
```bash
for p in /proc/[0-9]*; do for f in /proc/$p/fd/*; do t=$(readlink "$f" 2>/dev/null);
  case "$t" in /dev/video*) echo "${p#/proc/} $(tr '\0' ' ' < /proc/$p/cmdline 2>/dev/null|cut -c1-80) → $t";; esac
done; done 2>/dev/null | sort -u
```
实测: 一台 D435 的 6 个节点被 **两个不同进程** 分着开(AR 服务 + 8791 相机流服务), 后者的
`--usb-name` 默认值里含 `RealSense` 关键字 ⇒ 把 USB 深度相机当「USB 摄像头」扫走了。

**修法(独占小服务, 架构级)**:
1. 让**唯一一个单进程**拥有相机: `tools/rs_service.py` = `ThreadingHTTPServer` + 每请求一线程,
   端点 `/api/info /api/options /api/exposure /api/pose /api/detect /api/point /snap.jpg /rs.mjpg`; 端口
   必须现场核占用(实测 8796 已被 sam3 分割服务占 ⇒ 用 8789), 且 `/health` 要带 `"svc"` 名自证,
   否则起停脚本会把别人的 200 当自己起成功。
2. 原服务(forking)一律**代理**: `/api/rs_*`、`/snap/rs.jpg`、`/rs.mjpg` 转发到小服务, MJPEG 按块搬运;
   取帧函数不许在子进程里 import 相机库。
3. 任何「按卡名找摄像头」的逻辑都**显式排除** RealSense/D405(专用机), 否则一路推流就能把 AR 弄瘫。
4. EBUSY 光重试无用: 连续三次失败就 `dev.hardware_reset()` 让 USB 真掉线重枚举(复位后节点号会变,
   实测 video4-9 → video10-15, 别写死索引)。

**判据(六项全过才算好)**: ①节点只有一个进程持有 ②`/health` n 递增且 age<1s ③间隔 1.2s 两张图
字节都 >20KB **且 md5 不同**(排除冻帧) ④像素 `mean>30`、暗(<8) 占比 <50% ⑤经原服务代理仍 200 且 frames>0
⑥`/api/cams` 该路 online=true。落地脚本: `tools/verify_rs_camera.py`(`tools/rs_probe.py` 单独量 fps/首帧)。

**🔴 第一件事先看「服务在不在」, 不是相机**: 现场又一次「USB realsense 没有图像」(2026-10-20 17:21),
真因就是 `tools/rs_service.py`(8789) **根本没在跑** —— AR 侧 `/snap/rs.jpg` 回 **503 + 172B JSON**,
`/api/rs_info` 直接给 `"RealSense 小服务(8789)不可达"` + hint。设备/USB/曝光全部无关, 启动后立刻 6/6 PASS。
⇒ 排查顺序改成: ①`curl :8789/health`(没有 `"zmax-rs"` 就是没起) → ②`bash tools/rs_service.sh start`
→ ③`tools/verify_rs_camera.py`(六项) → ④ 才谈像素/参数。
**并且必须挂上保活**: 该服务原来只在手工 start 里起过, 开机/崩溃后**没人拉起** ⇒ 同类故障会反复发生。
`~/.hermes/scripts/rs_service_keepalive.sh`(cron `@reboot` + `*/5`): 三层判据 = `/health` 有 `"zmax-rs"`
+ **n 在递增**(在跑但不出帧 ⇒ 重启以抢回设备) + 进程是真 `rs_service.py`(扫 /proc, 禁 `pgrep -f` 防自杀);
正常时**输出 0 字节**。自验必做: stop → keepalive 拉起 → 再跑一次应静默。
凡「独占设备的小服务」都要这么办 —— 与本机 l2_daemon 那次「FIFO 在、执行器不在」同一类, 都是**文件/设备在、服务不在**。

### 🔭 跨相机判「同一个目标」: 这台相机不检出 ≠ 目标不在 (2026-10-20 实测)
老倪: 「D435 能看到手臂相机同样的光模块, 只不过位姿是侧面, 你能看到么?」—— 要的是**这台相机的画面里到底有没有它**, 不是把腕相机的框搬过来。
- **现役检测权重的"0 检出"没有否决权**: 实测 `models/yolo_peg_live.pt` 在腕相机帧 2 个命中(peg 0.79 / OPT_Gold 0.39), 而在固定 D435 帧 **0 个** —— 权重只认**训它的那个机位/尺度**, 换个视角就不适用。用它反推"目标不在"必错。
- **三件套取证(都要数字)**: ①把目标区裁出来**放大 3×** 再问 L5/VLM 拿 bbox(全图判小目标会漏, 置信度也低); ②`GET /api/point?u&v` 在该区域**扫格点**, 报「有效深度比 + 最近 z_m + xyz」, 与另一台相机算出的距离对齐(实测 D435 最近 z=158.0mm vs 臂相机 dist=159.2mm ⇒ 同一工件); ③说清是哪台相机(`lsusb`/持节点进程/`?cam=<key>`), 别用"内置/USB"这种对不上号的词。
- **单个像素 `depth=0` 不是没有目标**: 金属/反光面经常量不到(实测模块正上方格点无效), 换周围格点扫一片才算数, 并报 valid/total。
- **结论口径**: 「看得到」与「量得出/画得出位姿」是两件事 —— 固定相机要在画面上出 3D 位姿, 必须先标它自己的外参(或用它自己视角的检测头, 只给 2D)。别拿 VLM 每帧解析冒充实时位姿。

### 🧭 用户只说「某相机没图像」: 先出一张**全通道表**, 别一次只修一路
现场的原话往往就这么短(「usb 相机不好使」/「内置 USB 相机不好使」), **不要反问他指哪一台, 也不要修一路回一句** ——
修好一台他心里还有另一台, 同一句话会重复报三次, 每次都在等"到底哪几路能用"那张表。
**一次(只读)取齐再回答**: 8791 `/stats` 全部键(`local/local2/arm/depth/aoi_*`)+ 8789 `/health` 与 `/snap.jpg`
+ 8797 `/api/cams` + `lsusb` 与 `/dev/v4l/by-id`(谁持有节点: 扫 `/proc/*/fd`), 每路一行给
`online / frames_served / age / 分辨率 / mean / std`, 以及**页面名 · 设备名 · 通道键**三件套。
四条分流(判定顺序固定, 不许混):
1. **端点 503 / `/health` 里没有该服务名** ⇒ 服务没起(起 + 挂保活), 与相机无关;
2. **`online=false` + `frames_served=0` + `age=-1`, 且 `lsusb` 里没有这台设备** ⇒ 物理没插/没上电
   (要他插线, 不是软件)。先看承载服务的命令行 —— `--<key>-dev -1` 这类显式关闭也会让那一路永久 offline;
3. **有帧、`age≈0`, 但 `mean<8` 且 `std<1`、九宫格全平** ⇒ 在拍但进光≈0。**别一步跳到"物理遮挡"**: 先查
   软件可核实的 `camera_power` / `privacy`(隐私快门)控件(判据见 `linux-host-maintenance` §9b-3),
   这两个都不存在才说"只能看镜头/快门", 并把三个数一起给: 均匀纯黑只在读出噪声底 + 帧间差不为零(在拍) +
   同刻其它相机亮(场景有光);
4. **服务全绿而页面那格还黑** ⇒ 是那一格/那个窗口的陈旧状态: **别重启服务**(把页面再打断一次还会被当成"你越改越坏"),
   给他**新开一个窗口并置前**(带 `?cam=<key>` + 全新时间戳 profile), 再核该 key 的取帧请求在日志里连续 200。
口径: 表里必须同时写页面名与设备名 —— 现场说的"内置/本机/USB" 可能分别指 `local`(Integrated RGB⊗video0)、
`rs`(D435, 8789)、`arm`(D405), 用词对不上就会两边各说一台相机。


| 现象 | 真相 |
|---|---|
| 面板/网页某格"没有图像"但接口 200 | 先查**状态端点**是否 500(序列化崩)或响应体是不是 MB 级(整图像素进了 JSON) |
| 某格一直黑且怎么调都不亮 | 先核设备号是不是**解到 IR/GREY 那一路**(写死索引的经典坑), 按卡名+能力动态解析 |
| 多路面板里只有一路旧/坏，其它正常 | 逐路看 `dead/frames_served/age_s`; 一路死源会被拼进下游判据画面, 每轮都拉高拒发率 ⇒ 单独修那一路, 不要用"其它路正常"放过 |
| 文件 2 MB+ | 与内容无关(噪声不可压缩) |
| 真帧口/快照 **HTTP 200 但 0 字节** | 别判"相机坏": 先看服务是不是**早于相机插入**就起了(从没握设备)+ 扫 /proc 看有没有进程持有 `/dev/videoN`; 修法是重启该服务。dmesg 的 `Non-zero status (-71)` = USB 带宽/供电/抢设备 |
| 同一场景既报"过曝"又报"偏暗" | 高反差: 亮工件 + 暗背景 ⇒ **按 ROI 判**, 整帧均值两种结论会同时成立。现场人指认的工件位置就是 ROI 定义 |
| 原始取像口近全黑, 判据图却很亮 | 两条路径(原始 vs 派生加工图) ⇒ 先确认在量哪张图, 报数必须挂图片名/路径 |
| 画面/判据图"总变", 但图尺寸恒定、状态字段 ok | 先量化**帧间像素差占比 + 均值跳变**: 整幅换区域 = 上游取像档位被打回默认, 或失败回退端了别的视角的图(缓存未按视角隔离)。尺寸/状态码**不构成证据** |
| 微信/视频通话打不开摄像头, 但相机自检正常 | 自家常驻预览独占了 `/dev/videoN`; 冲突在 **`open()` 就失败**(实测 8/8 `opened=False`) ⇒ 基于 `/proc/*/fd` 的自动让位**永远不会触发**。修法是给自己加持久化的 `off` 档(不占设备 + 快照回 503 带原因), 让位只作补充 |
| 接口 200 + "success" | 只说明请求成功, 不说明画面有内容 |
| 文件名写着 `..._W1600_H220_...` | 可能是硬编码名, 实际 2448×2048(名实不符, 别据此判断) |
| 现役**程序**文件名写着 `..._work_v6.py` | 名字里的版本号常是**固定壳名**: 部署器每次都把最新内容**覆盖进同名文件**(实测 v6 文件内容 = 本地 v12 源, 字节数一致) ⇒ 判“现场跑哪一版”要比 `Get-ChildItem … | Select Name,Length,LastWriteTime` 或看程序**自报**版本/字段, **不看名字**; 同目录往往还躺着历版源与命名错乱的 `*_copy.py` |
| 上线后“版本没换” | 先查要部署的文件里**版本常量本身跟着改了没**(`_JUDGE_VER` 这类) —— 改了内容忘改常量, 上线后的版本校核会误判成没换版本, 白折腾一轮。**改内容必须同时改版本常量**, 部署后第一件事就是读它与交付件对齐 |
| 引用“某端口没有取图口/取不到图”的旧结论 | 这类结论**会过期**: 现场程序一升级路由就变 ⇒ 引用前用 `curl -X OPTIONS -D - http://<ip>:<port><path>` **现探一次**(零副作用, 不打拍照); 实测表面 10083 早期只有 `/capture_detect`, 升级后已有 `/picture`(原图 2448×2048) + `/crop_info` + `/last_result` |
| 在帧里"找目标/数个数"用最亮行或自相关周期定位 | 同一帧里能同时存在更亮/更周期但**不是目标**的带: 实测金手指帧 y≈1164 最亮行 = **镜面反光带**, y≈1570~1750 = 工件**下方背景/阴影**, 其列向自相关在 55px 上假峰高达 **0.93**(散焦纹理) —— 那两处一根片都没有(真排在 y≈679~768)。**先拿系统自报的几何锚定** (产线 `/region` 的 quad/bbox · 模板匹配 · `/crop_info` 的 `judged.kept_rows`), 再**只在那个框内**谈像素; 给目检的图必须带原图 x 标尺 + 明确 y 范围, 否则对方判不出"这条带在工件哪一面"。我自己 + 两次目检子代理都在这类假带上栽过 |
| 「只保留本体/其余全黑」改了两版还被否 | 本体带里可能同时有**离散竖条**(钢琴键式)与**满宽横条**; 形状不问清就实现必返工 ⇒ 先按**列向周期性**(亮列段数≥6 且间距规整 ⇒ 按键行; 跨条宽亮占比≥0.85 ⇒ 满宽横条要剔), 并把候选带画在真帧上让用户指认 (`references/judge-image-rendering-and-region-forensics.md` 铁律 6) |
| "窗口黑屏" | 先跑显示链路自证, 多数是图本身黑 |
| "相机坏了" | 先看序号/J基于同一进程的黑亮交替记录; 曝光参数常驻不变时, 变量是光 |
| 帧间差分说"到处都在动" | 相机**自动曝光漂移** ⇒ 先锁曝光(见「锁死曝光」节)再差分 |
| 自动找"动的目标"抓到托盘/键盘 | 打分条件只要含深浅/面积就必然被抓 ⇒ 判别条件只能是**帧间位移**, 且目标先由人/VLM 点准 |
| "标注图已经生成了" | 文件存在 ≠ 画上了框: **数一遍彩色像素**(红/蓝/绿各多少), 0 框说明标注链**上游**空了, 别把无框图当交付件发出去 |
| 画面判读结论后来被推翻 | 发布端冻结时也会秒回旧帧 ⇒ 下结论前先比两帧 md5 / 读 `age_s`; 一旦发现冻结, **作废并重判**已发布的结论 |
| “数出来的个数”忽多忽少 | 不是姿态/机械臂问题, 也不一定是相机参数: 实测同姿态下计数在 16/18/19 跳, 跟跳的是**预处理裁剪窗**(绝对阈值遇亮度漂移) ⇒ 量「指标 + 裁剪窗 + 亮度」三列; 修法是把绝对阈值改成对比度归一化的相对阈值, 不是调下游资格窗口 |
| 画面突变、相机没坏也没黑 | 先想**被挪了位置**: 均值 2~4 倍跳 + 单帧字节跳 + 本机 `/dev/video*` 消失 ⇒ 视野换了。**手眼外参与由它推的一切(重建/叠加/抓取)同时作废**, 先停作业再重标 |
| 相机能枚举、depth 出帧, 但 color 恒 `Frame didn't arrive` | 彩色 UVC 接口被内核 uvcvideo 独占(depth 走 vendor 接口所以正常)。**别卸 uvcvideo**(整机掉线) ⇒ color 走 `/dev/videoN`+OpenCV, depth 留给 librealsense。UVC 下不设 FPS(设 15 只出 4.7)、gain 显式给(16→240 使 mean 29→48) |
| 接口 200 + 真图头 + 几十 KB, 但**解码后一片黑** | 别先查相机: 可能是渲染层"抑制门"把图**整张吞了**(抑制显示≠不显示, 抑制分支用了全新黑画布而不是"原图+横幅")。字节数/状态码抓不出来, **必须解码量黑底占比** |
| 用户说「整版原图没了 / 画面在跳」 | 先量两个数: 整幅均值**恒定**+区域亮度**反相关** ⇒ 工件在视场平移(机械侧, 别扫曝光); 锐度(`Laplacian.var`)与 p95 远低于**同机基线**(实测 1.6 vs 17.4) ⇒ 失焦/没进光, 现场拧对焦环。都不是管道问题, 别去查网络/端口 |

## 🧭 相机没坏也没黑, 而是**被挪了位置** (亮度 / 字节 / 设备 三条同时跳)

这类既不是坏、也不是遮挡、也不是曝光跑偏。判据是**同一组数同时变**:

| 量 | 挪之前 | 挪之后 |
|---|---|---|
| 整幅均值(发布端 brightness/mean) | 46.6 | 188.5 (**4 倍**) |
| 单帧字节 | 49,154 | 77,680 (内容复杂度变了) |
| 本机 `/dev/video*` | 有节点 | **全空** (相机已不在本机, 图全靠远端桥转发) |
| 画面 | 俯视: 圆点标定板 + 黑圆盘 | 斜视近景: 工装夹具 + 托盘 + 工件 |

- **亮度一步跳 2 倍以上先想"视野换了"**, 不是"曝光跑偏" —— 曝光不会一步到位, 且同刻其它路正常。
- **必须把两张真图拉下来目检**: 只报数字分不清"换个角度看同一台面"与"完全另一处"。存到本机固定路径并给绝对路径。
- 🔴 **相机一挪, 所有"在位姿假设下推出来"的产物同时作废**: 手眼外参 `T_cam2tool`、由它推的相机位姿
  (3DGS 的 `cameras.json`、AR 叠加、抓取点)全部错位, 而且**下游不会报任何错**。
  实测最贵的一种: 挪动的时点正撞采集窗口(frames 采完 → cameras.json 生成 → 开训), 整批位姿错,
  训练指标只是偏低(PSNR 11.68dB) ⇒ 极易被误判成"模型不行/精度不够"。
  ⇒ 处置顺序固定: **先停用旧外参的作业 → 重标 → 重采 → 再谈精度**。让它跑完再判等于白烧一轮。
- 判定"挪了"全部只读: 两次取帧比亮度与字节 + `ls /dev/video*` + 两张图目检, 不动相机、不改参数。
- 位姿必须在挪动之前就已落盘, 否则"当时位姿是多少"永远查不回来(标定/采集前先开记录器
  `scripts/pose_recorder.py`: 10Hz 降采样, 同时记墙钟 `t` 与 ROS 时戳 `stamp` —— 实测两者可差 32s,
  只记一个就回放对不上帧; 订阅必须 `qos_profile_sensor_data`, 发布者是 BEST_EFFORT)。
