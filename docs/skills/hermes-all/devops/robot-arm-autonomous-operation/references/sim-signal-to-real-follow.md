# 仿真速度信号(v_ff) → 真机小幅度同节奏跟随

目标形态: 仿真每帧算出的速度矢量 `v_ff`(mm/s, base 系) 只提供**方向与节奏**;
真机做**幅度很小**、**与仿真同拍**、**三轴合成**的动作, 并且永不出一个硬包络。

## 三种接法的实测判据

| 接法 | 机制 | 结果 |
|---|---|---|
| 单轴技能 (`L2.forward/backward/left/right/lift/lower`) | 每阶段把 `v_ff` 归到 6 个方向之一 | 失败: 只有升降没有平移 —— 横向分量被整块丢掉 |
| SDK 流式追加 (`moveAppend` + `setDefaultZone`) | 每 0.2s 追加 2mm 小段, 指望控制器连续走 | 失败: 追加点不执行 => 10s 里只有 2% 时间在动, 峰速 3mm/s |
| 阶段事件 + 三轴 `move-rel` + `guard_box` | 仿真阶段一变就发一次合成小动作 | 可用: 12 个动作全 PASS, 各轴偏差 <0.1mm |
| **整轮一条多点 `path` + 单次 `moveStart`** | 把整轮轨迹重采样成 N 段相对增量, 一次排完 | ✅ 连续平顺: 50 点/40mm 一口气走完, 中间不停 |

## 工作流程 (阶段事件驱动 → 整轮一条路径)

1. 盯 `zmax_data/ss_live/trace_live.json` 的 `阶段`; 同时读 `plan_from_vff.json` 的 `truth_xyz`(真值)、`bridge`(总闸)。
   插拔场景阶段: 接近/对位/下降/抓取/抬起/转移/插入/完成;
   **摆盘场景阶段表不同**: 下降→抓取→抬起→转移→放下(没有"接近"), 所以一轮的边界**不能靠某阶段名**判,
   要用 `plan_from_vff.json` 的 `frame` 回绕。
2. 阶段变化后**等 ~150ms, 取窗口内 `u_ff_mms` 均值**定方向 —— 不读瞬时值:
   阶段切换那一刻读到的常是**下一阶段**的速度(实测: 下降被判成 forward、抓取被判成 lower)。
3. 位移 = 方向单位矢量 × `--step`, 各轴独立分配(单拍口径); 要做整轮则见下节。
4. 下发走 SDK 腿 `move-rel`(base 系直线, 姿态不变), 带三样:
   `dx/dy/dz`(mm) · `speed`(mm/s) · `guard_box={x:[lo,hi],y:[...],z:[...]}`。
   `guard_box` = 起点 ± band: 腿里每 0.15s 拿真值比一次, 出界**立刻 `stop()`**(扫掠闸)。
5. 读 `tcp_out/agent_result.json` 里本条 `id` 的回执, 报 `verdict` + `delta_mm`。
6. 累计偏移 > 包络的 60% => 先发一条反向 60% 的"回中"再继续。

## 平顺: 整轮一条多点路径 (唯一有效的做法)

一条 `move-rel` = 一段直线, **走完就停**, 发得再密也是"走一段停一段"; 现场的说法就是"一顿一顿"。

```json
{"cmd":"path", "points":[[dx,dy,dz], ...], "speed":7.4, "zone":10, "guard_box":{...}}
```

- `points` = **相对当前 TCP 的毫米增量**(代理内部 `/1000` 累加), 不是绝对坐标; `zone` = 转角区 mm(5~10, 否则每点微停)。
- 一次性 append 全部点 + **只调一次 `moveStart`** ⇒ 控制器一口气走完折线。实测: 10 点 × 5mm = 50mm, 2.8s, 终点残差 **0.0mm**。
- 整轮做法: 把模板轨迹等弧长重采样成 N 段(50~80 段), 一次发完 ⇒ 一轮 = 一条连续运动。
- 实测两档都一口气走完: 32mm/4.3s(7.4mm/s)、40mm/15.2s(2.6mm/s)。

## 串行闸: 下一条必须等上一条的回执

- 完成判据 = `tcp_out/agent_result.json` 的 `id` 与自己下发的 id 相同; 「臂静止 0.35s」只能当辅助(位姿 5Hz, 慢速段看不出在动)。
- 每次下发前先发 `{"cmd":"reset"}` 清旧队列 —— 上个进程/上一轮排的命令**会被真的执行一遍**(实测臂自己走出 100mm+)。
- **叠发两条的后果是连锁加速**: 40mm/条 × 16 条在 18s 内跑完、峰值 70mm/s、总位移远超条长, 直接顶穿 `guard_box` 并停在边界外。
- 旧版本推荐的"异步不等回执、靠 guard_box 保障"已实测推翻, 不要再用。

## 模板: 必须来自仿真真值, 不许自我衰减

- ❌ 边跟边录"上一轮实际走的路径"当模板 ⇒ 每轮回放更短的一截, 实测 501mm → 62mm → 11mm, 越跑越像没动。
- ✅ 用仿真真值(`plan_from_vff.json` 的 `truth_xyz`)采一轮完整轨迹当固定模板
  (`tools/capture_truth_template.py`), 跟随器 `--template <file> --no-record`; 若允许自动录, 只接受比现有长 20% 以上的。
- **单位陷阱**: 真值模板是**米**, `path` 点是**毫米**。忘乘 1000 时不会报错, 而是被判"路径太短"**静默 continue** ⇒
  臂一动不动、日志只有启动两行。判据: 启动后 5s 内必须出现第一行 `🎞 第 1 轮: N 点 · 路径 X mm`。

## 幅度与包络 (两个数分别管"走多远"和"跑不掉")

- `--max-path`: 单轮总行程**硬上限**, 超了等比缩整条路径 —— 这是"不要走太远"的唯一可靠旋钮。
- `--band`: 启动那一刻 TCP 为锚点的 ±mm 包络, 交给腿的扫掠闸;**必须大于单轮总行程**。
- 时长与距离分开控: `--dur-scale` 决定速度感; 只缩距离不改时长 ⇒ 看起来"很慢很慢"(2.6mm/s 级别)。
- 仿真整轮真值幅度: 插拔 X211/Y41/Z41mm · 摆盘 X270/Y78/Z142mm ⇒ **横向只占总行程 1/5**;
  压到 40mm/轮时横向只剩 3~5mm。汇报必须给"每轴实测行程", 否则现场会判成"没动"。

## 实时性: 先量网络, 再量回执, 最后看 CPU 抢占

- 到控制器: `ping -c 20 -i 0.05 <控制器IP>` — 实测 0% 丢包、RTT 0.14ms、mdev 0.046ms、1Gb 全双工 0 错误。
- 端到端: 写 FIFO 一条 `{"cmd":"pose"}` 到拿到回执 — 实测 11ms(抖动 ±0.3ms)。
- ⇒ 不平顺**不是网络问题**, 是"一条命令=一段直线"的架构结果; 真正的抖动源是宿主 CPU 抢占(相机推流单进程可占 300%+)。
  跟随进程用 `sudo nice -n -15 taskset -c 28,29,30,31` 绑独立核。

## 停机与进程管理

- `pkill -f bridge_xxx.py` 会匹配到**执行它的 shell 自己**(命令行含同一串) ⇒ 自杀(exit -15), 后面的停止/回读全不执行;
  同一命令行里也别出现目标脚本名(包括 `git add tools/bridge_xxx.py`)。
- 正确: 读 `zmax_data/ss_live/*.pid` + 校验 `/proc/<pid>/comm` ∈ {python,python3} 再 `kill -TERM`;
  保障扫 `/proc/*/cmdline`, 匹配逻辑写进脚本文件(如 `tools/stop_all_bridge.sh`)不要内联。
- 停臂: 依次发 `{"cmd":"stop"}`、`{"cmd":"reset"}`, 再连读 3 次 `/pose` 确认静止。

## 通用坑(与具体接法无关)

- **回执 `ok=True` 只代表"已投递"**: 5mm 段实际要 ~2s 才走完; 0.4s 就读位姿永远是 Δ=0, 会误判成"被闸拦下"。
  判到位 / 算下一步一律用**实测 TCP**, 不要用自己维护的 `commit`(控制器没执行时它会跑飞)。
- **腿不排队**: 上一条还在执行时新命令被拒(`上一条动作还在执行 => 拒(不排队)`) => 等 `robot.operation == idle`
  再发并留 ≥0.3s 余量; 用"走了 60% 就算到位"做判据必踩这条。
- **段长决定一切**: 一段 = 一次 MoveL 走完整段。发 100mm 就是一次性下探 96mm(实测);
  "band 只判起点在带内"挡不住 => 必须按剩余带宽收缩段长。
- **下向守卫与跟随冲突要显式定案**(现场同意放行), 放行后由 `guard_box` 保障, 而不是删守卫。
- **仿真场景切换后阶段表会变**(摆盘无"接近"), 用 `frame` 回绕判一轮, 别预先固定阶段名。
