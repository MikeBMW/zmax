# 回路级「指令 → 反馈」延迟怎么测才不被噪声骗

用于回答「某层的反馈延迟多少」——尤其是常驻回路里逐对象(每个技能/通道)的反馈延迟。与端到端延迟(`采图→输出`)_**不同源**, 两者别混一个数报。

## 1. 先拆腿, 别报一个总数

| 腿 | 含义 | 典型唯一依据 |
|---|---|---|
| ① 上游出块周期 | 上游多久算一次新指令 (常是 10Hz ⇒ 100ms 起步) | 上游 tap 里的时间戳差 |
| ② 块→消费端认领 | 块帧龄: 拿到时已经老了多久 | 消费端每拍写的 `age_s` / 块 ts |
| ③ 消费端→反馈跟上 | 指令阶跃后反馈值真变化的时间 | 消费端反馈值与时间戳配对 |
| 物理腿 | 真实世界的速度/位姿反馈 | 位姿源 ts (帧龄 >5s 即停更 ⇒ 如实标不可采) |

端到端 = ①+②+③。**“多久算一次”与“算得多快”必须分开写**: 上游单帧开销可能只有 0.05ms, 延迟仍 100ms+, 因为凑的是周期, 不是算力。

## 2. 配对铁律 (这几条曾直接造假数)

1. **用“真实阶跃”判指令变化, 不能用“数值有变化”**: 浮点噪声会让 `120.000 → 120.000` 看起来变了 → 配上 100ms 前的指令 ⇒ 假的 107ms。设阈值 (如 ≥1mm/s 或 ≥1% 量程) 才算新指令。
2. **FIFO 配对 + 超时丢弃**: 最早的未配对指令配最早的够格反馈; 超过 2~3s 未响应就丢并计入“未响应”。漏了这步, 长跑会出现 2×10⁵ms 的陈旧配对, Max 直接报废。
3. **分三个总体统计, 别混**:
   - `到达`: 反馈真的跟到新值 → 这才能算延迟;
   - `削过`: 反馈值恒定/不跟随 (被限幅器或物理上限阻塞) → 这是**限幅证据**, 不是延迟;
   - `未响应`: 窗口内反馈不动 → 陈旧/未覆盖。
   P50/P95 只在 `到达` 里算。
4. **亚毫秒负值不是负延迟**: min 出现 −0.5ms 级别 = 同机时钟/写序偏差, 报绝对值并注明来源。
5. **逐对象唯一依据优先**: 若每个技能/通道各自有一份高频刷写的 shm/json (如 60Hz 每拍刷), 直接逐个读 —— 比等一条共享轨迹扫过全链快得多且覆盖全。

## 3. 常驻服务自己的抖动要单独量, 且不算进延迟

用服务自己的埋点(tap jsonl)算拍期分位。若出现 **P99 ≈ 1s、约 10% 的拍 >100ms** 这类胖尾, 先找是不是“重活(认知层/pipeline/编码)同步压在控制拍上”——那部分不是被测量对象的延迟, 是服务骨架的结构问题。判据写法:
- 拍期 P50/P95/P99 单列一行;
- 胖尾占比 (多少 % 的拍 > X ms) 单列一行;
- 同步重活的命中率 (如每 10 拍跑一次 pipeline = 10% 命中) 单列一行, 把“胖尾”直接对到毫秒数。

## 4. 阈值判定怎么写得有用

分开报三行, 再下结论:
```
派发腿 P50 9.8ms (压线达标) / P95 17.0ms (超)
端到端 110ms (超 11×) — 瓶颈在 ① 周期与胖尾, 不在 ③
物理腿 不可采 (位姿源停更 14.8h)
```
比“平均延迟 110ms, 不达标”有用得多, 而且每个数都能指向一段代码。

## 5. 接进指标体系的注意

- 作为**补充指标**接入, 名字与旧指标分开 (如 `perf.sys_<层>_fb_latency`), 语义注释写清边界;
- 落盘文件带 `ts`, 采集器判**陈旧阈值**(如 1h) 并显示帧龄; 陈旧就标“非本刻实测”, 不冒充现值;
- 新指标没有基线时显式“未测/无基线”, 不补 0。
