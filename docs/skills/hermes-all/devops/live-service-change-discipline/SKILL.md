# 改“用户正在看的在线服务”的纪律

## When to Use（触发）
用户**正在盯着**一个在跑的常驻服务（视觉检测服务、推流面板、网关、网站、看板）边看边让你改；
或要上线/回滚/调参这个服务；或用户反馈“还是不对 / 没变化 / 没图片 / 怎么这么慢”。

用户边看边提要求、你边改边上线时，改法本身不难，**翻车全在“上线/验证”这几步**。

## 1. 三门齐备才允许一次部署（缺一不上）

1. **目标指标连续达标**：不是单次对上，而是**连续 ≥15 帧/次**稳定在目标值（实测过的阈值）。
2. **全部回归序列逐位零回退**：把历史基线帧/用例**逐条**复放，`np.array_equal` 式逐位对比。
   ⚠️ 一条过≠全部过：实测过“目标序列 13/18 看似达标、另一套参考序列却是 0/12”的版本。
   复放必须**每个场景/视角独立进程**，同进程连跑会带跨帧全局状态，伪造“无回退”。
3. **旁路/线体零影响自检**：同一服务上的其它业务口、其它端口、反向通道全部实测一遍。
   - 用户**点名保护的通道是硬约束**：上线前后都要**回读被保护服务的 pid/版本/内部状态**，证明它一动没动 ——
     “新服务起来了”只算一半证据。
   - ⚠️ **成对部署器会顺手重启“另一半”**：现成部署脚本常把一对紧耦合服务（取像/采集服务 + 判定/检测服务）
     一起重启，而现场只允许你改其中一个 ⇒ **走单侧路径**（备份 → 只换那一个文件 → 只重启那一个进程），
     图省事用成对部署器会把另一个无声重启（内部状态、曝光/增益档、暖机全丢，现场当场就能看出来）。
   - ⚠️ **部署器收尾的“复原档位”复的是“点位预设”，不是现值**：实测部署脚本最后一步把取像档位“复原”到某个
     预设（写成 20000us×8），把先前手调的档（24000×6）**无声覆盖** ⇒ **每次部署后都要回读档位字段**，
     需要别的值就再调一次。把“档位/参数”也放进部署后的回读清单，别只看版本号和 pid。

## 2. 禁止把 mid-flight 中间态留在线上

用户的画面就是他的“验收台”。指标在 20 → 12 → 16 之间漂，他只会得出“东西坏了”。
⇒ 实验一律在离线/复放环境做；**上线只上一次，且是已验证版本**。
⇒ 两个会话/子代理**不许各自往同一份产线文件上部署**（会互相覆盖，部署日志还全绿）。
   并行时约定唯一写手；每次部署后用第 3 条的回读确认。

## 3. “回读”才算生效 —— 静默 no-op 是这类系统最常见的坑

- **接口调对了但没生效**：HTTP 200 / `ok:true` 不等于参数变了。要**读回**目标字段。
  实测：一个参数接口**只认 query 参数**，用 JSON body 发 ⇒ 200 + `applied={}`，值一个没改。
- **版本号回读**：用户说“还是不对/没变化”时，第一件事是回读服务的 `*_ver`／版本字段，
  确认新版本到底上没上，**再谈效果**。别对着旧版本讨论算法。
- 🔴 **用户要“版本号升到 X”：只改文件里的 VERSION 字符串不算上线** —— 他是按**文件名**在设备上找的。
  四步缺一不可：① 程序里字符串与目标版本**逐字一致**（要 `5.50.750` 就写 `5.50.750`，不要自作主张写成 `v750`）；
  ② 复制成**带版本号的文件名**（旧名保留兼容，两文件 sha256 必须相等）；
  ③ 改**保活/启动脚本里“端口→文件名”的映射**（不改就照样拉起旧文件；改前先备份该脚本）；
  ④ kill 端口属主 → 等保活拉起 → **回读运行进程的命令行**（`Get-CimInstance Win32_Process` / `/proc/<pid>/cmdline`）
  证明它跑的就是新文件，同时回读服务自报的版本字段。
  顺手清 `.bak_*`：留**最近 3 个**（含“动之前”那版）足够回滚，其余删掉并报出释放空间。
- 🔴 **部署日志全绿 ≠ 设备磁盘上是新版**：实测遇到过“①已发布 / ②SHA256 一致 / ⑤验收全过”一步不差，
  而设备上那份文件已退回旧版（字节数回到两周前）。收工前三查：**文件名 · 字节数+sha256 · 运行进程命令行**，
  三者任一不一致就重推，别信日志。
- 🔴 **对独占设备的取图重试必须带间隔**：同一台相机/串口被连抓三次会**打坏句柄**（进程还在、端口还在，之后全部超时），
  只能等保活拉起（实测 ~75s）。重试策略：两次之间强制 ≥10s、最多 3 次；失败就如实报“冷启/被抢”，
  然后**停下来等自愈**，不要在手搓循环里连打 —— 那会把“一次失败”升级成“服务卡死”。
- 🔴 **用户说“以后要能旁路调试这个服务”⇒ 做一线独立的直连工具，不要在现有链路上加开关**。
  链路上的每一层（0.25Hz 取图 worker、去高光、帧槽缓存）都会把服务的**原始输出**包住，
  在链路上看到的东西不能当“服务是这样”的证据。
  形状（`tools/<svc>_bypass.py`，子命令式）：`status`（版本/参数/状态字段全打）· `setexpo`（改参数**并自己吃掉第一帧**，
  否则回执只是“参数已记住”）· `snap`（抓一帧存盘）· `judge`（同一帧**并排**跑本机算法与服务内置判据）· `watch`（循环观测）。
  三条硬约束写进工具里而不是写进文档：① 两次 grab 之间强制 sleep ≥10s 且不接受 0；
  ② 500/短响应自动重试 ≤3 次并打印每次的 http 码与字节数；③ 默认**只读**，改参数要显式子命令。
  `judge` 并排输出的价值：两套口径不一致时能一眼分清是“算法口径不同”还是“工件没摆到位”，
  而不是接着改阈值。

- **数据源更新了、服务却还报旧值 ⇒ 先问"它是不是启动时把数据读进内存了"**：
  重建了服务读取的库/注册表/配置后，接口会**照旧返回旧内容**（实测 `built_at` 报的是几十分钟前那次构建的时刻），看起来像"改动没生效"。
  处置：重建数据 → `systemctl restart <服务>` → **回读一个带时间戳/计数器的字段**确认确实换新，再谈效果。
  长时间没重启过的常驻服务，一律按这条查（配置、注册表、数据库、模型清单同理）。
- 🔴 **「我改了文件」≠「在跑的代码变了」—— 先把进程启动时间和链上每个文件的 mtime 并排量一次**。
  常驻服务启动时就把模块 import 进内存，之后改文件对它**零影响** ⇒ 你在命令行/离线工具里验得再漂亮，
  用户眼前的界面还是旧逻辑；而曝光/增益/阈值这类**服务端字段的回读却是对的**，
  极容易因此判定「参数没问题，是算法不行」，然后沿算法方向白查一整轮。
  一条命令定量：`ps -o pid,lstart,cmd -p <pid>` 对比 `stat -c '%y %n' <链上每个 .py>`；
  **任何一个文件 mtime 晚于进程 lstart ⇒ 整个诊断作废，先重启再谈效果**。
  重启后别只回读接口字段，要**量产物的形状**（尺寸/长宽比/均值/死白率这类结构性数字）：
  实测同一相机同一参数，旧进程输出「全幅未摆正原图」，新进程输出「1272×188 / aspect 6.77 / 死白 1.44%」——
  「接口 200 + 参数值对」两样全绿，根本证明不了摆正/后处理链路到底跑了没有。
  判据要落在**只有新代码才会产生**的那个结构特征上，不是落在参数值上。
- **部署器自检要选对判据**：`字节数 > 0`／`HTTP 200` 这类弱判据抓不出“整张黑图”。
  改渲染/输出的改动，要**解码后量内容特征**（黑底占比、均值、有没有目标结构），别只看大小。
- 🔴 **重启前先用“运行它的那个解释器”做语法自检**：`<服务venv>/bin/python -c "import py_compile;py_compile.compile('<服务源文件>',doraise=True)"`。
  这类服务的功能开关全在启动参数里，重启一次就是一次现场可见的抖动，语法错会让它**起不来**（用户看到的是“整个页面没了”）。
  改动混着“热读页面 + 要重启的服务端”时，顺序固定：**先改页面（热读即时可见）→ 语法自检 → 只重启一次 → 回读**
  （端点 200 + 新端点的字节数/响应体 + 页面里新标记的命中数），别改一处重启一处。

- 🔴 **"进程在跑"不等于"在干它的活"**: 常驻发布者/引擎常有两道静默门 ——
  (a) **功能开关未开**(改走新分支要的环境变量), (b) **上游数据源不在**(帧源/采集口没起)。
  两者都会让它**照转、照写日志、CPU 照吃**, 却**一个产出文件都不落**(或永远进 safe_stop)。
  ⇒ 判活看**产出物**: 落盘文件的 mtime / 帧龄, 连采两拍看它在变小; 不是 pid、不是 CPU、不是"周期在打印"。
  实测形态: 引擎日志每拍正常(`‖a‖=0` / `safe_stop`), 而闸文件停在一小时前的时刻 ⇒ 上游渲染服务没起 + 开关没开。
  联调顺序固定: 先把链上每个产出物点亮(上游源 → 带开关重启发布者 → 下游消费者), 每点亮一个就回读它的产出物, 再谈行为。

## 4. “抑制/兜底/降级”分支的第一不变量：**保留数据本身**

给输出加“不达标就不显示 / 抑制显示 / 降级”的门时，抑制的**只是标注/判定**，绝不是数据本身。
实测翻车：抑制分支用 `zeros` 新建一块画布 + 一行提示 ⇒ 用户看到的是“**没有图片**”，直接按故障处理。
✅ 正确形态：**以原图为底**，把提示横幅叠上去；没图时才退回占位。
同理适用于任何 gate：过滤的是“这一条该不该报”，不是“整个响应要不要给”。

## 5. 归因顺序：先量，再归因，最后才是代码

用户报“还是不对”时，按这个顺序排，不要跳到算法：

1. **回读版本**（新代码上了吗）→ 2. **回读状态字段**（门/状态/带/计数各是什么值）→
3. **量物理量**（相机/传感器/输入本身是不是变了）→ 4. 才是算法逻辑。

🔴 **先读上一轮的结论，再动手**：用户说“刚开始 XX 的时候挺好的，别乱改”“刚才不都改好了么”时，
正确动作是去翻**上一轮的 commit / 文档 / 台账**里已定的数字（曝光值、阈值、算法版本），而不是重新调一遍。
现场参数是有人调过的，你重调 = 把他调好的东西改坏，而且是**静默**的 —— 他只看到画面变差，看不到你改了哪项。
改坏了立刻回退到上一版，并在汇报里说清“哪一项是我改的、退到什么值”。
判据图/画面“看着没了”这类症状，诱因优先级通常是 **改参数 > 改算法 > 连续取图**，三者症状一模一样，
所以顺序必须是：读结论 → 回读当前参数 → 本地算法能否算出结果 → 输入本身（工件位姿）→ 最后才是阈值。

🔴 **两套判据口径不一致时，不要改阈值去迎合另一套**：同一画面在“本地算法”与“设备内置判据”上结论可以相反
（实测：本地按矩形刚体判据出图 1285×188，设备内置判据报“找不到过曝亮条”）。先分清各自判的是什么——
结构还是过曝亮条、各自的前置假设是什么——再决定哪一套是当前任务的真相；改阈值只会让两套都不可信。

两条可复用的**判别性测量**（比反复看日志快得多）：
- **扫参数看不变量**：把一个可疑参数（曝光/增益/阈值）扫一大片，若**结果字段与取带区几乎不动**
  ⇒ 与这个参数**无关**，立刻换方向（实测 22 组参数，计数与区间逐组相同）。
  附带结论：两值之间**没有连续临界点**（跳变都是“掉进另一个误选结构”的悬崖）时，说明问题不在这个参数。
- **量一个与目标强相关的结构指标**：例如对周期性目标做自相关取 lag≈周期处的峰值。
  好帧 0.387 → 现场 0.026（差 15 倍）= **周期性被物理条件洗掉了** ⇒ 离焦/距离变/照明或光路变/工件朝向变；
  此时**改算法、改参数都不会有效**。给现场的救法是**把物理条件调回去**，不是继续改代码。
- 排除法要做齐再下结论（同周期？同尺寸？重编码是否复现？），每条给原始数值。
- **量“画面本身”的廉价指标**：锐度用 `cv2.Laplacian(gray, cv2.CV_64F).var()`，配合 `mean/p50/p95`。实测同一相机同一算法：
   离焦帧 mean 19 · p95 25 · **锐度 1.6**（画面只剩一角失焦光斑）；现场拧好对焦后 mean 125 · p95 255 · **锐度 42.9（26 倍）**
   ⇒ 这类指标能**一眼定死“是画面问题还是代码问题”**。
  🔴 **离焦/欠曝期间定出来的阈值全部作废**：现场说“画面已经很清晰了”时，先按新帧把离线参数重标一遍再谈效果；
  反之，用户报“认不出/乱跳/没图”时先跑这一行，别先改算法。
  ⚠️ 别把“看不到东西”当成“图没传过来”：接口会照常回**真 JPEG**（magic `ffd8`、~190KB）而画面本身是黑的/糊的 ——
  前者要现场动镜头/灯，后者才查通道。
- **计数对 ≠ 位置对：位置错先量“相位”，别调阈值**（周期性阵列：成排针脚/触点/网格）。
  输出“个数对、间距对，但每个标注都落在目标之间的空隙里”= **整体差半个周期**，与“个数不对”是两回事，处置完全不同（改相位 ≠ 改门限）。量法：
  ① 先**钉死坐标空间**：标注坐标与渲染图**常常不是同一个坐标系** —— 实测标注间距 = 原图周期 71.0、
     末项坐标 1810 却超出裁剪宽 1455 ⇒ 它给的是原图坐标；拿去和 900 宽的渲染图直接比会算出假的“偏移 4px”。
     判据 = 用**已知的真实周期**反推：间距对得上谁，就是谁的空间。
  ② 在渲染图上比较「标注中心」与「中心 + 半个周期」两处的**信号强度**（亮度/衬度）：
     中心 < 中心+半周期 ⇒ **相位错半格**（实测 43.2 vs 56.4）—— 位置整体压在空隙上，用户会直接说“一个都没对上”。
  ③ 治法 = 不用默认相位，在 **±半个周期**内一维搜索，取使「中心 − 空隙」衬度最大的那个相位。
  ④ 验收必须**逐个**：每个标注都要“中心 > 空隙”，并给逐项的差数字（差值全为正才算过）—— 只看总数会把这条漏掉。
  ⚠️ 代码里若已有“防压缝”的门（衬度 > 下限之类），它多半是照**旧画面**定的 ⇒ 换光照/对焦后要按当前帧重验，
  否则门形同虚设、错相位照样放行。
- **用户说图上“多画了/画错位置”时，先动显示层**：标注/框/高亮的坐标是**显示层**的事，别据此去改检测逻辑。
  ① 显示层的缩放/放大常数只影响“人看的图”，改它要**明说“纯显示，不动输入/判定”**（用户会追问这一点）；
  ② 要去掉某种绘制（框/高亮）时，**把那个绘制函数体置空并留原实现**（函数体开头一行 `return` + 注释），
     比删调用点安全 —— 调用点常有多处，漏一处就是“改了还在”。验收 = 在输出图上量该颜色的像素占比 ≈ 0。
  ③ 旧画面下定的显示参数（拉伸倍数/叠加层）在**画面变化后要重新征询**：用户会直接报“高度要拉长到 N 倍”
     这类具体数值 ⇒ 当成常数改一次即可，别把它当成算法问题开一轮调查。

## 5b. 用户说「界面/页面不实时更新」的判别顺序 (先证不是数据源)

“冻住”与“源断了”看起来一模一样, 按这四步剪掉可能性, 别先去改算法或重写界面:

1. **量源**: `stat -c %Y <live/truth jsonl>` 看 mtime 与写它的进程是否在跑。源在秒级更新 ⇒ **不要再怀疑采集/总线**,
   问题在显示层。
2. **直接调刷新函数(离屏)拓异常**: 刷新路径每拍抛一次错 ⇒ 界面永远停在第一帧, 而源、日志、进程全部正常。
   实测一类根因: 某个 helper 的 `import` 写在**另一个函数的局部作用域**, 刷新函数里引用同名 ⇒ 每次 `NameError`,
   定时器照转、界面不动。修法 = 把这类依赖提到**模块级安全导入** (拿不到就置 None 并打印一行, 别静默回退)。
3. **比进程启动时间**: 用户正在看的那个实例早于你的修复 ⇒ 他跑的是旧代码。让他重启(不替他重启正在调试/正开着的实例),
   并把“重启后应看到什么”写成一句可核的话(例如“帧龄在 0~2s 之间跳”)。
4. **验收判据要判活**: 抓一个随时间变化的数(帧龄/live 龄/帧计数)连读两拍, 断言**在变小/在前进**;
   只判“能建起来 / 不抛异常 / 表里有行”会把冻住的界面判成通过。所有"实时"面板都该有这一条判据。

同源排查的例外: 判据红不一定是本轮引入 —— 先看历史判据记录(项数 + 失败项)区分"回归"与"陈旧判据",
再动手。写死在判据里的期望条数/节点数会随真源增长而过期 ⇒ 判据应从真源现算, 而不是把常量改大。

## 6. 单位与量纲陷阱（用户会当场问“为什么这么慢”）

- **界面上的数字未必是工程单位**：实测某速度控件是**档位刻度**而非 mm/s（1000 档 ≈ 3~5.8mm/s）。
  “拉大档位”才是提速，**跟网络/局域网延迟无关**——指令毫秒级就到。
- **两个参数相乘决定一个物理量**时，“一个降一个升”不改变结果（曝光×增益决定饱和 ⇒ 互补调整无效，
  且升增益只会更吵）。要动就动**乘积**。
- **硬件下限会静默夹住**你的值（写 0 → 实际 2.0）。下发后必须回读，才知道真值是多少。
- **忙拒 ≠ 故障**：服务“上一条还在执行 ⇒ 拒(不排队)”是防连点的设计，不是死了；
  单次动作耗时 = 距离 ÷ 真实速度 ⇒ 慢动作期间点任何键都会被拒。现场答法：先提速、等停稳 3~5s 再点。

## 7. 对用户的汇报口径

- 用户在现场等结果时：**给 ETA 或里程碑切片**（“第一小时能到什么程度”），不要“快了”。
- 没做好就直说“还没做好”，并说清**卡在哪一层**（版本/参数/物理量）——把“我方改动太密挤掉了他的窗口”这类事实也认下来。
- 用户提出的方向（“你调曝光试试”）**先照做**：便宜、可逆、能当场证伪；但**扫完要恢复或落到最优档**，
  扫了却恢复原值，用户看到的就是“你根本没调”。
- 每次交付带**可核证据**：回读值、字节数+magic、批量序列、对照图路径。
- 🔴 **每张图必须标“离线复放渲染”还是“现场实拍（带时刻·帧龄）”** —— 用户**会把画面当结果**：
  把离线复放渲染出的达标帧发过去，他回“效果很好，变成实拍的 N 根”，而线上此刻根本不是那个数
  ⇒ 之后一对账就是“你骗我 / 东西坏了”。离线图只能用来证明“**代码到位**”，
  **绝不用来回答“现场好了没有”**；发图时把线上当前读数一并写在同一条消息里。
- **“离线达标 ≠ 现场达标”要在发图之前就说清**：把“开关在场景（衬度/照明/位姿）还是在我方代码”定量拆开
  （消融天花板 ≪ 真值 ⇒ 场景问题，再改代码无效），并给出**具体可做的一条物理动作**（固定/增强照明、
  调焦、把光偏到目标面）——用户拿到的是“下一步做什么”，而不是又一轮参数扫描。
- **用户说“快点搞/你决定”时：给决定 + 已执行的结果，不再列选项**。把诚实底线（还差什么、卡在哪一层）
  摆在前面，别用“已优化/已修复”盖过去；他不问过程，只问“改了什么、现在什么状态”。
- **修复必须重启他正在看的 GUI 才生效时，不要停在“要不要我重启”**：这属于可逆且已默认授权的一类。
  要么直接重启并回读（窗口出现 + 页面能取到帧），要么给他**一个一点就好的动作**（已有的刷新按钮/F5）。
  连着请示两次，他接下来那句一定是“还是不好使”，因为问题还没变。
- **一旦被授予长期全权，就不要再“请示 + 等回话”**：用户明确说过“你有最高权限，自己决定，不用请示，我只要结果 /
  别绕了，直接解决 / 别浪费 token”，并强调“**以后也都这样**” ⇒ 这是**常驻授权**，不是一次性的通行证：
  可逆改动直接做，做完只报**结论 + 数字**（几行内），不写过程、不列选项、不复述他的话。
  只有**不可逆 / 动产线设备 / 花钱 / 需要人身体在场动作**的才回头问，且问时**只给一条具体动作**
  （“拧一下镜头对焦环”），不给选择题。
- **被问“现在在干啥 / 还要多久”时先自己去查**（进程 / 日志尾 / 线上读数），再按
  【此刻的实测数字 → 里程碑切片 → ETA】三段答；不要答“快了/正在处理”。他问这一句通常意味着**他看不到进展**。

## 10. 调试常驻 FIFO/执行器: 离线台 + dry 实例, 断点不落线上

常驻服务（FIFO 执行器、采集守护、引擎循环）**不能把断点下在线上实例里**：进程一暂停，硬件/下游仍按上一条指令继续跑，用户看到的界面还会超时。三层做法：

1. **计划层离线台（首选，零风险）**：写一个 `tools/<svc>_debug_offline.py`，`importlib` 加载服务模块（确认模块级**不启线程、不建 FIFO**），只调"算目标/分段/守卫"那几个纯函数，参数从 CLI 进。断点就下在这些函数里，改完直接重跑，不碰任何在役进程。
2. **dry 实例（全链路不下发）**：先给服务加三个**默认不变**的开关 —— 输入路径（独立 FIFO/套接字）、单实例锁路径、`*_DEBUG_DRY=1`（收到的任何命令强制演练）。锁必须换，否则 `_single_instance()` 按"新实例赢"把线上实例 SIGTERM。
3. **线上只读证据**：`tail -f` 服务 stdout + 它的 `/log` 端点；进程"好像卡住"用 `py-spy dump --pid`（不暂停进程），别指望 attach 一个没带 debugpy 启动的进程。

补充纪律：
- 调试实例必须能被一眼认出（日志里打一行"调试实例: 命令已强制 dry"）。
- 常驻保活（cron 每 N 分钟"没跑就拉起"）会把你的调试实例当成"服务在跑" ⇒ **调试期间生产实例其实是停的**，要在开工前就说清，收尾 kill 掉等保活拉起。
- 重启常驻服务前先读空命令队列（FIFO/队列里的旧点击会被当新命令真跑一遍）。
- 🔴 **要发布状态时别新开一个状态口**：从日志行里派生执行器状态（段号/阶段/拦截原因）最省事，也能顺手写成
  `exec_state.json`（5Hz 原子 replace）+ `exec_events.jsonl`（追加台账），节点与信号分析直接读文件 ——
  但观察钩子**只能读、不能改控制流**，且必须包 `try/except`（日志格式变了不能把执行器带崩）。
- 🔴 **从日志文本派生状态时只认锚定模式，不认子串**：阶段名/引用的原话里会含同样的词 ——
  实测阶段标签写着"斜线会被 50102 奇异点拒发"，用 `"拒发" in msg` 就把一次**正常规划**标成 blocked；
  启动横幅"🛡 安全层: …"又用 `startswith("🛡")` 把**空闲**标成 blocked。
  规则：要么按产出行的完整格式做正则（带数值分组），要么用**专属前缀**（`拒绝:` / `⛔` / `被拦(`）并对启动横幅做排除；
  改完拿"空闲 + 一次正常命令 + 一次真拦截"三态各验一次。
- 🔴 **状态文件里"事件时间"和"发布时间"必须分开**：只写 `t`（最后一次事件）时，空闲期帧龄一路涨，
  看 panel 的人会以为掉线/卡死。固定加 `t_pub`（每拍写文件的时刻）给帧龄判据用，`t` 保留"最后一次真实事件"。
- 浮点/列表字段**进不了数值表**：要上表看的量得摊平成标量（`target_x/y/z`），枚举/中文状态留在文件里给节点读。
- 🔴 **枚举要给数值 code, 否则窗口里没有进度**: 数值表只收 REAL ⇒ 状态机里的 `phase` 字符串
  (idle/accepted/dispatching/arrived/done/blocked) 进不了 Trace。固定再写一个 `phase_code`
  (0 idle · 1 受理 · 2 已规划 · 3 下发中 · 4 到位 · 5 完成 · 9 被拦), 用户才能看着 3→4→5 走完。
- 🔴 **收尾行与受理行常同前缀**: `受理: ✅ 全部 3 阶段完成` 也以 `受理:` 开头 ⇒ 一律判 accepted 会把状态
  打回起点, 臂动完了界面还写"受理中", 看着像卡死。先判 `全部 + 完成` ⇒ done, 其余才是 accepted;
  "一次完整走完"要和"空闲""一次真拦截"一起进三态验证。

断点表（进程结构 / 条件 / 各层看什么）+ launch.json 两套模板 + 变量清单: `references/resident-daemon-debugging.md`。

## 7b. 用户说「没有以前的版本好使 / 回到以前 <URL> 的状态吧」⇒ 先问清"以前"是什么

这句话不是"再优化一点"，而是**否定当前这条实现路线**。继续在新实现上调参数 = 白干一整轮。

1. **先把"以前"钉成具体事实**: 哪个 URL / 哪个端口 / 是浏览器直开还是宿主内嵌窗口 / 哪个版本号。
   拿到确切入口再动手；凭记忆猜一个入口去改，用户下一句就是"不是这个"。
2. **如果"以前"是浏览器直开，就不要再把资源花在调内嵌 WebView 上** —— 在服务端加一条入口路由即可
   (只做 302 到真源，**不在承载流媒体的那个服务上再挂一层代理**，否则 10Hz 取帧会把推流拖慢)，
   然后真验: `curl -o /dev/null -w '%{http_code} -> %{redirect_url}'` + 真开一次看服务日志里有取帧请求。
3. **自己引入的"优化"要先问用户会怎么感知**: 为省 CPU/请求数去降频、降刷新率、按可见性节流，
   省下的是服务端资源，赔的是用户每天看的流畅度 —— 实测一句「没有以前的网页好使」就能把一轮改动作废。
   ⇒ 任何"降频类优化"上线前先量**用户可见指标**(画面 fps / 交互延迟)并与改动前并列报数字；拿不到提升就回退。
4. **回退也要给证据**: 报"回到 <入口> 了"时附上 302 目标、页面帧率、服务日志里的取帧条数，
   不写"已恢复以前的版本"。

## 8. 重启常驻进程：别用自己的 shell 去匹配它（会连服务带自己一起杀）

重启服务/执行器/推流进程时，**绝不在自己这条命令行里内联 `pgrep -f <名字>` / `pkill -f <名字>`** ——
你的命令行本身（含路径、脚本名、甚至**日志文件名**）就含那个字符串，`-f` 会匹配到**执行这条命令的 shell 自己**：
- 实测：`pkill -f "<模块名>"` ⇒ 自己的 shell `exit -15`（SIGTERM），**同一条命令里后面的步骤一条都没跑**；
  日志名（如 `xxx_beep.log`）也会被 `pgrep "xxx.b eep"` 这类正则匹配上 ⇒ 同样自杀。
- 最坏是**半途自杀**：先杀掉了服务、再被杀掉自己 ⇒ **服务留在停掉状态**，现场表现是“用户点什么都没反应”
  （用户不会知道是你的 shell 死了）。
- ✅ 正确做法（任选）：① 把动作**写成脚本文件**（`write_file` → `/tmp/x.sh`）再 `bash /tmp/x.sh` —— 此时你的 argv
  只有 `bash /tmp/x.sh`，不含被匹配的字符串，匹配放进脚本内部做；② 脚本内用 **pidfile**，或按 `/proc/<pid>/cmdline`
  精确比对 argv 并显式跳过 `$$`；列进程用 `ps -eo pid,cmd= | grep '[x]xx'`（方括号技巧），别用 `pgrep -f`。
- 🔴 **复位动作必须回读才算做完**：回读 `exec.online=true` / 端口 LISTEN / 版本字段，**再发一条最小动作**验证放行 ——
  自杀或中断会让“我以为重启好了”和“其实服务是停的”看起来一模一样。
- 重启窗口内被代理的接口会**连续报 HTTP 500（几十字节短响应）**= 换文件 + 重启的窗口期，不是渲染坏：
  等它重试出图，或事后单独抓一帧验证。
- 🔴 **重启「页面在轮询的服务」会把前端取帧泵锁死 ⇒ 用户看到的是「画面冻住 / 卡死了」**：
  前端泵通常是 `if(busy) return; busy=true; onload/onerror 复位`；重启瞬间那一拍**既不成功也不报错**
  ⇒ `busy` 永不复位，之后只在刷面板数字。定性判据：服务日志里只剩 `/api/*`、**一条取帧请求都没有**
  （不是后端坏了，是前端泵死）。
  ⇒ 重启这类服务**前**先把看门狗放进页面（见 `low-latency-camera-streaming` 的泵看门狗）；重启**后**
  主动告诉用户“按一次刷新/重开就恢复”。别把“画面不动”当后端故障再重启一轮 —— 那会再冻一次，
  而且用户会认为你越改越坏。

- 🔴 **重启前先把原命令行抓下来照抄**: `tr '\0' ' ' < /proc/<pid>/cmdline` —— 带参数的开关 (如 `--arm-http <url>`)
  少一个就直接起不来, 而现场看到的是"整个页面没了"。起完立刻三件: 端口回 200 · 快照真有内容 (尺寸/均值/非黑占比) · pid 变了且存活。
  第一次起失败时**先把真实报错读出来**再试第二次, 不要连着重启 (每次多闪一次)。
- 🔴 **重启"写共享状态的常驻器"前先数实例**: 重复启一个采集/写库守护 (`--force`, 父进程 fork 出子进程, pidfile 记的是子 pid)
  会留下 2~4 个写者**同时写同一张表/同一个 JSON**, 彼此覆盖 ⇒ 探针和判据间歇假红 (同一秒里两种值来回写), 而代码一行没错。
  流程: 按 pidfile + `/proc/*/cmdline` 找全所有实例 → 全杀 → 只起一个 → 回读 pidfile 与 argv 匹配数**只一组** → 再跑判据。
  判据红的时候先数实例数, 别先改代码 (实测因此白查一轮, 清掉多余实例后全绿)。
- 🔴 **一个进程可能同时服务多个用户可见端点** (实测相机服务 8791 与站台页 8793 同 pid): 重启它 = 两个一起断。
  动手前告知会闪断几秒, 事后如实报"哪几秒断的" —— 别让用户把闪断当新故障。

## 8b. 用户说「你来重启, 刷新」= 替他做完, 连页面一起刷出来

默认纪律是"别动他正在调试/正开着的实例"; 但他**明确说这句**就是授权, 且他要的是结果不是命令。做四件:

1. **按角色分别重启**, 别只重启一个:
   - 数据/网页服务 (`cam_live_stream.py` 之类, 一个进程可能同时扛 8791 与 8793);
   - 执行器 (`l2_daemon.py`, pid 从 `zmax_data/l2_daemon.lock` 读, 不要扫 `/proc` 子串);
   - **GUI 控制台** (Trace/信号分析窗口是它渲染的): 改过 `attribution.py`/`canoe_graphic.py`/`dds_canoe.py` 后
     不重启 GUI 就一点都看不到。起法 `bash tools/gui/launch_studio.sh`, 判活 = `wmctrl -l` 出现窗口 **且**
     日志尾出现"控制台主窗口已经显示出来"(实测 19~22s), 不是 pid 活着就算。
2. **替他刷新他正在看的页面**: `DISPLAY=:0 wmctrl -l` 找窗口 id → `xdotool windowactivate <id>` → `xdotool key F5`。
   浏览器没有 CDP 端口时这是唯一能替他按 F5 的路子; 只重启服务不刷新, 他看不到任何变化。
3. **留证**: `DISPLAY=:0 scrot -o /tmp/<页>.png` 截图 + `curl -o /dev/null -w '%{http_code}'` 端点码,
   交付时给"服务 200 / 窗口 id / 截图路径"三样。
4. **刷完立刻造一条新鲜数据**, 否则他打开就是空的/陈旧帧: 用 dry 方式真走一遍业务端点
   (`arm=0` 只算不下发), 再回读产物帧龄 ≤ 几秒。**别为了造数据去真动设备**。

⚠️ 刷新后"看着慢"先量链路而不是改代码: 数据源 N Hz → 采集落库 M Hz → 窗口 tick T → 单次重建耗时。
实测一例: 5Hz 源 · 2Hz 落库(≤0.5s) · tick 0.8s · 重建 469 行 80~340ms ⇒ 端到端 ~1.3s,
把 tick 收到 0.5s 即 ~1.0s 且不卡(重建耗时 << tick 才敢收)。另外**事件型产物**(每次命令才写一次的表)
本来就不随秒变, 空闲时值不动是正确行为 —— 要跟进度得看 `phase_code`, 不是看那张表。

## 9. 探活与自愈守护：别用回环探活判“服务死了”，别把健康服务重启掉

- 🔴 **探活必须走真实客户端那条路**（页面/手机用的那个地址）。拿 `127.0.0.1` 探活会被**回环上的连接名额**骗：
  HTTP/1.1 keep-alive + 每路 MJPEG 一条连接，名额占满后新回环连接一律超时，而**同一时刻真实客户端那条路 200 正常**
  ⇒ 你会把健康服务报成“卡死”，甚至去重启一个用户正在看的服务。
  一次定性的两个数：`ss -tn | awk '$4~/:<port>$/{print $5}' | cut -d: -f1 | sort | uniq -c` —— **按对端 IP 分组数连接**
  （实测 `20×127.0.0.1 + 1×LAN` ⇒ 不是服务死，是回环被占满）。最讽刺的占用者：**自己的浏览器会话**。
- **`Recv-Q` 满 + 老连接还能答** 这个组合**不等于**进程死了：先按对端分组数连接，再看进程/端口/日志是否在动。
- 🔴 **自愈/守护脚本的判据：只在“进程真没了”时拉起**。“进程在、但新连接探不通”只**记日志**（带上各对端连接数与时刻）
  —— 重启治不了名额占满，却会**打断用户正在看的页面**（他正看的东西一黑 = 又多一个问题要回答）。
- 探针失败时**同一批里要给对照**：同机器的另一个端口/另一个服务回 200（证明机器与网络是好的），
  才能把范围收在“这一个服务”上；否则“探不通”很容易被自己升级成“机器/网络坏了”。
- 自愈脚本永远：**正常时一个字节都不打** + 只在“真拉起过”时写一行 + 带冷却（例 10 分钟），防拖/防循环。
