## 独立三维页 `/ar3d` (2026-10-26)
- 需求原话: 「三维视图要单独打开一个页面…完全独立的一个页面, 只有三维视图, 没有其它的按钮」。
- 实现: 同一份 `tools/web/tcp-ar.html`, 服务端 `p in (..., "/ar3d")` 直出页面; 前端在**脚本最前面**按
  `location.pathname=='/ar3d'` 给 `<body>` 加 `vronly vrfull`(放 `loadCams()` 里会先闪整页)。
  CSS: `body.vrfull aside/footer/header/main/#leftcol/#vrcard h2,.row,pre{display:none!important}`
  + `#vr{width:100vw;height:100vh}` + `body{margin:0;overflow:hidden}`。
- 可选参数: `?traj=xiaohong|square|map|safe|real` 预置轨迹 · `?spin=1` 自动环绕。
- 判据脚本 `tools/verify_ar3d_page.py`(offscreen QWebEngine 真加载): 可见按钮=0 · canvas=视口 ·
  scrollH≤视口 · 画布非背景像素>0.5% · 对照 `/ar` 仍有按钮(证明判据非恒真)。2026-10-26 实测 6/6 全绿。

### 第二个口径: 按钮放**左侧**(同屏看按钮+图像)
老倪: 「在这个窗口左侧，增加所有的 执行轨迹 坐标系等按钮, 但是要放在左侧, 这样我可以同时看着按钮和图像」。
- 做法: 把 #vrcard 里所有 `.row`/`pre` 包进 `<div id="vrRail">`(普通页面里它就是画布下方的块, 外见无变化);
  `body.vrfull #vrcard{display:grid;grid-template-columns:300px 1fr;grid-template-rows:100vh}` +
  `#vrRail{grid-column:1;overflow-y:auto;background:#0d1117}` + `#vr{grid-column:2;height:100vh}`。
  实测 1600×1000 视口: rail=300px(19 个按钮全可见), canvas=1300×1000, scrollH=1000(不可滚)。
- 栏内按钮要竖排满宽(`#vrRail .row{flex-direction:column}` + `button{width:100%;text-align:left}`),
  否则 `.row button{flex:1 1 46%}` 会把两个按钮挤在半宽, 名字长的按钮被截断。
- 窄屏(<820px, 手机竖屏)用 media query 把左栏改成底部 34vh 横条, 不然画面被挤没。
- 判据(6 项全实测): 左栏在画布左侧 · 画布满高且页面不可滚 · rail 内按钮≥12 全可见 ·
  画布非背景像素>0.5% · **对照 `/ar` 不是左栏版式**(防判据恒真) · 点『坐标系』class 翻转。
- 判据实现坑: 同一个 QApplication 里第二个 QWebEngineView 大概率超时 ⇒ **先跑对照 /ar, 再跑 /ar3d**;
  页面数据(traj/URDF/光模块)异步到, 只探一次会误判"没画出来" ⇒ 1.2s 轮询取 pct 最大的那次。

### 实验桌 750 + 箱体落地平齐 + 四轮 (2026-10-26 r22)
老倪: 「在机器人底座箱体前面摆放一个实验桌子, 高度750; 机器人的箱体高也降低到750平齐; 且底座增加4个轮子」。
- 🔴 **只有一种几何能同时满足「750 + 平齐 + 不抬臂」**: 地面(轮底/桌腿落地点) = `z=-0.750`,
  桌面顶 = 箱体顶板 = 两臂安装面 = `z=0`; 箱体**向下长**(本体 680 + 轮露出 70 = 750), 顶板一动不动。
  反过来说, 若把 750 当成"从 z=0 那块 base 网格往上量", 桌面就跑到 +0.75, 比臂安装面高 750, 不可能平齐
  —— 「降低到 750」是箱子向下落地, 不是把臂压低。**先把这个口径写进页面注释再动手**, 否则做出来的图必被退。
- 口径参数: `CHS={L:.6,W:.8,H:.75(落地总高),HB:.68(本体),wr:.075(轮半径),cy:.25}` ·
  `TAB={x0:.35,x1:.95,cy:.25,w:1.6(沿y, 老倪定稿1600),t:.03,h:.75}` · `FLR={z:-.75,x:[-.5,1.25],y:[-.7,1.2]}`。
  桌子摆 +X(前脸 HMI 那侧 = 两臂/顶视相机作业方向), 桌沿离箱体前脸 50mm ⇒ `TAB.x0 > CHS.L/2` 是硬闸。
- 画法: 轮子用**轴沿 y 的圆柱**(`_discY` 22 边圆盘 ×2 端面按屏幕深度排序 + 轮毂 + 亮芯), 比原来的扁盒子像;
  地面层 = 半透明深色 quad + 250mm 暗格 + 标签; 桌子 = 4 腿 + 两条下横撑 + 桌面 + 顶面高光线 + 750 竖标尺。
- 绘顺序: 地面 → 桌子 → 箱体 → 臂。默认视角 `yaw=-0.9` 是从 -X+Y 看过来, 桌子在箱体**远侧**,
  所以必须"先桌后箱", 反过来桌子会盖在箱体上。
- 💥 判据坑(都实测踩过):
  1. **顶视相机视锥(10% 半透青)压在桌面上**, 木色 `#7a5f45` 被染成 `(119,109,84)` ⇒ 只数纯木色只有 66px,
     看着像"桌子没画"。改用"木色域"判(R 90~150 · G 72~135 · B<105 · R>G>B · R−B>28), 实测 15881↔关3437。
  2. 轮毂色 `#39424e` 与暗色抗锯齿杂点撞色(关掉箱体还剩 ~350px) ⇒ 轮子判据改用**轮芯亮钉 `#b9c6d4`**
     (全页独有, 实测 165↔关2)。桌腿色也因此从 `#3d444d` 改 `#4a4f58`(与轮毂同色系会互相污染)。
  3. 工程点位那条判据(亮点 全开→全关 掉 60%)会被**暖色标注/高光**污染: 桌面高光 `#f0d9ac` 与 750 标注
     `#d8b98c` 的 min 通道都 >125 ⇒ `bright()` 必须加 `min(R,G,B)<125` 只数饱和色, 否则 ⑦ 假红。
  4. `baseZ` 别写 `LINKM.base_link`(没有这个键): URDF 基座名是 `XMS5-R800-W4G3B4C_base`,
     按 `/_base$/` 找。它是"臂安装面没被抬动"的唯一硬证。
- 判据已扩到 12 项: ⑩ 箱体 600×800×750(本体680) + 臂安装面 z=0 · ⑪ 桌面在前脸之外/1000×600×750/真画+开关不动相机 ·
  ⑫ 桌高=箱体落地高=750 + 地面 -750 同层 + 四轮真画出来。2026-10-26 实测 12/12 全绿。

### 🎯 目标点单选 + 轨迹5「实时」= 当前TCP→目标点 (2026-10-26 r25)
老倪: 「当我选择轨迹5 实时的时候, 你要规划一个从当前点到目标点的轨迹; 在每个空间点位的左侧增加一个小开关, 表明是目标点, 只能有一个; 选好之后你来规划到这个点的轨迹路线并显示出来」。

**接口契约**
- `GET /api/traj/named?k=real&target=<点名>` —— 新增 `target`(不传=安全点1); 返回多 `target` 字段。
- 路径骨架固定 4 点: `[当前TCP, (cur.x,cur.y,zs), (tgt.x,tgt.y,zs), 目标点]`, `zs=max(cur.z,tgt.z)+50mm` ⇒ **原地升→平移→垂直落点**, 不做低空横移。
- `traj_from_named.py`: `real` 只在 `len(pts)>8` 时才塌成首尾 (老版 25 点直线才需要), 4 点骨架必须保形(RDP 5mm 保角)。CLI 加 `--target`。
- `POST /api/traj/exec {k,target}` 必须把目标点带下去, 否则**页面显示去A、执行去安全点1**(真源不一致)。

**UI(老倪让我设计)**: 左栏每个空间点位行左侧一个 17px 靶心单选钮 `.tgtbtn`(灰空心)→选中变橙实心+暗芯+外发光; 行内 `data-target`; 单选靠 `CFG_TARGET` 一个变量; 三维里给目标点套橙色靶环+十字+「🎯 目标点」; 换目标时若轨迹5 亮着立刻 `refreshNamed('real')` 重算且**相机不动**(存/恢复 VR.yaw/pitch/dist/tgt)。

**坑**
- 🔴 本服务 query 是手写 split, **不做 percent 解码**: 中文点名必须 `urllib.parse.unquote`, 否则台账查不到(实测 `target=%e9%87%91...` 一直 ok=false)。
- 🔴 `systemctl restart/stop zmax-traj-ar` 会 Connection timed out 而进程不退(97 线程收不掉): 用 `tools/restart_traj_ar.sh`(stop --no-block → 等 25s → SIGTERM/SIGKILL → start → 等 /ar3d 200), 别手敲。
- 🔴 offscreen QtWebEngine 把页面当后台页**限流 setTimeout**(300ms→~1s): 自验里等 fetch 必须用 Qt 侧 QTimer 轮询 `runJavaScript`, 不能靠页面 `await new Promise(setTimeout)`。
- ⚠️ 页面有 5~6 个高频轮询(refresh 1.5s / robotTick 1s / peg2dTick 600ms / lockTick / cams 4s), Chromium 每 host 6 连接 ⇒ **轨迹5 的 named 请求可能排队十几秒才回来**; 自验判据要按「最终终点=当前目标」等, 不能按固定时长量。
- 判据 ⑭ 写法: step1(点靶心+点轨迹5, 同步) → Qt 轮询 m1(终点↔CFG_TARGET) → step2(换目标) → 轮询 m2 → 断言 24 个靶心/单选唯一/4 点骨架/换目标重算/四段相机一致。

## 8793 与 8797 的关系 (老倪问过「通道怎么还变了」)
- 8793 = `tools/cam_live_stream.py`(工位总览 `/station` + 状态空间视频源); 8797 = `tools/tcp_ar_server.py`(AR 真源)。
- `8793/ar` **只做 302** → `8797/ar`, 不代理(`cam_live_stream.py` 的 `/ar` 分支); 所以 8793/ar 秒回 302,
  真正的页面/取帧/判据 API 全在 8797。控制台的页面入口固定 `10.163.146.78:8793/ar`(他记的地址),
  服务探测走 `127.0.0.1:8797`(回环优先) —— 同一台机两个端口, 不是"通道变了"。
- **打不开的真因**: 8797 是 fork-per-connection(`max_children=24`, backlog 5)。多开几个 AR 页后实测
  24 个子进程 / RSS 合计 12.3GB / LISTEN Recv-Q=6 满 ⇒ 新连接排队, `curl -L 8793/ar` 要 **175.8s** 才通
  (直连当时也 30s 超时), 浏览器窗口一直空白(标题 `Untitled`)。
- 配套坑: `ar_spawn_browser` 只要 Popen 成功就报「页面已送出」, 不看窗口也不看加载 ⇒ 状态栏"送出了"
  但屏幕上没画面。判"开了"要认窗口标题/连接数, 判"页面真出来"要认标题变成 `Z-MAX · TCP 轨迹 AR/VR`。
- **已修(2026-10-26)**: 改成 `ThreadingMixIn` 单进程多线程 —— `request_queue_size=128` · 线程上限 96(信号量,
  满了直接关连接不排队) · `H.timeout=20`(断链线程 20s 必收)。实测 6 个页面同时刷时新开页 4—320ms(中位 122ms)、
  零错误、单进程 103 线程 / RSS 789MB 稳定; 旧 fork 模型是 24 子进程 / 12.3GB / 175s。

## 五个必踩的坑
1. **别自己构造轨迹**。工程配置里没有的元素不要"以某个中点为心造个正方形"——他会立刻指出"不是新的"。
   要么读工程配置里真实元素, 要么读真源产物(planned_traj.json 等), 取不到就报缺什么, 不画。
1b. **"旁边那条粉色矩形"= 页面上的洋红规划航路闭环**, 不是工程配置里的盒子/设备顶面。
   认错元素的后果是轨迹贴着检测设备走(取 z=盒子顶面 ⇒ 净距 0), 他会立刻问"那不碰撞了?"。
   判据: 这条轨迹的首点应当≈当前 TCP(真机刚走过), 且到设备盒子的距离是几十到几百 mm 而不是 0。
2. **自动取景 = 视图跳**。`vrFitBox()` 会重算 target/dist 并写回 VR; `drawVR()` 里若还有
   `if(VR.auto) vrFitBox()` 则每帧都跳。改法: 画前后原样存取 `{yaw,pitch,dist,tgt}`, 并 `VR.auto=false`。
3. **数据变化指纹漏项 = 画不出来**。`drawIfChanged` 的指纹不含 NAMED 时, 点第二个按钮判"没变化"直接 return; 指纹里要放"哪些轨迹亮着 + 总点数"。
4. **同一语义两套 id ⇒ 只测一套会漏**。按钮同时存在顶部工具条 `tA1..tA5` 和三维视图下方 `t1..t5`,
   解析序号若写 `id.replace('tA','')` 对 `t1` 不动手, `Number('t1')` = NaN ⇒ key=undefined ⇒ 那一排**永远不变蓝**。
   必须显式剥前缀(`startsWith('tA') ? slice(2) : slice(1)`), 且自验时**两排各点一遍**——只点自己新加的那排会把 bug 藏起来。
5. **页面被第二个端口转发时, 只转页面不转 `/api/*`**。直接用 `curl <第二端口>/api/...` 验证;
   404 时页面里 fetch 全失败、按钮不亮。改法: 脚本最前面装一次 fetch 兜底, 页面不是从主端口打开就把
   `/api/*` 打到主端口(主端口已带 `Access-Control-Allow-Origin: *`)。
6. **数据是 0 点的按钮也必须点亮**。服务端对没有数据的轨迹回 `ok=false`, 前端若在那分支直接 `return`,
   按钮永远黑着——用户看到的就是"按钮坏了"。**激活是按钮状态, 有没有数据是另一件事**:
   `ok=false` 时同样置 `NAMED_ON[k]=true` 并重绘, 文字写"已激活 · 0 点 · 真机还没走过, 不能执行";
   汇总行不许把这类条目当"关着"过滤掉; 『▶ 执行轨迹』侧加闸, 0 点直接拒(不许走到空下发)。
7. **`confirm()` 会静默失效, 结果必须走页面横幅**。浏览器勾过"阻止此页面创建其他对话框"后,
   `confirm()` 直接返回 false ⇒ 处理函数第一行就 `return`, 什么都不发、无任何提示, 症状与"按钮坏了"一样。
   改法: 执行结果(成功/被哪道闸拒 + 实测数字)同时弹一条 6 秒固定横幅(`position:fixed` + 绿/红),
   不能只写按钮旁一行小字(会被轮询覆盖), 也不要把关键确认只压在 `confirm()` 上。

## 执行链口径
页面『▶ 执行轨迹』→ `POST /api/traj/exec {k}` → `tools/traj_from_named.py --k`
→ RDP 抽骨架(容差 5mm) → 骨架点间拆轴对齐段(先 Z 再 X 再 Y, 单段 ≤300mm)
→ `traj_plan.precheck_point` 逐点净空(≥20mm) → 写 `planned_traj.json` + `plan_latest.json` → 执行器。
- **起点闸**: 当前 TCP 必须离轨迹首点 ≤20mm, 否则拒(与 550C 执行器同口径)。"先去起点"是独立运动, 不许混进轨迹。
- 失败原因必须**原样**回页面(`⛔ 起点闸: ... 差 278.6mm`), 不许只回"失败"。
- 示意坐标 / 已走过的记录(建图、实时)默认拒绝执行, 要试得 `--force`。
- **轨迹5『实时』= 当前位姿 → 安全点1 的待执行路径**, 不是"真机走过的记录"。用户要去安全点时点的是这一条:
  服务端现读当前 TCP + 点位台账的 `安全点1` 生成点列, 规划侧只取两端点交给轴对齐拆段, 并把单段上限
  强制压到 **100mm**(去安全点要抬 200mm+; 长单段会被控制器静默丢弃)。起点=当前 TCP ⇒ 起点闸天然过。
  旧的 "读 `bridge_real_path.json` 实测记录" 分支要挪走/改名, 别让它继续占着 `real` 这个键。
- **路径形状**: 先去安全点这类动作按「先抬到目标 z → 再平移 → 到位」拆(z 先走), 不要低空横移;
- **激活 ≠ 一直在画**: 把轨迹「保存成围栏点元素」是错的。`savePointsElement` 写进 `fences.json` 的
  `type="points"` 项与按钮状态无关, 每帧都绘 ⇒ 用户没点任何按钮却看见好几条轨迹。轨迹显示**只允许**
  由 `NAMED_ON` 驱动(`drawNamedVR`/`drawNamedOV` 都按它过滤); 已经落进 `fences.json` 的轨迹点要
  清掉(备份后只删 `type=="points"`, 保留 box/line 真围栏), 判据 = 围栏清单里只剩 box/line, 页面未按按钮时零轨迹。
- 🔴 **"以当前 TCP 为基准"的轨迹必须每次按 live 真值重算, 不能读历史计划**。臂走过一趟后位置变了,
  而 `planned_traj.json` 的起点还是上一趟的 ⇒ 550C 起点闸报 `起点已变 100mm`, 页面只闪一行小字,
  用户看到的就是"点了执行没反应"。判据: 这类轨迹(如臂旁那个矩形)取数时 `read_tcp()` 现算
  (抬60 → 后(x-)80 → 降60 → 前(x+)80 这种相对段), 首点恒等于当前 TCP, 点一次就能走。
  绝对位置的轨迹(小红/安全)相反: 保持严格起点闸, 不许为了"能点"而偷偷改成相对。
- 🔴 **覆盖扫描类轨迹(建图)起点必在外, 用 `--lead-in` 而不是让他先手动去起点**: 把「TCP→首点」
  也拆成轴对齐段写进同一份段表, 段表起点=当前 TCP ⇒ 起点闸过。代价是段数会变多
  (三行扫描 ≈ 12 段), 所以 `plan_exec_550c.py` 的收包上限必须从 8 提到 24, 否则发布出去被静默丢弃。
- **拒绝判据要按 `src` 判, 不能按 `k` 一刀切**。同一个键(如建图)可能有两个数据源: 老的
  "2D 栅格平移"示意坐标(该拒)与 `explore_traj_fenced.json`(真 base 坐标、逐点过围栏复核, 可执行)。
  按 k 写死会把它误杀: 页面显示 44 点、执行端却说"不可执行" —— 两处口径必须同源。
- 执行链推 550C 时, 550B 只算段表 + 发 `ss_plan`, 逐段下发与真值对账归 550C; `exec_by.json` 一行切回本机。
- 🔴 **一票否决的闸必须在页面常驻可见, 不能只靠按钮旁一行小字。** 「点执行怎么不动」的头号原因不是链路, 而是
  授权窗过期 —— 而拒绝理由平时藏在按钮下方的小字里, 用户根本不会看。做法: 标题栏放一个状态牌, 轮询只读端点
  (`POST /api/auth` 返回 `{armed, left_s, left_min, epoch, where}`), **红 = 已失效 + 直接写明去哪授权
  (`8793 工位总览 → 授权真动`), 绿 = 剩 N 分钟**; 状态牌要在首屏, 不靠滚动。
  同一原则适用于起点闸/预检: 拒绝时把「闸名 + 实测数字 + 下一步动作」三样一起回页面, 不说"失败"。
- ⚠️ **只读端点也可能挂在 POST 分支**: 与 `/api/traj/exec` 写在同一段 `elif` 里的 `/api/auth`,
  前端 `fetch('/api/auth')`(GET) 直接 404 ⇒ 状态牌永远显示"查询失败"。新端点先用
  `curl -s -o /dev/null -w '%{http_code}'` 把 GET / POST 各试一遍再写前端。

## 围栏避让规划 (tools/explore_traj_fenced.py)
- 覆盖路径必须按 `fence_store` 真源避让: 逐行扫描, 每行先算该 y/z 上被哪些围栏占掉再减掉(留 30mm 净距)。
- 盒子按三轴重叠判; **直线元素(小兰/小青)也是围栏**, 按线段采样点避——只避盒子会被自己的复核抓住。
- 规划完逐点 `check_point` 复核, 命中就报错不写文件; 汇报每条围栏的最小净距。

### 配置里没有的障碍: 用臂相机深度图现场量成 AABB 再注入围栏
用户问「你看到你面前那个相机了么」时, 光读 `fences.json` 不够 —— 配置里往往只有 侧面检测相机/检测设备/上横梁 三四个盒子,
台面上临时立的相机、支架、料盘都不在里面, 于是轨迹被算成「净距 455mm 很安全」。定式 (`tools/scan_obstacles.py`):

1. 取一帧彩色 + 深度: `http://<orin>:8792/frame.jpg` + `/depth.png`(D405 · uint16 · unit 0.1mm · 65535/0 = 无效)。
2. 位姿用**桥 `/status` 的 `endInRef`(米/弧度)**算 `T_base2cam = T_base2tcp @ T_cam2tool`; 别用 `tcp_out/latest.json`
   兜底时不核对它的 `rx/ry/rz` 是否真值(全 0 = 陈旧), 更别默认 rpy=0 —— 位姿错会把台面推到 700mm 上去,
   整份障碍清单看起来"有 8 个物体"其实全是假的。**先看 z 直方图的峰是否落在台面高度(几十 mm)再采信结果**。
3. 台面高度 = 点云 z 直方图首峰; 台面以上 `>25mm` 的点按 **15mm 体素 8/26 邻域 BFS 聚类**, 保留 ≥800 点的簇,
   每簇出 `p1/p2/size/center/距离当前TCP`, 外扩 20mm 写进 `fences.json`(`type="box"`, note 写实测尺寸与点数)。
4. 加完**必须重跑覆盖规划**并报每条围栏的最小净距 —— 判据是「新盒子出现在净距清单里」而不是脚本没报错。
5. 与既有盒子对账: 实测常在 `上横梁` 范围内(同一条导轨上的顶摄), 先比中心/尺寸再决定是新增还是把旧盒子改紧,
   免得同一物体两个盒子把可通行区扣没了。
- 汇报口径: 「量到的盒 x/y/z 范围 + 尺寸 + 点数 + 距 TCP 多远 + 已注入围栏」, 用户才认这是看过而不是猜的。

## 自验方法 (不靠肉眼)
浏览器 console 直接量:
- 画点数: `window.__NAMED_DOTS__` 归零后 `drawVR()` 读回, 应等于各亮着轨迹点数之和(如 41+54=95)。
- 高亮是否生效: 点完读 `className` + `NAMED_ON` 的 key 集合, **两套 id 一起读**(见坑 4);
  并且必须读**计算样式** `getComputedStyle(b).backgroundColor` —— className 对但 CSS 被后面的同级规则
  覆盖时, 用户看到的仍然是黑按钮; 只比 className 等于没验。同时确认 `NAMED` 里点数与服务端一致。
- 相机是否被挪: 点按钮前后比对 `{yaw,pitch,dist,tgt}` 四元组, 必须完全一致。
- 是否碰设备: 用 `FENCES` 里的盒子算点到 AABB 距离, 报最小距离 + 落进盒内的点数;
  别只信服务端返回值, 页面侧独立算一遍才算取证。

## 让用户一眼确认"你这版到底有没有生效"
- 页面标题旁放**版本戳**（如 `构建 2026-10-26 r8 · 五条按钮都能点亮`），改一次页面就递一次号。
  用户再说"还是没变"时, 让他看这行号——比反复解释省事, 也避免把"他缓存了旧页"当成代码 bug 重查。
- 页面响应带 `Cache-Control: no-store` 也不保证他拿到新版(浏览器后退/标签页复用); 版本戳是唯一可靠判据。
- 重启主服务用 `systemctl restart zmax-traj-ar`; `restart` 可能报 `Connection timed out` 而旧进程仍在服务,
  此后**子进程会继续用旧构建**: 查 `pgrep -af tools/tcp_ar_server.py` 的 master 启动时间是否晚于改动, 不对就
  `systemctl stop` → `start`。同一端口挂十几个 fork 子进程 = 有的连接拿到旧页, 症状就是"时好时坏"。
- 清进程一律走 systemd 或写成脚本再执行; 内联 `pkill -f '<脚本名>'` 会匹配到执行它的那条 shell 自己,
  把自己 SIGKILL 掉(实测两次)。
