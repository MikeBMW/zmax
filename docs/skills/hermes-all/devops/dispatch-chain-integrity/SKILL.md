# 下发链完整性核验(名义值 vs 实际值 / 读者端存活 / 数据来历)

## When to Use

一条命令从**界面/脚本**经**常驻执行器**、**本地库**、**代理进程**到**设备**(机器人/PLC/驱动)时, 出现:

- 档位调了**看不出来快**; 同一个数在两处生效却不一样;
- 点了**没反应**, 错误里带 `No such device or address` / `Errno 6` / "没在跑?";
- 动作**跑到了别的地方**(不是这次点的地方), 或者现场说"这不是我写的点";
- 报出的指标跟现场实测对不上。

⇒ 不要先怀疑设备, 也不要先改代码 —— 先把**链路每一层的实际值**量与**读者端还在不在**验完。

## 铁律 ①: 逐层找夹紧点, 然后**在末端量**, 不要报中间值

链路里每一层都可能**静默夹紧或替换**用户给的值。典型形态(界面 → 执行器 → 库 → 代理 → 设备):

```
界面/脚本给值
  → 常驻执行器:  sp = min(speed, 该技能.speed_max)              # 配置, 逐技能, 常热加载
  → 本地库:      sp_mm = max(FLOOR, min(HARD_CAP, K * units))   # K≈0.0935, FLOOR≈1.0
  → 代理进程:    speed = min(speed, 自己的 HARD_CAP)
  → 设备
```

- **有效值是所有上限里最小的那个**; 只改用户看得见的那层数字等于没改, 必须**逐层同时抬**。
- 换算系数不等于真实速度: 实测经常是**标称的固定倍数**(常见 1/10), 而且**超过某档后被硬上限封顶**
  ⇒ 两个不同的高档位可以落在**同一个实际速度**上。
- 🔴 那个固定倍数多半来自**设备侧在线倍率**(控制器/驱动器自带), 不是链路里的任何一层 ⇒ 想"点的数字 = 实际速度",
  正确做法是**把设备倍率设回 1.0**(`adjustSpeedOnline(scale)`, 非实时模式生效, 无 getter ⇒ 改完只能靠实测), 而
  **不是**把下发数字乘 10 去补 —— 名义会膨胀到 1e4 mm/s 量级, 倍率一旦被谁改回 1.0 就成 ~10 m/s 的雷。详见 `references/speed-and-stop-chain.md` §1b。
- 🔴 **报"快了多少"之前必须在末端量**: 连采设备真值文件算 `Δ/Δt`, 或读执行器/驱动的到位回执行
  (它常自带 `… · 18.3s · speed=X mm/s`)。只报标称值 = 下一次现场实测就要打脸。
- 🔴 **等待/超时窗口必须按"夹紧后"的值算**, 不能按用户填的原始值:
  `eff = 实测系数 × min(设定值, 硬上限/换算系数)`。少这一层 `min`, 高档位时就会高估实际速度
  ⇒ 等待偏短 ⇒ **动作没走完就被判"未到位"并中止整条计划**(已下发的指令不会撤回, 现场看到的是
  "走到一半停了")。同一口径要在**所有**等待处都改: 执行器的阶段超时 / 库的分片等待 / 代理的预算 / 上层脚本自己的等待。
- 改哪一层要重启什么: 配置类(注册表/JSON)多半**热加载**; 执行器自身代码、它进程内 import 的库, 要**重启执行器**;
  代理在容器里只读挂载 ⇒ 要**重启容器**; 页面热读。逐项对照见 `references/speed-and-stop-chain.md`。

## 铁律 ②: 读者端存活 —— "点了没反应"先判是谁不在

- `[Errno 6] No such device or address` / `ENXIO` 打开一条 FIFO/管道来写 ⇒ **该管道没有读者**,
  即**常驻消费端不在**(不是设备坏、不是权限、不是配置)。探针: 以 `O_WRONLY|O_NONBLOCK` 试着打开,
  能开 = 有读者; 再核进程 + 它的启动横幅(含它监听的路径与项数)。
- 🔴 **急停/全停脚本通常会连带杀掉消费者** ⇒ 全停之后必须**显式重启它**, 否则界面上**每个**按钮都报同一句
  "打不开" —— 现场以为全坏了, 其实只是读端不在。
- 🔴 **重启本身有 2~4s 空窗**, 这期间点击必报同样的错 ⇒ 重启后**先自检可写, 再让现场点**。
  与另一实例并存时, 先起的那份可能还在读**已被删除的旧 inode**(ps 看得见、收不到命令) —— 先杀干净再拉。
- 🔴 **管道的 inode 被任何一端重建, 另一端就握在死 inode 上** —— 不只是"又起了一份":
  **重启读端(消费者)容器**也会重建命名管道(实测 `docker restart <消费容器>` 重建 `cmd_arm.fifo`)。
  此时下发端进程活着、日志照写、回执照回「已下发」, 但命令进不了新管道。
  ⇒ **顺序固定: 先重启容器, 再重启下发端进程**, 并核对管道文件的 mtime 是刚变的; 反过来会把下发端又留在旧 inode 上。
- 🔴 **"写 stop 到管道"不等于立刻停**: 消费端**顺序处理**, 它正卡在某次动作的"盯真值/等待"循环里时,
  后写的 stop 要等那段循环结束才被读到(实测 1~2 分钟), 期间在飞动作照走。
  ⇒ 想让在飞动作**立刻**停, 只能**掐链路**(重启消费端容器/进程、杀掉下发方), 别指望写一条 stop。
- 报状态时把"消费者在不在"和"动作有没有下发"**分开说** —— 这两件事现场最容易混。
- 🔴 **失败阶段之后的命令会排队**: 执行器顺序消费, 某阶段失败后它仍要**等满该阶段的到位超时**
  (只按真值判到位, 零位移那条必须等满), 期间后写的命令**一行都不会被读** ⇒ 现场看到的正是
  "已下发却不动/点了没反应"。判据: 执行器日志**最后一行的时刻**停在那条失败、而现场那条命令在日志里
  **一行都没有** = 它还在队列里。⇒ 卡住期间**别重复点**(每点一次多堵一条、各等满一次超时);
  先给现场"队列第几位 / 还要等多久", **别把排队说成"命令丢了"**; 清队列=读空 FIFO, 要用户点头。见 §6。
- 🔴 **重启消费端会把排队的旧命令放出来真跑**: 队列就是 FIFO 里的**文本行**, 新实例照样逐行读 ⇒
  现场"点了没反应"期间连点的几条, 会在重启那一刻**按原值真下发**(实测: 重启后臂自己走向几分钟前点的点位)。
  ⇒ 重启前 ①确认无在途计划(执行器日志尾的时刻 + `/ctl/status` 的 operation) ②非阻塞读空 FIFO 并
  **打印清掉的条数**(`os.open(fifo, O_RDONLY|O_NONBLOCK)` 循环读到 `BlockingIOError`);
  重启后**立刻读日志确认没有任何新的"已下发"行**, 有就当场叫停并主动说明。
  ⚠️ "清空时读到 0 条"**不等于**队列真空 —— 消费端可能已把命令读进自己的缓冲、然后才被重启 ⇒
  只有"重启后日志无新下发"才算证据。清了队列就必须说清"哪些点击被我作废了"。

## 铁律 ③: 数据来历 —— 先确认这个值是不是他要的那个

存在多份同名数据(两套点库/两份配置/演示学习 vs 手工示教)时:

- 解析常有**优先级**(同名以某一套为准), 且**缺了不报错**: 找不到就**静默回落到另一套**
  ⇒ 落点变成"某个历史时刻恰好在那里的值", 现场的话就是「**这个点不是我写的点**」。
- ⚠️ **技能注册表锁的点名 ∩ 点库的键**要每一对都对得上: 注册表有 `goto_X` 而点库里**没有键 X** ⇒
  点它只会安静地报"点位 X 不在点库"(现场像"点了没反应")。重建/重录点位后做一次差集核对再交付。
- **覆盖式写入**的判据(不是猜): 看该条目的 `recorded_at`/更新时间, 并把它与**当时**的真值/现场状态对照 ——
  值逐位相同且时间很近 ⇒ 它是"被记录的当时状态", 不是人教/人设的值。
- 🔴 **凡"清除/覆盖"都要留痕, 而有留痕就一定可还原**: 找同目录的审计流水(
  每条含被删的完整值 + 来源 + 原始 `recorded_at`)与整库快照(常见 `/tmp/<lib>.cleared_<name>_<时间>.json`)。
  还原 = 按名字取"**覆盖前最后一次**"的原件(按 `recorded_at` 排序取最晚早于覆盖时间者) →
  **先备份现库** → 写回 → 回读校验 → 发一次 dry(不下发)核对目标与写回值逐位一致。
  可跑的取值片段见 `references/point-store-and-recovery.md`。
- ⚠️ 现场正在**手改这份数据**(清空+重记)时**不要插手** —— 只报证据(原值/现值/覆盖时间/原件在哪个文件)
  并给出"可一键还原"选项, 由他选。抢着还原 = 把他正在做的事覆盖掉。

## 铁律 ④: 通道选择会**静默丢掉请求里的字段** —— 姿态/角度这类"次要字段"最先丢

链路对"运动"常有两套下发形态(按**位移**分片的相对平移 / **整位姿**的绝对位姿), 而分片通道
**只带位置、不带姿态** ⇒ 用户要的是"转", 系统只做了"移"。

- 症状: 纯旋转(位移≈0)点了**毫无反应**; "小位移 + 大角度"则**只平移不转**
  (现场看到"没转却掉了几十毫米" —— 掉的是目标的**位置分量**)。假报也在这里:
  事后回报的"实测转过 0.0°"可能是**真的**, 别当成误报/假失败。
- 判据: 选通道的条件若是 `位移 ≤ 阈值` ⇒ **姿态变化根本没参与判断**。
  铁律: **凡姿态差 ≥0.3° 一律走整位姿通道**, 与位移大小无关; 该通道的等待窗口还要**按角度**补一项
  (转头慢, 10° 实测数十秒), 否则"没转完就判失败"。
- 🔴 **dry/演练验不了最后一跳**: dry 在"选通道/下发"之前就 return ⇒ 它只证明"目标算得对",
  不证明"发出去会转"。零运动的**腿级**验证: 进程内 import 下发模块, 把 `send_agent`/`read_pose`/写证据
  换成桩, 直接调入口, 断言**纯旋转的命令 = 整位姿形态且请求里带姿态分量**,
  再发一条纯平移断言仍是分片形态(防回归)。
- 排错顺序: ①该条是"已下发"还是"演练/DRY" ②有没有**该通道自己的**下发行(同时含位移**和**姿态差的那行)
  ③选通道那行代码 ④**真值**: 位置 Δ **和**姿态夹角都量 —— 只平移不转时位置是对的, 只有姿态骗不了人。
- 修完一处要反问: **还有哪些动作也带姿态/角度?**(旋转 · 转身 · 回姿态的点位) —— 它们走同一条分片通道。

## 铁律 ⑤: 改设备/服务参数 —— 写"形状"要对, 生效要认"回读"

- 参数类 REST 路由常常认 **query 参数**而不是 JSON body, 而且**发错形状也回 200**(服务端解析不出就默默跳过):
  实测 `POST /param?exposure=24000&gain=6` → `200` + `applied{exposure_us:{ok:true},gain_db:{ok:true}}`;
  而 `POST /param -d '{"exposure_us":24000,"gain_db":6}'` → **同样 200 但 `applied:{}`、值一个没变**。
  ⇒ 现场看到的就是"**你根本没调**"（本轮用户原话）。
- 🔴 **写完参数必须读回**：不带参的同一路由回 `now`、或读设备真值文件；把 `applied`/`now` **原文贴出来**。
  "HTTP 200" 不是生效证据。
- 静默夹紧在参数层同样存在: `gain=0` 被钳到 **2.0**(硬件下限) ⇒ 报设定值时必须报**设备回读值**。
- 先确认这个旋钮**在不在这条通路上**: 接口可能只暴露某几个参数(如曝光/增益/Gamma, **不含光源**) ——
  别在能改的旋钮上反复试一个根本不属于它们的问题。
- **改判据/渲染类输出后要解码量内容**(如黑底占比/饱和占比), 不能只看"字节>0": 纯黑画布也有 29KB ⇒
  部署器/验收探针会误判通过。

## 铁律 ⑥: "我改的那版在跑吗" —— 三件套指纹

用户说"改了怎么没变化"时, 不要把"没变化"当结论, 先把这三条对上:

1. **元数据里的版本串**(如 `/crop_info` 的 `judge_ver`) —— 在跑的到底是哪版;
2. **在役文件的 mtime + SHA256**(`certutil -hashfile <file> SHA256`) —— 磁盘上是不是新那份;
3. **当场只读复现** —— 拿**同一帧**离线跑同一版, 看能不能得到线上那个数。

- 三者对不上 ⇒ 大概率是**输入/场景/参数变了**, 不是代码没生效 —— 急着回滚会白折腾一次产线。
- 多会话/多子代理并行改同一份产线文件会**互相覆盖** ⇒ 上线前先 `production_sync.py pull` 之类的命令
  **从产线现版改起**, 别从仓库旧副本改。
- **版本号印在程序里**(`_JUDGE_VER` 常量)比看文件名可靠 —— 它随包走, 回读即刻可知。

## 铁律 ⑦: "观测在缓慢漂"先量时序、再问人, 别忙着加"锁"

- 漂移指纹: 多个观测量**同向缓慢变化**(画幅尺寸 1455×70 → 1411×68 · 判决带区间 · 计数 16→12)。
- **取证 = 只读时序采样**: 每 15s 读一次【设备真值 + 观测量 A/B/C】连读 8~10 次;
  **135s 真值冻结到 6 位小数(0.000mm) 且观测量全恒定 = 场景已稳**。这一步能把"设备在自走"与"人在动"分开。
- ⚠️ **最常见的漂源是「人」**(现场手动点动) ⇒ **先问用户**, 别归因成伺服下沉/程序 bug。
- ⚠️ **别承诺你手上没有的能力**: 先只读查清链路到底提供哪些"停"的手段 —— 实测本仓只有**规划停止**
  (语义明确写"不断电"), **没有下电/撤伺服/抱闸/模式切换** ⇒ 要物理固定就让现场动示教器,
  不要用"移动到某点"去冒充"停稳"。

## 铁律 ⑨: opt-in 字段"声明了但不生效" —— 找**被默认值无条件覆盖**的那一行

新增一个开关字段(`atomic`/`use_xxx`/`src=skill`)后, 现场看到的行为和没加字段**一模一样**:

- 典型形态: `if opt_in: target = 新口径算出(点位 + 偏置)` 紧接着 **无条件** `target = 默认来源`(点位库/旧公式)。
  新口径算了白算, 而日志可能**同时**打"已用新口径"和"退回默认" ⇒ 读日志的人以为生效了。
- 🔴 判据只能看**打印/落盘的值**, 不能看日志措辞: 目标里**带不带该字段声明的偏置/差异**。
  实测例: 声明 `atomic: SK03Descend` 的技能, 目标应 = 点位 + 4.0mm; 若等于点位本身(偏差 0.0mm) ⇒ 被覆盖了。
- 修法: 用 `_hit` 标志控制默认回落 (`if not _hit: target = 默认`), 警告分支放进 `else`, 成功分支不要再打"退回"。
- 验收两条同时要: ① 声明路径的目标差 == 该字段声明的偏置(逐位) ② **未声明的 N 条逐位不变**(基线逐条比对)。
  ⚠️ ②要把 opt-in 的那几条从"逐位一致"里**显式排除并单独验**, 否则基线判据会永远红; 排除数必须 == 声明数。
- 同一个病在常驻消费端还有第二种形态: **只在启动时解析一次** 配置/段/版本(gate/注册表/状态机段), 之后外部变了它不跟。
  判据 = 连采 3 拍看值/段是否随外部文件变; 修完后**重启消费端**才算生效(旧值锁在进程内存里)。
  旁证: 生产者的落盘文件帧龄在 0.x s 跳动, 而消费端记录里的段一直不变 ⇒ 就是这一条。

- 🔴 **高处不能再就地抬升**: 包络上限 (实测 z≤0.6802) 已贴近时, "先抬 50mm 再走"会被包络闸直接拦 ⇒
  顺序改成 **先垂直降 20~50mm 腾余量 → 再抬 / 再转移**。下发前自己算目标 z 是否越界 (当前 z ± 行程), 别等控制器兜。
- 🔴 **撤销/停机脚本超时不等于撤掉了**: 实测 `tools/ctl_revoke_stop.py` exit=124 却什么都没撤,
  日志照打"撤销看门人启动 · epoch=N armed=True"。判据只能回读 `/ctl/status` 的 `motion_armed == false`;
  仍为 true ⇒ 换 `tools/sdk_arm_auth.sh --revoke` 或站台页撤销按钮, **再回读一次**;
  撤不掉就明说"授权还在、FIFO 还能执行" —— 报"已停"是事故级的谎报。急停后同理: 先读 `estop/has_error/operation`,
  等现场说"恢复了"再动, 恢复后的位置重新采样存档 (最低位写 `zmax_data/ss_live/lowest_pose.json`)。

## 诊断法: 消融阶梯(定量分辨"阈值"还是"输入质量")

指标上不去(数不够/分不开/命中率低)时, 在**同一帧**上离线跑本体, 四档递进分开"放宽参数"与"换输入":

| 档 | 做法 | 实测例 |
|---|---|---|
| A | 现役口径 | 6 |
| B | **只**放宽阈值/分级参数 | **6 ← 一点没变** |
| C | 用正确输入(强制到真实目标带/区域) | 9~11 |
| D | C + 全面放宽 | **14 ← 天花板** |

- 判读: **B 不动 = 阈值不是瓶颈**; **D 的天花板 = 本份输入的物理可分辨上限**。
- 天花板 ≈ 预期值 ⇒ 去调阈值; 天花板 ≪ 预期值 ⇒ **别再调算法**, 去查衬度/照明/对焦/位姿 ——
  并把定量证据交上去(逐单元局部衬度 = 中心灰度 − 相邻谷灰度; 本轮左段 +14~+35(好)、中段 +2.5~+12.5(塌))。
- 🔴 **宁可少而准, 不要多而假** —— 把阈值放宽到误判/多认, 等于给现场看假结果, 比差几个更糟。
- 同类"输入质量"问题的一个硬指纹: **结果对某个旋钮不敏感**(如过曝量差一个数量级而计数恒定)
  ⇒ 瓶颈不在那个旋钮上, 别继续扫。

## 铁律 ⑧: 「已下发」≠ 到设备 —— 按**当前那条腿**核真动作证据, 并先算"看不看得出来"

执行器回「受理: 已下发」只说明**它自己受理了**。换过腿(ros ↔ 本机 sdk)之后, 判据跟着换, 拿老腿的判据会误判:

| 腿 | 真动作的硬证据 |
|---|---|
| ROS/ssh | 日志里那条自己的 `ROS: making request` + 设备真值变了 |
| **本机 SDK/容器** | **容器自己的日志**(如 `~/zmax_data/rokae_sdk/logs/global_logger_<日期>.log`): 出现 `Process posture trans:` + `Append cmd l#N` + `moveStart end` + `Notified l#N … finish:true` |

- ⚠️ **容器日志只出现"设置类"行**(`setMotionControlMode`/`setDefaultSpeed`/`moveReset`/`setDefaultConfOpt`)
  **而没有 `Append cmd`/`moveStart` ⇒ 运动根本没发出去** —— 命令在链路上丢了, 不是设备拒动。
  容器的日志时间戳可能是 UTC ⇒ **+8 才是现场墙钟**, 对齐时刻时先校正。
- ⚠️ **下发行的"目标"那栏是空的**(`已下发 <技能> ->  · Δ=(…)`) = 这一步**没有生成任何真实指令**,
  常见于"动作只有一种通道, 而那条通道没在跑"(见下条)。别被「受理: 已下发」骗过去。
- 🔴 **换腿只换最后一跳, 换不掉"这个动作在新腿上有实现吗"**: 实测把臂换成本机 SDK 腿后,
  该腿只认 `move-rel/move-abs/stop/reset/ping` —— **夹爪类动作仍写死在 ROS 服务上**, 于是
  "臂能动、夹爪一定不动": 现场点多少次都不动, 日志只跟一句 `ROS: waiting for service to become available...`
  或 `rcl node's context is invalid`。⇒ 换腿/改通道后**逐动作清单核实现**: 每种动作在新腿上的入口在哪;
  缺失的如实说"这条没通道", 别用重试掩盖。
  诊断: `ros2 service list | grep -i <关键字>` 为 0 = 没有通道; 服务名对不上时用 `ros2 service type <名>` 逐个核
  (实测调用方写的名字与驱动服务表里的名字**可能不是一个**)。厂家方案包里的 launch 才是这些服务的来源
  (Orin 上 `resource/config/<项目>/start.launch.yaml`) ⇒ 包没起就没有服务。
- 🔴 **先算"看得见吗"再下结论**: 下发行的 `位移 Xmm · speed=Ymm/s` ⇒ 秒数 = X/Y。
  实测 `1mm @ 1mm/s` 的下降 = 1 秒挪 1 毫米, 肉眼就是不动 ⇒ **那不是故障, 是步长/速度太小**。
  现场说"怎么都不动"时, 先把它算出来给他看, 再谈别的。
- 🔴 **零位移的判据**: 设备侧记录里 **残差 ≈ 指令全量位移 ⇒ 一步没动**; 必须再配 `rc` / 报警变化 /
  报警码(如奇异 50102 · 姿态变化超阈值 50113)才能定性"是设备拒了"而不是"还在排队"。
- 🔴 **别用姿态差预测"必被拒"**: 同一对点位在不同路径上过与不过都可能(实测 横移 196mm 叠姿态差 27.5° 被拒,
  而同机同期另一条**姿态差 45° 的横移 263mm 一次到位 PASS**) ⇒ 拒发取决于该路径的**奇异区/可达性**, 不只取决于角度。
  姿态差只能当**风险提示**; 据此说"这点必被拒、别点了"会把用户挡在其实走得通的路外。要定性: ①记录里的 rc/残差/报警码,
  或 ②先发**最小步**探路(单轴 ≤10mm / 姿态 ≤5°)看放不放行。
- 🔴 **设备侧前置状态(示教/手动/未上电)是独立一层, 报错原文可直读**: `⛔ ABORT 前置条件不满足:
  机器人不空闲 (OperationState.drag)` / `不是自动模式 (OperateMode.manual)` ⇒ 与授权、快层/慢层、包络、
  服务名**全都无关**(那些都过了才会走到最后一跳)。判据: 复读设备真值里的 `operationState` / `operateMode`。
  ⚠️ **别把"没接口"当成"切不了"**: 下"只能现场示教器操作"的结论前必须写明**哪条通道** —— 实测
  直连 SDK 通道一直有 `setOperateMode` / `enableDrag` / `disableDrag`(ROS service 路径没暴露而已),
  能自己切并读回: 退拖动 + 切自动各一条子命令, 回读 `idle` + `automatic` + 落证据才算切成功;
  仍报 drag 才是被示教器/末端按钮把持。**重录点位/示教完成后必做这一步** ——
  现场"重新标定了怎么还是不动"十有八九就是留在 drag/manual。
- ✅ **大姿态变化在最后一跳自动分步, 别只靠调用方拆段**: 下发腿对"姿态差 > 阈值(实测 15°)"的整位姿动作,
  自动 slerp 拆成若干 ≤5° 的**原地**转身段(位置取起转点、逐段核真值、任一段不到位即**中止且不续发平移**),
  转身完再发原平移(此时姿态差 ≤5° ⇒ 不被设备侧奇异/姿态阈值拒)。日志指纹:
  `🔀 姿态差 N° > 15° ⇒ 拆成 k 段原地转身(每段 ≤5°, 位置不动), 转身完再平移` →
  每段 `… 原地转身 i/k · 残差 0.0mm` → `🔀 转身完成 ⇒ 续发平移(姿态差已降到 M°)`。
  把"单段姿态幅度上限"变成**收口层的保证**, 调用方不必每个点对重算; 阈值/开关用环境变量可退可调。
  ⚠️ **分步转身不是万能的**: 实测 95.3° 的姿态差拆 19 段, 前 11 段到位、**第 12 段依旧被拒**
  (`rc=6 · CHECK · 残差=整段 662mm · 真值一点没动 · 报警变化=True · 疑似 50102 奇异点`)。
  路径穿腕部奇异 (b→-90°) 时每段都在奇异区, 拆得再细也过不去 ⇒ 见此签名**立即中止、绝不重发**。
  兜底 = 关节空间 `moveJ`: 执行器加 `ZMAX_L2_FORCE_J=1` + `ZMAX_MOVEJ_RETRY=1`, 用 `tools/l2_daemon_up.sh` 拉起
  (别手写 nohup, 环境变量会丢)。代价是路径不可控但能到; 实测 `125mm @ speed=32` = 43.9s、残差 0.0mm。
  🔴 **别用"已自动分步"当配置成功的证据** —— 分步只是把拒发点往后推; 判据仍是真值逐位到位。
  ⚠️ **本仓消费者 = `zmax-sdk-arm-agent` 容器**: FIFO 有写无读时 `❌ SDK 腿失败: rc=-1 · SDK 代理 FIFO 没有读者`,
  这时 8793 已授权、8798 在听**都不算**; `bash tools/start_sdk_arm.sh` 起容器, 再用 5mm 微动核 tcp 差值正好 +5.000mm。
  ⚠️ 改最后一跳的代码**必须重启消费端**才生效; 离线自证(零运动) = `scripts/verify_rot_split.py`
  (真实点对 + 90/150/179° 极端: 每段 ≤5° · 留给平移段的残差 ≤5° · 四元数转 rpy 无 NaN)。

## 回报纪律

- 拿数字说话: 名义值 vs 实测值、改动前 vs 改动后、原件 vs 现值, 一行一条。
- 现场说"不对"时, 先去找**证据链**(审计/真值/日志时间线), 不要先解释; 证据出来了再给结论。
- 任何"已验证"结论都要写清是**在哪一层验的** —— 中间层的日志漂亮不代表末端动了。
