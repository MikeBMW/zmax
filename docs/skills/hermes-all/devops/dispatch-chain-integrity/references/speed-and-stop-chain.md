# 逐层限速链 / 停止链 —— 实测口径与逐级上限

## 1. 一条命令经过几层限速

```
界面/脚本「速度」(相对量)
  → 常驻执行器:  sp = min(speed, 该技能.speed_max)              # 配置热加载, 逐技能
  → 本地库:      sp_mm = max(FLOOR, min(HARD_CAP, K * units))   # K≈0.0935, FLOOR≈1.0
  → 代理进程:    speed = min(speed, 自己的 HARD_CAP)
  → SDK / 驱动 → 控制器
```

- 三处上限**各自独立**, 谁最小谁生效。典型: 技能上限 200~1000, 库硬上限与代理上限 30~60。
- 库的下限 (`max(FLOOR, …)`) 会把**小档位往上抬**(例如填 8 → 算 0.75 → 被抬成 1.0)。
- 实测结论: **实际速度 ≈ `min(库硬上限, K×units)/10`** —— 标称的约 1/10(多点独立测量一致)。
  ⇒ **两个不同高档位可以落在同一个实际速度上**(都被硬上限封顶)。
- 提速 = **逐级同时抬**; 抬完在**末端**量一次再报。
- 🔴 **还有一层按"按钮身份"的夹取, 最容易漏**: 手动点击回点位(命令带 `manual_point`)会被执行器额外压到
  `MANUAL_SPEED_UNITS`(实测 200 units ≡ 名义 18.7mm/s), 日志 `🐢 手动回点位限速: 535 → 200 档` ——
  这是**故意**留的保护(手动回已记的点要慢一些), 不是 bug, 但也必须在报告里点名。
  ⇒ 现场报"我点 50 怎么不到 50"时, **按顺序报五层**: 页面夹取 → 库/代理硬上限 → 技能 `speed_max`
  → 手动回点位限速 → 设备在线倍率(§1b)。只报其中一层就会让下一轮实测打脸。

## 1b. 那个固定倍数是**谁**给的 —— 设备侧在线倍率(这才是根治手段)

- 逐层抬完上限后剩下的固定倍数, 多半来自**设备(控制器/驱动器)自带的在线速度倍率**, 不是链路里的任何一层。
- 接口(xCoreSDK, 珞石): `Robot.adjustSpeedOnline(scale, ec)` —— 文档口径「动态调整机器人运动速率,
  **非实时模式(NrtCommandMode)时生效**; scale=1 ⇒ 以路径原本速度运动」, 范围 **[0.01, 1]**。
  凡下发走 Nrt/非实时模式的动作这个倍率都生效 ⇒ `scale=1.0` 时 **名义 = 实际**。
- 🔴 **不要用"把下发数字乘 10"来补偿**: 名义值会被推到 1e4 mm/s 量级; 一旦倍率被谁(示教器/产线程序/重启)
  改回 1.0, 同一条指令就以 ~10 m/s 执行 —— 那是埋在链路里的雷。**把倍率归 1**, 名义值留在合理区间, 两个方向都安全。
- 🔴 **没有 getter**: SDK 不提供回读当前倍率的接口 ⇒ 改完**必须实测**(让现场点一次小距离小速度,
  用真值算分段速率, 看记录里的 `📏 整段平均速率` 行), 没实测不要对现场说"已生效"。
- ⚠️ 倍率是**设备级**的: 会同时影响其它走同一控制器的通道(如产线 ROS 那条, 它另有自己的
  `rt_speed_ratio` 限速) ⇒ 改之前确认现场没有别的动作在跑。
- 回退/复位: 同一条命令换参数(如 0.1)即回退; 控制器重启/下电后倍率可能回落旧值(表现为"又变慢了") ⇒ 重跑一次;
  要粘性就让下发端/腿启动时设一次。
- ⚠️ 倍率归 1.0 后界面档位**就是** mm/s 真值 ⇒ 最高档可能就是 1 m/s: 先小档试, 别一上来点最高档。
- ✅ **实测确认(可作基线, 换工位要重测)**: 同一名义 18.7mm/s —— 倍率归 1 前 **1.83mm/s(10%)**、
  归 1 后 **15.22mm/s(81%)**; 名义 10 ⇒ **9.44mm/s(94%)** ⇒ 界面数字就是实际 mm/s,
  剩下 6~19% 是加减速/收尾。写这种结论必须用**同一批点位、同一速度**的前后两次实测对照,
  别把"感觉快了"当证据。
- 改完口径**界面文案/技能记录要同步改**(别留着"实得≈10%、要实得 50 就点 500"的旧话),
  但**等实测确认之后**再改 —— 没验证就改文案等于给现场写错口径。

## 2. 标定表(某工位实测样例, 线性, 到封顶为止)

| 设定 units | 库下发 mm/s | 实测 mm/s |
|---|---|---|
| 8 | 1.0(被下限抬) | 0.10 |
| 19 | 1.8 | 1.90 |
| 30 | 2.8 | 3.00 |
| 50 | 4.7 | 4.97 |
| 100 | 9.4 | 9.99 |
| ≥642 | 60(封顶) | 6.0 |

数值随工位/配置变, 但**形状**不变: 线性段 + 硬上限封顶 + 下限抬高。复制这张表时**务必重测**。

## 3. 量它, 别信它

- 末端真值连采(`latest.json` 之类)每 2s 读一轴, 算 `Δ/Δt` —— **整段测**, 不是首尾两点(起步/收尾有加减速)。
- 执行器/驱动的到位行常自带实测: `… 残差 […] mm · 18.3s · speed=30.0mm/s`。
- 界面提示里那句"某档位 ≈ 多少 mm/s"往往是**标称**, 实测能差 30 倍以上 ⇒ 别抄进新界面, 要写就写实测换算。

## 4. 时间上限必须跟着封顶走

```python
_v      = min(speed, HARD_CAP / K)     # ① 先过库的封顶
_mm_eff = max(MEASURED_K * _v, 0.35)   # ② 再按实测速率估 mm/s
return max(base, 15.0 + lin_mm / _mm_eff * 1.6)
```

- 少了 ① 就在高档时高估实际速度(实测高估 ~56%) ⇒ 等待偏短 ⇒ **动作没走完判"未到位"并中止整条计划**;
  已下发的指令不会撤回 ⇒ 现场看到"技能只走了一半"。
- 同口径要一起改: 执行器的阶段超时 / 库的 `_run_abs` 与分片等待 / 代理的预算 / 上层脚本自己的等待。

## 5. 改哪一层要重启什么

| 改的东西 | 生效方式 |
|---|---|
| 注册表/配置文件(技能定义、per-item 上限) | **热加载**(每条指令前重读), 不用重启 |
| 常驻执行器自身代码 | 重启执行器 |
| 执行器进程内 import 的本地库(腿/桥) | 重启执行器 |
| 代理(容器内只读挂载) | 重启容器 |
| 网页(静态 HTML) | 热读, 刷新页面即可 |
| 推流/网关服务的白名单(进程内常量) | 重启该服务 |

## 6. 「已下发但不执行」—— 先排队, 别先怀疑设备

执行器是**顺序**消费: 某阶段失败后它仍会**等满该阶段的到位超时**(它只按真值判到位, 零位移那条必须等满才放弃),
这期间**后写进 FIFO 的命令一行都不会被读** ⇒ 现场看到"已下发却没反应"。

判据(全部只读, 顺序走):
1. 审计日志有 `skill=… speed_mm_s=… dry=False` + 响应"已收到" ⇒ 命令**已进 FIFO**(没丢);
2. `tail` 执行器日志看**最后一行的时刻**: 若它是几分钟前、内容是某阶段失败, 而现场那条命令在日志里
   **一行都没有** ⇒ 执行器**还没读**它(在队列里排着)。队列深度 = 阻塞之后审计日志里的条数(FIFO 长度不可读);
3. 腿的记录里 **残差 ≈ 指令全量位移 ⇒ 一步没动**(零位移), 配 `rc`/报警变化/报警码才能定性是谁拒的。

纪律:
- 排队**会自己走完**, 但每条要各等满一次超时 ⇒ 阻塞期间**别重复点**(每点一次多堵一条);
- 现场问"怎么不动了"时先给"队列第几位 / 还要等多久"这个**可验证的现状**, 再谈根因; **不要**把排队说成"命令丢了";
- 清队列 = 读空 FIFO(等于动用户的命令通道) ⇒ 必须用户点头, 不擅自做。
- ⚠️ **重启消费端 = 队列里的旧命令会被放出来真跑**: 队列就是 FIFO 里的文本行, 新实例照样逐行读 ⇒
  重启前先确认无在途计划(日志尾时刻 + 状态端点) + 读空 FIFO 并**打印清掉的条数**;
  重启后**立刻核日志无新的"已下发"行**。"清空时读到 0 条"不等于队列真的空
  (消费端可能已把命令读进自己的缓冲) ⇒ 只有"重启后无新下发"才算证据, 清过什么要对用户说清。

## 7. 停止链

- 界面/脚本 stop → FIFO → 执行器 → 库 → 代理 FIFO → SDK。
- ⚠️ **代理 FIFO 顺序处理**: 卡在某次动作的盯真值循环里时, 后写的 `stop` 要等那段循环结束才被读到
  (实测 1~2 分钟)。要立刻停 = 掐链路(重启代理容器/杀下发方), 或在**下一段下发之前**停掉上游计划。
- ⚠️ 全停脚本(听到"要碰撞"时那条)会**连带杀掉常驻执行器** ⇒ 之后必须重启它, 否则界面每个按钮都报
  `[Errno 6] No such device or address`。
- 判"消费者在听": `open(fifo, os.O_WRONLY | os.O_NONBLOCK)` 能否打开 + 进程在 + 启动横幅(路径 + 项数)。
- 重启执行器本身有 **2~4s 空窗**, 期间点击必报同样的 Errno 6 ⇒ 重启后**先自检可写, 再让现场点**。
