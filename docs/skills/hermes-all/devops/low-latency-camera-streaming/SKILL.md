# 实时视频流交付（压缩 · 低延迟 · 带取证）

## When to Use
- 用户说「把实时视频流发过来」「我要看现场画面」「视频流要压缩」「提高实时性」。
- 旁路调试时要目检真机/产线画面；多路相机（本机 USB + 远端 ROS 而来）要并排看。
- 已有链路在"出图"但用户觉得慢/卡 —— 要定位延迟到底阻塞点一跳。

## 铁律 1: 先量天花板，再动手写代码
三个数按序量完（全部只读、零副作用），再决定压什么：
1. **相机原生帧率** `ros2 topic hz <topic>` —— 常常远低于你以为的。实测产线相机只 **1.92 Hz**（0.52s/帧），
   而 `camera-frame-forensics` 里那套 tap "1Hz 解码"的设计再叠一层 → 最终只剩 **0.5 fps**。
2. **单帧原始体积** `ros2 topic bw <topic>` —— 640×480×3 = 921KB/帧；2448×2048 ≈ 15MB/帧。
3. **源侧落盘/转发频率** —— `stat -c %Y <file>` 观 8 秒变化次数（别读日志行数）。
4. **必须在真实负载下量** —— 业务在跑（机器人运动 / 训练 / 产线节拍）时主机 CPU 是共享的，
   空闲量到的数是**天花板**、不是交付数。实测同一路相机：静止 16.0 fps，机器人运动时掉到 **8.0 fps**。
   交付一律引用**负载下**那个数并注明它是下限；拿空闲值当结论就是夸大。

**压缩提不了相机帧率上限。** 帧率低是采集侧决策，别承诺「压缩后就流畅了」；
先把这三个数摆给用户，讲清延迟瓶颈在**相机**还是在**链路**。

### 🔴 但「帧率上不去」三层别混：设备能力 / 实现（节点） / 传输
不要一到慢就说"设备上限、救不了"。按这三层分，**每层都有独立的取证方式**：
| 层 | 怎么确认 | 能不能修 |
|---|---|---|
| 设备能力 | 厂商 SDK 报的**模式表**（`pyrealsense2` 等，见 references §2.5） | 不能，但常常不是这里 |
| 实现（厂商节点） | 模式表明明有 30/90，实测只有 2 ⇒ **实现问题** | **能**：直驱替掉它 |
| 传输（发布一步） | **分层卸载测速**（下） | 能：旁路小消息 / 根因是 socket 缓冲需 root |

**分层卸载测速是定位瓶颈最快的一招**：拆成 "只读相机 → +对齐 → +拷贝 → +发布"，每层数 8 秒帧——
实测 30.0 / 30.0 / 30.0 / **4.6** ⇒ 相机、对齐、拷贝全免费，**发布一步就吃掉 6.5 倍**。
得到这个结论之前，不要花时间优化编码/拷贝/对齐。完整配方见
`references/frame-rate-ceiling-diagnosis.md` §3.7。

### 🔴 图像「一发布就掉速」: 先分「Python 打包」还是「传输」
最后一档必须发到**0 订阅者的测试话题**: 实测 只取帧 26.5fps → +深度(0.6MB) 7.5fps → +彩色(0.9MB) **3.0fps**,
而把网络订阅端整个停掉帧率纹丝不动(3.07→3.15) ⇒ 病在 rclpy 逐字节打包(0.9MB≈170ms), 不是网络/带宽/UDP 缓冲。
定式 = 同一进程持相机(hub): 图像走**小消息**全速出口, ROS 只保低频给生产 RELIABLE 订阅方。
小消息有两条路, 都实测过, 按下游要不要 ROS2 选:

| 出口 | 实测(Orin→Intel 同一 /24) | 适用 |
|---|---|---|
| **ROS2 CompressedImage**(JPEG 41KB / 16bit PNG 159KB), BEST_EFFORT | 彩色 **9.09Hz** · 深度 **8.43Hz**, 帧龄 0.07/0.01s | 下游本来就是 ROS2 节点(采集/推理)→ **优先这条, 别为了 3Hz 就弃用 ROS2** |
| HTTP `/frame.jpg` + `/depth.png` | 取一轮 **2.6ms**(上限 378fps), 帧龄 0.02s | 下游是网页/脚本/跨机取图; 或要 raw 级新鲜度 |

⇒ **一发布就掉速时, 先换小消息, 再谈换协议**: 大消息 raw 走哪条协议都慢(病在打包), 小消息走 DDS 和走 HTTP 都够用。
判别步骤、实测表与实现要点见 `references/frame-rate-ceiling-diagnosis.md` §3.8。
- 订阅端 QoS 要**显式 BEST_EFFORT** 才能和压缩发布端匹配(默认 RELIABLE 订阅会报
  `incompatible QoS. No messages will be received` 且一条都收不到)。
- 压缩图像**复用采集线程已编码好的字节**, 不要为了发 compressed 再编码一次(白烧 CPU, 还可能把帧率压回去)。
- 订阅端不要每帧 `cv2.imdecode` 只为量亮度: 每 20 帧解一次就够(比 41KB 传输贵一个量级的从来是解码, 不是传输)。

### 用户嫌「卡/不实时」时：先分清「配置节流」还是「真设备上限」
实测帧率**远低于话题里配置的目标值**（如 `color_fps: 15` 而实测 1.83Hz）时，别急着说"设备就是慢"，
按序证伪下面每一条 —— **每条都能被一条只读命令排除**，全排除完才能下"设备上限"的结论：

| 假设 | 一条命令证伪 | 实测结论 |
|---|---|---|
| 带宽/线缆 | `lsusb -t`（看 `5000M` = USB3 SuperSpeed） | USB 3.2/5000M ⇒ 与带宽无关 |
| 参数配置 | `ros2 param get <node> <p>` | 配置本来就是 15fps，不是配置问题 |
| 运行时能改 | `ros2 param set <node> <p> <v>` 后立刻 `topic hz` | **改了 6 项全无变化** ⇒ 参数只在启动时读 |
| 算力不够 | `ps -o pcpu` 看该节点 | 仅 38% ⇒ 不是 CPU 瓶颈 |
| 能另开一路高速流 | `fuser /dev/videoN` | 全部 videoN 被同一 PID 独占 ⇒ 无法旁路 |

**两条硬规矩（都是从现场换来的）：**
1. **动生产参数前先记原值，实验完立刻逐项还原并回读确认。** 在役相机节点的参数属于产线配置，
   试完不还原 = 留下无人知道的配置漂移。回读全部 6 项逐条打印才算还原完成。
2. **参数只在启动时生效 ⇒ 唯一修法是把该节点重启**，而重启生产节点必须先确认它**是否会被自动拉起**
   （launch 里 `respawn=True`？还是由生成的 launch 动态描述？）。没确认 `respawn` 前**不要 kill** ——
   杀掉的节点可能不会回来，产线直接丢感知。缺证据就报"需要现场确认"，不要赌。

### 先问一句「这些参数针对的传感器存在吗」—— 能一次终结整条证伪链
厂商节点日志里出现 `... sensor not found, skip ... option config` 时，**该类参数永远进不去**，再改多少次都是零效果。
所以**认型号是第一步**：`lsusb | grep -iE "intel|realsense|<厂商>"`。
实测：`8086:0b5b Intel RealSense D405` —— 405 是**立体深度相机，本身没有 RGB 传感器**，
因此 `color_fps` / 曝光 / 分辨率这些**彩色参数被全部跳过**，节点跑内部回退路径钉在 1.7~1.9Hz。
⇒ **配置层 / 链路层 / 型号层要分开报**：改参数解决不了"传感器不存在"，这一类只能报厂商或换相机；
⇒ 永远不要拿"改了参数没反应"当成"设备上限已证"——先看日志里有没有 `skip` / `not found` 告警。

### 「慢」和「死了」是两回事 —— 用户说"一卡一卡"先排除挂死
进程在 + CPU 高 **不等于** 在发帧。判活三条一起看：
```bash
ros2 node list | grep <node>                    # 节点还在 ROS 图里吗(不在 = 已从图里退出)
ros2 topic info <topic> -v | grep -i publisher  # "Publisher count: 0" = 没人在发
stat -c %Y <tap落盘文件>                         # 帧计数/时间戳是否还在推进
```
实测形态：进程活着烧 40%CPU、但**不在 `node list`、`Publisher count: 0`、帧计数冻结** ⇒ 节点已挂死（不是慢）。
后果：录像"后半段整段静止"、看板帧龄几百秒 ⇒ **交付前用 `/stats` 的 `age_s` 判活**，别只看"服务在线"。

**但 `Publisher count` 不能单独当"活得"证据 —— 它会把尸体也报成活的。**
厂商节点若是单独 `ros2 run` 起（**不在 launch 里 ⇒ 没有 `respawn`，死了没人拉起**），
实测 `realsense_source` 已死 6.9 小时，而 `ros2 topic info -v` **仍显示 `Publisher count: 1`** ——
那是 DDS **发现缓存里的旧端点**。⇒ 第 0 条判据永远是
`ps -eo pid,args | grep <节点名>`（进程不在 = 已死，别的都不算）。
同理自建桥的 `/st` 也会骗人：实测 `{n:3983, age_s:25040, err:""}` —— 计数有值、`err` 为空，
**只有 `age_s` 暴露了 6.9 小时零帧** ⇒ 判活只看 `age_s`，`n` 和 `err` 都会骗人。

**重启厂商节点必须带原环境**（capture 自仍活着时的 `/proc/<pid>/environ`，
或 launcher 里 `source /opt/ros/humble/setup.bash` + 厂商 workspace 的 `install/setup.bash`），
否则报 `ModuleNotFoundError: No module named 'rclpy'`；厂商 launch 的参数文件常还在 `/tmp/launch_params_*`，**照抄它**。
脚本里**别用 `set -u`** —— ROS 的 `setup.bash` 有未绑定变量（实测 `AMENT_TRACE_SETUP_FILES`），会直接中止。

### 🔴 另一种「活着但不响应」: fd 表被继承满 ⇒ 页面永远停在上一次成功的旧图
症状从用户嘴里出来是**"页面不更新"**: 「叠加页怎么还是历史框」「工位总览也没有新东西」。
此时**先怀疑服务僵死, 不要怀疑自己的规格没生效**（规格是每帧重读的, 写完立刻就生效）。
- 三条判据一起看（实测形态: 打开数 **1024 / 上限 1024**）:
  `ls /proc/<pid>/fd | wc -l` · `awk '/Max open files/{print $4}' /proc/<pid>/limits` ·
  带超时的 `curl -m 8 /stats`。表满时 curl 返回码是 **000(超时)**, 而 `ss -ltnp` 仍显示在听、`pgrep` 仍显示活着、
  CPU 也正常 —— 只有 fd 数对上上限才看得出来。
- **分清"自己漏的"还是"继承来的"**: 数日志里该错误的**行号** vs **启动横幅**。第一次报错若紧跟横幅
  （实测第 15 行, 之后 7 小时只重复它 4761 次）⇒ 进程**一出生 fd 表就是满的** = 从父进程**继承**的, 不是自己漏的。
- 冤枉库之前先做**受控实验**: 循环制造同一种失败（连接被拒 / 黑洞地址超时）各 200 次, 每轮读 `/proc/self/fd`
  —— 实测 `urlopen` 在被拒与超时路径上 **0 增长**。没有这类实验就别写"某库会漏 fd"当根因。
- **根治写在拉起脚本里（不是重启了事）= 抬上限 + 清掉继承的 fd, 再 exec**:
```bash
ulimit -n 65535 2>/dev/null || true
nohup "$PY" -c 'import os,sys,resource
try:
  _s,_h=resource.getrlimit(resource.RLIMIT_NOFILE); resource.setrlimit(resource.RLIMIT_NOFILE,(_h,_h))
except Exception: pass
os.closerange(3,65536)
os.execv(sys.argv[1], sys.argv[1:])' "$PY" tools/<服务>.py <原参数...> &
```
  重启后**回读** `/proc/<新pid>/limits` 确认生效（实测 65535）。`setrlimit` **超不过父进程的硬上限** ⇒
  只能"取父上限": 父的硬上限低时就拿不到 65535, 此时**如实报"取到的是父上限"**, 别把脚本里的数字当实测值。
- **守护的探活方式决定它救不救得了**: 判据若是"端口能连 / 进程在跑" ⇒ 对僵死**完全失明**（TCP 握手在内核层照样完成,
  连 fd 表满的进程都能通过探活）⇒ 探活必须是**带超时的 HTTP GET**（`urlopen(.../stats, timeout=…)`）;
  并且**确认守护真的被调度** —— 实测守护脚本存在、逻辑也对, 但**从来没进过 crontab**, 于是僵死 7 小时无人自愈。

### 用户问「这个帧率够么」——用「每帧盲走距离」回答，别只报数字
```
每帧盲走 = 运动速度 ÷ 帧率
```
把它和**任务精度要求**并列最有说服力：实测 10mm/s ÷ 1.86fps = **每帧盲走 5.4mm**，而精细插拔要控到 ~0.1mm
⇒ **差 16 倍**；且"插入"这类接触事件只有 50~200ms，帧间隔必须 ≤33ms 才能不漏。
需求档：遥操作/视觉伺服 ≥15(推荐 30) · **精细插拔 ≥30(推荐 60)** · 模仿学习采集 ≥10(推荐 30) · 纯监控 5~15。
汇报时把"我这边能做的"与"必须厂商做的"分开列，别把两者混成一句"实时性提高了"。

完整命令链与解读（含型号/传感器核对、挂死判据、授权后重启配方、帧率够不够的算法）见 `references/frame-rate-ceiling-diagnosis.md`。

## 铁律 2: 压缩要压在最贵的那一跳
- 只压**通向用户/显示**的那条链路（如工位机 → 手机），省的是最贵的一段。
- 局域网内 raw ROS 图像 1.77MB/s ≈ 千兆链路 **1.4%** ⇒ **不是**带宽瓶颈，别为它大动干戈。
- 真要省 Orin→工位机的线缆流量，压缩必须发生在**源头**（Orin 侧 republish / 相机配置），
  那是产线在役感知链 ⇒ **动之前必须用户点头**，别自己改。

实测压缩梯（640×480 BGR，raw 921KB）：

| 编码 | 体积 | 相对 raw |
|---|---|---|
| PNG（现役 tap 的 zlib） | 420 KB | 2.2× |
| JPEG q80 | 37.0 KB | 24.9× |
| JPEG q70（推荐） | **29.1 KB** | **30.9×** |
| JPEG q60 | 24.5 KB | 37.6× |

⇒ **要推流就写 JPEG，不要写 PNG**：体积小一个量级且编码快得多。看到链路在落 PNG 就是现成的优化点。

## 铁律 3: 服务端只推最新帧（否则延迟随队列增长）
MJPEG 服务端必须**丢过期帧**、不排队积压：共享"最新帧"槽 + `seq` 判重，客户端只拿最新。
响应头带 `X-Frame-Age-S`，页面上把**帧龄**数字显示出来。

**画面必须自标状态**（相机名 / 采集时间 / 帧龄 / 分辨率 / 帧率）：用户会把画面当结果，
没有帧龄就分不清"实时"还是"几十秒前的旧帧"。这与「实时数据须标拍照时间·帧龄」同源。

### 每条流必须有「收摊」条件 —— 客户端断开会留下空转子进程（把整机拖卡）
写 MJPEG 透传/推流循环时三件套缺一不可:
1. **硬上限时长**(如 300s): 到点 `break`, 让页面自己重连; 不设就是永久连接。
2. **每块 `flush()`**: 不 flush 时 `wfile.write` 在 socket 缓冲写满前**不报错**,
   断链要拖到缓冲满才暴露成 BrokenPipe ⇒ 中间那段全是白烧。
3. **`finally: self.close_connection = True`**: 保证 handler 返回时真的关掉连接。
取证(出现「整机变慢」时先跑这两条):
```bash
ss -tan | grep -E ":<端口>.*CLOSE-WAIT"        # 有行 = 服务端还没收摊
ps -eo pid,ppid,pcpu,etime,args --no-headers | awk '$2==<服务pid>'   # 对上的子进程: CPU 高 + etime 很长
```
- 实测形态: 两个断流子进程各 **38% CPU**、空转 **7 分钟**; fork 模型下每条还各占一个 `max_children` 名额 ⇒
  名额满时**新连接被拒/排队**, 表象是「打开页面白屏好久」; 整机 load 冲到 14(8 核)而 CPU 还空闲 70%。
- 验收: 关掉客户端后 3s 内 `CLOSE-WAIT` 归零 + 子进程数回到 1; 只看「端口还在听」不算。

## 铁律 3b: 客户端取帧泵自己就是一道硬顶 —— 先量节拍, 别先怪相机/带宽
服务端 `/stats` 报的 fps 是**源**的帧率, **不是用户眼睛看到的帧率**; 浏览器端的轮询节拍常低一个量级。
- 量法(**在页面里跑**, 不是读 `/stats`):
  `performance.getEntriesByType('resource').filter(e=>e.name.includes('/snap/'))` → 条数 n 与首末 `startTime`
  得 `fps=(n-1)/span`, 同时看单条 `duration`。
- 判据: **单帧只要 3~9ms 而 fps 只有个位数 ⇒ 病在节拍, 不在相机/带宽/编码**
  (实测 `period=150ms` 死钉 6.67fps; 改 60ms 后同机 16.67fps, 单帧仍是毫秒级)。
- ⚠️ **提泵周期前先看服务端是不是 fork-per-connection**: 每请求 fork 一个进程的服务(本仓 AR 台就是 `ForkingMixIn`),
  16.7 req/s = **16.7 次 fork/s**, 会把**打开新页面**的 HTML 请求挤到后面(表象「点开白屏、好久才出来」),
  并给整机加 load。单帧 3ms **不等于** 可以压到 60ms —— 那是客户端视角, 服务端和整机的账要单独算。
  定式: 先 `ss -tan | grep <端口> | grep -c CLOSE-WAIT` + `ps --ppid <服务pid>` 子进程数, 再定节拍;
  现役口径 **period=100ms (10fps)**, 首帧强制走便宜的单帧快照。
- 🔴 **绝不用 `document.hidden` 做减速闸**: 内嵌 WebView 常把窗口判成 hidden, 一旦按可见性降到 1s 一帧,
  用户看到的就是「没有以前的网页好使」, 而且刷新也救不回来(新页面照样 hidden)。`visibilitychange`
  只用于「到可见时立刻补一帧」, 不是用来降频。省压力只靠 `period` 本身和看门狗 —— **不拿流畅度换 CPU**。
- 页面打开本身另算一项: `performance.getEntriesByType('navigation')` 的 DCL/load(实测 18/19ms)
  ⇒ "打开慢"常是伪问题, 一条数字就排除, 别为它改服务端。
- 顺序固定: 打开耗时 → 单帧 HTTP 耗时 → 泵周期 → 才是源帧率。前两项都很便宜, 常常一量就把锅洗清。

### 🔴 取帧泵的 `busy` 标志会被「永远 pending 的那一拍」锁死 ⇒ 画面冻住, 而面板数字照常在刷
泵的互斥常写成 `if(busy) return; busy=true; img.onload=…busy=false`。服务重启/断链时那一拍的
`<img>` 或 `fetch` 可能**既不 onload 也不 onerror**（连接被 reset、请求悬挂）⇒ `busy` 永不复位,
之后每个 tick 都第一行 return：**画面停在最后一帧**，同一页面的数据轮询却照常跑。
用户嘴里是「卡死了 / 不动了 / 还是死了？」——不是相机、不是后端。

- **一眼定性（服务端日志）**：只剩 `/api/*` 之类的轮询，**一条 `/snap` 或 `/api/module3d` 都没有** ⇒ 泵死。
  反过来若取帧请求在刷、只是帧少，那才去看帧率/带宽/编码。
- **修法 = 泵自带的看门狗，而不是只在回调里复位**：
  `if(FPUMP.busy && performance.now()-(FPUMP._bt||0) < 2500) return; FPUMP.busy=true; FPUMP._bt=performance.now();`
  超时那一拍直接放弃（屏幕保持上一帧），下一拍重新开始。
- **验证可脚本化**（不用等人看）：离屏 `runJavaScript` 注入 `FPUMP.busy=true;FPUMP._bt=performance.now()-5000`，
  再调 `pumpTick()`，**2.5s 内 `FPUMP.ok` 必须增长且 `busy` 归 false**（实测 0→17 帧）。
- **重启在役服务前先把看门狗放上去**：重启一次就冻一屏，而用户会把它报成「服务坏了」。

### 「图 + 标注」一次取回的接口必须能退化成「只出图」
`/api/xxx?img=1` 这类把帧和框一起返回的端点, 标注后端没结果时**必须退回单帧快照**, 不许直接 return:
- 反例形态: 检测线程还没出结果 ⇒ 每 tick 拿 `ok:false` 就 return ⇒ **页面永远黑**, 而 `/snap/<cam>.jpg`
  明明 200; 一屏 30+ 次请求全 `ok:false`、画布 mean=0 ⇒ 现场看着像"相机/链路坏了", 实际是渲染分支吞了整幅图。
- 修法: 失败即降级到纯快照(用一次性标志如 `forceSnap`, 别让降级自己无限递归回标注分支),
  并在画面上如实标「取帧失败×N · 显示上一帧」。
- 标注后端自己的节拍也算进上限: `period=0.15s` 的检测线程 ⇒ 该模式下显示最多 6.7Hz, 图像和框都被它压住;
  要么提频, 要么把"图"与"框"拆成两条路(图走快照、框走最新结果并标 `result_age_s`)。

### 「点一下要马上打开」—— 把"打开"拆成四跳量, 别笼统说慢
用户说"打开还是慢/点了半天没反应"时, 打开耗时和画面帧率是**两条独立的链**, 分开量(全是只读):
| 跳 | 怎么量 | 实测形态 |
|---|---|---|
| ① 宿主侧冷导入 | `python -X importtime -c "import <mod>"` 看末行累计 | 0.21s ⇒ 常常不是它, 别先怀疑 import |
| ② 服务探测 | 对探测端点 `curl -w '%{time_total}'` | 0.15s(探测带超时也没事) |
| ③ 进程拉起 + 窗口映射 | Popen 后 50ms 轮询窗口表(`wmctrl -l`) 打时间戳 | 浏览器出窗 **0.38s** = 物理下限 |
| ④ 搬到目标屏 + 置前 | `wmctrl -i -r/-a/-R` | 0.13s |
- **隐形大头是轮询粒度, 不是任何一跳的耗时**: 等窗口的循环写 `sleep(0.6)` ⇒ 窗口 0.38s 就出来了还要白等到
  0.6/1.2s 才被看见, 用户报"1.5s"里 0.9s 是它。等 UI 出现的轮询一律 **≤0.1s**。
- **最省的"马上"是复用已开的窗口**: 窗口已在 ⇒ 找窗口 `wmctrl -l` **3ms** + 置前 **0ms**, 比重新拉起快两个数量级。
  ⇒ "点了不出东西"先查是不是窗口**已开但被挡/在另一块屏**, 先抬起再谈拉起; 调完这类功能就把一个窗口留着别关,
  后续每次点击都是近零延迟(交付时把这条告诉用户)。
- **不用在 GUI 里点也能量**: 直接 `import` 那个模块、调按钮背后那个函数, 传一个自带 `time.time()` 差值的
  `status_cb` 打印每行耗时(实测输出 `+0.14s 服务在跑` / `+1.48s 页面已送出` / `+1.61s 就绪`) ⇒ 一眼看出哪一段占时间。
  先 `wmctrl -c <窗口>` 关掉目标窗口才能量到冷路径; 量完把窗口留着(热路径更快)。
- **验收**给两个数: 冷启(窗口没开) / 热启(窗口已开)。只报一个数会被追问"再点一次呢"。
- 改 GUI 侧代码不会热生效(`.py` 已被常驻 GUI 进程导入) ⇒ 当场能给的"马上"是**复用已开窗口**; 轮询粒度这类补丁
  写进文件并如实说"下次控制台启动生效", 别让用户按已修好的预期去点。
- **首屏到底多久出画面: 用虚拟时间预算截图逐档量**, 不需要人盯屏:
```bash
for vt in 600 1200 2500; do chromium --headless=new --no-sandbox --hide-scrollbars \
  --window-size=1440,900 --virtual-time-budget=$vt --screenshot=$HOME/p_$vt.png http://127.0.0.1:<端口>/<页>; done
```
  ⚠️ snap 版 chromium 的 `/tmp` 是**私有的** ⇒ `--screenshot=/tmp/x.png` 会打印 "written to" 而文件根本不存在;
  一律写到 `$HOME` 下再读。
  ⚠️ 判「白屏」要量**视频/相机区**的白像素, **不要量全屏**: 深色主题页面的浅色文字/表格让全屏白像素恒在
  8~14%, 拿全屏当阈值会把正常页面判成白屏(实测踩过)。

### 黑画面会被人当成"页面没打开/还是慢"—— 必须在画面上说清"没有画面"
无帧时那块画布是纯黑, 用户读到的是"页面没打开"而不是"这一路没有图"。规则:
- 取帧连续失败 N 次(如 3 次)就在**视频区域**盖一条显式说明: 哪一路没画面 + **页面本身没慢, 是这一路没有图像** +
  下一步查什么(切在线那一路 / 查链路与电源)。来帧即撤, 不许留着挡图。
- 覆盖层 `pointer-events:none`(页面本身有点图取点/标定类交互, 别被它吃掉点击)。
- **两态都要实测**: 无帧那一路 `display:flex` 且文案出现; 有帧那一路 `display:none`(实测 39 帧/2.3s 时保持 none)。
  只测一态就等于没测。
- 同理先排除"源真的没有帧": 多路全黑时先逐路看 `online/frames_served/age_s` 与链路可达性, `No route to host`
  这类是硬件侧, 页面调到 0.4s 打开也还是黑的 —— 如实说"快到这里是物理上限, 有画面要恢复 X"。

### 失败态不许"刷屏": 一个格子一个写者 · 定宽 · 只写一次
用户说「取帧失败总显示」「字/屏幕在跳」时, 病通常不在取帧, 而在**页面每帧都在改写头部**:
- **同一个状态格子只许一个写者**: 实测相机帧龄(取帧泵 100ms 一次)与 TCP 真值帧龄(1.5s 轮询一次)
  写同一个 `<span>` ⇒ 两个数互相覆盖, 用户看到的就是"字在跳"。拆成两个格子(底图帧龄 / 数据源帧龄), 各自单写者。
- **状态格子定宽**: `min-width + max-width + white-space:nowrap + ellipsis`。文字长短一变, 头部 `flex` 就重排,
  整条头在跳; 定宽后数字怎么变都不动。
- **失败不计数刷屏**: 不要每 tick 重写「取帧失败×N」; 只在**刚进入失败态**写一次稳定文案(如「无画面(相机未出图)」)。
  取帧失败本来就是"跳过这一帧": 屏幕保持上一帧, 不重绘。
- **覆盖层幂等**: 显示/隐藏都先判当前状态再改 DOM —— 每帧重写 `innerHTML` 会让那块闪。
- **验收可量化**: 3 秒内取样头部各元素的 `getBoundingClientRect()` 的 x/y/w, 前后**必须逐像素相同**;
  无帧那一路说明要出现、有帧那一路要自动撤(两态都测)。只凭"看着不跳了"不算验收。
- 顺带查**重复 id**: 同一 id 出现两次时 `getElementById` 只命中第一个, 另一个永远不更新、样式也漏掉 ⇒
  "谁被更新"和布局都会错。

## 铁律 4: 出局域网交付 —— 先算带宽预算, 再谈"实时"
本机/工位机常落在**被隔离的私网段**（同一个办公网的另一段都够不到, 手机蜂窝网与云主机更不可能）
⇒ 用户要在别处看流, 只能走「本机主动出网」的通道。**上通道前先做一轮刷新的字节预算**, 否则必然被
判成"推了但没推 / 是静态图片"：

```
需求带宽 = (一轮刷新要搬的字节) ÷ (刷新周期)
```

实测形态：叠加页 6 格一轮刷新 **287 KB**, 页面每 2 秒一轮 ⇒ 需 **143 KB/s**; 而免费 ssh 隧道实测只有
**21~66 KB/s** ⇒ 一轮要 **4~14 秒** ⇒ 用户看到的就是"静态图片"。此时源实际是活的(连取 5 帧 md5 全不同,
三路逐像素平均差 91.7, 分辨率都不同) —— **别被"图是不是假的"带偏, 先量预算**。

- **必须给一条能过管道的档位**：多相机拼成**一张**图 + 降尺寸降画质（`w=240&q=45&fps=2` ≈ **26 KB/s**,
  实测 1.9fps 连续动）。多格页面在窄带下永远刷不动; 单张快照轮询同样吃带宽(单帧 36~67KB, 一格不少搬)。
- **报告口径**：给出「管道实测能力 / 本轮需要的带宽 / 能过的档位」三个数, 并明说档位换来的画质代价。
  不要用"应该能看"代替实测。

### 转发方必踩: `proxy_buffering off`
MJPEG 经 nginx 默认会被**缓冲**, 表象与带宽不足**完全一样**("推了但不动")。反代流必须：
`proxy_http_version 1.1; proxy_buffering off; proxy_cache off; proxy_read_timeout 3600s;`
排查"对面看不到流"时**先查这条**, 再查带宽。

### 暴露带"动作接口"的服务前: 只读闸门 + 用案例表验收
推流服务常与**手动控制真机**的接口同一端口 ⇒ 绝不整条映射出去。做法：前面挂**只读闸门**
(GET 白名单放行; 一切 POST/PUT/DELETE 一律 403; 另有明确点名拒绝的控制/触发路径, 白名单放宽也不放它们),
穿透只指向闸门。**验收必须用案例表, 每条实测**：
页面/快照/拼图 200 · 无口令 403 · **带正确口令 POST 动作接口仍 403** · 触发拍照/大模型类 403 · 随手路径 403。
- 令牌用 `?k=<token>` 打开一次即种 cookie, 页面内同源子请求自动过闸(自建 MJPEG 流要显式 `Connection: close`)。
- **判据写错会全线误报**：断言里 `str(status) == 200`(int) 恒为假 ⇒ "全 ✗"而实际全通过。**比较前统一类型**。

### 外部隧道地址会变 ⇒ 不许烧进 APP/网页, 改成"发布-发现"
免费 ssh 隧道**每次重连都换地址**(实测一个半小时内换 5 次), 写进 APK/页面迟早失效(表象是 503)。
- **先钉住地址**: 免费 ssh 隧道会被 `tunnel inactivity timeout` 踢(ssh 层保活不算数) ⇒
  每分钟经隧道**真取一帧**(约 15KB) 保活 ⇒ 地址不再漂, 给用户的链接长期有效。
- 钉不住再"发布-发现": 把**当前地址**定期 POST 到对接方已有的固定域名/中转, **只在地址变化或心跳超时时推**(别刷屏),
  由对方暴露成一份固定地址的清单 ⇒ APP 只认那份清单, 隧道怎么变都不用重装。
- systemd 里悬着 `Requires=` 会让"重启闸门"**连带重启隧道 ⇒ 地址再变一次**; 用 `Wants=`。

出局域网交付的完整配方(闸门白名单/令牌 cookie、隧道常驻 unit、拼图合成、带宽测量脚本、
发布-发现、与转发方的接口清单)见 `references/remote-stream-delivery-and-gate.md`。

## 步骤 1: 起流服务（stdlib，不要引 flask）
`http.server.ThreadingHTTPServer` + `BaseHTTPRequestHandler` 就够，免依赖、免装包。
每路相机一个线程，把 JPEG 编码进共享最新帧槽；HTTP 只负责吐流。

端点设计（缺一不可）：
- `GET /` 看板：多路并排 + JS 每秒拉 `/stats` 显示帧率/帧龄
- `GET /<cam>.mjpg` MJPEG 流（`multipart/x-mixed-replace`）
- `GET /snapshot/<cam>.jpg` 单帧（给聊天工具/证据用）
- `GET /stats` **JSON 证据口径**：`fps · kb_per_frame · raw_kb_per_frame · compress_x · age_s · frames_served`
- `GET /motion` 当前动作状态 JSON（方向 / Δ / 目标位姿 / 下发于几秒前）——**读数直读执行器侧日志尾部**，
  与相机用**同一系统时钟**渲染 ⇒ 是"真同步"而不是事后拼接。有多路相机 + 动作要一起看时必加这个端点。

监听 `0.0.0.0`，交付时给出**局域网 IP 的两个地址**（WiFi 口 + 产线口）。
帧格式与解析细节见 `references/mjpeg-serving-and-ros-raw-tap.md`。

### 「一格两视图」按钮（判据图 / 整板原图 这类）= 两条流 + 前端切 src，别新开通道
用户要在一格里切换"给人看的 / 给模型吃的"两种图时：
- 服务端**每个视图一条 MJPEG 流**（如 `/aoi_xxx.mjpg` = 判据图 · `/aoi_xxx_raw.mjpg` = 整板原图），
  页面两个按钮切 `data-stream`（换 `img.src`）—— 一视图一端点比在格里塞模式参数好调，也能分别看 `/stats`。
- **每格必须标明自己是哪种口径，且优先选「零本地加工」那一种**:
  · `same` 口径 = 直接上屏**源端已经算好的那张**（源端 `?kind=judge|crop` 的内存帧），本机不裁不转不缩放
    ⇒ "页面那张 == 源端那张"，有争议时拿源端文件直接对拍（逐像素 r≥0.98 才算同源）；
  · `canonical` 口径 = 另取**原图**在本机派生（去倾角/裁带/拉伸/定尺）。两条都可以留，但页面上要说清当前是哪条。
- **改"人看的图"绝不动"模型吃的图"**: 让源端把模型输入那张另存/另报（如 `/last_result` 同时给 `topview` 与
  `model_input` 两个字段），判据图口径变了也不影响召回；两张都进台账，追溯不断。
- 验收**别只看尺寸对**: 拿源端同源文件与本机显示帧比相关性（整帧 + 行剖面 r），并核对
  "人看的"确实换成新口径而"模型吃的"**字节未变**。

## 步骤 2: 各相机源的取法
- **本机 USB 相机**：`cv2.VideoCapture(idx)` + **低延迟三件套** ——
  `CAP_PROP_FOURCC='MJPG'`（相机端就压好）、`CAP_PROP_BUFFERSIZE=1`（不攒缓冲）、固定分辨率。
- **远端 ROS 相机**：见步骤 3。
- **远端 HTTP 相机（产线 Flask / 自建服务这类）**：**先确认远端“取图路由”存在, 别指望按文件名下载** ——
  实测某产线服务的 `/storage/<文件名>` **不是下载口**(只回几百字节的 stub)、`/raw` `/frame.png` `/last_frame`
  `/original` 全 **404**、带目录的深路径连接直接被丢(`000`)。正确两条路:
  ① **本机推流服务那一格自己的 mjpg/快照端点**(`/<cam>.mjpg` · `/snapshot/<cam>.jpg`, 即步骤 1 建的) ——
     “把远端那一帧拿到本机”最省事的口; ② 远端真正存在的取图端点(用 `curl -X OPTIONS -D -` 看 `Allow:` 零副作用定性,
     常见形如 `?kind=origin|crop|natural`)。要**逐位无损**存证(上目检/上离线复放) 就走“反向通道 + base64 分块”回传成文件,
  别用二次 JPEG/截图。⚠️ 该帧“人眼看着很清晰”不等于“算法输入可用”(实测同一帧大面积过曝发白、目标只剩一排低对比细齿)
  ⇒ 目检结论与像素统计(p50 / 过曝占比)分开报。

### 🔴 本机预览服务会独占 `/dev/videoN` ⇒ 别的 App（微信/视频通话）**open() 直接失败**

用户口子里的病是"微信摄像头无法打开/一直是黑的"。别先怀疑隐私开关/驱动/微信，先查**谁握着节点**：
```bash
sudo -n ss -ltnp | grep <端口>        # 我们的预览服务在跑吗
for p in /proc/[0-9]*; do for f in $p/fd/*; do
  [ "$(readlink $f 2>/dev/null)" = /dev/video0 ] && echo ${p#/proc/}; done; done | sort -u
v4l2-ctl --list-devices
```
- **关键机制**：被独占时对方的 `cv2.VideoCapture()` 是 **`opened=False`（EBUSY 直接失败）**，不是"能开会话但取不到帧"。
  ⇒ 任何"发现别人有 fd 就让位"的机制**永远触发不了**（对方拿不到 fd）。实测 8 次抢设备全部 `opened=False`。
- 唯一可靠解：给取流服务加一个**显式"关闭/让出"档**（`kind=off`：不打开设备；快照端点返回**占位说明**而不是 500，
  也不许继续回上一帧旧图），并**落盘持久化**（重启/开机后仍是 off，不会自己抢回去）；页面那格如实写"本机相机已关闭(让给视频通话)"。
- fd 让位仍可作为第二层（对方能成功 open 的场合），但**不能当主方案**。
- 验收必须用**独立进程**去开同一节点取帧（模拟视频通话 App）：连续 N 次成功 + 均值合理才算让出；
  再切回自己的档确认服务能重新出图（可逆）。只报"设备没人占用"不算验收。
- "重启微信"只是**收尾动作**（释放它手里的失败句柄），不是根因；先把设备真让出来再重启它。

## 步骤 3: 绕开「raw 订阅 + 低频解码」的节流
若现役 tap 为省 CPU 做成「raw 订阅, 1Hz 解码」，那么无论相机多快，推流都被钉在 ~0.5-1 fps。
**绕开它的正确做法**（不动在役服务）：另起一个容器按相机原生帧率订阅，只做「拷字节 + 落共享内存」，
JPEG 编码交给工位机本机的 cv2：
```bash
sudo docker run -d --name zmax-arm-raw --restart unless-stopped \
  --network host -e ROS_DOMAIN_ID=0 \
  -v /dev/shm:/dev/shm \            # 必须先挂进来, 否则工位机读不到
  -v <repo>/tools:/repo:ro \
  ros:humble-ros-base bash -lc \
  'source /opt/ros/*/setup.bash; exec python3 /repo/ros_arm_tap_raw.py'
```
落盘用 **tmpfs**（`/dev/shm/`，不磨损磁盘）+ **原子写**（写 `.tmp` 再 `os.replace`，避免读到半帧）。

实测收益：手臂帧率 0.50 → **1.86 fps**（摸到相机天花板）· 帧龄 **1.80s → 0.26s**（6.9×）
· 921KB → 29.1KB/帧。

**⚠️ `raw=True` 陷阱（一次实测踩中）**：`create_subscription(..., raw=True)` 的回调拿到的是
**CDR 序列化 bytes**，没有 `.encoding` / `.height` / `.step` 字段，报
`'bytes' object has no attribute 'encoding'`。**需要字段就别加 `raw=True`**，让 rclpy 正常反序列化。
（`camera-frame-forensics` 技能的 ros-image-chain-forensics 参考里记着"我方 tap 即 raw=True + BEST_EFFORT 订阅"，
那只是它能收帧的半句 —— 需要像素/元数据时必须去掉 raw。）

## 步骤 4: 录片段（用户要"能看"，不只是"服务器在跑"）
- 🔴 **用户判"平顺/实时"时，必须让目标真的在动**再录。静止画面证明不了任何事，用户会直接反问
  "机器人没动，怎么看？"。做法：先执行一遍真机动作技能，全程录；交付给**一个完整周期**（4 段动作）
  **加**后程另一个周期（证明全程一致），不要只给开头一段。
- **长录制边收边写成 raw `.mjpg`**（把 MJPEG 里的 JPEG 字节原样落盘），不要攒内存、也不要边采边重编码：
  689MB / 25min 无压力，最后一次性转 H.264。配方与 ffmpeg 裁剪坑见
  `references/mjpeg-serving-and-ros-raw-tap.md` §2.5。
- **自己解析 MJPEG 的 multipart**（按 `Content-Length` 切帧），不要用 `cv2.VideoCapture(<mjpeg-url>)` —— 对 MJPEG URL 不可靠。
- **按实测帧率写** mp4（`fps = (n-1)/span`），这样播放速度 = 真实速度；预先固定 30fps 会把 1.9fps 的画面播成快进。
- 叠标注：相机名 + 分辨率 + 帧率 + 采集时刻 + 帧龄。
- 交付前用 `ffmpeg -c:v libx264 -pix_fmt yuv420p -movflags +faststart` 转 H.264（编码器 `mp4v` 有些聊天软件播不了）。
- **录制器必须处理 SIGTERM/SIGINT**：若实现是"先把帧攒在内存、结束时才写文件"，那么中途 `pkill`
  会把**整段视频全丢掉**（文件根本没被创建）。加信号处理器把采集循环置停、让 `VideoWriter` 正常收尾
  （`_STOP` 标志 + `while ... and not _STOP`）。**更好的做法是把时长设成动作结束后自然退出**，
  kill 只作保障。
- **录像窗口先算完动作时长再定**：窗口 = 动作总时长 + 余量。别一边录一边做慢速取证 ——
  每次经 docker 读一次真值位姿要数秒，几十次就把窗口吃光、后半段动作录不到。
- **双路合录会压低单路的「内容帧率」**: 合录器要同时拉两路 + 合成, CPU 竞争使手臂一路的真实内容帧率
  从单录 **8.0 fps 降到 3.0 fps**（合录容器自身仍记 15fps，看容器帧率看不出来，必须量**内容**去重后的帧率）。
  ⇒ 交付时**两个都给**：单路版(判平顺度用，帧率最高) + 双路合成版(看现场全景用)，
  并明说合成版里手臂那半是降速后的 —— 别只给合成版让用户拿它判平顺度。

## 步骤 5: 发之前必自检（不许直接发）
1. **黑帧判据**：`cv2.cvtColor(img, COLOR_BGR2GRAY)` → `std < 5` 视为无效帧/黑帧。
   真图实测 std ≈ 62-70，黑帧 std ≈ 0.5-2。**文件大小不是证据**（噪声不可压缩）。
2. **每路都验**，包括"另一路"——用户说的"都发过来"就是两路都要。
3. 报告里必须出现数字：**帧率 · 帧龄 · 压缩比 · 每帧KB**，外加一句"当前瓶颈在哪"。
4. **目标真的在画面里吗** —— 这是最容易漏、代价最大的一步。低帧率流"看起来没动"有两种完全不同的原因：
   ① 目标确实没动；② **相机根本没对准目标**。只算相邻帧差**分不出来**（见下面坑表），
   必须做**方向性光流**：把动作窗口按命令方向逐段切开，算每段首尾帧的中位光流向量，
   比对**主轴与正负号**是否随命令交替。
   - 命令 "抬升/下降" 应给竖直主向，"向左/向右" 应给水平主向且**符号相反**；
   - 幅值必须显著高于噪声底（静止画面的光流 ≈ **0.0x px**；真有位移是 **3~5px** 量级）。
   - 实测：装在臂上的相机 8 步全部方向+符号正确 ✅；另一路固定相机 8 步全是 `(0.00, 0.00)` ⇒ **没对准目标**。
   直接跑 `scripts/verify_motion_in_video.py`（吃 mp4 + 命令时间轴，打印逐段判定）。
   **没确认目标在画面里，不要把视频当结果交付** —— 先如实说明并把"把相机对准目标"作为用户侧动作提出来。

## 交付清单（一次给全三样）
1. **在线看板 URL**（手机/PC 同网可开，多路并排）
2. **录好的片段**（H.264，画面自带时间戳+帧龄）
3. **证据端点** `/stats` + 单帧快照

外加一句**诚实的上限说明**：帧率天花板是相机本身还是链路，以及要突破它需要谁点头。

**别把"加硬件"当修法。** 用户说某个设备有问题时，交付物是**把他现有的设备修好**；
提议"再加一路相机""换一台"会直接被顶回来（现场往往根本没有备件）。
先穷尽直驱 / 旁路 / 改配置这些**不动硬件**的手段；真要换件就把话说成
"这条我做不到，需要厂商或采购"，而不是建议用户去装一个不存在的东西。

## 常见坑
| 现象 | 真相 / 对策 |
|---|---|
| 推流只有 0.5-1 fps，相机明明更快 | 中间 tap 在做「1Hz 解码」省 CPU ⇒ 另起全速订阅（步骤 3） |
| 帧龄很大但 fps 看着正常 | 服务端在**排队**而非丢帧 ⇒ 只推最新帧 + `seq` 判重 |
| 关掉页面/窗口后整机越来越慢, 新开页面白屏好久 | 客户端断开 ⇒ 服务端写循环还在跑, 连接停在 `CLOSE-WAIT` 空转子进程并占 `max_children` 名额 | 每条流加 300s 硬上限 + 每块 `flush()` + `finally close_connection`; 取证 `ss \| grep CLOSE-WAIT` + `ps --ppid`, 杀僵尸子进程后 CLOSE-WAIT 必须归零 |
| 页面 fps 只有个位数, 但单帧取回只要几 ms | 客户端取帧泵的 `period` 就是硬顶(实测 150ms⇒6.67fps) ⇒ 在页面里用 `performance.getEntriesByType('resource')` 数条数量真实 fps, 别拿服务端 `/stats` 当用户看到的帧率 |
| 开了"图+标注"模式后画面永远黑, 而 `/snap` 端点 200 且字节正常 | 标注后端无结果时渲染分支直接 `return` ⇒ 必须降级成"只出图"并在画面上标失败次数/帧龄, 不许静默 |
| 用户说"点按钮打开还是慢/像没打开" | 两条链分开量: 打开=导入+探测+出窗+置前(实测 0.2/0.15/0.38/0.13s, 热启 3ms), 画面=泵周期。**等窗口的轮询粒度(0.6s)常是白等的那一秒** ⇒ ≤0.1s; 窗口已开就先抬起。黑画面会被读成"没打开" ⇒ 视频区盖"这一路没有画面"说明, 来帧即撤 |
| 换了源还是只 1.9fps | 按三层分（设备模式表 / 厂商实现 / 发布传输），先跑分层卸载测速定位在哪一层，别直接报名"设备上限"。实测真根因是厂商节点回退路径 + 大消息发布 216ms/帧，**直驱+旁路后提到 16.6fps** ⇒ 先看 `references/high-rate-camera-bypass-node.md` 再下结论 |
| 直驱能跑 30fps，一发布就崩到 4.6fps | 先判是**打包**还是**传输**: 发到**0 订阅者**的测试话题还崩 ⇒ rclpy 逐字节打包(0.9MB≈170ms, 实测 26.5→3.0fps, 深度 0.6MB 单独发就 7.5fps), 停掉网络订阅端帧率不变; 插上订阅者才崩才轮到 socket 缓冲/分片。**修法是换小消息不是换协议**: compressed(41KB/159KB)走 DDS 实测 9Hz, HTTP 实测 25fps, raw 哪条都慢 |
| 一台相机被两个服务各开一路(彩色一路/深度一路) | 抢设备 → 一方 EIO、彩色时有时无(`/dev/videoN` 被 UVC 独占而 vendor 接口又被另一进程占) | **一个进程持相机**: 采集线程只做 `wait_for_frames`+`rs.align(color)`, 再分发给 HTTP(全速) / ROS raw(低频) / ROS compressed(10Hz); 别让另一个服务去开同一个设备 |
| 停掉相机服务后立刻重开 → `RuntimeError: Couldn't resolve requests` / EIO | 设备没释放完(实测停服务后 **8s 不够, 15~20s 才行**) | 重启前 `sleep 18~20` 再开; 连着失败几次后设备可能**从 `lsusb` 整个消失**(并非硬件坏): 逐级核 `sysfs` 里 `idVendor`, 对父 hub 端口 `authorized=0`→`1` 重新枚举即回(实测 `Bus 002 Device 005: 8086:0b5b` 回来了), 回来后再起服务 |
| DDS 发布拖慢采集（12.9 vs 22.9fps） | 大消息发布必须在**独立线程 + 有界队列丢帧**，不能内联在采集循环里 |
| 改了 `--arm-fps 30` 还是只 15fps | 推流服务另有全局 `--fps`（默认 15）在封顶，两个都要传 |
| 容器订阅报 `'bytes' object has no attribute 'encoding'` | 用了 `raw=True` ⇒ 去掉 |
| docker 报 permission denied | 本机 docker 需 `sudo` |
| 微信/视频通话说"摄像头无法打开/黑的"，而本机预览页正常 | 我们自己的取流服务独占 `/dev/videoN` ⇒ 对方 `opened=False`(EBUSY)，fd 让位检测永远不会触发 ⇒ 加"关闭/让出"档并持久化，用**独立进程开节点取帧**验证；不要建议"重启微信试试"当修法 |
| 工位机读不到容器的帧文件 | `/dev/shm` 没挂进容器 |
| 录出来的视频快进/鬼畜 | 预先固定了 fps ⇒ 按实测帧率写 |
| 裁出来的片段比真实速度快一截 | 从 raw `.mjpg` 转码时解复用器**默认按 25fps** ⇒ `-framerate <实测>` 必须放在 `-i` **之前**（`-ss` 放 `-i` 前还会得到 0 字节输出，改用 `-vf select='between(n,A,B)'`；`-r` 与 `-fps_mode passthrough` 同时给会报 contradictory） |
| 停止信号发了录制还在跑（录到超时、文件巨大） | `urlopen().read()` 阻塞时 SIGINT 不一定落地 ⇒ 每次 read 设超时 + 循环查 stop 标志，发信号后**用 `pgrep` 校验进程真的退出了** |
| 建议"再加一路相机/换设备"被顶回 | 现场没有备件 ⇒ **修现有设备优先**；提硬件方案前先确认现场有没有这件东西 |
| 读 MJPEG 只拿到 0-3 帧 | 用了 `cv2.VideoCapture(mjpeg_url)` ⇒ 自己解析 multipart |
| `pkill` 录制器后视频文件不存在 | 帧攺在内存、结束才写盘 ⇒ 加 SIGTERM 处理器 或 让时长自然跑完 |
| 录到的只有前半段动作 | 窗口没算动作总时长，或被慢速逐项取证吃光 ⇒ 先算时长、取证改用日志 |
| 单路录得挺顺，双相机合录后同一路变卡 | 合录器 CPU 竞争压低单路内容帧率(实测 8.0→3.0fps) ⇒ 单路版与合成版都要交，并说明差异 |
| 画面发出去用户说"不对/是黑的" | 发之前没跑 std 自检 ⇒ 必须每路验 |
| 用户说"几个画面都一样／是静态图片" | 三问按序答: ①三格是不是同源(逐像素平均差 + 分辨率) ②源帧在不在变(连取 5 帧 md5) ③**一轮刷新需多少带宽 vs 管道实测**(铁律 4)。实测真因是带宽不足, 不是假图 |
| 反代后"推了但不动／没流" | nginx 默认缓冲 MJPEG ⇒ `proxy_buffering off` + `proxy_cache off` |
| 昨天能用的隧道地址今天 503 | 免费隧道重连换地址 ⇒ 改"发布-发现", 别烧进客户端；systemd 依赖用 `Wants=` 不用 `Requires=` |
| 闸门验收显示"全部 ✗"但实际都通过 | 断言拿 `str(status)` 比 int ⇒ 比较前统一类型 |
| 动作录下来了但用户看不出在动 | **相邻帧差占比不是判据**：静止画面的传感器噪声就能让各段峰值都"像在动"，实测每个动作窗口都被判成"有位移"而画面里根本没有目标 ⇒ 改用**方向性光流对齐命令方向**（`scripts/verify_motion_in_video.py`），再看幅值是否 > 噪声底。分不清就如实说哪一路没对准，给改进选项（挪近/对准/加大位移） |
| 叠加页/工位总览一直显示旧图, 新要素永不出现 | 先查服务**僵死**, 不是规格没生效: `/proc/<pid>/fd` 数 vs `limits`(实测 1024/1024)、curl 超时返 000 而端口仍在听。第一次报错紧跟启动横幅 = 继承了满 fd 表 ⇒ 按「另一种活着但不响应」那节根治 |
| 服务僵死几小时没人管 | 守护可能**从没被调度**（脚本在、逻辑也对、就是不在 crontab 里）⇒ 先确认它真被调度; 探活要 HTTP GET 带超时, "端口可连/进程在否"抓不到僵死 |
| 用户说"取帧失败总显示 / 字在跳 / 屏幕在跳" | 不是取帧变慢: 同一状态格子被两个源轮流写(相机帧龄 vs 数据源帧龄)+ 每帧重写失败计数 ⇒ 文字长短变 ⇒ 头部 flex 重排。一个格子一个写者 + 定宽 + 失败只写一次 + 覆盖层幂等; 验收用 3 秒 `getBoundingClientRect()` 逐像素对比 |
