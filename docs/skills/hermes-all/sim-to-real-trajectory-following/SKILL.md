# 仿真动作 → 真机跟随 (平顺 · 小幅度 · 不叠队)

## When to Use
- 「按仿真里那条路/那个方向, 让真机也动起来」「幅度小一点, 不要走那么远」「你得保证平顺啊」。
- 仿真侧已经有每个阶段的期望速度/轨迹(例如 80Hz 的速度流或一条参考轨迹), 真机侧只能下发离散命令。
- 现场已经授权、场景在出数, 但臂**看着不动** —— 先按本文的"不动三查"走一遍。

## 铁律

1. **平顺 = 整条路径一次 `moveStart`。** 单段 `move-rel`/单条 MoveL 必然是"走一段停一段"。
   把轨迹重采样成 N 个点, **一次性 append 全部点, 再一次 moveStart** ⇒ 控制器一口气走完
   (实测 10 点 50mm 走 2.8s, 到位残差 0.0mm)。
   ⚠️ **先 moveStart 再边动边 append** 实测臂几乎不动(10s 里只有 2% 时间在动)⇒ 只能"排完再启动"。
2. **绝不叠队。** 上一条路径的**回执 id** 没回来, 不发下一条。叠两条会被控制器混着走,
   越走越快、越走越远(实测 40mm/轮 ⇒ 16 轮走了 640mm), 包络闸被顶穿。
3. **幅度用绝对上限收口。** 一轮总行程的 `--max-path`(mm) 硬上限 > 缩放比例: 超了等比缩。
   现场说"太大了"就只改这一个数, 不动轨迹形状。
4. **模板不许自我重录。** 从"上一轮实际走的路"录模板 ⇒ 越跑越小(实测 696→62→11mm)。
   正解 = 从仿真真值录一轮当模板(固定文件) + 关掉自动录制。
5. **单位必须显式换算。** 真值差是**米**, 腿的 path 点要**毫米** ⇒ 乘 1000。
   漏乘时"总行程 < 3mm"的守卫会**静默 continue**, 症状和"没授权/没数据"一模一样(改什么参数都不动)
   ⇒ 这类跳过必须打印一行日志。
6. **姿态显式写"未建模"。** 4 维速度流里没有角速度, 不要用位置积分去假装姿态; 桥接输出的姿态一律 `null`
   并在页面上标注, 不许写 0° 冒充已知。
7. **地图围栏是下发前的硬闸。** 用户在 AR 视图里画的长方体/直线就是禁入体积: 每段路径要先用
   **当前 TCP + 逐点累加**换成绝对坐标(路径本身是相对量), **逐点**判定, 任一点落进围栏就整段不发;
   起点已在围栏内时**只放行"末点在围栏外"的往外走段**(否则臂进去就出不来)。判定库与页面共用一份
   (`tools/fence_store.py`), 不要两边各写一套口径。围栏编辑/判定细节见 `fixed-camera-ar-overlay`。
   ⚠️ **线是轨迹, 盒子才是围栏**(用户明确纠正过): 要沿某条线跑时, 该线必须从闸里摘掉 ——
   路径整条压在线上, 逐点判距离必然 <margin ⇒ 被自己的线拒成“进围栏”。定式 = 只临时禁用它本身、
   跑完 `finally` 恢复并回读确认; box 照拦, 不放水。

## 🧩 「1 2 3 4 步一次发, 中间不能停顿」——先分清是哪一层的不停顿

用户说「把这几步一次性发到执行器, 点一次全部执行, 中间不能停顿」时, 先判定他要的是
**软件层不逐段等位** 还是 **机器人物理上不停**:

| 通道 | 一次下发 | 拐点会停吗 | 适用 |
|---|---|---|---|
| L2 FIFO 逐条技能 (`L2.lift`/`L2.backward`…) | 可以写多行 | **会**, 每个拐点 0.3~1s(控制器当每条独立点到点) | 步数少、拐点需要确认 |
| `/move_sequence`(多点 + 一次 moveStart) | 一次 | 不停(≤18 点/块, zone 混合端点) | 真连续插补(本节铁律 1) |

- FIFO 逐条下发时:**绝不要「发一段 → 等执行器 `phase=done` → 发下一段」**。
  执行器收到 ROS `TargetPose` response 后常常**停在 `phase=accepted`**不写 done ⇒ 调用方永远等不到,
  实测 25s 后零新增日志、臂已抬完 60mm, 却只走了第 1 段(现场只会问“怎么就执行了一段”)。
- **到位判据只认真值**(目标 vs `read_joints()` 的 TCP, 差 ≤8mm 且帧龄 ≤5s);`phase` 只用来拦 `blocked`。
- **起点闸/锚点校验只查一次**, 绝不放段循环里: 第 1 段走完位置就变了, 第 2 段立刻被判「起点已变 N mm」而中止。
  段间只校验「当前 ≈ 上一段目标」。
- **叠队的第二种形态 = 两个执行进程抢同一 FIFO**(页面重复点/重试), 一条在走、一条被起点闸拦, 日志自相矛盾。
  执行脚本开头 `fcntl.flock(lock, LOCK_EX|LOCK_NB)`, 抢不到就退出并明说「已有另一个在执行」。
- **汇报纪律**: 软件层消掉的只是“等位”那截, 控制器拐点减速依旧 ⇒ 不许把“软件已无等待”说成“机器人不停顿”。
  要真不停就换 `/move_sequence`, 不要靠连发���条命令去模仿。

## 沿一条“画出来的”直线跑 (往复 N 次 · 要一段不要停)

用户口径: 「沿着这条线, 来回走 3 遍」「为什么你分成 3 段走? 要一段, 不要停」。

1. **直线只要 1 个点。** MoveL 本身就是笛卡尔直线 —— 把 400mm 的线重采样成 40 个点**不是更平顺**,
   是把队列塞满(第 2 条)。定式: `points=[[dx,dy,dz]]` 只给终点 + `speed`; 采样点只对付**弯曲轨迹**。
2. 🔴 **一次 `moveStart` 大约只消费 18 个点, 超出的点静默丢弃。** append 48 点 + 一次 moveStart,
   实测 400mm 只走了 173mm 就停: **没报警、`moveStart ec=0`、机器人回 idle、无 estop**、
   看起来像“围栏拦了/授权没了/包络越界”, 实际是点太多了。判据**数点不数距离**: 每段 ≤18 点
   (实测 90mm 一块稳定走通); 长路就切成 ≤18 点的块、每块等回执再发下一块。
3. **往复要不停, 把端点交给 zone 混合。** 3 个来回 = 6 段 = 6 个端点, 起点+6 点**一次下发**,
   `zone 5mm` 让端点为“抹过去”而不是“到位停一下”; 否则每个端点都是一次减速到 0 再加速,
   用户看到的就是“顿、还分成了几段”。
4. **速度有三层上限, 逐个查**: 你传的 speed → agent 的 `do_path` 钳位
   (本项目原来是 `min(speed, MAX_SPEED_MM_S, 100.0)` ⇒ 要 200 只给你 100, 不报错) →
   控制器 `MAX_SPEED_MM_S`(1000)。提速无反应先看钳位那行, 别只看自己传的参数; 改完要**重启 agent 容器**才生效。
5. **验收用真值采样, 不用命令回显。** 三件必报: 换向次数(=2×往复数) · 两端覆盖(实际到没到线端) ·
   中段有没有低速停顿(排除“下发前”与“跑完后的静止窗口”两段)。实测同一条 400mm 线: 25mm/s → 2400mm/98.5s
   (有效 24.4) · 100 → 26.8s (89.4) · 200 → 14.8s (162.2); 三档换向都是 5 次、Y 严格覆盖 ±200、X/Z 偏差 ≤0.05mm。
   命令值越接近上限, 端点加减速占比越大, 有效速度越低 ⇒ 名义值和实测值一起报。

⚠️ 真值流本身是 **5Hz**: 按 10Hz 采样会得到“一帧 0、一帧双倍”的假速度序列, 一半间隔看上去“停着” ⇒
采样频率跟真值同频, 或按 2~3 帧窗口算速度, 判“停”必须连续 ≥0.5s 低速。

## 「场景有数, 你怎么不动」= 三查 (按顺序, 一条比一条常见)

```
① 总闸层   画布 plan 节点的「桥接开关」+ plan_from_vff.json 的 bridge 字段
          关着时常驻跟随会**自己退出**(日志 `⏹ 桥接开关已关 ⇒ 停`), 不是崩了也不是没数据
          ⚠ switch 的真值在**运行中的控制台内存**里 ⇒ 从外部改画布 JSON 会被它覆盖, 只能让人点一下开关
② 模式层   /ctl/status: operation 必须 idle · mode 必须 automatic
          腿报 rc=3 `ABORT 前置条件: 不是自动模式/机器人不空闲` ⇒ 有人在手动点动, 退避 1s + 打印原话
③ 包络层   腿报 rc=4 `扫掠越界急停: ['x']` ⇒ 臂已被手动挪出旧包络(实测差 0.9mm 就全拒)
          ⇒ 立刻以**当前位置**重锚定再发; 拿旧锚点死磕会连拒上百轮
④ 队列层   回执里最后一条不是你自己发的 id ⇒ 前一条还在执行/被拒, 别再加
```

判据: **"已下发"/"已投递"都不是成功**; 只有"同 id 的回执 + 真值位姿变了"才算真动。

### 一轮的边界别用阶段名
场景一换阶段表也变(摆盘是 下降→抓取→抬起→转移→放下, 根本没有「接近」) ⇒ 用阶段名当边界,
模板录制会**永远不触发、也永远不回放**(日志只显示「先录一轮」)。用仿真 `frame` 回绕(变小)判一轮,
或直接“走完发下一条”的闸门; 触发条件只能依赖与场景无关的信号。

## 链路实时性: 先量三个数, 再谈改 (别默认"慢 = 网络")

现场说「你和机器人的网络得保证实时性」时, 先把三个数摆出来:

```bash
ip route get <控制器IP>                       # 哪块网卡
ethtool <if> | grep -E 'Speed|Duplex'         # 速率/双工
ip -s link show <if>                          # RX/TX errors、dropped
ping -c 20 -i 0.05 <控制器IP>                  # RTT / mdev / 丢包
```

再加一条**命令往返**: 往 FIFO 写一条只读命令(`pose`), 量"写→拿到 SDK 回执"的耗时。
实测参考值: 1Gb 全双工 · 0% 丢包 · RTT 0.098/0.141/0.288ms(mdev 0.046) · 命令往返 **10.7~11.0ms, 抖动 ±0.3ms**。

**结论口径**: 这三项都优秀 ⇒ 顿挫/跟不上**不是网络**, 是"一条命令一段直线 + 等回执"的架构问题(铁律 1/2),
别去加延时、降频、换协议, 那只会让现场更慢。真正要抢的是**主机 CPU**: 相机/推流常占 200~300%,
跟随进程会被饿 ⇒ `nice -15` + `taskset -c <空闲核>` 起跟随进程。

⚠️ `nice -15` 需 root(普通用户报 `cannot set niceness: Permission denied`, 此时 `taskset` 仍生效)。

## 验收口径 (缺一条都会被当成没做)
- 平顺性: 采样 10~15s, 报 **累计行程 mm + 均速 + 变动采样占比**, 不是只看包络框
  (闭环模板走"出去再回来", 包围盒只有路长的一半, 用它说幅度会低估)。
- 幅度: 分轴报 X/Y/Z 行程, 与仿真同口径对比(仿真真值一段时间的 X/Y/Z 振幅)。
- 叠加视图: 真机实际轨迹要单独一条序列画出来(颜色/验收见 `fixed-camera-ar-overlay` 的"真机轨迹"一节)。
- 授权: 每拍复查 `motion_armed`; 撤了**一行都不发**。

## 参数怎么调 (现场只会说三个词)

| 现场话 | 改什么 | 说明 |
|---|---|---|
| "太大/不要走远" | `--max-path` (mm) | 整轮总行程硬上限, 40 → 25 就是缩小 |
| "太慢/跟不上" | `--dur-scale` (0~1) | 同一条路的时长压缩, 越小越快; 受路长/实际执行速度限制 |
| "不安全/出界" | `--band` (mm) | 以启动那一刻 TCP 为锚点的包络; 出界腿自己 stop |

⚠️ 命令里给的 speed 只是**名义值**: 控制器侧还有自己的倍率, 实测"名义 4.3mm/s 走了约 8~10mm/s"。
报速度一律同时给名义值和实测值, 别只报设置值。

## Pitfalls

| 坑 | 症状 | 修法 |
|---|---|---|
| 每个阶段只发一条相对移动 | 走一段停一段, 用户说"一顿一顿" | 重采样成多点 + 一次 moveStart |
| 不等回执就发下一条 | 越走越快越远, 包络被顶穿 | 按回执 id 严格串行 |
| 手动挪过臂后仍用旧锚点 | 腿连拒上百轮, "有数但不动" | 收到越界就以当前位置重锚 |
| 自动重录模板 | 幅度一轮比一轮小 | 真值模板 + 关闭自动录制 |
| 真值模板直接当 mm 用 | 守卫静默跳过, 永远不动 | 米→毫米 ×1000; 静默跳过要打日志 |
| 用 `pkill -f <脚本名>` 收尾 | 把自己那条命令也杀掉(exit -15) | 专用停脚本 + pid 文件 + `/proc/<pid>/comm` 判身份; 同一条命令里连 `git add tools/<脚本>.py` 这种出现脚本名的写法都会自杀 |
| 围栏/禁入判定只看路径终点或只按起点判 | 中段穿过围栏不报警, 臂直接穿过禁区 | 相对路径先累加成绝对点云, 逐点判; 已在区内只放行"往外走"段 |
| 拿"受理/已投递"当成功 | 未授权/被拒都看着像"发了" | 只认同 id 回执 + 真值变化 |
| 用 `dur_eff` 定时发下一条 | 小名义速度(2~5mm/s)**不被控制器当真**, 40mm 的路 1s 就走完 ⇒ 定时器还在等, 实际已能发下一条; 反过来若排得快就叠队 | 闸门只用两个硬条件: **上一条同 id 回执到** + 连续 0.35s 真值没动; 名义速度只用于报数, 不用来排时序 |
| 把直线重采样成几十点“求平顺” | 走一半静默停住: 无报警、`ec=0`、机器人 idle, 以为是围栏/授权/包络 | 直线 1 点就够; 长路每块 ≤18 点, 等回执再发下一块 |
| 往复跑用“净位移”判有没有动 | 3 个来回回原位, 净位移 ≈ 0 ⇒ 守卫把自己的成功当“没动”而中断 | 判据用同 id 回执(或途中采样); 往复的验收看换向次数与两端覆盖 |
| 按 10Hz 采 5Hz 的真值 | 相邻采样一帧 0 一帧双倍, 一半间隔“速度 0”, 误报中途停顿 | 采样频率跟真值同频(5Hz), 或 2~3 帧窗口算速度 |
| 用“包围盒行程”说幅度 | 闭环模板是出去再回来, 包围盒只有路长一半 ⇒ 低估 | 报**累计行走 mm**(逐段 |Δ| 求和) + 均速 + 分轴振幅, 三个都给 |
| 用户提"网络要保证实时性"就直接加延时/降频/换协议 | 平顺没改善, 端到端更慢 | 先量 RTT/命令往返/丢包; 三项优秀就转向架构(整条路径 + 串行)与主机 CPU 争用(nice/taskset) |
