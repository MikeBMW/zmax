# 生成数据要真可见 + 数据总线切面不假成功 + 同一真源只一个写入口

## “生成的数据能在数据集管理里集中管理” 的硬标准 = 扫得到, 不是“写了一份清单”
先查扫描根: 若清单工具的根是 `data/datasets/*` 的**一级子目录**, 而生成物落在数据盘 (如
`zmax_data/<cache>/datasets/*.h5`), 那就是**扫不到 = 用户看不到**。用 `grep 文件名 <工具 --json 输出>`
证实命中 0 再动手, 不要凭感觉说“已经登记了”。

### 做法: 只读补充清单 (不改扫描逻辑) + 逐条真 stat
- 生成器写 `data/datasets/<组>/manifest.json` (带 group / generator / 参数字段); 清单工具加一个
  `scan_manifest_supplements()`: 读每个 `manifest.json` 的条目, **逐条 `os.path.exists` + 真扫目录**再组记录。
- **铁律**: 清单只是“索引”, 数字一律以磁盘实况为准。清单指向的文件不存在 ⇒ 标 `missing=True`,
  **绝不照抄清单里写的 size** (否则清单写错就变成假数据)。
- 这样“生成数据集中管理”是**一条可复跑的证据**: 工具输出里出现带生成器/帧数/seed/出处的条目。

## DDS / 数据总线: 登记 ≠ 接上, 不许假成功
- 全局话题表是**映射表本身** (生产者/消费者/门 QoS/档位/key_fields/质量判据/provenance)。新增切面时
  把这些元数据一并登记, 口径写死“各功能区 = 同一数据源的不同切面, 消费者不得自行编数”。
- **不要**把新话题塞进守护的 `MODE_TOPICS`: 守护会按档位**预建 DDS 类型**, 而类型还没落地时会让整个档位
  起不来 (比“没接”更糟)。正确做法是单列 `MODE_TOPICS_PENDING` + 写明缺什么 (如 IDL 类型 + 发布脚本),
  类型落地后再并入各档。
- 同一份档位表常有**多份副本** (权威守护 / 备用守护 / GUI 遥测), 漂移会导致“同一个档位允许的话题不一致” ⇒
  改一处必须几处对齐, 改完跑一次守护 `--status` 确认还起得来, 且不动 prod 档 (量产零开销)。

## 同一份真源只有一个写入口
场景/参数这类共享 JSON (参数中心 + 场景编辑器都改它), 所有调用方**不得自己写 JSON**, 一律过同一个写盘工具
(备份 + 原子写 + 回读 + 围栏校验)。两处各写各的必然打架 (曾因此把对象增改全写挂)。
参数中心登记这类实体时, 也要用**纯相对路径** (不带 `json:` 之类前缀) —— 工程库判据会 `join(ROOT, source)`
直接找文件, 带前缀会报“缺真源”, 假缺口会掩盖真缺口。
